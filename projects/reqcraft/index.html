Reqcraft：把需求转成可以开发和验收的规格

AI 已经能够根据一段需求描述生成前后端代码，但代码写得快，并不意味着需求被理解得准确。

一份 PRD 可能写着：“用户填写申请并提交，系统校验通过后进入审批流程。”这句话能说明功能方向，却没有回答哪些字段需要校验、什么状态允许提交、重复请求如何处理，以及审批服务失败时应当发生什么。开发时如果直接填补这些空白，得到的可能是一套运行正常、却不符合实际业务预期的实现。

Reqcraft 是一个面向 Codex、Claude Code 等 AI 编程助手的 Agent Skill，用于把 PRD、用户故事或需求变更整理为可追踪的业务规则与验收规格，并在开发前后审查需求覆盖和已有验证证据。

它并不替代开发或测试工具，而是帮助回答一个更早、也更基础的问题：我们究竟要实现什么，以及怎样判断它是否正确？

从需求描述到验收依据

直接把 PRD 交给 AI 开发，常常会遇到三个问题。

首先是规则不完整。需求描述通常强调正常流程，权限、状态冲突、边界输入、重复提交和依赖失败等情况可能尚未明确。如果没有先识别这些空缺，AI 容易把自己的假设写进实现。

其次是业务预期和技术方案混在一起。产品需求说的是“不能重复创建审批流程”，而后端究竟采用幂等键、状态检查还是数据库约束，属于技术设计。过早确定实现方式，反而可能掩盖业务层面的未决问题。

最后是缺少共同的验收依据。前端页面可以正常操作，后端接口也能返回成功，但整个流程未必满足业务要求。需要有一套独立于具体实现、能够被开发与测试共同引用的验收标准。

Analyze：先把业务问题说清楚

需求分析阶段从原始材料中提取业务场景（SC）、业务规则（BR）、状态转换和待确认问题（Q），并保留来源位置。

它不仅整理 PRD 写了什么，也检查哪些重要条件没有写清楚。例如：“提交申请时需要校验”并不足以成为验收标准；必须进一步确认校验对象、触发条件、失败结果，以及失败后哪些数据不能改变。

对于未确认的行为，Reqcraft 会保留为待确认项，区分 PRD 已明确的内容、用户已确认的决策、仓库中发现的事实，以及尚无依据的建议。未确认的业务决策不会被悄悄转换成既定规则。

Spec：让业务要求变得可判断

在业务规则的基础上，Reqcraft 使用 Given–When–Then 形式生成验收标准（AC）：

  • Given：在什么角色、权限、状态和数据条件下；
  • When：执行什么业务动作；
  • Then：必须观察到什么结果，以及哪些副作用不能发生。

例如，假设业务已经确认“只有草稿状态的申请允许提交”，可以写成：

AC-01：非草稿申请不得再次提交
Given：申请已处于待审批状态。
When：用户再次提交该申请。
Then：系统拒绝此次提交；申请状态保持不变，不创建新的审批流程。

这里的业务前提只是示例，并不代表 Reqcraft 会替真实 PRD 补造这条规则。

这种规格既能指导开发，也能作为后续单元、接口、集成或端到端测试的依据。不过，验收标准本身不是测试代码：它描述需要证明什么，具体如何构造测试数据和执行测试，由下游测试流程负责。

Audit：区分“写了”“实现了”和“验证过”

验收审计阶段，Reqcraft 可以对照 PRD、已有验收规格、相关源码、测试文件和已有运行报告开展只读检查。

它重点回答：原始需求是否被遗漏；规则与验收标准之间是否存在冲突；关键行为是否能在源码中找到实现线索；已有测试报告是否真的覆盖了相应的验收标准。

这里尤其需要区分不同层次的证据：

能找到的材料可以支持的判断不能直接推导出的结论
PRD 与验收规格某项业务要求已经被描述或覆盖功能已经实现
相关源码存在与要求对应的静态实现线索运行行为一定正确
测试代码存在相关验证设计或断言测试已经执行并通过
可核实的运行报告在指定环境、版本和覆盖范围内有通过或失败证据未覆盖的功能也已经通过

Reqcraft 不在审计阶段运行测试，也不把“找到了代码”当作“验收通过”。缺少充分证据时，结论就是证据不足。

PRD 阶段不知道前后端规范，也可以先开始

这是 Reqcraft 特别考虑的使用场景。

只有 PRD 时，它先确定业务场景、规则和验收标准。对于尚不知道的框架、接口路径、错误码、数据库结构等技术细节，不猜测、不提前绑定；技术映射保持“未开展”或“待确认”。

拿到真实仓库后，它再参考现有 UI、Controller、Service、鉴权、数据模型及接口约定，补充前端、后端和跨层的验收责任，并指出需要进一步设计的技术问题。

因此，业务规格是否就绪与技术映射是否就绪是两项独立判断。需求可以先被澄清，再进入技术方案阶段，而不需要等全部工程细节确定后才开始整理。

用一套编号把需求、实现和验证联系起来

Reqcraft 为不同对象保留稳定标识：

标识含义示例
SC业务场景SC-01 提交申请
BR业务规则BR-01 仅草稿可提交
AC验收标准AC-01 非草稿提交被拒绝
Q待确认问题Q-01 审批服务超时如何反馈

一条验收标准可以关联对应场景和规则。后续需求变更时，尽量保留已有编号，标记修改、废弃和影响范围，而不是把整份规格重新生成一遍。开发和测试工具也可以引用同一组 AC，减少对原始需求的重复解释。

Reqcraft 默认在对话中交付内容；明确要求保存时，才在目标仓库中创建或更新规格文档。它提供 Markdown 规格模板，以及可选的只读格式检查脚本，用来检查编号、关联和必要字段。格式检查通过并不等于业务内容已经正确或完整。

如何使用

项目仓库：github.com/Zong-Liang/reqcraft

Reqcraft 提供一个主 Skill 和多个快捷入口，适用于 Codex 与 Claude Code。安装方法及版本适配以仓库 README 为准。

操作Codex 入口作用
需求分析$reqcraft-analyze提取业务场景、规则和疑问
验收规格$reqcraft-spec生成可追踪的验收标准与责任映射
验收审计$reqcraft-audit检查规格、静态实现及已有报告
查看用法$reqcraft-help查看功能入口和适用范围

在 Claude Code 插件安装方式下，对应入口为 /reqcraft:reqcraft-analyze、/reqcraft:reqcraft-spec 等。

例如，先把一份 PRD 转换成验收规格：

$reqcraft-spec 分析 docs/prd/organization.md，
识别业务规则、状态流转和待确认问题，

尚未确认的业务规则不要自行决定。

不要运行测试或修改代码。

如果只想梳理需求、不准备生成完整验收规格，也可以单独使用 analyze。

为什么将职责限制在这三件事

Reqcraft 的目标不是成为一个包办开发、测试、部署的全能代理。

它负责确定并审查“什么才算正确”；开发 Skill 负责技术设计与代码实现，测试 Skill 负责测试方案、测试代码及实际执行。这样既能避免需求工具替业务方作决定，也可以让后续工具复用同一份已确认的规格。

对于个人全栈开发者，这种分工并不意味着增加角色或审批流程。相反，同一个人只需要在不同阶段调用不同能力，减少需求理解、代码实现与结果验收之间的相互干扰。

目前项目已经具备流程定义、规格模板、安装与打包工具，以及结构检查相关的自动化测试。但这些工程检查不能代替真实 PRD 场景评测；复杂需求的提取质量、覆盖完整性和审计准确性，仍需要结合实际项目检验。

Reqcraft 的价值不在于多生成一份文档，而在于让需求中的假设、规则、结果和证据变得明确。 当这些内容能够被逐项追踪和验证，前后端开发才有更稳定的目标，验收也不必等到功能完成后才重新讨论“到底什么算做对了”。
