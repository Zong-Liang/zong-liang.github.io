1. Canal 是什么？解决什么问题？

Canal（读作 canal，意为“水道”）是一套基于 MySQL Binlog 的增量数据订阅与消费组件。 它把数据库已经发生的数据变更解析成可供应用程序处理的事件，例如“用户表新增了一行”“订单状态从待支付更新为已支付”。它的核心工作不是替应用执行业务 SQL，而是在 SQL 成功提交并记录到 Binlog 之后，捕获、解析并向下游提供数据变更。

例如，业务系统执行：

1

UPDATE canal_demo.user_account SET name = '李四' WHERE id = 1;

数据提交后，一条 CDC 处理链路可以表示为：

flowchart LR

  B --> C[Canal Server 解析变更]
  C --> D{消费方式}
  D --> E[Java Canal Client]
  D --> F[Kafka / RocketMQ]
  E --> G[搜索索引 / 缓存 / 派生表]
  F --> H[异步消费者 / 数据处理服务]

下游可获知操作类型 UPDATE、库名/表名、主键、变更前后字段以及 Binlog 位置信息（具体字段与值取决于 Binlog 格式和配置）。Canal 捕获的是数据库变更事件，不等于业务领域事件。 例如“订单已支付”可能对应多张表、多个字段；只看到一条 UPDATE 并不天然知道完整的业务语义。

1.1 先理解几个经常混淆的概念

概念说明与 Canal 的关系
BinlogMySQL 的二进制变更日志，用于复制、恢复等Canal 的主要输入
CDC（Change Data Capture）捕获数据库变更的技术/模式Canal 是 CDC 工具的一种
Canal Server连接 MySQL、解析 Binlog、管理订阅实例的服务核心组件
Canal Client获取 Canal Server 提供的变更并执行业务处理应用侧消费组件
MQKafka、RocketMQ 等消息中间件可选的变更事件分发渠道
Canal Adapter把变更映射到下游系统的适配组件降低部分同步场景的编码量
Canal Admin管理 Canal 节点、配置及任务的 Web 管理组件运维管理，不是数据采集本体

1.2 Canal 不是什么

  • 不是 MySQL 数据库：不保存一份可直接查询的业务关系型数据库。
  • 不是全量数据迁移工具：既有历史数据通常要另外做一致性快照/全量导入，然后衔接增量。
  • 不是业务消息总线的天然替代品：Binlog 捕获物理数据变更，业务语义和消息契约通常需要额外设计。
  • 不是分布式事务解决方案：捕获变更不自动保证 MySQL、Redis、ES 或其他服务之间的强一致性。
  • 不是所有实时场景的最佳答案：对简单的应用内事件，可能有更低成本的方案。

2. 什么时候应该用 Canal？什么时候不该用？

2.1 典型适用场景

场景 A：MySQL → Elasticsearch / OpenSearch 搜索索引
业务数据库作为权威数据源，增量变更更新搜索索引。索引更新异步进行，允许短暂最终一致；必须考虑重试、删除、乱序以及全量重建。

场景 B：MySQL → Redis 缓存失效或刷新
多个入口都可能修改数据库时，监听数据变化可作为统一缓存失效通道。但不能仅靠 Canal 来严格保证缓存与数据库的实时一致；高并发下仍要处理乱序和读写竞争。

场景 C：业务库 → 分析平台 / 实时指标
通过 Canal 把变更送到 Kafka，再由流处理系统计算指标、构建宽表或审计流水。设计时必须弄清“数据变更”和“业务行为”的区别。

场景 D：异构数据库 / 跨系统增量同步
例如 MySQL 表变化后维护另一套数据副本。一般需要全量初始化、增量衔接、字段映射和校验修复，不能仅把事件消费成功视为“目标端一致”。

场景 E：既有系统无法轻易改造写入代码
当不能在每个写入入口加入消息发送逻辑时，基于 Binlog 捕获变更可以降低对业务代码的侵入。

2.2 不优先使用 Canal 的场景

需求通常更直接的选择原因
同一 Spring Boot 单体内部的一次普通业务调用同步方法调用、事务内逻辑、事务后事件没必要部署独立 CDC 系统
严格要求“业务写入与外部系统同时成功”重新审视事务边界、事务型 Outbox / Saga 等CDC 本身不能跨系统提供原子提交
需要表达“用户取消订单的原因”等丰富业务语义领域事件 / Outbox 事件Binlog 行变化并不等于业务事件
主要处理存量历史数据全量导出 / 批处理 / 迁移工具Canal 主要解决增量
需要把多个数据库的变更合成一个全局强顺序流专门的事务/排序设计不同源之间没有天然统一顺序
数据库平台不提供兼容的日志/复制接口对应平台的 CDC 连接器或应用事件Canal 不能跨所有数据库通用

决策原则： 当核心问题是“数据库变更已发生，如何低侵入、持续地通知多个下游”，且业务接受最终一致性时，Canal 值得考虑；如果核心问题是“可靠发出一条有明确业务含义的事件”，则应认真比较事务型 Outbox。

3. 底层原理：MySQL Binlog 与伪装从库

3.1 Binlog 为什么能够实现 CDC

MySQL 在启用二进制日志的前提下，会记录需要复制的变更事件。通常使用：

  • STATEMENT：主要记录 SQL 语句；部分语句在复制语义上有局限。
  • ROW：记录行级变化；CDC 最常用、最可预测的模式。
  • MIXED：混合模式，具体事件取决于 MySQL 判断。

对基于行级变更的同步，建议使用 ROW 和 binlog_row_image=FULL。FULL 使 UPDATE 的前后镜像更容易被完整解析；MINIMAL 可能不包含所有未变更字段，不能假设每次事件都带整行。

MySQL 8.4 默认启用 Binlog 且默认格式为 ROW，但不要靠默认值判断生产环境配置，应实际查询。MySQL 8.4 中 binlog_format 已被标记为弃用项；今后新部署仍应优先采用行级日志及相应数据库版本推荐方式。

sequenceDiagram
  participant App as 业务应用
  participant DB as MySQL Source
  participant Canal as Canal Server
  participant Consumer as 下游消费者
  App->>DB: 执行 INSERT / UPDATE / DELETE
  DB->>DB: 事务提交并记录 Binlog
  Canal->>DB: 以复制客户端身份请求 Binlog
  DB-->>Canal: 持续发送 Binlog events
  Canal->>Canal: 解析、过滤、形成 Entry
  Consumer->>Canal: 获取变更 batch
  Canal-->>Consumer: 返回 Entry 列表
  Consumer->>Consumer: 执行下游处理
  Consumer->>Canal: 成功 ACK / 失败 rollback

Canal 模拟 MySQL 复制客户端的协议来订阅日志，但并不执行传统从库的完整重放流程。从库会把事件用于更新副本，Canal 则把事件解析为可被下游消费的数据对象。

3.3 Binlog 文件、Position、GTID

  • Binlog 文件 + Position：标记复制流中的位置，例如 mysql-bin.000003 / 12345。文件切换后文件名变化。
  • GTID：全局事务标识，可用于复制及故障切换场景的事务定位。是否启用须与 MySQL 侧配置匹配，不能只改 Canal 的一个开关。
  • 游标 / Cursor：Canal 已读取或已确认的处理进度。读取到哪里与下游成功处理到哪里不能混为一谈。
  • Binlog 保留时间：如果 MySQL 已经清理了 Canal 尚需读取的日志，就可能出现不可直接续读的缺口，需要重新初始化或进行受控恢复。

3.5 关于顺序与事务的三个限制

  1. 同一 MySQL Binlog 流中事件有确定读取顺序，但通过多分区 MQ、并发消费者后，下游整体不一定仍有全局顺序。
  2. 一个数据库事务可能包含多行、多表；Canal 中的 Entry / MQ 消息边界不应未经验证就当成完整业务事务边界。大事务可能被拆分处理。
  3. 如果多个 MySQL 实例共同提供数据，不同实例之间没有天然全局先后顺序。

4. Canal 系统组成与数据流模式

4.1 主要组件

组件职责什么时候需要
canal.deployer / Server连接 MySQL、解析日志、持有订阅实例、提供 TCP/MQ 输出必需
canal.clientJava 等语言直连 Canal，getWithoutAck / ack / rollbackTCP 消费模式
Canal MQ Connector直接投递 Kafka、RocketMQ 等消息系统希望多服务解耦、缓冲与扩展
canal.client-adapter配置化同步到部分目标端（具体适配能力随版本变化）目标端已有适配支持时
canal.adminWeb 化集中配置和节点管理节点增多或集中运维时
ZooKeeper在官方支持的部分集群/高可用模式中协调实例、节点等需要相应 HA/集群特性时

destination 是客户端连接的订阅实例名，默认演示实例为 example。多个 destination 不是默认就能对同一数据库任意独立扩展，也不能简单等同 Kafka 的消费者组；规划时应按 Canal 实际部署与订阅机制设计。

4.2 两类最常见架构

模式一：直连 TCP，适合学习、少量消费者及明确的单一处理链路

1

MySQL → Canal Server（TCP:11111）→ Java Canal Client → Redis / ES / 目标 DB

优点：拓扑简单，便于理解变更内容、ACK、回滚和位点。局限：需要自己解决下游消费故障恢复、业务缓冲、扩容和多系统分发。

模式二：Canal → MQ，适合多消费者及较大规模的异步处理

1
2
3
4

MySQL → Canal Server → Kafka / RocketMQ
                           ├── 搜索索引服务
                           ├── 缓存失效服务
                           └── 数据分析服务

优点：解耦消费端、可缓冲流量、多个业务消费群组独立处理。局限：需要同时管理 Canal 到 MQ 的可靠性、MQ 的保留/重试/分区策略，以及消费端幂等性。引入 MQ 并不自动获得端到端 Exactly Once。

5. 本地实战：Docker Compose 启动 MySQL + Canal

本例使用 MySQL 8.0.36 和 Canal 1.1.8，以 TCP 模式演示 INSERT / UPDATE / DELETE → Java 订阅。在 macOS Apple Silicon 上，官方 canal/canal-server:v1.1.8 镜像有 ARM64 版本；也支持 AMD64。示例用 Docker Compose，暂不引入 Kafka、Canal Admin 和 ZooKeeper，先把核心链路走通。

import com.alibaba.otter.canal.client.CanalConnector;
import com.alibaba.otter.canal.client.CanalConnectors;
import com.alibaba.otter.canal.protocol.CanalEntry;
import com.alibaba.otter.canal.protocol.Message;
import com.google.protobuf.InvalidProtocolBufferException;

import java.net.InetSocketAddress;
import java.util.LinkedHashMap;
import java.util.Map;
import java.util.concurrent.TimeUnit;

public class CanalDemo {

    public static void main(String[] args) {
        CanalConnector connector = CanalConnectors.newSingleConnector(
                new InetSocketAddress("127.0.0.1", 11111),
                "example", "", ""
        );

        try {
            connector.connect();
            // Java 字符串中的 \\. 对应正则中的 \.，用于匹配实际的点号
            connector.subscribe("canal_demo\\.user_account");
            connector.rollback();

            System.out.println("Canal client started.");
            while (!Thread.currentThread().isInterrupted()) {
                Message message = connector.getWithoutAck(100, 1L, TimeUnit.SECONDS);
                long batchId = message.getId();
                if (batchId == -1) {
                    continue;
                }

                try {
                    for (CanalEntry.Entry entry : message.getEntries()) {
                        handle(entry);
                    }
                    // 所有事件处理成功后才能确认
                    connector.ack(batchId);
                } catch (Exception processingError) {
                    System.err.println("Batch failed: " + batchId);
                    processingError.printStackTrace();
                    connector.rollback(batchId);
                    TimeUnit.SECONDS.sleep(1);
                }
            }
        } catch (Exception connectionError) {
            // 演示程序简单结束；生产代码需要连接重试和健康检查
            throw new IllegalStateException("Canal connection failed", connectionError);
        } finally {
            connector.disconnect();
        }
    }

    private static void handle(CanalEntry.Entry entry)
            throws InvalidProtocolBufferException {
        if (entry.getEntryType() != CanalEntry.EntryType.ROWDATA) {
            return;
        }

        CanalEntry.RowChange change =
                CanalEntry.RowChange.parseFrom(entry.getStoreValue());

        String table = entry.getHeader().getSchemaName()
                + "." + entry.getHeader().getTableName();
        if (change.getIsDdl()) {
            System.out.printf("DDL table=%s sql=%s%n", table, change.getSql());
            return;
        }

        CanalEntry.EventType type = change.getEventType();
        for (CanalEntry.RowData row : change.getRowDatasList()) {
            Map<String, String> before = toMap(row.getBeforeColumnsList());
            Map<String, String> after = toMap(row.getAfterColumnsList());
            System.out.printf("table=%s type=%s before=%s after=%s%n",
                    table, type, before, after);
        }
    }

    private static Map<String, String> toMap(
            java.util.List<CanalEntry.Column> columns) {
        Map<String, String> result = new LinkedHashMap<>();
        for (CanalEntry.Column c : columns) {
            // 教学展示使用字符串；真实入库时保留 NULL 和数据类型信息
            result.put(c.getName(), c.getIsNull() ? null : c.getValue());
        }
        return result;
    }
}

运行后执行第 5 节的 SQL，应看到相应 INSERT、UPDATE 和 DELETE 事件。UPDATE 的 before / after 可以用于理解字段变化；是否出现完整列信息取决于 MySQL 行镜像配置及表元数据解析情况。

关于示例的重要限制： 上述代码展示的是核心 API，不包含后台服务所需的生命周期管理、重连、线程停止、告警、持久化消费侧处理结果等逻辑；不能未经改造直接作为生产消费者。

6.3 API 的正确使用顺序

1

connect()
  → subscribe(filter)
  → getWithoutAck(batchSize, timeout, unit)
  → 执行业务处理
  ├─ 成功 → ack(batchId)
  └─ 失败 → rollback(batchId) → 后续重试
  → disconnect()
  • get(...)：自动确认，不适合需要按下游处理结果控制消费确认的场景。
  • getWithoutAck(...)：先获取，不自动确认；适合需要可靠消费的应用。
  • ack(batchId)：通知服务端已成功处理该批次，推进已确认进度。
  • rollback(batchId)：将尚未确认的消费位置回退，以便重读。这里的 rollback 不是回滚 MySQL 原事务，更不是撤销已经发送到外部系统的副作用。

ack 应在所有该批数据的下游处理成功提交之后执行。否则 Java 服务可能因为“先确认、后写入、写入失败”而丢失业务侧处理机会。

7.1 flatMessage 需要注意什么

  • canal.mq.flatMessage=true：消息可按 Canal 的扁平 JSON 约定处理，适合普通 JSON 消费者。
  • false：通常使用 Protocol Buffers 格式，下游需要匹配的解码逻辑。
  • JSON 数据结构属于 Canal 的消息契约，不是 JDBC ResultSet；数据类型、空值、更新前字段及 DDL 字段都需要做协议适配。
  • 消费分区会影响顺序：需要按行主键保证更新顺序时，应规划 partitionHash、分区数以及消费组处理模型，并检验实际发出的路由。
  • Kafka 侧是否成功投递，与消费业务是否成功处理是两层确认机制；二者都要分别考虑故障恢复。

7.2 “每张表一个 Topic”是不是必须？

不是。可以按数据库、业务域、表或事件用途设计 Topic；通常不宜一开始就为每个小表创建独立 Topic。重要的是下游权限边界、事件量、消息模式、路由与分区规划，而不是追求数量越多越好。

8. Canal Adapter 与 Canal Admin 应该如何看待

8.1 Canal Adapter

Adapter 适合将标准的数据库变更按配置映射到下游系统。与手写 Java 消费者相比，它可以减少重复的连接、解析和映射代码。不过它不替你决定：主键映射、字段转换、全量初始化、冲突处理、删除语义和数据校验。

什么时候优先考虑 Adapter：目标系统在当前版本明确受支持、映射逻辑简单、团队希望通过配置而不是开发独立业务服务来维护同步链路。对于复杂聚合、业务校验、多源联合与严格幂等要求，定制消费者通常更可控。

8.2 Canal Admin

canal.admin 可提供节点、配置和任务管理的 Web 界面；它不负责自行生成全量数据，也不代替 Kafka、MySQL 和业务消费者。学习阶段不必部署；当实例较多、需要集中配置管理和运维时再引入。

生产部署时必须对 Admin、Canal TCP 端口和指标端口进行网络隔离和访问控制，避免把内部管理接口直接暴露到公网。1.1.8 发布说明专门提到默认管理口令风险与配置读取漏洞修复，因此旧版本的安全配置不应照搬。

9. 企业开发中最重要的部分：可靠性与一致性

9.1 Canal 能做到什么一致性？

典型应用是最终一致性：主库先完成事务，Binlog 随后被 Canal 读取，下游在一定延迟后追上。这个过程中可能出现消费失败、重复投递、乱序和短暂数据不一致。

可靠性失误示例

1
2
3
4
5
6

数据库 UPDATE 成功
  → Canal 产生事件
  → 消费者拿到事件
  → 写入 Elasticsearch 成功
  → 消费者在 ACK 前崩溃
  → 恢复后再次拿到同一事件

上述过程产生重复消费。所以“尽量只处理一次”不能依赖 ACK 单独实现，必须使目标端重复执行可接受。

9.2 幂等怎么做

下游操作一般实践仍需注意
ES 索引以数据库主键为文档 ID，重复更新覆盖同一文档旧事件可能晚到、覆盖新状态；应结合版本/位点保护
Redis 缓存按业务 key 删除缓存，删除操作通常天然适合重复执行写入与失效竞争可能产生旧值回填
MySQL 派生表使用主键约束与 UPSERT，或用事件记录表去重需要保证去重记录和数据更新处在同一目标端事务
消费者调用外部 API传递幂等请求 ID，并由目标 API 真正实施去重调用超时不等于未成功，不能盲目无界重试

对同一个数据主键可能并发到达的事件，最重要的是保证顺序或阻止旧版本覆盖新版本。仅“UPSERT 能重复执行”并不能解决乱序。

9.3 失败处理与死信

推荐区分三类失败：

  1. 暂时性失败（网络抖动、目标库限流）：有限次数退避重试。
  2. 不可自动恢复的业务失败（类型不兼容、缺失配置）：记录错误并进入可回放的隔离队列/死信处理流程，避免无限阻塞和静默跳过。
  3. 源日志缺口（Binlog 过期、位点丢失）：需要运维介入，校验和补齐数据，不能简单从“最新位置”继续却不记录缺失区间。

最不应该的做法是：解析失败就打印日志，然后无条件 ACK。 这会把暂时错误变成永久的数据缺口。

9.4 端到端 Exactly Once 为什么难

MySQL 提交、Canal 位点确认、Kafka 生产确认、消费者偏移量提交、ES/Redis 写入分别处在不同系统；它们之间不存在默认的单一原子事务。实际工程通常采用“可重放 + 幂等处理 + 进度可观测 + 对账修复”，而不是宣称只靠 Canal 就达到了端到端 Exactly Once。

9.5 全量 + 增量如何衔接

Canal 只跟踪变更，不等于完整复制现有表。对于需要把历史数据同步到索引/目标库的场景，标准思路是：

1
2
3
4
5

记录一致性快照起点 / 可衔接位点
   → 导出并导入历史全量数据
   → 从正确的 Binlog 位点连续回放增量
   → 对账（总量、抽样、主键与字段）
   → 切流并持续增量维护

实际顺序可按工具能力变换，例如先启动增量缓冲、再导出一致性快照；但必须确保全量快照与增量位点之间没有遗漏窗口，并处理回放期间的重复与冲突。MySQL 的 MVCC 快照并不自动解决所有 DDL 或跨实例的一致性问题。

9.6 数据安全和权限边界

Binlog 可能包含用户姓名、手机号、薪资字段或其他敏感业务数据。即使消费端只需要某几个字段，源端订阅范围、传输链路、MQ Topic、消费端日志及权限都可能暴露更多信息。需要按数据分级执行最小订阅、字段脱敏、链路加密、网络隔离、凭据轮换及保留周期控制。

12. Canal 与其他常见方案的区别

方案关注点优势典型限制
CanalMySQL Binlog 的增量解析、订阅与消费面向 MySQL，直连与 MQ 模式比较直接全量、可靠性、业务语义仍需补齐
Debezium多种数据库的 CDC 连接器与生态对接 Kafka Connect 等生态成熟，多源能力较丰富平台复杂度、运维模型取决于部署模式

13. 结合典型 Java 业务的三个设计例子

13.1 订单状态同步搜索索引

设计：MySQL 为主数据源，Canal 监听订单表，事件经 Kafka 进入搜索服务。搜索服务用订单 ID 作为文档 ID，发生更新时以版本号或能保证单调的业务版本防止旧消息覆盖新状态。删除事件需删除/标记对应索引。上线时先全量建索引，再衔接增量，最终按主键对账。

这里“写库成功、搜索稍后可见”是正常的最终一致性；若要求事务后立刻检索到新值，则必须另外设计读取/写入路径。

13.2 多服务共享缓存失效

设计：MySQL 变更由 Canal 捕获，消费者按主键找到缓存 key 并删除。如果复杂查询缓存依赖多个表或动态条件，则需要提前维护依赖映射；否则无法仅凭表主键知道应该删哪个缓存。高并发还要考虑旧查询在失效后回填旧值的竞态。

13.3 组织管理系统的派生数据同步（示意）

假设组织关系源表变更后，需要维护供其他应用查询的组织树索引。可以让 Canal 捕获组织单元、上下级关系变化，但不能把“修改某一行”直接等价为“组织树已完成调整”；一个业务动作可能涉及多行、审批状态或多个事务。可采用：

  • 监听数据库变更，只做派生视图的最终一致更新，并具备整体重建能力；或者
  • 在业务事务中保存表达“组织调整已生效”的 Outbox 事件，明确事件 ID、组织标识、版本与状态，再异步发布。

选用哪种方式取决于下游是需要表数据的实时副本，还是需要完整的业务事件语义。

14. 高频问题与容易犯的错误

Q1：Canal 是不是实时同步？
更准确地说是低延迟增量同步。日志读取、解析、投递和消费均需要时间，业务侧观察到的延迟取决于负载、网络和下游吞吐；不是强实时或同步事务。

Q2：Canal 能不能监听 DELETE？
能。ROW Binlog 中的删除事件通常可还原被删除行的字段信息；前提是该事件被记录且订阅、解析正常。

Q3：Canal 能不能监听 ALTER TABLE？
可处理/识别相应 DDL 变更，具体表现和消息格式依赖版本与配置。DDL 可能影响表元数据，因此线上变更应有兼容性测试。

Q4：Canal 挂了会丢数据吗？
不能一概而论。如果保存了正确位点，MySQL 仍保留对应 Binlog，且消费者按正确逻辑确认/重试，可以续读。反之，如果日志已经清理、位点损坏、提前 ACK 或下游漏处理，则可能出现缺口。

Q5：Canal 能不能直接做全量同步？
Canal 主要负责增量，完整全量流程需要快照/导出/数据迁移工具与衔接设计。部分上下游生态可能提供组合方案，但不要把它误解为 Canal Server 的基础能力。

Q6：同一条数据会不会消费两次？
会。恢复、重试、MQ 投递等均可能带来重复。消费侧应具备幂等处理能力。

Q7：一个 Canal 实例能不能让任意多个服务独立订阅？
不要以为 TCP 客户端订阅与 Kafka 消费组语义完全相同。不同消费方需要独立进度和扩展时，通常应评估 MQ 分发、订阅实例隔离与 HA 设计。

Q8：线上数据库已经有主从复制，Canal 会影响它吗？
Canal 作为另一个复制协议客户端读取日志，通常不需要替换现有复制拓扑，但会增加源库的 Binlog 传输、连接、CPU/网络/磁盘相关负载；需要配置独立 server-id，评估资源消耗与故障切换行为。

Q9：MySQL 8.4 还能用吗？
Canal 1.1.8 Release 说明明确新增 MySQL 8.4 适配；仍须验证实际 MySQL 小版本、认证方式、SSL、云数据库行为及数据类型兼容性。不要把“支持版本”理解成所有部署形态都无需验证。

Q10：Canal 与 Spring Boot 如何整合？
Spring Boot 中可以把 Canal Client 封装为独立生命周期管理的后台组件，管理连接、心跳、重试、关闭和监控；不要直接将上述无限循环塞进 HTTP Controller。多数企业链路更适合 Canal→MQ，再在 Spring Boot 中使用成熟的 MQ 消费机制。
