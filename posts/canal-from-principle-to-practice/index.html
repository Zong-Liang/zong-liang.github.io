一、Canal 是什么

Canal 是阿里巴巴开源的、基于 MySQL Binlog 的增量数据订阅与消费组件。

它可以在不修改业务代码的前提下，感知 MySQL 中的数据变更，并将变更提供给其他系统消费。

假设用户管理系统更新了用户姓名：

1

用户修改姓名 → Spring Boot → UPDATE users ... → MySQL

如果系统还使用 Redis 缓存、Elasticsearch 搜索索引，那么在 MySQL 更新后，还要同步这些下游系统的数据。引入 Canal 后，可能形成这样的链路：

flowchart TD
    A[Spring Boot 业务服务] -->|更新| B[(MySQL)]
    B -->|Binlog| C[Canal Server]
    C --> D[Java 消费服务]
    C --> E[MQ / Adapter]
    D --> F[(Redis)]
    E --> G[(Elasticsearch 等下游)]

业务服务专注于写入 MySQL；变更捕获及后续同步由独立链路处理。这类通过数据库变更日志捕获数据变化的技术，称为 CDC（Change Data Capture，变更数据捕获）。

1.1 典型应用场景

场景Canal 的作用
MySQL → Redis感知数据更新，触发缓存删除或更新
MySQL → Elasticsearch增量维护搜索索引
MySQL → 其他数据库进行异构数据库同步
MySQL → Kafka / RocketMQ将数据库变更转换为消息流
数据分析将业务变更传递给下游分析系统
审计与变更跟踪提供数据库变更事件作为审计数据来源之一

Canal 负责捕获和传输变更，不自动保证下游系统的数据绝对一致。消费幂等、失败重试、数据对账和历史数据初始化仍需业务系统设计。

1.2 哪些问题不适合直接交给 Canal

例如，订单支付成功后必须发放权益。若要求严格的业务一致性，不能简单地依赖 Canal 异步触发权益发放。CDC 存在同步延迟，而且数据库变更未必完整表达业务意图。

对于需要明确业务语义或严格控制事件发布的场景，还应了解事务消息和 Transactional Outbox（事务发件箱）等方案。

二、先理解 MySQL Binlog

2.1 什么是 Binlog

Binlog（Binary Log，二进制日志）记录 MySQL 中用于复制和恢复的数据变更事件，是 MySQL 主从复制与基于日志的增量恢复的重要基础。

1

UPDATE users SET name = '李四' WHERE id = 1;

启用行级 Binlog 后，MySQL 会记录受影响数据行的信息。Canal 通过 MySQL 复制协议获取这些变更，不需要监听 Spring Boot 接口，也不需要读取业务应用日志。

2.2 Binlog 的三种格式

格式记录内容特点
STATEMENT执行的 SQL 语句体积可能较小，但某些操作的复制结果可能不确定
ROW数据行的变化可准确获取受影响数据行，是 CDC 的主要选择
MIXED混合使用上述格式根据操作选择格式

例如：

1

UPDATE users SET status = 1 WHERE id IN (1, 2, 3);

在 STATEMENT 模式中，日志主要记录 SQL；在 ROW 模式中，日志记录受影响数据行的变化。Canal 可以进一步解析为结构化事件。

学习和部署 MySQL CDC 时，优先使用 ROW 模式。MySQL 8.0 默认使用 ROW；自 MySQL 8.0.34 起，binlog_format 被标记为废弃配置项，实际部署仍需核对数据库版本和配置。

2.3 Before、After 与 Row Image

假设原始数据是：

idnamestatus
1张三0

执行：

1

UPDATE users SET name = '李四', status = 1 WHERE id = 1;

当 binlog_row_image=FULL 时，可以获得如下前后镜像：

1
2

Before: {id: 1, name: "张三", status: 0}
After:  {id: 1, name: "李四", status: 1}
  • INSERT：通常有 After，没有 Before。
  • DELETE：通常有 Before，没有 After。
  • UPDATE：通常存在 Before 和 After。

binlog_row_image=MINIMAL 时，更新前可能只包含定位数据行所需的列，更新后只包含必要的变更列。因此，不能默认所有变更事件都具有完整的字段值。

2.4 Binlog、Redo Log、Undo Log 的区别

日志主要职责典型用途
Redo LogInnoDB 崩溃恢复保证已提交修改能够恢复
Undo Log保存必要的旧版本及撤销信息事务回滚、MVCC
Binlog记录数据库变更事件主从复制、增量恢复、CDC

Canal 读取的是 Binlog，而不是 InnoDB 的 Redo Log。MySQL 的提交与恢复机制还涉及 Redo Log 与 Binlog 的协调提交，不能把二者理解为完全独立的两次写入。

三、Canal 的工作原理与核心组件

3.1 模拟 MySQL 复制客户端

MySQL 主从复制通常通过复制协议传输 Binlog，并由从库重放。Canal 使用类似的获取机制：它以复制客户端身份连接 MySQL，接收并解析 Binlog，但它不是保存业务表副本的 MySQL 从库。

sequenceDiagram
    participant M as MySQL
    participant C as Canal Server
    participant J as Java Client
    C->>M: 建立复制连接，请求 Binlog
    M-->>C: 持续发送变更事件
    C->>C: 解析行变更、组织事件
    J->>C: 拉取变更批次
    C-->>J: Message / Entry
    J->>J: 处理业务逻辑
    J->>C: ACK（处理成功后）

完整链路可拆为七步：

  1. Canal Server 与 MySQL 建立复制连接。
  2. Canal 请求指定位置之后的 Binlog。
  3. MySQL 持续发送日志事件。
  4. Canal 解析事件，并结合表结构元数据生成字段级变更信息。
  5. Canal 将事件保存在内部存储中。
  6. Java 客户端拉取事件，或由 Canal 投递给 MQ。
  7. 消费者完成缓存、索引、数据库等下游处理。

3.2 核心组件

组件职责
Canal Server / Deployer连接 MySQL，订阅、解析、存储和提供 Binlog 事件
Canal Instance管理一个逻辑数据订阅实例
Canal Client获取并处理结构化数据库变更
Canal Adapter将变更数据适配到 Elasticsearch 等目标系统
Canal Admin集中管理配置、实例和任务

Instance 是服务端的逻辑订阅实例；Destination 是客户端连接时使用的目标名称，例如 example。

四、两种主要消费模式

4.1 TCP 直连模式

1

MySQL → Canal Server → Java Client → Redis / ES / DB

Java 程序使用 Canal SDK 连接 Server，主动获取事件。优点是依赖少、结构简单；但连接管理、ACK、异常重试、断线恢复需要自己处理。

4.2 MQ 模式

1
2
3
4
5

MySQL → Canal Server → Kafka / RocketMQ
                              ↓
                         Java 消费者
                              ↓
                        Redis / ES / DB

这种模式更适合多个独立下游消费同一份变更，可以利用 MQ 的持久化、保留和消费组能力。

维度TCPMQ
接入复杂度较低中等
外部依赖少依赖 MQ
多消费者扩展需要额外设计适合独立消费组
数据缓冲Canal 内部机制可利用 MQ 的保留与持久化
典型使用阶段学习、简单同步较复杂的生产链路

注意：接入 MQ 不等于获得端到端 Exactly Once 语义。仍需考虑位点、消息重试、幂等和保留时间。

import com.alibaba.otter.canal.client.CanalConnector;
import com.alibaba.otter.canal.client.CanalConnectors;
import com.alibaba.otter.canal.protocol.CanalEntry;
import com.alibaba.otter.canal.protocol.Message;

import java.net.InetSocketAddress;
import java.util.List;

public class CanalStudyApp {

    public static void main(String[] args) throws Exception {
        CanalConnector connector = CanalConnectors.newSingleConnector(
                new InetSocketAddress("127.0.0.1", 11111),
                "example", "", ""
        );

        try {
            connector.connect();
            connector.subscribe("demo_canal\\.users");
            connector.rollback();

            while (!Thread.currentThread().isInterrupted()) {
                Message message = connector.getWithoutAck(100);
                long batchId = message.getId();

                if (batchId == -1) {
                    Thread.sleep(500);
                    continue;
                }

                try {
                    for (CanalEntry.Entry entry : message.getEntries()) {
                        handleEntry(entry);
                    }
                    // 处理成功后确认
                    connector.ack(batchId);
                } catch (Exception e) {
                    // 处理失败后重新读取
                    connector.rollback(batchId);
                    e.printStackTrace();
                    Thread.sleep(1000);
                }
            }
        } finally {
            connector.disconnect();
        }
    }

    private static void handleEntry(CanalEntry.Entry entry) throws Exception {
        if (entry.getEntryType() != CanalEntry.EntryType.ROWDATA) {
            return;
        }

        CanalEntry.RowChange rowChange = CanalEntry.RowChange.parseFrom(
                entry.getStoreValue()
        );

        if (rowChange.getIsDdl()) {
            System.out.println("DDL: " + rowChange.getSql());
            return;
        }

        String table = entry.getHeader().getSchemaName()
                + "." + entry.getHeader().getTableName();
        CanalEntry.EventType type = rowChange.getEventType();

        for (CanalEntry.RowData row : rowChange.getRowDatasList()) {
            System.out.println("Table: " + table);
            System.out.println("Type: " + type);
            System.out.println("Before: " + format(row.getBeforeColumnsList()));
            System.out.println("After: " + format(row.getAfterColumnsList()));
        }
    }

    private static String format(List<CanalEntry.Column> columns) {
        StringBuilder result = new StringBuilder();
        for (CanalEntry.Column column : columns) {
            result.append(column.getName()).append("=")
                  .append(column.getIsNull() ? "NULL" : column.getValue())
                  .append(" ");
        }
        return result.toString();
    }
}

这是学习用最小示例。生产消费者还要实现重连退避、数据落地幂等、错误隔离、优雅退出和监控。getWithoutAck() 的批次参数不是“每次必然返回 100 行”。

六、Java Client 的关键 API 与协议结构

6.1 connect 与 subscribe

1
2

connector.connect();
connector.subscribe("demo_canal\\.users");

connect() 建立 Java Client 到 Canal Server 的连接，不是直接连接 MySQL。subscribe() 指定要读取的表，需要与服务端过滤规则相匹配。

6.2 getWithoutAck、ACK 和 Rollback

1
2
3
4
5
6
7
8

Message message = connector.getWithoutAck(100);
long batchId = message.getId();

// 处理成功
connector.ack(batchId);

// 处理失败
connector.rollback(batchId);
  • getWithoutAck：拉取事件但不自动确认。
  • ack：确认已成功处理的批次，推动消费确认位置。
  • rollback：撤销尚未确认的读取状态，使有关事件有机会再次读取。

Canal 的 Rollback 不是 MySQL 的事务回滚。如果下游 Elasticsearch 已更新成功、Java 进程却在 ACK 前崩溃，恢复后仍可能再次消费同一事件；Rollback 不会自动撤销 Elasticsearch 更新。

七、生产系统的关键问题

7.1 重复消费与幂等

假设消费者处理积分变更：

1

UPDATE user_score SET score = score + 10 WHERE user_id = 1;

如果业务处理成功，但 ACK 之前进程崩溃，恢复后重复执行可能导致积分额外增加。

方案一：最终状态覆盖。如果事件有完整目标状态，可采用确定值更新：

1

UPDATE user_score SET score = 110 WHERE user_id = 1;

重复执行通常不会继续累加，但如果旧事件晚于新事件到达，仍可能把新状态覆盖成旧状态，因此还要考虑版本号与顺序。

方案二：业务幂等键。为事件建立稳定唯一标识，在同一目标数据库事务中检查处理记录、执行业务变更并保存处理记录。对无法参与同一事务的外部系统，还要使用其幂等接口、补偿等机制。

7.2 ACK 时机

错误流程：

1

收到事件 → 先 ACK → 写入目标系统 → 写入失败

正确的基本顺序：

1

收到事件 → 处理业务 → 确认目标系统成功 → ACK

处理成功后 ACK + 消费端幂等 + 重试与告警是常用的可靠性基础，但它本身不是端到端精确一次保证。

7.3 全量同步和增量同步

如果表中已有 100 万条数据，今天才接入 Canal，它不会自动把全部历史数据重新生成 100 万条 INSERT 事件。

flowchart TD
    A[(MySQL)] --> B[一致性全量快照]
    A --> C[增量 Binlog]
    C --> D[Canal]
    B --> E[目标系统]
    D --> E

不能简单地“先把全表查完、再开始监听 Binlog”，否则两步之间发生的修改可能遗漏。需要设计一致性快照、起始位点、增量缓存和回放顺序，或采用成熟的全量加增量同步方案。

7.4 位点与断点续传

Binlog 文件和位置可以表示为：

1
2

mysql-bin.000012
position: 456789

GTID 也可以用于跟踪事务执行位置。恢复时不仅要看 MySQL 位点，还要检查 Canal 的位置记录、客户端确认状态以及相应持久化机制。不要随意清除 Canal 的元数据与数据目录。

7.5 Binlog 过期清理

1

SHOW VARIABLES LIKE 'binlog_expire_logs_seconds';

若 Canal 停机过久，尚未读取的 Binlog 已被清理，可能无法从原位点恢复，需要重新初始化同步并进行数据校验。应结合磁盘空间和故障恢复目标设置保留期限，并监控同步延迟与最后成功时间。

7.6 顺序一致性

同一用户先发生 status=1，再发生 status=2。若并行消费导致后一个事件先落地、前一个事件后落地，目标系统可能错误回退为 status=1。

常用对策：对相同业务主键进行稳定分区；保持分区内处理顺序；利用业务版本号拒绝旧事件覆盖新数据。分区有序不等于全局有序。

7.7 DDL 与表结构变化

1

ALTER TABLE users ADD COLUMN email VARCHAR(128);

Canal 需要结合表结构元数据解释字段。表结构变化可能影响下游解析和映射。生产环境执行新增、删除、重命名字段时，应检查消费者兼容性、适配器映射并进行验证。

八、典型业务方案

8.1 Redis 缓存一致性

用户查询采用 Cache Aside 模式：

1
2
3

GET /users/1 → 读取 Redis
             → 未命中则读取 MySQL
             → 回填缓存

更新时：

1
2

PUT /users/1 → 更新 MySQL → 提交事务
            → Canal 捕获变更 → 删除 Redis 缓存

为什么通常选择删缓存而不是更新缓存？因为缓存对象可能由多表聚合而成，一条 Binlog 未必包含构造完整缓存所需的信息。

但异步删除仍可能遇到并发竞态：例如读取旧数据的请求在缓存失效后又写入旧值，仍需考虑 TTL、版本校验或并发控制。

8.2 Elasticsearch 搜索索引

例如组织域有：

1
2
3

org_department
org_employee
org_position

搜索索引可能需要组合部门、员工、岗位字段。Canal 能识别数据变更，却无法自动理解多表聚合规则。消费者还需解决：

  • 哪张表发生变化，影响了哪些搜索文档？
  • 是否需要重新查询 MySQL 聚合最新数据？
  • 如何批量更新，避免大量逐条写入？
  • 如何避免旧事件覆盖新索引？
  • 如何校验源库与索引的一致性？

CDC 负责告诉系统发生了什么数据变化；同步业务负责决定变化之后要怎么处理。

九、Canal 与其他技术对比

技术主要定位和 Canal 的关系
MySQL 主从复制数据库副本复制Canal 利用类似复制协议读取 Binlog
Kafka分布式事件流和消息平台Canal 可投递变更到 Kafka
DebeziumCDC 平台与连接器生态与 Canal 有能力重叠
Flink CDC面向实时数据管道的 CDC 能力常用于涉及快照和实时处理的流式管道
MyBatis / JPA应用数据库访问框架负责应用读写数据库，不负责跨系统 CDC
Canal Adapter数据落地适配组件为 Canal 变更提供预置目标适配

选型时应比较数据量、延迟需求、全量初始化、一致性目标、现有基础设施和运维成本，而不是简单认为组件越多越好。

十一、可观测性与数据质量指标

指标用途
同步延迟衡量从源端变更到下游生效的时间
位点推进时间发现同步链路停滞
消费吞吐量衡量每秒处理的事件或数据行数
消费积压量识别消费速度不足
消费失败率观察异常情况
重试次数定位持续失败或不稳定的依赖
最后成功处理时间发现消费者没有进展
源端与目标端数据差异校验最终同步结果

进程健康并不代表目标数据正确。可靠的链路需要联合使用监控告警、数据对账、故障恢复演练和定期校验。
