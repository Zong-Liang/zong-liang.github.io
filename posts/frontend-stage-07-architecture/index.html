第一部分：企业级 React 应用架构

第 1 章 软件架构的目标与约束

1.1 从页面数量到变化成本

小型项目可以把网络请求、表单、表格、弹窗与页面导航全部写在一个组件里。随着业务增加，这个组件会同时承担数据加载、用户交互、表单校验、权限展示与缓存更新。单次修改涉及更多互不相关的逻辑，回归范围随之扩大。

企业项目的架构目标并非“代码层级越多越好”，而是降低变化成本：

  • 内聚（Cohesion）：同一模块中的代码围绕明确的业务能力变化，例如员工信息维护。
  • 耦合（Coupling）：模块之间依赖尽量少，依赖方向与接口可被解释。
  • 可替换性：模块可以独立调整实现，不要求所有消费者同步理解内部细节。
  • 可测试性：业务逻辑可与浏览器渲染、网络请求分别验证。
  • 可观测性：错误能定位到页面、应用版本、接口与业务操作。
  • 可交付性：团队能在合理范围内构建、测试、部署与回滚。

这些目标可能冲突。严格拆分很多 npm 包会增加依赖管理；每个页面独立成微前端会增加运行时和发布复杂度；为了复用而抽象所有业务组件，可能反而形成一个难以升级的公共库。设计选择应与团队规模、变更频率和独立发布需求相符。

1.2 三个不同维度的边界

维度典型划分主要约束
代码边界模块、Feature、包、仓库谁可以 import 什么；谁维护什么
运行时边界React Root、single-spa Application、iframe状态、DOM、生命周期与脚本是否共存
交付边界应用构建产物、部署单元、发布流水线谁独立构建、上线、回滚、监控

多仓库不自动等于微前端；微前端也不必然意味着多个 Git 仓库。 一个 Monorepo 可以构建多个独立部署的子应用；几个仓库也可以合并构建为一个 SPA。

1.3 架构判断的最小问题集

在调整现有项目架构前，要能回答：一项需求涉及哪些业务模块？谁拥有接口契约？路由、权限、页面状态由谁控制？代码如何加载？发生错误时谁负责降级？哪些内容需要一起发布？改动的回归范围如何确定？

仅通过文件改动范围推定模块责任是不可靠的。理解企业存量项目时，应结合路由、数据流、接口调用、实际使用方与发布关系建立完整视角。

2.4 组件职责与复用层次

组件通常可以分为：基础 UI 组件（Button、Modal）、通用业务模式组件（分页查询表格、人员选择器）、领域组件（员工编辑表单、部门树）、页面组件（员工列表页）。

复用的依据应是稳定且一致的行为，而不是“长得差不多”。两个页面虽然都有表格，如果列规则、权限、交互、提交语义差异很大，强行抽象成统一配置式组件可能增加维护难度。

第 3 章 数据流、状态与依赖边界

3.1 不同状态有不同的所有者

一个员工管理应用的状态并非都属于“全局状态”：

状态类型示例通常的所有者
临时交互状态弹窗是否打开、表单输入草稿组件或局部 Hook
URL 状态关键词、页码、详情 IDReact Router / URL
服务端状态员工列表、详情、部门选项TanStack Query 等数据层
全局展示设置当前语言、主题、导航收起Shell 或应用级 Context
认证后的会话信息当前用户、允许展示的能力由可信服务端会话接口返回

把所有状态复制到 Redux 或 Context，会增加同步责任。把 URL 筛选条件也保存在单独的 Context 中，容易让浏览器后退与页面显示不一致。将服务端数据复制到另一个全局 Store，则会出现缓存更新之后多个副本不一致的问题。

3.2 单一事实来源（Single Source of Truth）

单一事实来源不意味着所有数据必须放在一个全局对象。它意味着对于同一个事实，在特定范围内有清楚的权威来源。

例如：员工数据以服务端为权威；TanStack Query 缓存是客户端的读取视图；表单草稿则可以暂时偏离服务端数据，用户点击保存后才通过 Mutation 提交。

3.4 状态跨微前端共享的边界

不同 React Root 不能假定共享同一棵 Context 树。即使两个子应用都安装了 React，A 应用内的 RoleContext Provider 并不会因为名称相同就自动被 B 应用读取。

对少量全局展示配置，可以通过明确的生命周期 customProps、受控事件或共享服务提供；需要持续一致的业务数据应尽量回到有权威性的服务端 API。不要让多个子应用同时修改一个未定义所有权的浏览器全局对象。

第 4 章 公共组件与共享包治理

4.1 什么应该放入共享包

共享包适合承载：设计 Token、基础组件、稳定的 API Client 基础设施、类型工具、日志埋点接口、统一国际化基础设施等。业务枚举、人员领域对象以及某个页面专用的 Hook，通常应由对应业务域维护。

两个关键问题决定是否值得抽取：是否确实存在多个消费者，以及该抽象能否保持稳定语义。尚未出现复用需求时，过早公共化会增加版本控制与兼容责任。

4.2 组件库与业务组件

以 Ant Design 为例：Form、Table、Modal 是通用组件，但“组织树人员选择器”还包含部门层级、可选范围、员工权限、查询接口、禁选规则等业务语义，属于领域组件。它是否放进共享包，取决于它是否成为多个业务稳定使用的产品级能力。

组件的公开 API 需要覆盖受控值、回调、校验、加载与错误状态、可访问性和扩展点。例如：

4.3 包版本与更新策略

共享包升级会影响多个消费者。要根据 SemVer、兼容性约定和真正的变更类型控制发布：移除必需属性、改变事件含义、变更 CSS 全局样式，都可能破坏消费者。发布流程至少包含变更说明、影响面、自动化验证与回滚方案。

共享 React 相关依赖时需要额外注意：一个依赖树中出现多个不兼容的 React 实例可能引起 Hook 或 Context 问题；通过 peerDependencies、externals、import maps 等机制共享运行时，需要保证实际部署版本可兼容。共享依赖是性能和治理权衡，不是 single-spa 的强制要求。

4.4 CSS 隔离

在同一个 document 中运行的多个子应用，默认共享页面的 CSS 层叠与 DOM 环境。body { ... }、button { ... }、.header { ... } 等全局规则可能影响主应用和其他子应用。

常见方案包括 CSS Modules、BEM/前缀命名、CSS-in-JS、作用域约定，以及在需要时使用 Shadow DOM。Shadow DOM 能提供样式与 DOM 的一部分封装，但并不自动提供 JavaScript 或认证隔离；弹窗 Portal、字体、全局覆盖层也需要单独处理。

配套实战为子应用使用 .org-app 前缀，主应用样式使用 .shell-*，通过可读规则避免普遍的全局冲突；它不是浏览器提供的强隔离沙箱。

第 5 章 多层级路由与导航责任

5.1 三种不同路由责任

  • 浏览器 URL：用户最终访问的地址，例如 /organization/employees/emp-101。
  • 主应用路由调度：判断应该激活哪个业务子应用，例如 /organization 交给组织应用。
  • 子应用内部路由：在组织应用中选择概览、员工列表、详情页面。

single-spa 更接近一个顶层应用调度器，不替代 React Router 处理每个子应用的内部页面。将 /organization 交给 single-spa，子应用的 /employees/:id 交给 React Router，两个系统的路由所有权清楚。

5.3 直接访问和刷新页面

用户在 /organization/employees/emp-101 刷新时，服务器首先收到一个 HTTP GET 请求；若静态服务器找不到对应文件，可能直接返回 404。对于使用 History API 的 SPA，通常应将符合前端路由规则的页面路径回退到主应用 index.html，随后由主应用与子应用共同完成激活。

对 /api/*、静态文件和不存在的资源，不能简单地全部回退为 HTML，否则 API 错误会变成 200 text/html，前端解析 JSON 时才发现异常。正式部署的回退策略应区分接口、资源与页面路径。

5.4 导航、菜单和权限

主应用提供全局菜单与应用入口；子应用负责具体业务页面导航。菜单展示应来自可信服务端能力数据，但是否真的允许访问某个资源，仍由后端在每个请求上独立判断。前端隐藏菜单只能改进体验，不能构成授权依据。

第二部分：企业应用的横切能力

第 6 章 认证、授权与权限模型

6.1 Authentication 与 Authorization

认证（Authentication）回答“当前请求对应哪个经过验证的主体”。授权（Authorization）回答“该主体是否可以对特定资源执行这项操作”。一个系统可以准确知道当前用户是谁，却仍然因为角色、组织范围、资源归属或数据分类等条件而拒绝其操作。

前端常见做法是在登录后获取用户信息和可展示能力，用于菜单过滤、按钮展示、操作提示与路由交互。真正具有安全意义的授权必须在可信服务端、网关或后端资源处理层执行。React 组件中的 canEdit、路由守卫和 CSS 隐藏均容易被用户自行修改，不能作为后端放行依据。

1
2
3
4

const { canEdit } = usePermissions();
return canEdit('employee:update')
  ? <Button onClick={openEditor}>编辑</Button>
  : null;

这段代码说明了展示逻辑，没有说明后端是否允许修改该员工。服务端至少还要验证：认证主体是否有效、是否有 employee:update 操作权限、该员工是否属于允许管理的组织范围、是否满足业务状态约束。

6.2 RBAC、ABAC 与资源范围

  • RBAC（基于角色的访问控制）：角色与权限建立关系。适合权限分配有稳定岗位含义的场景。
  • ABAC（基于属性的访问控制）：根据主体、资源、操作与环境属性判断，例如“本人 + 所属部门 + 工作时间段”。
  • 组织或数据范围：很多 HR 系统并非只有“是否能查看员工列表”，还要约束“能查看哪些组织、哪些员工”。

例如，用户具有 employee:read 并不足以让其读取整个公司全部员工。列表接口必须按允许的数据范围过滤，详情接口也必须基于资源 ID 再次校验，避免通过猜测 ID 绕过列表筛选。

6.3 会话与浏览器凭证

浏览器应用可能使用 Cookie 会话、OAuth/OIDC 登录流程或其他企业 SSO。Cookie 会话常用的安全属性包括 HttpOnly、Secure、SameSite、合理的有效期与作用域。HttpOnly 防止客户端脚本直接读取 Cookie 值，但不能单独防止 XSS 发起带 Cookie 的请求；跨站请求伪造防护还需结合 SameSite、CSRF Token、来源校验等具体威胁模型。

localStorage 不适合被当成无法访问的安全保险箱，因为同源脚本可以读取它。把用户名或角色放进前端状态用于展示可以，但这些字段不能单独作为服务端授权的事实来源。

6.4 微前端场景下的身份边界

多个脚本同页运行时，通常共享 origin、DOM 和相应的浏览器存储权限。不同仓库、不同 npm 包、不同 React Root 或不同子应用名称，都不会自动建立浏览器安全隔离。

主应用不应把长期凭证、任意敏感字段作为 customProps 广播给所有子应用。即使传递了权限列表，后端也必须在每个请求中使用可信身份重新鉴权。子应用被攻陷后可能影响整页脚本环境，因此依赖来源、发布签名、CSP、前端注入风险和第三方脚本同样属于治理范围。

6.5 配套项目为什么使用服务端演示会话

上一阶段 Mock API 曾通过 X-Demo-Role 展示不同角色的行为，但客户端能够自行构造这个请求头，它不具备认证可靠性。本阶段为了说明更准确的边界，服务端改为给浏览器设置 HttpOnly 的演示会话 Cookie，并在服务端 Map 中保存当前演示角色。员工写入接口查询服务端会话角色，而不是信任请求头。

不过项目仍公开了 POST /api/demo/role 方便读者切换演示角色。这个端点允许本地任何用户自行升级为编辑者，因此它只是一套教学环境，不是生产身份认证系统。将其部署至真实环境之前必须移除此端点，接入真实登录、可信身份及资源授权。

第 7 章 国际化与本地化

7.1 i18n 与 l10n

国际化（Internationalization，i18n）是让软件具备支持多语言、多地区的结构与机制；本地化（Localization，l10n）是为具体语言与地区提供符合当地表达习惯的内容。

仅将“新增员工”替换成 “Add employee” 不足以完成全部本地化。真实应用还涉及日期格式、数字与货币、姓名与地址、排序规则、时区、文案长度、复数、性别语法、从右向左的文字方向，以及服务端返回的错误消息。

7.4 跨应用语言切换

主应用拥有全局语言偏好时，子应用需要在初始化时接收当前 locale，并在运行过程中监听更改。此处需要区分：

  • 初始化快照：主应用通过 customProps 把 locale 传给子应用的 mount。
  • 后续变化：子应用已挂载后，customProps 不是一个会自动引起 React 重新渲染的响应式状态源；需要独立订阅或重新传递。

本阶段实战采用 course:settings-change 事件仅传递 {locale, role} 这类演示展示信息，并在子应用 React Context 中更新语言。该事件没有认证能力，不应作为授权判断依据。

7.5 如何学习企业自研 i18n 平台

如果所在公司使用企业自研 i18n 平台，首先应在现有仓库确认它的初始化方式、资源组织格式、语言切换 API、缺失 key 回退机制、页面或组件的实际调用约定。

迁移已有业务时，可按“公共布局 → 表单标签 → 表格列名 → 提示与异常 → 动态业务文案”划定范围，使用自动化检查识别遗漏 key 和语言资源差异。国际化应该成为维护中的持续约束，而不只是上线前的一次性翻译。

第 8 章 错误边界、日志与可观测性

8.1 分清不同错误发生在哪一层

一个企业页面可能遇到：

  1. 主应用无法加载远程子应用 JavaScript，例如资源 404、跨域或模块解析失败。
  2. 子应用完成加载，但 mount 抛出错误。
  3. React 组件渲染时出错。
  4. API 请求失败、超时，或返回 401/403/404/409/500。
  5. 业务数据存在不满足页面假设的值。

这些错误分别需要不同的观测与恢复措施。React Error Boundary 可以捕获其子组件在渲染期间的部分错误，但不会自动处理每个异步请求、事件处理器错误，也不能替代 single-spa 生命周期错误处理。

8.2 错误分级与恢复

错误层次用户可见表现常见处理
资源加载页面模块不可用主应用错误提示、重试、检查发布资源
生命周期子应用挂载失败single-spa 错误处理、记录状态、降级入口
页面组件某块视图崩溃React Error Boundary、局部占位
HTTP 请求列表或详情失败保留页面骨架、允许重试、区分 403/404
表单校验字段不符合约束展示字段错误、保留用户输入

不要把所有错误统一展示为“系统异常”。403 与 404 在授权与资源状态上语义不同；409 冲突应引导用户修改输入或重新获取数据。

8.3 可观测性数据的最小关联维度

前端异常报告应尽可能附带：发生时间、页面路由、子应用名与版本、发布环境、相关请求的 Trace/Request ID、稳定的错误类别以及必要的客户端信息。避免把员工姓名、邮箱、Token 或完整接口敏感响应直接写入日志。

在微前端架构下，主应用版本和子应用版本可能不一致。因此日志需要能回答：“哪个 Shell 版本在加载哪个业务应用的哪个构建产物？”这也有助于快速判断是兼容性故障还是局部业务故障。

8.4 运行时依赖的错误

子应用 JS 成功下载并不意味着它可运行。它仍可能因为运行时共享依赖版本不匹配、CSS 没加载、环境配置错误、权限会话失效或后端接口契约变更而失败。错误分析不能只停留在 Network 面板看到 200 OK。

第三部分：微前端架构与 single-spa

第 9 章 微前端的适用场景与方案选择

9.1 微前端解决的是协作与交付边界

微前端把一个浏览器产品拆成多个相对独立的前端应用，这些应用可以由不同团队维护、构建和发布，并在同一用户体验下组合运行。与微服务相似，独立性带来的收益和复杂性都会体现在团队协作与部署流程中。

值得考虑微前端的典型情况：业务系统已有多个大型前端仓库；不同团队存在相对独立的发布周期；技术栈难以统一迁移；某些功能需要作为子应用被多个入口使用；单一发布流程对多个团队造成明显阻塞。

不宜仅因为“页面很多”就引入微前端。页面数量多但团队规模小、发布节奏一致、共同依赖高度耦合时，先做好 Feature 划分、路由懒加载、模块边界与 CI，往往成本更低。

9.2 主流组合方式

方案运行机制优势主要代价
单体 SPA + 功能模块一套 React 应用内按 Feature 拆分简单、共享依赖自然通常共享构建与发布边界
single-spa按激活规则调度应用生命周期适合多个 SPA 组合与独立发布需治理模块、CSS、路由和部署
Module Federation运行时加载远程模块，按模块共享能力适合组件/模块级运行时组合共享依赖、版本与远程失败治理复杂
iframe浏览器创建独立文档上下文更强的文档、脚本与样式隔离路由、通信、样式一致性和交互集成成本
服务端页面组合服务端拼装或路由分发可控制首屏和后端集成取决于具体技术与部署方案

这些概念并不严格互斥。例如一个 single-spa 子应用也可以使用内部代码分割，或通过 Module Federation 加载远程模块。

9.3 不要误解“隔离”

single-spa 并不自动为每个应用创建 iframe 或 Shadow DOM。其注册的应用一般共享同一个浏览器 document、JavaScript 全局环境和 origin 权限。它主要提供生命周期协调，而非安全沙箱。

所谓“独立部署”也不是无条件成立。主应用仍需能够加载子应用的资源；所有需要共同升级的接口契约、共享依赖及路由都可能形成发布依赖。要通过适当的兼容窗口、资源版本和回滚机制治理这些依赖。

注册时，app 可以是一个返回应用生命周期对象的加载函数；activeWhen 决定应用何时需要挂载；customProps 是附加给生命周期函数的应用数据，可以是对象，也可以是以 (appName, location) 为参数、返回对象的函数。上例使用函数形式，使 getElementById 在每次调用生命周期时才求值；若写成对象字面量，会在注册时立即查找节点，而此时容器可能尚未渲染。start() 之后 single-spa 才会真正开始应用挂载流程。

10.2 何时重新评估激活规则

single-spa 会在适当的路由变化时评估 activeWhen，包括 History API 的 pushState、replaceState 和浏览器历史变化。激活规则应该是没有副作用的纯函数，只根据当前 Location 判断是否属于子应用路由。

不推荐直接写：

1

activeWhen: (location) => location.pathname.includes('organization')

因为它可能错误匹配 /reports/organization-history。可以使用前缀边界正则或官方支持的路径前缀规则，明确区分 /organization、/organization/... 与其他路由。

10.3 状态机与生命周期

理解 single-spa，不能只记住三个函数名。它维护应用状态并随着路由激活与失败情况转换。关键状态包括注册、加载、准备启动、挂载完成、卸载或错误。

最重要的生命周期函数：

  • bootstrap：第一次挂载前的一次性准备。不会因为每次进入路由就重复调用。
  • mount：应用从非激活状态进入激活状态时负责渲染及建立事件订阅。
  • unmount：离开应用激活范围时销毁 DOM 和资源，清理订阅。
  • unload：可选实现。只在调用 unloadApplication（或 unregisterApplication）时触发，用于重置应用：应用状态回到 NOT_LOADED，下次激活时重新执行 bootstrap。普通的路由退出只会触发 unmount。

脚本加载 CORS 与业务 API CORS 不是同一个问题。 本项目主应用开发服务器把 /api 代理到 Mock API，因此浏览器发出的 API URL 与主应用同源；子应用 ESM 资源则由另一端口提供，需要其自己的跨源策略。

11.4 CSS 资源与加载顺序

Vite Library Mode 可输出独立 CSS，但原生 import() 只加载 JavaScript 模块，不保证浏览器自动加载旁边同名的 CSS 文件。本项目在导入子应用前显式加载 organization.css，并等待 <link> 的 load 事件，然后再导入模块，避免第一次挂载时样式未就绪。

CSS 是否在卸载时移除，应结合是否有多个子应用、是否需要共享组件样式、是否存在样式污染确定。本项目通过命名空间控制业务 CSS，并保持 link 已加载；这是一种教学权衡，非通用隔离方案。

11.5 产物版本与缓存策略

企业生产环境应为子应用资源提供不可变版本或内容哈希，主应用通过受控 Manifest 引用具体版本；主应用入口/Manifest 适当使用短缓存或可更新策略。若使用固定 organization.js 文件名和长时间缓存，用户可能继续加载旧模块，与已发布的 API 契约不一致。

本项目为简化学习使用固定文件名和 Cache-Control: no-store，适合本地开发，不适合直接推导为推荐生产缓存策略。生产构建、CDN、资源回滚和兼容窗口需要协同设计。

11.6 Vite 与 single-spa 的集成并非唯一方式

single-spa 官方提供 Vite 生态说明，其中包括可选的 vite-plugin-single-spa 等方式。但插件的行为与项目构建目标、CSS 处理及模块共享策略相关，使用前要核对所选版本。本文采用显式生命周期 + Vite Library Mode，目的是直接观察微前端的基本运行机制，避免用插件隐藏学习重点。

示例中的 validateSettings 需要运行时检查字段值，并在卸载时移除监听器。TypeScript 类型声明不能阻止其他脚本发出不符合契约的事件。事件名最好有清楚的命名空间、版本策略和所有者。

12.3 事件不是可信身份来源

同一页面的任意脚本通常都能派发 CustomEvent。因此 event.detail.role === 'editor' 只能用于演示页面显示，不可作为安全授权依据。某个子应用接到“删除员工”事件后，依然必须通过后端完成有权限控制的删除请求。

12.4 跨应用数据同步的难点

假设组织应用编辑了员工，审批应用正展示此人的审批任务。这时单纯发送 employee:changed 事件并不等于两个应用数据自动一致：另一个应用可能尚未加载、缓存已过期、事件丢失，或需要按不同权限展示不同字段。

更稳妥的模式是将事件视为失效通知：另一个应用收到后触发自己的 API 重新获取所需数据，仍由服务端决定返回内容。对于必须保证一致性的核心业务流程，应由后端服务和业务事务保障，不应依赖浏览器内的事件顺序。

第 13 章 共享依赖、运行时隔离与失效治理

13.1 React 应用并置时的风险

多个 React 子应用可以分别拥有自己的 React Root，但如果运行在同一个 document，仍需要治理：

  • 全局 CSS 和字体；
  • 弹窗、下拉框、浮层的 Portal 容器；
  • 全局事件处理与快捷键；
  • history 的使用和路由优先级；
  • Fetch/Axios 全局拦截器与认证刷新；
  • React/ReactDOM 版本、第三方组件库 CSS 和运行时重复加载；
  • 页面异常时的隔离和恢复。

13.2 独立打包还是运行时共享

本项目把 React 及相关依赖打进子应用，优点是部署边界简单、不会要求主应用提前暴露共享 React；缺点是体积较大，多个 React 子应用会重复下载与执行依赖。

生产系统可通过 External、Import Maps 或相关微前端工具共享依赖，但共享版本要有治理策略。以 React 为例，版本不兼容或混用 React / ReactDOM 实例可能导致 Hook 行为异常。不要为了减少几十 KB 的传输而忽略升级耦合和线上风险。

13.3 子应用加载失败的恢复策略

考虑以下失败：

  • Manifest 指向不存在的版本；
  • ESM 资源因 CORS、MIME 或 CSP 被拒绝；
  • JS 下载成功但初始化抛错；
  • CSS 未加载；
  • 共享依赖版本不兼容；
  • API 不可用，页面数据报错。

主应用应提供明确的错误反馈。发布系统应允许把 Manifest 指回上一个兼容版本，并在主应用与 API 变更时保留必要兼容窗口。只在组件里捕获错误不足以应对加载前失败。

13.4 子应用的自动销毁与残留

React Root 卸载并不会帮你移除所有手工注册在 window 的监听器。要明确规定外部资源由创建者负责释放：配套项目中，Shell 创建的 #microfrontend-root 由 Shell 保留，子应用在其中创建的 section 由子应用在 unmount 时移除。一个可重复挂载的子应用，应该能经历：进入 /organization → 退出 / → 再次进入 /organization，而不会重复注册监听器、出现两个 Dialog 或保留不应共享的草稿状态。

第四部分：多团队工程协作与交付

第 14 章 Monorepo、多仓库与代码所有权

14.1 仓库组织不是运行时架构

一个企业系统可能包含主框架、组织系统、移动端、公共组件及其他业务系统。它们的 Git 仓库数量与运行时的应用边界不必一一对应。

常见选择有两类：

  • Monorepo：多个包或应用在一个 Git 仓库中，通常配合 npm/pnpm workspaces、统一版本与部分共享流水线。
  • Polyrepo / Multi-repo：不同应用或公共库位于独立仓库，依赖通过发布包、模块地址与 API 协议组合。

Monorepo 的主要收益是跨包重构和统一检查较方便；代价是工作区依赖、构建缓存、变更影响判断和权限治理更复杂。多个仓库可以给团队更清楚的所有权，但跨仓库原子化变更、接口兼容和联调成本增加。

14.2 一个需求涉及多个仓库时如何分析

不应从“修改了哪些文件”反推出“只需要理解哪些业务”，也不能因为某开发者改过模块中的一个文件就把整个业务归为其个人职责。

契约管理可以采用 OpenAPI、类型生成、消费者契约测试等方式。类型生成有助于减少 DTO 手写错误，但仍需验证服务器行为与实际响应符合契约。TypeScript 生成的类型在浏览器运行时不会自动校验 JSON。

14.4 代码所有权与文档

企业项目至少应说明：模块维护团队、业务负责人、入口与关键路径、上下游接口、发布链路、故障定位、公共依赖、回滚责任。内部文档可以记录已核实的实际架构，而不是把“设计上应该如此”写成现有项目事实。

14.5 面对真实 React 微前端存量仓库的阅读顺序

当接手某个 single-spa 子应用（例如组织管理类业务系统）时，建议从可执行证据建立整体结构，而不是从文件名或 Git 修改记录推测功能所有权：

  1. 查启动链：读取 package.json、构建脚本与运行环境配置，明确实际入口、开发服务器、依赖管理和编译工具。例如仓库可能通过企业内部脚手架的 start/build 命令或 webpack 构建，而不是直接执行 Vite，不能直接套用本文的 Vite 配置。
  2. 查接入链：搜索 bootstrap、mount、unmount、registerApplication、single-spa 和顶层 DOM 容器，确认谁负责注册、何时挂载，以及主应用与子应用如何交付路由。
  3. 查页面链：从路由定义进入具体页面，追踪组件树、状态、表单、权限展示和用户操作。

15.4 Mock 与真实联调的分工

Mock API 用于快速验证前端交互和请求契约，但它不覆盖真实身份平台、真实组织权限、网关 Cookie/跨域策略或实际数据规模。联调应通过可重复的测试账户和环境配置进行，避免把生产 Token 写入 .env 或提交到仓库。

“复用已登录浏览器会话”只属于联调便利性。自动化环境依然需要隔离测试数据、凭证与运行环境，防止把本地个人权限误用于敏感真实系统。

15.5 测试与构建流水线

一个合理的提交验证流程通常依次执行：静态检查、单元测试、模块构建、契约/集成测试、必要的 E2E，之后将验证过的构建产物部署至环境。

独立部署意味着子应用可以拥有自己的流水线，但主子应用兼容的 Smoke Test 仍有价值。E2E 测试不必验证每一个 Button 的所有组合，应该优先覆盖跨应用核心路径、重要权限和典型故障。

第 16 章 性能、发布与可演进架构

16.1 微前端可能增加初始成本

若主应用加载一个子应用，而子应用重复打包 React、ReactDOM、组件库与路由框架，用户会下载和解析更多 JavaScript；多个应用可能还会重复加载字体、基础样式、鉴权请求与配置。

因此必须考虑：首次加载所需资源、首次进入子应用的等待时间、切换路由后的缓存、解析与执行成本，以及对弱网和低端设备的影响。微前端并不天然带来更好的页面性能。

16.2 懒加载与预加载

single-spa 只有在激活规则满足时才需要挂载相应子应用，可以延迟导入代码。对于高频进入且稳定的业务应用，可考虑在空闲期预取资源，但必须注意 CPU、网络和用户实际使用概率。预加载不应让所有子应用在首页同时执行复杂初始化。

16.3 发布工件和回滚

推荐把部署产物视为不可变工件：每次构建与发布有可追踪的版本；主应用通过 Manifest 或其他受控机制引用具体子应用版本。需要回滚时，恢复 Manifest 引用与相关 API 兼容配置，而不是现场修改构建文件内容。

对于存在共享依赖的系统，回滚也必须判断：旧子应用能否继续使用当前 Shell 版本、公共库版本和后端 API？如果依赖都被绑定为单个最新版本，所谓独立回滚可能无法实现。

16.4 观察数据与治理指标

可以监控：子应用加载失败率、挂载失败率、应用路由切换成功率、主要 API 错误率、子应用首屏可交互耗时、bundle 大小、部署频率、平均故障恢复时间，以及跨仓库变更需要协作的时间。这些指标不应只有一个“项目构建成功率”。

16.5 架构演进路径

比较务实的顺序是：

  1. 先弄清业务范围、路由与数据流。
  2. 在现有单应用中完成 Feature 级组织与稳定公开接口。
  3. 建立公共组件、国际化、权限与发布契约。
  4. 当独立交付需求真实存在时，再抽出适合的子应用。
  5. 最后根据运行时成本与团队约束决定是否使用共享依赖、Import Maps 或其他组合机制。

从现有 React SPA 迁移时，不必“一次性微前端化”。可以选择相对独立的业务路由逐步迁移，保留其他页面正常运行，并在应用级验证路由与权限边界。

17.6 语言设置和跨应用更新

Shell 维护展示层的 locale，并通过生命周期属性传入初始值。切换语言时发送 course:settings-change，子应用通过带运行时校验的监听器更新 Context 并重新渲染文案。

这类同步可以用于界面设置。但数据访问权限必须由 API 服务端检查，不依赖 Shell 事件中携带的 role。在正式项目中还应考虑语言资源版本、文案缺失、日期时区和组件库多语言等问题。

17.7 Mock API 与演示权限

API 使用 course_session 的 HttpOnly Cookie 识别服务端演示会话，前端通过 /api/session 读取当前角色。/api/demo/role 仅用于教学切换；编辑、删除等请求从服务端会话读取角色，忽略客户端自报的 X-Demo-Role。

浏览器端的 canEdit 用来决定是否显示编辑按钮；服务端使用自己的会话角色判断是否允许真正修改员工数据。两者分别是展示与授权，不应混为一谈。

17.9 生产部署需要补齐的条件

当前示例故意以固定文件名和 no-store 资源响应简化学习。真实部署必须考虑以下工程能力：

  • 由可信 Manifest 或配置下发已发布的子应用 URL，优先使用不可变版本或哈希资源；
  • 主应用静态服务器正确处理 SPA History Fallback，/api 和静态资源错误不能回退成 HTML；
  • 子应用脚本与 CSS 使用可控来源，设置合适的 CSP、CORS、MIME 和缓存策略；
  • 真实认证、服务端操作授权与数据权限替换演示角色接口；
  • 主应用与子应用共同采用可追踪版本、错误上报、接口契约测试和回滚机制；
  • 验证子应用卸载后的全局订阅、Modal/Portal、缓存与状态是否清理。
