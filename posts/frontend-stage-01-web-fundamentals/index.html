第一部分：Web 平台与 HTML

第 1 章 Web 应用的基本运行模型

1.1 浏览器、前端工程和后端服务分别负责什么

传统 Java Web 开发中，一个 HTTP 请求到达 Spring Boot Controller，服务端执行业务逻辑并返回 JSON 或 HTML。在现代单页应用中，浏览器通常先下载 HTML、CSS、JavaScript 等静态资源，再由客户端代码管理页面变化并请求后端 API。

这几种职责需要区分：

运行位置典型职责典型技术
浏览器解析和渲染页面、执行客户端脚本、处理用户输入、发送 HTTP 请求HTML、CSS、DOM、Web APIs
开发和构建环境安装依赖、开发时热更新、转换与打包源码、生成部署资源Node.js、npm、Vite、Webpack
Web 服务器或 CDN提供构建后的静态文件、缓存和分发资源Nginx、CDN、对象存储
业务后端身份验证、授权、业务规则、数据访问、事务处理Java、Spring Boot、数据库

“前端项目使用 Node.js”通常意味着开发和构建过程使用 Node.js；它不意味着浏览器能够直接运行 Node.js 的文件系统 API。需要服务端渲染时，Node.js 也可能作为运行时，但这是另一种部署形态。

1.2 Web 页面不是一张图片

一份 HTML 文档描述内容结构；CSS 规则描述视觉呈现；JavaScript 负责可编程行为。浏览器会解析标记，构造 DOM，再结合样式与布局产生实际像素。

例如：

3

<h1>员工管理</h1>
<p class="description">共 128 名员工</p>
<button type="button">新增员工</button>

1
2

.description { color: #64748b; }
button { border-radius: 6px; }

HTML 的 h1 表达“一级标题”，不是“默认大字体”；button 表达操作控件，不是“有边框的盒子”。把语义与样式分开后，同一份结构可以用于不同屏幕、主题及辅助技术。

1.3 从输入 URL 到看到页面的过程

输入 https://example.com/employees?page=2 后，浏览器大体经历以下过程：

  1. 解析 URL：识别协议、主机、端口、路径、查询参数等。
  2. 确定资源来源：可能命中浏览器缓存；需要联网时，通常需要通过 DNS 获取可用服务器地址。
  3. 建立连接和安全会话：HTTPS 通常使用 TLS 保护通信；实际传输可能使用 HTTP/1.1、HTTP/2 或 HTTP/3，连接过程各有差异。
  4. 发送请求、接收响应：状态码、响应头和响应体决定后续处理。
  5. 解析 HTML：构建 DOM，发现并请求 CSS、图片、字体、脚本等依赖资源。
  6. 计算样式并布局：建立 CSSOM，计算可见节点的样式、尺寸与位置。
  7. 绘制和合成：形成屏幕像素；后续输入、脚本或窗口变化可能触发局部更新。

这些步骤是理解模型，不是每次导航都严格串行的时间线：资源可以并行加载，浏览器可能复用连接，HTML 也可以在响应尚未完全接收时开始解析。

图中省略了重定向、缓存验证等分支；HTML 解析和依赖资源加载可以交错进行。

|----|   |------------| |-| |-------------| |------------| |----|
协议          主机名       端口       路径          查询参数     片段
  • scheme：协议，如 https。
  • host：主机名，如 hr.example.com。
  • port：端口；HTTPS 默认端口为 443，常可省略。

第 2 章 HTML 语法、文档结构与语义

2.1 元素、标签、属性和嵌套

1

<a href="/employees" class="nav-link">员工管理</a>

这段标记中，a 是元素类型；<a> 和 </a> 是开始、结束标签；href、class 是属性；“员工管理”是文本内容。

HTML 中有空元素（void elements），例如 img、input、meta、link、br，它们不能包含子内容，也不需要对应的结束标签。HTML 并不要求采用 XHTML 的自闭合写法，<img ...> 是有效写法。

元素必须按合法规则嵌套：

1
2
3
4
5

<!-- 合理 -->
<p>阅读 <strong>重要提示</strong> 后继续。</p>

<!-- 不合理：交叉闭合 -->
<p>阅读 <strong>重要提示</p></strong>

浏览器会尽力修复错误 HTML，但生成的 DOM 不一定等于作者预想。典型例子是在 p 中放置不允许的块级结构，浏览器可能自动结束段落。不能把“浏览器看起来能展示”作为结构正确的依据。

布尔属性只关心是否存在，例如 disabled、required、checked：

1
2

<input type="checkbox" checked />
<button disabled>不可操作</button>

写成 disabled="false" 仍表示属性存在、控件禁用。需要解除禁用，应删除该属性或通过脚本改变对应 DOM 属性。

2.6 原生交互与可访问性基础

原生的 a、button、input、select 已包含大量键盘和辅助技术行为。用 div 模拟按钮，通常还需自行补齐键盘激活、焦点与角色等功能。

1
2

<a class="skip-link" href="#main-content">跳转到主要内容</a>
<button type="button" aria-label="关闭通知">×</button>

仅图标的按钮通常需要明确的可访问名称。aria-label 用于补充名称，不应替代本来能够直接看到的清晰文本。可访问性至少包含：正确语义、键盘可达、可见焦点、表单标签、图片替代文本和不只依赖颜色表达状态。

2.7 DOM 事件的基本模型

页面中的点击、输入、键盘操作等会产生 DOM 事件。事件通常有目标（target）、事件类型和传播过程等概念。对于在 DOM 树中传播的事件，事件监听可以发生在捕获阶段、目标阶段以及冒泡阶段；是否冒泡取决于具体事件。

例如，用户点击按钮时，浏览器可以触发 click 事件。JavaScript 可以使用 addEventListener 注册监听函数，也可以在必要时调用 preventDefault() 阻止可取消事件的默认行为；但这不会自动阻止事件继续传播。停止传播使用不同的 API。

1
2
3
4
5
6

<button id="save" type="button">保存</button>
<script>
  document.querySelector('#save').addEventListener('click', () => {
    console.log('收到点击事件');
  });
</script>

这段代码仅用于辨认事件与 DOM 的关系。事件对象、事件委托、捕获/冒泡顺序和异步执行将在 JavaScript 专题完整讨论。

HTML 原生表单具有聚合字段、校验、编码、提交和重置能力。典型结构：

3.3 表单提交与编码

method="get" 的表单会把成功字段编码为 URL 查询参数，适合查询、筛选等不会导致数据修改的操作；GET 参数往往暴露在地址栏、历史记录和部分日志中，不应用于发送密码等敏感信息。

method="post" 会把表单数据放在请求体中。默认编码通常是 application/x-www-form-urlencoded；包含文件上传时一般需要 enctype="multipart/form-data"：

1
2
3
4
5

<form action="/upload" method="post" enctype="multipart/form-data">
  <label for="attachment">上传附件</label>
  <input id="attachment" type="file" name="attachment" />
  <button type="submit">提交</button>
</form>

表单 POST 并不自动等于 JSON 请求。使用 JavaScript fetch 发送 JSON 是另一种提交方式，在第二阶段说明。

第 4 章 CSS 语言基础与层叠机制

4.1 CSS 规则、声明和引入方式

4

4.3 为什么 CSS 会互相覆盖：层叠而不只是优先级

比较多条 CSS 声明时，浏览器要考虑规则是否适用、来源与重要性、层叠层、选择器优先级，以及在必要情况下的作用域接近程度和源码顺序。

在普通项目样式、相同来源与相同层叠层等条件下，可以先掌握以下直观的选择器优先级：

1
2
3

p { color: black; }          /* (0,0,1) */
.notice { color: blue; }     /* (0,1,0) */
#warning { color: red; }     /* (1,0,0) */

优先级比较通常按 ID、类/属性/伪类、元素/伪元素三个维度逐项比较，而不是把它们粗略相加。普通行内 style 声明也有特殊的高优先级位置。

!important 改变声明在层叠中的重要性顺序，不能简单理解成“它永远最高”；层叠来源、用户样式、动画与过渡等都有具体规则。@layer 又能对不同层的正常声明建立优先关系。

调试顺序：先检查规则是否匹配，再看 CSS 来源、层叠与优先级，最后查看 Computed 中真正应用的属性值。不要靠不断追加更长选择器或 !important 硬压其他规则。

4.4 继承、初始值与计算值

有些属性会从父元素继承，例如 color、font-family；有些通常不会继承，例如 border、margin、padding。

1
2

.panel { color: #334155; }
.panel p { margin-bottom: 16px; }

父元素的文本颜色通常会传递给后代，除非后代自己指定。父元素的外边距不会因为继承自动出现在子元素上。

理解几个概念：

  • 指定值：层叠算法等步骤确定要应用的值。
  • 计算值（computed value）：按 CSS 规则计算后的值，部分相对单位和百分比仍可能保留。
  • 使用值（used value）：布局完成后得到的实际使用值，例如最终尺寸。

因此 DevTools 的 Computed 面板显示的信息不一定是屏幕上最终每一项几何量的完整答案；布局尺寸还与包含块、内容和其他规则有关。

第 5 章 盒模型、普通文档流与尺寸

5.1 每个元素如何占据空间

在常规 CSS 盒模型中，元素的盒子从内到外包含：

  1. 内容区（content）：文本、图片等内容的主要尺寸区域。
  2. 内边距（padding）：内容与边框之间的空间。
  3. 边框（border）：围绕内容及内边距的边界。
  4. 外边距（margin）：边框外侧、与周围元素的距离。
1
2
3
4
5
6

.card {
  width: 300px;
  padding: 20px;
  border: 2px solid #cbd5e1;
  margin: 16px;
}

默认 box-sizing: content-box 时，width: 300px 指内容区宽度；边框盒宽度为 300 + 20×2 + 2×2 = 344px，左右 margin 再分别占据 16px 空间。margin 不计入边框盒宽度。

企业项目普遍会设置：

1

*, *::before, *::after { box-sizing: border-box; }

这样 width 通常指定包含内边距和边框在内的盒子尺寸，特别适合表单、卡片和栅格排版，但 margin 仍然在盒子之外。min-width、max-width、内容的固有尺寸仍可能影响最终结果。

5.2 display 决定盒子如何参与布局

值典型行为使用场景
block常形成块级盒，沿块方向依次排列容器、段落
inline参与行内格式化上下文文本中的链接、强调
inline-block行内排版、可设宽高的原子盒小徽标、行内图标容器
flex为直接子元素建立弹性布局工具栏、导航、表单布局
grid为直接子元素建立网格布局主体区域、卡片矩阵
none元素及其子树通常不参与布局和渲染条件隐藏内容

需要区分 display: none 与 visibility: hidden：前者通常不占据布局空间，后者仍保留其布局空间、只是不可见。opacity: 0 虽然透明，却通常仍参与布局并可能接收鼠标事件。三者在布局和交互上不等价。

5.3 普通文档流与外边距折叠

没有特殊定位或布局规则时，块级元素通常沿块方向排列，行内内容沿文本方向排布，这称为普通文档流。

两个相邻的垂直外边距在某些块级布局条件下可能发生外边距折叠（margin collapsing），并非总是简单相加：

1
2

<div class="first">第一块</div>
<div class="second">第二块</div>

1
2

.first { margin-bottom: 24px; }
.second { margin-top: 16px; }

在常规块级格式化上下文且符合折叠条件时，两块之间的间距是 24px，而非 40px。Flex 和 Grid 项目之间的外边距不会按这种规则折叠，因此现代组件布局常使用容器的 gap 直接管理间距。

5.4 宽高约束、固有尺寸与溢出

1
2
3
4
5
6
7

.panel {
  width: 100%;
  max-width: 1080px;
  min-width: 0;
  min-height: 240px;
  overflow: auto;
}
  • width/height 是优选尺寸，不代表所有布局条件下最终都严格等于它。
  • min-*、max-* 表示尺寸上下界，可与优选尺寸共同生效。
  • height: 100% 依赖包含块的高度解析条件；“父元素没有确定高度，子元素却想撑满”是常见问题。
  • 图片、长单词、不换行文本等可能带来固有最小尺寸，导致盒子无法按预想收缩。
  • overflow: auto 在内容超出时提供滚动机制；hidden 裁剪内容并可能隐藏操作控件。

对于长名称，通常有两种合理处理方式：允许换行，或者在明确限制宽度后使用省略号。实现单行省略常用：

1
2
3
4
5
6

.employee-name {
  min-width: 0;
  overflow: hidden;
  text-overflow: ellipsis;
  white-space: nowrap;
}

截断文本应保留可访问或可查看完整内容的途径，避免重要数据无法读取。

5.5 文本排版与可读性

实际开发中，字体大小只是排版的一部分，还需要考虑：

  • font-family：字体族与后备字体。
  • font-size：字号。
  • font-weight：字重。
  • line-height：行高；正文通常应避免行间过于拥挤。
  • text-align：文本对齐。
  • white-space：空白和换行行为。
  • word-break、overflow-wrap：长内容的换行策略。
1
2
3
4

10

  font-family: system-ui, -apple-system, "Segoe UI", sans-serif;
  font-size: 16px;
  line-height: 1.5;
}

  max-width: 68ch;
  color: #475569;
  overflow-wrap: anywhere;
}

排版尤其需要检查中英文混排、长工号、长部门名称以及用户缩放后的可读性。不要为了让单行永不换行而任意把字体缩小到难以阅读。

第 6 章 Flexbox：一维布局的计算机制

6.1 主轴、交叉轴与弹性项目

1
2
3
4
5
6
7

.toolbar {
  display: flex;
  flex-direction: row;
  justify-content: space-between;
  align-items: center;
  gap: 16px;
}

display: flex 把容器的直接子元素变成 Flex 项目。默认 flex-direction: row，主轴沿行内方向排列；column 则沿块方向排列。主轴、交叉轴分别是布局的两条坐标轴，与某个固定的“水平/垂直”方向并不永久绑定。

  • justify-content：控制项目在主轴上的分布。
  • align-items：控制项目在交叉轴上的对齐。
  • align-self：覆盖单个项目的交叉轴对齐。
  • gap：项目之间的间距。
  • flex-wrap：是否允许换行。
  • flex-direction：主轴方向和项目次序的布局方向。

注意：justify-content: space-between 通常用于分配剩余主轴空间。如果子项总宽已经超过容器，剩余空间不足，就不会得到预期的大间距。

6.2 为什么 flex: 1 会自动伸缩

Flex 项目的伸缩主要由三个属性影响：

  • flex-grow：有正的可用空间时按规则扩展。
  • flex-shrink：空间不足时参与收缩。
  • flex-basis：计算主轴尺寸时采用的基准尺寸。
1
2

.sidebar { flex: 0 0 220px; }
.content { flex: 1 1 0%; min-width: 0; }

这里侧栏具有 220px 的基准宽度且不参与伸缩；内容区域会占用剩余空间，并在允许的条件下收缩。常见简写 flex: 1 在浏览器中通常等效于 flex: 1 1 0%，但在某些未明确主轴尺寸的容器中，百分比基准的解析可能影响最终行为，因此不能把 flex: 1 简单理解为“绝对平均分宽度”。

6.3 Flex 项目为什么会撑破容器

常见代码：

1
2
3
4

<div class="row">
  <div class="sidebar">左栏</div>
  <div class="content">一个特别长且不换行的字符串...</div>
</div>

1
2
3

.row { display: flex; width: 600px; }
.sidebar { flex: 0 0 180px; }
.content { flex: 1; }

即使内容区设置 flex: 1，它也可能受自动最小尺寸约束而不愿缩小。对希望能够收缩的 Flex 项目设置 min-width: 0 常是关键修复：

1
2
3
4
5

.content {
  flex: 1;
  min-width: 0;
  overflow: hidden;
}

min-width: 0 放宽最小宽度约束，overflow 决定内容超出时如何处理。两者用途不同，不能把“所有 Flex 布局溢出问题”统统归结为同一个属性。

6.4 flex-wrap 与业务表单排版

1
2
3
4
5

10

.filters {
  display: flex;
  flex-wrap: wrap;
  align-items: end;
  gap: 12px;
}
.filters__field {
  flex: 1 1 220px;
  min-width: 0;
}

flex: 1 1 220px 表示每个字段优先以 220px 为基准，空间宽裕时适度扩展，空间不足时允许换行/收缩。Flex 多行布局中各行通常独立计算，不适用于要求所有行列严格对齐的二维表单；此时 Grid 更合适。

6.5 Flexbox 与 Grid 的取舍

Flexbox 适合一维排列，例如导航栏、按钮组、横向卡片、标题与操作区；Grid 适合二维约束，例如固定侧栏加自适应内容区、多列筛选表单、仪表盘卡片。复杂页面很常见的做法是用 Grid 管整体，Flex 管局部组件。

第 7 章 Grid：二维布局与自适应网格

7.1 列轨道、行轨道和网格区域

1
2
3
4
5
6

.app {
  display: grid;
  grid-template-columns: 220px minmax(0, 1fr);
  grid-template-rows: auto minmax(0, 1fr);
  min-height: 100vh;
}

这里 grid-template-columns 定义两列：第一列固定为 220px，第二列占用其余可分配空间。1fr 表示网格可分配空间的一个份额，不等价于任何固定像素值。minmax(0, 1fr) 为第二列提供 0 的下限，有助于避免内容固有尺寸把主布局撑开。

当 Grid 有多列时，gap 分配轨道之间的间距。项目可以使用 grid-column 或 grid-row 指定所处位置或跨越轨道。

7.2 repeat()、minmax() 与自动响应式卡片

1
2
3
4
5

.dashboard-cards {
  display: grid;
  grid-template-columns: repeat(auto-fit, minmax(min(100%, 240px), 1fr));
  gap: 16px;
}

含义：在可用宽度内尽可能放入以约 240px 为下限的卡片列，并让它们分配剩余空间。min(100%, 240px) 可以避免父容器比 240px 更窄时卡片仍强制撑开容器。

  • auto-fit：空轨道可以折叠，使已有轨道扩展。
  • auto-fill：倾向于保留理论上可容纳的轨道位置。

二者在项目数量少、容器宽度大时的行为可能不同，实际选择应以布局目标为准。

  grid-template-rows: auto 1fr;

.sidebar { grid-area: sidebar; }

grid-template-areas 对页面骨架可读性很好，尤其在响应式断点需要重新排列主要区域时。注意 Grid 用于视觉位置安排，不能随意打乱对键盘和读屏顺序很重要的 DOM 内容顺序。

第 8 章 定位、层叠、响应式与视觉样式

8.1 position 的实际行为

取值是否脱离普通文档流定位特征
static否默认定位方式，偏移属性通常不生效
relative否保留原占位，可相对于原位置偏移
absolute是相对于其定位包含块定位
fixed是通常相对于视口定位，某些祖先属性会改变包含块
sticky否（布局中仍保留占位）在滚动阈值与包含块约束下表现为粘附
1
2

.card { position: relative; }
.card__badge { position: absolute; top: 8px; right: 8px; }

为角标提供相对定位参照是 relative + absolute 的典型组合。不过绝对定位元素的包含块规则比“最近的 relative 祖先”更广泛，例如其他非 static 定位祖先也可能建立定位包含块。

8.2 层叠上下文与 z-index

1

.modal-layer { position: fixed; inset: 0; z-index: 100; }

在同一个可比较的层叠上下文中，更高的层叠级别通常会覆盖较低级别。但 z-index: 9999 并不保证元素总处于屏幕最上层；祖先元素可能创建新的层叠上下文。

常见触发条件包括具有相应 z-index 的定位元素、opacity 小于 1、transform 不为 none 等。某个低层级祖先中的子元素，无法仅靠给自己极大的 z-index 跨越祖先层叠上下文的边界。

浏览器还存在 top layer（例如某些原生对话框、popover 的特殊展示层）；不能把所有覆盖关系都解释成单一的 z-index 比较。

8.3 sticky 的条件与陷阱

1
2
3
4
5
6

.table-header {
  position: sticky;
  top: 0;
  z-index: 1;
  background: #fff;
}

sticky 需要设置适用方向的偏移值，并受最近相关滚动容器与包含块范围约束。祖先的 overflow 设置、滚动容器的实际高度、元素没有足够滚动空间等因素，都会影响粘附效果。排查时不要只检查 top: 0，还要检查祖先的滚动行为。

8.4 响应式设计不是只写一个 768px

响应式设计的目标是：页面随着视口和容器条件变化仍然保持可读、可操作。常见方法：

  1. 不依赖固定像素宽度构建所有组件。
  2. 使用 Flexbox、Grid、自适应单位组织布局。
  3. 在需要结构切换时使用 @media。
  4. 当组件布局更依赖父容器而非整个视口时，可以考虑容器查询 @container。
1
2
3
4
5
6
7

.app-shell {
  display: grid;
  grid-template-columns: 220px minmax(0, 1fr);
}
@media (max-width: 800px) {
  .app-shell { grid-template-columns: minmax(0, 1fr); }
}

响应式断点应从内容真正出现拥挤或溢出的条件出发，而不必机械遵循某一设备型号的固定尺寸。

对于后台表格，多列信息可能不适合在手机屏幕上强行压缩。合理的方式是提供横向滚动容器，并保留清楚的表头：

1
2

.table-scroll { overflow-x: auto; }
.table-scroll table { width: 100%; min-width: 700px; }

对侧栏导航，移动端可以改为顶部或横向导航。仅通过 display: none 把所有导航隐藏掉，会造成移动端无法访问功能；如果需要收起式菜单，通常还需要后续 JavaScript 交互阶段来实现。

8.5 焦点、颜色与基本无障碍

1

3
4

a:focus-visible,
input:focus-visible,

  outline: 2px solid #2563eb;
  outline-offset: 2px;

不要一味设置 outline: none 而不给出等效的焦点指示。重要状态需要文本、图标等可辨识信息，不应只用红绿颜色区分；文本与背景之间应有足够对比度。交互目标的尺寸和间距也应保证易于点击。

第三部分：浏览器运行机制与网络通信

第 9 章 浏览器解析、渲染与资源加载

9.1 HTML 源码、DOM 与渲染结果的区别

HTML 源码是文档文本；DOM 是浏览器解析后生成的对象树；最终页面 是浏览器在样式、布局、绘制等步骤后生成的视觉结果。

例如：

1

<div id="app"><p>欢迎使用</p></div>

解析后 DOM 中有对应元素节点和文本节点。后续 JavaScript 修改 DOM 时，DevTools 的 Elements 面板展示的是当前 DOM，而“查看网页源代码”通常展示初始 HTML 响应文本；两者可能不一致。

DOM 节点不一定对应独立可见盒子。例如 display: none 的元素仍在 DOM 中，但通常不会生成可绘制的盒子。

9.2 CSSOM、样式计算、布局和绘制

浏览器渲染可以按以下概念理解：

  1. DOM 构建：解析 HTML，形成文档结构。
  2. CSSOM 构建：解析 CSS，形成可供样式计算使用的结构。
  3. 样式计算与渲染树：结合结构与样式确定需要绘制的内容和计算样式。
  4. Layout：计算盒子的尺寸、位置及相互关系。
  5. Paint：准备和绘制颜色、文字、边框、阴影等视觉内容。
  6. Composite：按需要组合绘制层，形成最终画面。

这是便于理解的模型。浏览器会按修改类型跳过不需要的步骤，并非每次都完整执行全部流程。

为什么这影响开发？ 改变元素宽度可能引起后续布局重新计算；改变某些纯视觉属性可能避免大范围布局；某些合成相关变化可能主要影响合成阶段。这些是后续性能优化理解“重排”“重绘”的基础。

9.3 CSS、脚本和图片什么时候加载

浏览器解析 HTML 时，遇到外部 CSS、脚本、图片、字体等资源，会根据资源类型、优先级和当前状态请求它们。

常规外部样式表通常会影响首屏样式计算；没有 async、defer 等设置的经典外部脚本可能阻塞 HTML 解析。这也是为什么脚本引入位置与加载属性会影响页面展示时机。

1
2
3

<script src="./classic.js" defer></script>
<script src="./analytics.js" async></script>
<script type="module" src="./app.js"></script>
  • defer：适用于外部经典脚本；HTML 解析过程中可并行下载，通常在文档解析完成后执行，并保持同类 deferred 经典脚本的顺序。
  • async：下载完成后在可执行时机执行，不保证多个异步脚本的源码先后执行顺序。
  • type="module"：模块脚本默认具有类似 deferred 的解析时机行为，并使用模块依赖图；也有自己的跨源与执行规则。

本篇不要求掌握脚本编程，但需要理解为何“CSS 没加载”和“脚本过早操作 DOM”会引起不同问题。

9.4 页面加载相关事件

  • DOMContentLoaded：初始 HTML 已解析完成，且 deferred 与模块脚本已按规则执行；不需要等所有图片下载完。
  • load：文档及相关依赖资源达到加载完成状态；某些延迟资源不在等待范围内。

现代前端应用的“页面可交互”“业务数据加载完成”不一定与这两个事件同步。React 页面可能在文档加载后继续请求数据和渲染组件。

9.5 缓存与资源版本

浏览器不一定每次都重新下载相同资源。常见机制包括：

  • 强缓存：在有效期内使用本地已存资源，典型相关字段为 Cache-Control: max-age=...。
  • 条件请求与重新验证：用 If-None-Match / If-Modified-Since 等请求头让服务器判断资源是否变化，服务器可返回 304 Not Modified。
  • 内容哈希命名：前端构建后的 app.abc123.js 等文件名有助于实现长期缓存与版本更新。

304 是成功重新验证缓存的协商结果，不表示“服务器返回了完整的新文件”。在 Network 面板观察资源时，需要区分网络传输、内存/磁盘缓存和重新验证。

9.6 浏览器多进程模型与任务边界

现代浏览器通常通过浏览器进程、渲染进程、网络相关进程/服务等隔离职责，但具体进程划分取决于浏览器实现和平台，不能把某个 Chrome 版本的内部结构当作 Web 标准。

对应用开发者，更实用的边界是：浏览器主线程上部分脚本执行和渲染工作可能相互竞争；耗时同步脚本会阻碍交互响应。事件循环、任务与微任务机制将在 JavaScript 专题中系统讲解。

第 10 章 HTTP/HTTPS、请求与响应

10.1 HTTP 是请求-响应协议

客户端发送 HTTP 请求，服务器返回 HTTP 响应。HTTP 的基本语义不依赖使用 Java 还是 JavaScript 实现。

HTTP/1.1 文本报文的概念示例：

1
2
3
4

Host: hr.example.com
Accept: application/json

1

3
4
5

HTTP/1.1 200 OK
Content-Type: application/json; charset=utf-8

{"code":0,"data":{"total":10,"items":[]}}

示例只为便于阅读。HTTP/2 与 HTTP/3 在传输中采用不同的帧和编码方式，不会原样传输这份 HTTP/1.1 文本格式。Network 面板仍会以统一的请求、响应概念展示它们。

请求包括方法、目标、首部和可选内容；响应包括状态、首部和可选内容。实际的请求体编码由 Content-Type 等信息与应用协议约定共同决定。

10.2 HTTP 方法的语义

方法主要语义安全性和幂等性
GET获取资源表示规范语义为安全、幂等
HEAD获取响应元数据而不传响应内容安全、幂等
POST按资源定义的方式处理提交内容不天然幂等
PUT创建或完整替换目标资源的状态幂等
PATCH部分修改资源不天然幂等；具体操作可设计为幂等
DELETE删除目标资源的关联幂等
OPTIONS查询通信选项安全、幂等；CORS 预检会用到

幂等指多次发送相同请求，其对服务器目标状态的预期效果与发送一次相同；不意味着每次返回的状态码必须完全一样。安全是 HTTP 语义对不应引发请求者所要求的状态改变的约束，不代表服务器绝不会产生访问日志等附带行为。

企业内部 API 可能习惯使用 GET/POST 两类方法，这属于服务端接口约定，不改变 HTTP 方法本身的标准语义。

10.3 HTTP 状态码如何读

状态码含义常见排查方向

204 No Content请求成功且无响应体不应强行按 JSON 解析空响应

403 Forbidden服务端拒绝访问授权策略、资源范围

409 Conflict与当前资源状态冲突并发更新、版本控制

在部分公司 API 中，HTTP 200 的 JSON 仍可能包含业务错误码。网络层与业务层必须分别判断：HTTP 状态码 反映 HTTP 处理结果，code/message 等是服务端自行定义的业务协议。

首部方向主要用途

Cache-Control两者控制缓存行为
ETag响应资源表示的验证标识
If-None-Match请求条件请求，常用于缓存重新验证
Location响应重定向或新建资源位置等

Access-Control-Allow-Origin响应CORS 允许读取响应的来源规则

Accept: application/json 表示希望获得 JSON；Content-Type: application/json 表示消息体是 JSON。两者作用不同。请求没有内容体时不必机械附加 Content-Type。

10.5 HTTPS 到底保护什么

HTTPS 是通过 TLS 保护的 HTTP 通信，主要提供传输过程中的机密性、完整性和服务端身份认证。它可以防止常见的链路监听与篡改，但不会自动保证页面业务逻辑正确，也不会替代后端鉴权、输入校验或防范 XSS。

浏览器通常依据服务器证书及受信任的证书链验证连接目标。证书错误、混合内容（HTTPS 页面加载不安全子资源）可能影响资源加载和安全提示。

10.6 常见前后端联调故障如何定位

如果页面显示“请求失败”，先不要马上认定是服务端 Java 代码出错，应拆解：

  1. 是否发出了请求？Network 中有没有该记录？
  2. 请求 URL、路径、方法、参数、Content-Type 是否正确？
  3. 是否发生重定向、预检、代理转发？
  4. HTTP 状态码是什么？响应体是否为预期类型？
  5. Cookie、认证头、跨源规则是否允许对应访问？
  6. 后端是否收到请求？如收到，是否在业务校验或数据库逻辑报错？

例如请求返回 HTML 登录页，但前端按 JSON 解析，会出现解析错误。根因可能是未登录后被重定向，而不是“JSON 语法写错”。

第 11 章 Cookie、浏览器存储、同源策略与 CORS

11.1 Origin 是什么

Web 的 Origin（源） 通常由 URL 的协议（scheme）、主机名（host）和端口（port）组成。

URL AURL B是否同源
https://example.com/ahttps://example.com/b是
https://example.comhttp://example.com否，协议不同
https://api.example.comhttps://app.example.com否，主机名不同
https://example.com:443https://example.com是，默认端口等价
https://example.com:8443https://example.com否，端口不同

“同源”和“同站点（same-site）”并非同义词。Cookie 的 SameSite 规则关注站点概念，而 DOM 访问和 CORS 等大量浏览器能力依赖源。不同子域名往往同站点但不同源，不能混用两套判断。

11.2 同源策略保护什么

同源策略限制一个源的脚本对其他源资源的某些访问与读取能力，例如直接读取跨源文档的 DOM、使用 Fetch 读取跨源响应等。

它不是“浏览器完全不能向其他域名发请求”。图片、样式表、链接等资源具有各自的跨源加载规则；跨源 fetch 也可能发出请求，但能否把响应暴露给页面脚本要受 CORS 等规则控制。

这一区别对前后端排错非常重要：后端可能已经收到并处理请求，但浏览器仍会阻止页面脚本读取其结果。

11.3 Cookie 的作用与属性

服务端可以通过 Set-Cookie 设置 Cookie，浏览器会根据规则保存，并在符合条件的后续请求中携带：

1

Set-Cookie: session=opaque-value; Path=/; Secure; HttpOnly; SameSite=Lax
  • Path：控制 Cookie 在哪些请求路径下发送，不是安全隔离边界。
  • Domain：若指定，可能允许该域及其符合规则的子域携带；不指定通常形成 host-only Cookie。
  • Expires / Max-Age：控制持久性和有效期；不设置时通常是会话 Cookie，但浏览器的会话恢复机制可能影响存续。
  • Secure：通常要求使用安全传输通道发送 Cookie。
  • HttpOnly：禁止页面脚本通过 document.cookie 直接读取该 Cookie；但浏览器仍可能在合适请求中发送它。
  • SameSite：限制 Cookie 在跨站点请求中的发送情形，可设置 Strict、Lax 或 None；SameSite=None 通常需要 Secure。

Cookie 可以用于会话识别，但并非所有 Cookie 都是 Session ID，也不能假设浏览器在任意跨源请求中都会自动携带需要的 Cookie。跨站点 Cookie 的可用性还受浏览器隐私策略影响。

11.4 localStorage 与 sessionStorage

机制存储范围与生命周期是否自动进入 HTTP 请求
Cookie按 Cookie 的域名、路径、有效期与发送规则管理满足条件时会
localStorage通常按源隔离，持久保存字符串不会
sessionStorage通常按源和顶层浏览上下文的页面会话隔离不会

浏览器存储并不等同于数据库。它们有容量、隐私模式与浏览器策略限制，也可能被清理。localStorage 和 sessionStorage 都是同步 Web Storage API，读写并不适合用作大量数据的高性能持久化方案。

对鉴权数据，不能只从“能不能持久保存”判断选择。存储在可由页面脚本读取的位置，若存在 XSS，就可能被恶意脚本访问；HttpOnly Cookie 则能降低被脚本直接读取的风险，但在采用 Cookie 凭证的场景仍需考虑 CSRF 等问题。最终方案取决于应用的认证架构及威胁模型。

11.5 CORS：允许受控跨源读取响应

假设页面运行在 https://app.example.com，接口位于 https://api.example.com。两者是不同源：

1

Origin: https://app.example.com

服务端可以使用 CORS 响应头表示允许对应源读取：

1

Access-Control-Allow-Origin: https://app.example.com

CORS 是浏览器与服务器协作的一套访问机制。后端是否应该授权某个用户访问某条员工记录，仍需由身份认证与业务授权判断，不能用 CORS 配置替代。

11.6 预检请求为什么会出现

对于某些跨源请求，浏览器会先发出 OPTIONS 请求，询问服务器是否允许实际请求使用对应方法和请求头。这称为 CORS 预检（preflight）。

概念示例：

1
2
3
4

OPTIONS /api/employees HTTP/1.1
Origin: https://app.example.com
Access-Control-Request-Method: POST
Access-Control-Request-Headers: content-type,authorization

服务端可能返回：

1
2
3

Access-Control-Allow-Origin: https://app.example.com
Access-Control-Allow-Methods: GET, POST, OPTIONS
Access-Control-Allow-Headers: content-type, authorization

是否预检取决于请求方法、请求头、媒体类型等是否满足 CORS safelist 相关条件，以及其他平台规则。不能只根据“GET 不预检”“POST 一定预检”判断。

例如跨源 POST 且请求体使用 application/json 时，通常需要预检；在特殊限制条件下使用符合 safelist 的请求方法、请求头和媒体类型可能不需要预检。

11.7 带 Cookie 的跨源请求有额外约束

当页面希望携带 Cookie 等凭证进行跨源 Fetch 请求时，还需要关注客户端的 credentials 设置、服务器的 Access-Control-Allow-Credentials，以及 Cookie 自身的 SameSite/Secure 属性和浏览器的第三方 Cookie 策略。

使用凭证的 CORS 场景中，响应的 Access-Control-Allow-Origin 不能以 * 通配所有来源；服务器必须返回明确允许的源，并满足对应凭证要求。

关键区分：

  • CORS 决定浏览器脚本能否读取对应跨源响应。
  • Cookie 发送规则决定凭证是否会被附带。
  • 认证与授权决定请求者是否应取得资源。

这三个机制彼此有关，但解决的是不同问题。

11.8 浏览器安全基础：XSS、CSRF 与混合内容

本阶段只建立必要的安全模型：

  • XSS：恶意内容进入可执行的页面上下文。错误使用不受信任的 HTML、脚本执行上下文等都可能造成风险。输出转义、正确使用框架默认转义、CSP 等可以构成防线。
  • CSRF：攻击者诱使已登录用户的浏览器向目标站点发出非预期的带凭证请求。SameSite Cookie、CSRF Token、服务端验证等措施可按架构使用。
  • 混合内容：HTTPS 页面请求不安全的 HTTP 资源，浏览器可能升级或阻止这些请求。
  • 前端权限展示：隐藏按钮只是界面行为，服务端必须独立实施数据和操作授权。

安全机制的边界应理解清楚，但详细攻击场景与企业安全治理不在 Web 基础篇展开。

第 12 章 使用 Chrome DevTools 排查问题

以下以 Chrome DevTools 的常见面板名称说明；不同浏览器或版本的菜单位置可能略有差异。

12.1 Elements：检查实际 DOM 与 CSS

Elements 面板应重点理解：

  • DOM 树：当前页面真实节点结构，而非仅初始 HTML 文本。
  • Styles：元素命中的 CSS 规则、被覆盖的声明、继承关系。
  • Computed：计算后的 CSS 属性及盒模型信息。
  • Layout / Grid / Flex overlay：在支持的浏览器中标识网格与弹性布局边界。

分析“卡片宽度为什么不对”时，通常先选中元素，检查 box-sizing、width、padding、border、父容器尺寸，再检查是否受到 Grid/Flex 尺寸约束。这样比无差别增加 !important 更可靠。

12.2 Network：跟踪完整请求

重点字段：

位置关注内容可解决的问题
Name / URL实际请求地址是否请求错了域名或路径
StatusHTTP 状态码404、401、500 等基本分类
Request MethodGET、POST、OPTIONS是否因预检或接口约定造成问题
Headers请求头、响应头Content-Type、Cookie、CORS、缓存
Payload查询参数或请求体参数是否正确传递
Preview / Response返回内容JSON、HTML 登录页、错误消息
Timing请求各阶段耗时网络等待、服务器响应等瓶颈
Initiator触发资源请求的位置资源由 HTML、CSS 或脚本引起

排查时可开启 Preserve log 保留页面跳转或重定向前后的记录；Disable cache 主要用于开发者工具打开期间的调试，不应把它当作真实用户的正常缓存条件。

12.3 Console：错误信息与脚本输出

Console 可显示脚本运行错误、警告和显式日志。典型现象：

  • Failed to load resource：资源加载失败，进一步到 Network 看具体状态。
  • Refused to apply style ... MIME type：可能请求到了 HTML 错误页，却被当成 CSS 处理。
  • CORS 相关错误：应检查请求是否发送、预检结果、响应头和凭证规则。
  • Uncaught ...：脚本运行异常，可利用 Sources 查看堆栈和断点。

控制台错误文字通常只是入口，不足以单独证明根因。必须结合 Network、Elements 和服务端日志交叉判断。

12.4 Sources：理解断点的用途

Sources 可查看加载的脚本、设置断点、逐行调试、观察调用栈与变量。虽然 JavaScript 会在下一阶段深入，但现阶段应知道它与 Network 的职责不同：Network 检查请求，Sources 主要检查脚本执行路径。

12.5 Application：检查 Cookie 和存储

Application 中通常可以查看 Cookies、Local Storage、Session Storage、Service Workers 等。这个面板便于核对登录态相关信息的存在和范围，但不要在团队沟通、截图或日志中泄露真实 Cookie、Token、个人数据。

12.6 三个典型排障路径

现象一：手机端横向滚动异常

  1. 在设备模式下切换不同视口尺寸。
  2. 用 Elements 定位超出视口的元素。
  3. 检查固定 width、min-width、Flex/Grid 自动最小尺寸和不换行文本。
  4. 决定是应允许内容换行、改变布局，还是让特定表格容器横向滚动。

现象二：CSS 修改后不生效

  1. 确认 Network 里当前 CSS 资源的 URL 和响应内容。
  2. 检查 Styles 是否命中选择器，以及是否被其他声明覆盖。
  3. 检查是否修改了错误的类名、元素或媒体查询分支。
  4. 再根据需要确认缓存、构建产物和实际部署路径。

现象三：页面请求接口失败

  1. 看 Network 中是否有 OPTIONS 和真实业务请求。
  2. 确认请求 URL、方法、参数和凭证。
  3. 看 HTTP 状态码与服务器实际返回内容。
  4. 若浏览器拦截读取响应，检查 CORS 响应头和凭证规则。
  5. 如果请求真正到达 Java 后端，再结合后端日志判断业务异常。

第 13 章 实战：构建响应式员工管理后台静态页面

本篇只有这一个综合实战，同时应用语义、表单、表格、CSS 布局、响应式、焦点样式、浏览器资源加载和调试。

13.1 项目目标与边界

实现以下静态页面结构：

  • 页面左侧为功能导航，顶部为当前系统和用户信息。
  • 主内容区包含页面标题、统计卡片、筛选表单和员工表格。
  • 导航、表单、表格具有合理的语义与键盘可访问性。
  • 窄屏布局能够自动切换，保留导航可用性；数据表格可横向滚动。
  • 整体不依赖 JavaScript 或第三方框架，文件放在同一目录便可运行。

本阶段不实现接口调用、真实筛选、增删改查或客户端路由。为了展示 HTML 原生 GET 提交语义，筛选表单提交后只更新当前 URL 的查询参数，不会过滤静态数据。数据操作按钮保持禁用并标记后续阶段实现。

13.6 代码结构为什么这样设计

语义层面：导航使用 nav 和有效页内锚点；列表使用 table、thead、tbody 和表头；筛选项使用 label 与表单控件关联；主要内容用 main；数据统计用清楚的文字标签而不是只依赖颜色。

布局层面：Grid 承担页面整体两列结构，Flex 承担导航、表单和标题区的一维分布；min-width: 0、minmax(0, 1fr) 缓解内容最小尺寸带来的横向溢出；overflow-x: auto 为宽表格提供局部滚动。

响应式层面：视口变窄时，左侧导航转为顶部横向导航，避免简单隐藏导致功能入口消失。表格保留足够的列宽而不是挤压到难以辨认。

实现边界：编辑操作暂时禁用，明确说明“待实现”；筛选表单仅展示 HTML 原生提交机制，不冒充已实现业务过滤。第二阶段可以通过 JavaScript 添加动态行为，第三、四阶段再用 TypeScript 和 React 进行重构。
