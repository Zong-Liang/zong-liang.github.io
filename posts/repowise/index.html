1. 项目定位

Repowise 是一个面向开发者和 AI 编程智能体的代码库分析与知识索引工具。 它在本地解析源代码、依赖关系、Git 历史、测试信息、项目文档和架构决策，并将结果通过命令行、可视化界面和 MCP（Model Context Protocol）提供给开发者、Codex、Claude Code、Cursor 等工具。

本文根据项目文档和维护方公开的基准介绍工具能力。第 10 节提供试点验证方案，实际收益取决于目标仓库和任务。

它重点解决三类问题：

  1. 理解代码：仓库如何组织；文件和函数如何关联；业务入口与关键依赖在哪里；某项设计为什么存在。
  2. 评估修改：修改某个文件或符号可能影响哪些调用方；哪些文件可能需要同步调整；本次变更应运行哪些测试。
  3. 维护代码：哪里存在技术债、复杂度和性能风险；哪些代码可能不再使用；哪些问题值得优先处理。

Repowise 将这些分析结果保存在可复用的索引中。开发者和智能体可以先查询索引定位相关代码，再回到源码核对具体行为。

2. 工作机制

传统的 AI 代码理解往往从即时检索开始：搜索文件、查看定义、追踪引用、阅读更多文件，再综合判断。新任务开始时，部分探索工作可能重复发生。

  1. 读取仓库资料。 输入包括源代码、Git 历史、测试报告、项目文档和架构决策记录（ADR）。
  2. 分析并建立索引。 Repowise 解析 AST、提取符号，建立文件、函数和模块依赖图，分析共同变更、代码所有权、健康度、死代码和变更风险。文档与架构决策也会纳入索引，模型生成和语义检索可按需启用。
  3. 保存分析结果。 本地索引以 SQL 保存符号、文档、历史和分析记录，以图结构保存导入、调用和继承等关系，另可选用向量索引支持语义检索。
  4. 提供查询入口。 开发者可用 CLI 或 Web Dashboard 查询，Codex、Claude Code、Cursor 等客户端可通过 MCP Server 接入。

首次执行 repowise init 建立索引；后续可以使用 repowise update 增量更新，或通过 repowise watch 监听代码变化。是否生成自然语言文档、是否使用 Embedding、是否连接外部模型，由配置和运行模式决定。

技术边界： 静态依赖图描述能够从源代码推断的关系，并不完整等同于运行时调用链。反射、依赖注入、动态路由、配置驱动调用等机制可能造成漏报或不确定结果。

3. 主要功能

3.1 代码结构与架构分析

Repowise 使用 AST 解析代码，提取文件、类、函数、方法、导入、调用和继承等信息，建立文件级与符号级关联图。可用于：

  • 查找某个函数的调用方与被调用对象。
  • 了解模块之间的依赖、关键节点和循环依赖。
  • 分析入口到下游模块的可推断执行路径。
  • 查看交互式架构图、C4 视图，或导出 Structurizr DSL。

例如，在 Java 后端项目中，可辅助分析 Controller → Service → Repository 的静态调用路径；在 React 项目中，可分析组件和模块之间的导入关系。

项目将调用边的解析依据及置信度显式记录，便于区分较有把握的引用与推断关系。但 Spring 代理、反射、运行时注册等场景仍需结合代码和实际执行验证。

参考：Graph Intelligence、Language Support。

3.2 自动生成项目文档

Repowise 支持为仓库、模块和文件生成 Wiki 文档，并对文档引用的代码结构进行检查。

模式生成方式是否要求 LLM
基于代码的文档根据符号和代码结构构建文档不要求
模型增强文档在已有索引基础上编写更完整的自然语言说明要求
语义检索使用 Embedding 将查询与文档关联需要 Embedding 模型

其 Doc Drift（文档漂移） 功能可检查 Markdown 中引用的文件或符号是否仍然存在，并指向相关位置。

此功能适合为缺少文档的遗留项目生成初始技术资料，但自动结果不能替代业务方确认：源代码本身未表达的需求、操作规程和组织约束，不会因建立索引而自动变得准确。

参考：Wiki / Documentation、Doc Drift。

3.3 代码健康度与技术债分析

项目文档称其使用 53 个确定性检测器，从代码结构、依赖和 Git 历史中发现可维护性、缺陷风险及性能风险信号。每个源文件可获得 1—10 的健康度评分，并生成优先修复建议。

维度典型关注点
缺陷风险复杂逻辑、修改频率、历史缺陷等
可维护性高复杂度、过深嵌套、结构分散、重复逻辑等
性能风险N+1 查询、循环中的 I/O、异步代码中的阻塞调用等

常用命令：

1
2

repowise health   # 查看健康度、低分文件及主要发现
repowise next     # 查看建议优先处理的问题

评分不是缺陷证明。 低分意味着值得优先检查，不表示文件必然存在 Bug；重构是否必要，还需结合业务价值、变更风险、团队规范和测试成本判断。

参考：Code Health、Performance。

3.4 变更风险与影响范围分析

Repowise 能结合代码关系及 Git 历史，给出修改某个文件或符号时的关联信息，例如：

  • 调用方和下游依赖。
  • 历史上经常一起修改的文件（co-change）。
  • 涉及的测试及可能遗漏的测试。
  • 文件的历史缺陷信息与代码所有权。

对当前分支进行分析：

1

repowise risk main..HEAD

风险分数的解释必须准确： repowise risk 主要衡量某次 diff 在仓库近期提交中的规模、分布和相对位置，并辅以历史修复信息；它不是“此 PR 将发生故障的概率”。静态影响范围也不能保证找到全部实际受影响的运行时调用者。

参考：Change Risk。

3.5 测试影响分析（Test Impact Analysis）

Repowise 试图回答两个工程问题：

  1. 本次代码变更可能影响哪些测试？
  2. 哪些高风险代码尚未得到充分测试？

它明确区分两种证据：

数据来源能说明什么不能说明什么
实测覆盖率报告哪些代码在测试运行中被执行；部分格式可对应具体测试报告过期后不能代表最新代码
依赖图推断哪些测试通过静态引用关系可能触达目标文件不能证明测试实际执行，也不能据此生成真实覆盖率百分比

支持的覆盖率格式包括 LCOV、Cobertura、Clover、JaCoCo XML、Go coverprofile、coverage.py 等。对于 Java 项目，可接入 JaCoCo 报告；对于前端项目，可使用支持的 LCOV 等格式。

示例：

1
2
3
4
5
6
7
8

# 将已有的测试覆盖率报告导入 Repowise
repowise coverage add coverage/lcov.info

# 查看覆盖率导入状态
repowise coverage status

# 选择当前分支可能受影响的测试
repowise impacted-tests main...HEAD

以上命令中的 coverage/lcov.info 只是示例路径，实际应替换成测试框架输出的报告位置。

该能力适合用于本地增量测试选择、测试补强和 CI 优化，但不能取代完整测试策略。框架运行时注入、隐式注册和动态调用可能未被静态图捕获。

参考：Test Intelligence。

3.6 死代码检测

Repowise 可以报告：

  • unreachable_file：未发现可达引用的文件。
  • unused_export：未发现被使用的导出符号。
  • zombie_package：仓库内部未发现依赖的包。
  • 可选的 unused_internal：疑似未使用的内部符号。

命令：

1
2

repowise dead-code
repowise dead-code --safe-only

结果附带置信度和证据。所有结果都应视为候选问题，而不是直接删除指令。 动态导入、Java 反射、Spring Bean 注册、脚本入口和外部消费者都可能使静态“无引用”判断失效。

参考：Dead Code。

3.7 架构决策与历史原因

Repowise 可以把设计决策与对应代码关联，支持的证据来源包括 ADR、代码中的 # WHY: 注释，以及在适当配置下从提交、PR 和智能体会话中提取的候选信息。

它区分：

  • 事件（Episode）：能提供证据的历史事实。
  • 候选决策（Candidate）：从证据中归纳出来、尚待确认的决定。
  • 正式决策（Decision）：经过确认、对特定代码范围生效的约束。

因此，模型提出的解释不会自动成为项目规范；需要确认的候选决策也不会被直接当作已生效的约束。

参考：Architectural Decisions。

3.8 多仓库 Workspace 与跨仓库分析

Repowise 支持将相关仓库组织成 Workspace，并尝试关联不同仓库间的 HTTP、gRPC、消息 Topic、API 契约和服务依赖。

适用场景包括：前后端分别位于不同仓库、多个微服务之间存在调用、一个项目依赖多个共享组件库等。它可以辅助识别上游接口修改对其他仓库的影响。

跨仓库分析取决于能否从实际代码、配置与契约中识别可靠关联。对于动态构造的接口地址、运行时服务发现、没有声明的消息约定等，仍需人工验证。

参考：Workspaces / Multi-Repo。

4. MCP 与 AI 编程工具集成

Repowise 的 MCP Server 将分析结果提供给 AI 编程客户端。默认有 10 个核心工具；还提供若干按需启用的专业工具。

MCP 工具主要用途
get_overview仓库总体结构、入口与模块概况
get_answer综合索引回答代码库问题
get_context文件、模块、符号的上下文与关系
get_symbol指定符号的源码与位置
search_codebase根据名称、路径或概念检索
get_risk文件及修改范围的影响、风险与测试信息
get_change_risk分析 Git 提交、分支或工作区修改
get_why查询设计决策与历史依据
get_health查询代码质量、健康度与整改建议
get_dead_code查询可能无用的代码

另有依赖路径、执行流、生成重构代码、问题状态管理及 Workspace 专项工具，其中部分需要显式启用。除少数可选操作外，MCP 工具主要提供分析数据；AI 客户端仍自行负责修改代码与验证结果。

参考：MCP Tools Reference。

与直接使用 Codex / Claude Code 的区别

开发任务未使用 Repowise接入 Repowise 后
熟悉项目临时检索目录与源码可优先查询已有结构化概览
追踪调用搜索符号与逐级查看引用可查询索引中的调用关系
评估变更由智能体根据已读取代码推断可同时参考调用图、Git 历史和测试关系
选择测试搜索测试文件与人工判断可查询测试影响分析结果
整理技术债一次性代码审查可查询有记录的健康度与优先处理队列
理解历史原因搜索 ADR、提交和 PR可查询与代码关联的决策证据

Repowise 提供证据与分析；智能体负责完成具体开发任务。两者互补，而非替代。

这里的三类存储分别服务不同查询：SQL 保存实体和历史，图结构保存依赖，向量索引用于语义匹配。不能把 Repowise 简单理解成“把仓库放进向量数据库的 RAG 工具”。

6. 安装与入门

6.1 环境要求

  • Python 3.11+。
  • Git。
  • 使用本地 Dashboard (repowise serve) 时，需要 Node.js 20+；首次运行可能下载界面资源。

建议使用 uv 或 pipx 隔离安装，避免修改已有工程的 Python 环境。

6.2 安装

1
2
3

uv tool install repowise
# 或：pipx install repowise
# 或：pip install repowise

6.3 初始化单个仓库

1
2

cd /path/to/your/repo
repowise init --yes --no-prose --no-editor-setup

--no-prose 跳过模型生成，建立代码、Git、健康度、死代码和基于结构的文档索引。--no-editor-setup 跳过编辑器和 MCP 配置写入，适合先在本地试用。参数见 Quickstart。

6.4 查看分析结果

1
2
3
4
5
6
7

repowise status                    # 索引状态与版本差异
repowise health                    # 代码健康度
repowise next                      # 优先处理事项
repowise dead-code                 # 死代码候选项
repowise risk main..HEAD           # 变更风险分析
repowise impacted-tests main...HEAD # 受影响的测试
repowise serve                     # 本地 Dashboard + MCP 服务

6.5 接入 Codex

官方提供仓库级的 Codex 集成：

1
2

repowise init --codex
codex mcp list

集成会涉及项目中的 .codex/config.toml、.codex/hooks.json，以及受管理的 AGENTS.md 片段；具体写入内容以所安装版本为准。初始化前应检查已有配置，并确认项目允许安装对应 Hooks。

Codex 也可以通过 Repowise 提供的插件和 Skills 使用相关能力。完整说明：Codex Integration。

6.6 增量更新

1
2
3

repowise update       # 更新索引
repowise watch        # 监听变化并持续更新
repowise status       # 检查当前索引是否落后于工作区

MCP 查询结果携带索引新鲜度相关信息。对于变动频繁的仓库，应在分析前检查索引是否与目标代码版本匹配。

快速入门：Quickstart。

7. 模型调用、隐私与许可证

7.1 哪些能力需要模型

能力模型依赖
AST、依赖图、Git 分析不需要
健康度、死代码、变更风险不需要
测试关系分析不需要；真实覆盖率需要外部测试工具产生报告
基于结构的 Wiki不需要
模型增强的自然语言 Wiki需要生成模型
模型综合回答与代码重构生成视所用操作和配置，需要模型
语义检索需要 Embedding 模型；全文检索不要求

外部服务需要相应凭证；也可以按项目文档配置本地 Ollama 等方案。避免将“静态分析无需模型”误解为“所有高级功能均无需模型”。

7.2 数据与部署

  • 开源版本支持本地分析与自托管。
  • 本地确定性分析不要求上传源码到外部 LLM。
  • CLI 默认存在可关闭的匿名遥测，详见项目隐私文档；可执行 repowise telemetry disable 或按文档设置相关环境变量。
  • 选择外部模型或 Embedding 服务时，代码派生内容可能发送至所配置服务商。
  • 托管服务需要由 Repowise 平台处理所连接的仓库数据，应独立评估组织的信息安全要求。

许可证： AGPL-3.0。个人测试与组织商用、自托管、网络服务改造或二次分发时，需分别评估该许可证的实际适用要求；不要简单将“开源”理解为“任何闭源集成都不受限制”。

参考：Privacy（README）、Telemetry、Commercial、License。

9. 局限与使用风险

  1. 静态分析存在覆盖盲区。 Spring 代理、Java 反射、动态装配、插件、配置化路由和运行时依赖可能不在调用图中。
  2. 推断测试关系不是执行证据。 没有覆盖率报告时，只能推断测试可达性，不能把它当作真实覆盖率。
  3. 死代码候选不等于可安全删除。 应验证动态引用、外部消费者、启动路径及其他运行时入口。
  4. 质量评分不能成为唯一整改依据。 不应为追求分数而增加无必要的抽象或拆分。
  5. 索引会过期。 分析结果必须与当前代码版本对应，尤其是对合并前的修改进行审核时。
  6. 模型增强功能涉及成本与数据边界。 组织内部仓库应检查网络请求、遥测、凭证管理、生成内容处理和合规要求。
  7. 项目仍在快速迭代。 公开包配置的开发状态标记为 Alpha；正式进入 CI 门禁前，需验证命令稳定性、误报率及运行成本。

10.2 推荐 PoC 路径

先选择一个边界清晰、保留历史提交且仍在维护的仓库，记录 Repowise 版本、仓库提交和索引配置。

阶段 A：索引和结构准确性

  • 建立本地索引，确认主要语言和框架是否得到有效解析。
  • 随机选取一组核心类、方法或模块，人工核对调用方、导入关系和入口识别。
  • 记录漏报、误报以及动态机制相关的问题。

阶段 B：变更影响与测试选择

  • 回放历史问题时，以修复前的提交建索引，只提供修复前可见的问题描述和代码。将后续修复 PR 的文件清单留作评分依据。
  • 评估已知 PR diff 的影响范围时，以该 PR 当时的基线和分支提交为输入。导入与索引版本匹配的覆盖率报告，对照完整测试结果，记录漏选和额外选中的测试。

阶段 C：Codex 集成与开发体验

  • 固定仓库提交、模型和任务描述，分别用直接检索代码和接入 Repowise 的方式完成同一批任务。
  • 比较目标文件定位、工具调用次数、人工纠错、结论引用依据及耗时。
  • 检查项目配置文件和 Hooks 的实际修改是否可维护。

阶段 D：是否纳入日常工作流

  • 如果索引准确、收益稳定，将其作为代码理解和改动前检查的辅助工具。
  • 如果测试影响选择满足要求，再逐步接入本地脚本或 CI；保留兜底测试策略。
  • 不建议单凭项目演示数据，直接设立阻断式健康度门禁或自动删除策略。

10.3 与其他 AI 开发能力的职责划分

Repowise 更适合作为代码事实与工程分析层，与其他职责明确的工具协作：

环节工具与产出
定义需求需求与验收规格工具明确要实现的行为和验收条件。
修改代码Codex 或 Claude Code 编写代码，可查询 Repowise 提供的仓库结构、依赖、变更影响、风险和测试关联。
验证交付测试工具或测试技能搭建并运行测试。真实测试结果和代码审查为交付验收提供依据。

Repowise 本身不负责定义需求是否正确，不替代测试执行，也不能代替业务验收。这样的分工能减少工具能力重叠，并避免将静态分析结论当作最终交付依据。

11. 结论

对于模块关系复杂、历史较长的仓库，适合先用 Repowise 辅助代码导航和改动前的影响分析。若计划将测试选择或健康度评分接入 CI，先在真实 PR 上测量漏选、误报和维护成本，再决定是否设为门禁。
