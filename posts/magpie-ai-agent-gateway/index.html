Magpie：统一管理 Claude Code、Codex 和 OpenCode 的模型与账号

次浏览 11 分钟阅读

Magpie：统一管理 Claude Code、Codex 和 OpenCode 的模型与账号

同时用 Claude Code、Codex 和 OpenCode，最烦的往往是管理它们背后的模型和账号。每个工具各有一套配置文件，API Key、Base URL 和模型名称都要分别维护。想让 Claude Code 临时换成 Kimi，或者给 Codex 接上 DeepSeek，就得先翻出配置文件改一轮。

Magpie 把这部分工作收到了一处。它在 Agent 和模型服务之间运行一个本地网关：Agent 照常使用，模型选择、账号管理和请求分配交给 Magpie 统一处理。

项目采用 MIT 许可证开源，主体用 Go 编写，支持 macOS、Windows 和 Linux，提供图形界面、命令行、终端界面和 Docker 部署。

一、为 Agent 切换模型

图形界面的 Agents 页面会列出本机已安装的受支持工具，可以从统一的模型列表里为每个工具选择模型。模型按 provider/model 命名，例如 moonshot/kimi-k2.5。

命令行也能完成同样的操作：

1
2
3
4
5

# 让 Claude Code 使用 DeepSeek
magpie claude deepseek/deepseek-v4-pro

# 让 Codex 使用 Kimi
magpie codex moonshot/kimi-k2.5

这两个模型名取自项目文档示例，实际能用哪些型号取决于服务商和账号权限。

切换时，Magpie 会改写对应 Agent 的配置文件，并尽量保留原有的注释、顺序和格式。新配置通常在新会话中生效。

如果经常在几套配置之间来回切换，可以把多个 Agent 的设置保存成 Profile，比如「日常开发」和「复杂任务」各建一个。切换 Profile 就能同时改好 Claude Code、Codex 和 OpenCode。

二、本地网关

只改配置文件的话，普通的切换工具也能做到。Magpie 多做的一步是在本机运行网关，由它实际转发模型请求。

网关默认监听 127.0.0.1:3425，兼容以下接口：

  • OpenAI Chat Completions
  • OpenAI Responses
  • Anthropic Messages
  • Gemini

Agent 把请求发给网关，Magpie 按当前配置转发到选定的模型服务，并在需要时转换协议。上游可以是普通的 API Key，也可以是 Ollama、LM Studio 这类本地模型服务。

普通的 OpenAI 兼容客户端，把 Base URL 指向网关即可接入：

1
2

export OPENAI_BASE_URL=http://127.0.0.1:3425/v1
export OPENAI_API_KEY=magpie

这里的 magpie 是文档给出的本地示例值，不是服务商的 API Key。上游的账号和密钥要先在 Magpie 里配好。

Magpie 还能接入部分已登录的订阅账号，如 Claude、ChatGPT/Codex 和 Copilot，通过适配或插件机制提供给其他 Agent 使用。其中一些订阅接入已经从内置实现移到了社区插件。这种用法和按量付费的 API 调用性质不同，技术上能跑通，不代表服务商允许这样使用，接入前最好先看一下对应的服务条款。

三、多账号与路由组

Magpie 更有特色的是多账号管理和路由组。

比如平时想优先用某个订阅模型，额度用完或者服务暂时不可用时再换备用模型。这时可以建一个路由组，把几个模型加进去，再把整个路由组当作一个模型分配给 Agent。

路由组支持以下策略：

策略做法
order按预设顺序依次尝试
rotate在成员之间轮流分配
usage优先选使用量少的成员
smart、pace结合订阅额度和重置时间调度

路由组只能在已配置的成员之间切换。没有可用的备用账号，或者备用模型的工具调用不符合 Agent 的要求，请求照样会失败。不同模型的上下文窗口、工具调用兼容性和输出质量也有差别，自动切换后效果可能和原来不一样。

另一种方式是意图路由：先让一个模型判断任务类型，再按分类结果选执行模型。比如简单问答交给便宜的模型，复杂的代码修改交给更强的模型。这样省去了手动挑选，代价是分类本身也要调用模型，而且可能分错。需要稳定复现结果的开发任务，用固定模型或顺序明确的路由组更容易排查问题。

四、其他功能

4.1 用量统计

Magpie 会统计 Token、缓存读写和会话数，并按模型价格估算费用；部分接入方式还能看到套餐余额和额度窗口。终端里运行 magpie quota 也能查看。

估算费用和服务商的实际账单可能对不上。订阅套餐和按量计费混用时，两类成本不能直接相加比较。

4.2 统一维护 Agent 资料

资料库用来集中维护指令、MCP Server、Skills 和子代理配置，Magpie 会按各个 Agent 的格式写到对应位置。同时维护 Claude Code、Codex 和 OpenCode 的话，不用再在几个目录之间复制同一份内容，各工具的配置也不容易出现差异。

4.3 隐私脱敏

Coding Agent 可能读取 .env、日志和配置文件，把密钥、邮箱等敏感内容带进模型请求。开启脱敏后，Magpie 会在本地识别这些值，发送前替换成占位符，收到响应后再还原。识别可以只用规则，也可以额外下载本地模型辅助。

这个功能默认关闭，需要手动开启。识别可能漏掉敏感数据，也可能误伤正常文本；如果任务本身就要分析某个密钥，脱敏反而会妨碍结果。它只作用于经过网关的模型请求，Agent 能读哪些文件、执行哪些命令、访问哪些网络，仍然要在 Agent 侧单独限制。

4.4 插件与远程共享

插件可以扩展 Provider，也可以用 JavaScript 中间件在请求发出前后修改内容。Magpie 还内置了联网搜索工具。

网关可以通过局域网或远程部署共享给其他设备。这样一来，网关就暴露在了更大的网络范围里，部署前要想好认证方式、哪些网络可以访问，以及上游凭据存放在哪里。

五、安装与上手

最简单的方式是从 Magpie 官网 下载对应系统的安装包。也可以用安装脚本：

1

curl -fsSL https://usemagpie.ai/install.sh | sh

执行远程脚本前，建议先看一遍脚本内容。此外还支持通过 Go 安装和 Docker 部署。

装好后可以按这个顺序配置：

  1. 在 Providers 中添加一个 API 服务商或受支持的账号。
  2. 在 Agents 中为 Claude Code、Codex 或 OpenCode 选择模型。
  3. 新开一个会话，确认普通对话、代码编辑和工具调用都正常。
  4. 基本链路稳定后，再加备用模型、路由组和用量管理。

刚开始只接一个服务商比较稳妥。链路简单时，出了问题更容易判断是 Agent 配置、网关协议转换、上游认证还是路由策略的原因。

六、适合谁用

如果同时在用多个 Agent、多个 API 服务商和订阅账号，Magpie 能把散落在各个配置文件和账号页面里的管理工作集中到一个入口。

如果已经有一套稳定的配置，只是偶尔手动换一次模型，多运行一个常驻网关未必划算。协议转换、上游认证、路由策略和插件都可能带来新的故障。

值不值得装，主要看这些重复的配置工作在日常开发中占了多少时间。
