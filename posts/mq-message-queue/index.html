1. MQ 是什么？为什么会出现？

MQ 是应用之间异步传递消息的基础设施。 生产者（Producer）把业务消息发送到消息代理（Broker）；消息代理负责接收、路由、存储或保留消息；消费者（Consumer）按约定获取并处理消息。

它解决的核心问题不是“把一个 HTTP 请求换成消息”，而是让业务处理和下游执行在时间上解耦，并以队列、订阅、确认、持久化、重试等机制管理异步协作。

以电商订单为例：用户完成支付后，订单系统需要记录支付结果，同时触发支付通知、会员积分和经营统计。支付状态的确认属于核心业务；通知、积分和统计通常可以在支付成功后异步完成。

如果订单服务依次同步调用三个下游系统，其中一个服务响应缓慢或暂时不可用，就可能拖长接口响应时间，还会把下游故障传递给上游。引入 MQ 后，订单系统可以发布 OrderPaid（订单已支付）事件，由各订阅方分别处理。

flowchart LR
    A[支付结果确认] --> B[订单服务更新支付状态]
    B --> C[可靠发布 OrderPaid 事件]
    C --> D[(MQ)]
    D --> E[通知服务]
    D --> F[积分服务]
    D --> G[统计服务]

图中“可靠发布”并非简单地先保存数据库、再调用发送接口。业务状态与消息发布之间存在一致性问题，需要通过 Transactional Outbox、适用的事务消息等机制处理，第 8 节会详细说明。MQ 不负责替代支付校验，也不能证明通知、积分等下游已经执行成功。

后文以同一订单领域贯穿：订单支付成功后产生 OrderPaid 事件；不同消费者负责通知、积分和统计。讨论顺序时再引入 OrderCreated、OrderShipped 等订单生命周期事件。

1.1 MQ 的三个主要价值

  • 异步处理：把非关键路径工作放到后台，降低用户接口的等待时间。例如，支付结果确认后不必等待通知服务发送站内信。
  • 系统解耦：订单服务不必感知积分、通知、统计服务的部署地址、扩缩容状态和内部实现。
  • 削峰与缓冲：大促期间短时间产生大量订单事件，统计服务按照可承受速度处理。这里缓冲的是工作量，不会凭空增加处理能力。

MQ 还常用于任务分发、事件广播、最终一致性、数据集成，以及日志和埋点处理。

1.2 MQ 会引入哪些新问题？

它不是免费提升架构质量。异步后需要处理消息重复、乱序、积压、消费延迟、发送失败、链路可观测性不足、事件版本兼容和跨系统数据一致性。如果流程必须立即得到下游结果，或者业务本身很简单，直接调用往往更容易理解和维护。

2. 核心概念与一条消息的生命周期

概念含义常见误区
Producer创建、发送消息的应用调用发送 API 返回，不代表下游业务完成
Broker接收、路由、保存、投递消息的中间件服务Broker 确认，不等于消费者处理成功
Consumer订阅和处理消息的应用同一消息可能被重复交付
Message / Event传递的数据及其元数据消息应描述清楚业务语义，不要只放含糊的 type=1
Queue任务等待处理的逻辑队列不同产品的“队列”语义并不完全一致
Topic按主题组织消息或事件RabbitMQ 的 Topic Exchange 与 Kafka Topic 不是同一种存储结构
ExchangeRabbitMQ 按路由规则转发消息的实体Exchange 不是消费者直接消费的队列
Routing Key / Message Key路由或分区依据，具体取决于产品RabbitMQ 路由键 ≠ Kafka 消息键
Consumer Group消费者协作或订阅隔离的逻辑单位Kafka 中同组实例分摊分区，不同组可以独立读取同一 Topic
ACK / Offset确认处理或推进消费位置不能证明外部数据库或第三方接口绝不会重复执行
DLQ死信队列，用于隔离无法正常处理的消息放入死信并不等于问题解决

2.1 典型生命周期

以 OrderPaid 为例，一条消息通常经历创建、发布、Broker 接收、路由、消费、业务处理和确认等阶段。

flowchart TD
    A[订单服务构造 OrderPaid] --> B[发布消息]
    B --> C[Broker 接收、路由或存储]
    C --> D[消费者获取消息]
    D --> E{业务处理成功？}
    E -->|是| F[ACK 或提交消费位点]
    E -->|否| G[按策略重试或隔离]
    G --> H[达到条件后进入死信或人工处理]

图中展示的是通用逻辑，不代表各产品具有完全相同的确认机制。RabbitMQ 传统队列中的消息通常在消费者 ACK 后完成该队列的消费；Kafka 以保留日志和消费者位点为核心，消费后记录仍可在保留期内被其他消费组读取或被符合条件的消费任务重放。二者不能简单理解为“消费完就删除消息”。

2.2 “命令”和“事件”要分清

  • 命令（Command）：要求特定处理者执行操作，如 SendPaymentNotification（发送支付通知），强调“请做这件事”。
  • 事件（Event）：表示已发生的事实，如 OrderPaid（订单已支付），强调“这件事已经发生”。

命令通常只希望一条工作链执行；事件可让多个独立订阅方各自处理。一个事件不应承诺某个下游已经完成动作。

3. 两种最常见的消费模型

3.1 竞争消费者：一份工作交给一个执行者

订单支付后，通知服务收到一条“发送支付成功通知”的任务。通知服务部署了三个 Worker 实例，它们共同消费同一个通知任务队列。在正常工作模式下，一次投递由其中一个实例处理；如果处理失败，消息可能被重投递给该实例或另一实例。

任务队列消费实例消费关系
payment.notification.qWorker A、Worker B、Worker C实例间分担任务，而不是三份重复执行

这种模式适合通知发送、生成报表、文件处理等。增加 Worker 可能提升吞吐，但实际能力仍受队列、数据库、外部接口和热点资源限制。

3.2 发布/订阅：同一个事件由多个业务方独立处理

与通知任务不同，OrderPaid 是描述“订单已支付”的业务事件。通知、积分和统计服务都需要知道这件事，因此应当为每个业务方建立独立的订阅关系。

flowchart LR
    A[订单服务] -->|OrderPaid| B[事件交换机 / Topic]
    B --> C[通知队列或订阅]
    B --> D[积分队列或订阅]
    B --> E[统计队列或订阅]
    C --> F[通知服务]
    D --> G[积分服务]
    E --> H[统计服务]

图中的“事件交换机 / Topic”是概念示意，不是说 RabbitMQ Exchange 与 Kafka Topic 具有相同实现。

RabbitMQ 通常通过 Exchange 与不同绑定队列实现发布/订阅；一个订阅服务的多实例再竞争消费自己的队列。Kafka 通过不同 Consumer Group 独立读取同一 Topic，同组实例分摊分区。

常见错误是让通知、积分、统计服务共同竞争同一个 RabbitMQ 队列：这样每次投递通常只由其中一个服务获取，无法保证三个服务分别处理事件。

4. 什么场景值得用 MQ？什么场景不值得？

场景是否适合设计重点
订单支付成功后发送通知、增加积分适合支付主流程与下游解耦；消费幂等、防重复发放
订单支付事件驱动统计和搜索索引更新适合事件发布可靠性、版本顺序、最终一致性
秒杀订单或抢票任务排队有条件适合入口限流、库存原子扣减、幂等、队列容量、用户状态反馈
海量埋点、访问日志、CDC 数据流适合吞吐、分区、保留与回放，常考虑 Kafka
订单超时自动关闭有条件适合定时任务、延时消息、状态再次校验；允许触发时间误差
必须立刻拿到库存扣减结果才能下单不宜把关键确认完全异步化同步事务/接口或明确的状态机与补偿
单体应用内很轻量的后台计算不一定需要本地任务队列/线程池可能已足够，注意重启后任务丢失风险
跨服务强一致事务MQ 本身不能直接保证事务边界、Outbox、业务补偿和状态机
高频同步查询或用户等待响应的 RPC通常不优先直接 HTTP/gRPC 往往更直观

4.1 选型前的五个问题

  1. 这项工作能否稍后完成？用户能否看到“处理中”状态？
  2. 下游失败时，是否允许重试？重复执行有什么副作用？
  3. 业务要求多久处理完成？积压最多能承受多久？
  4. 是否需要广播、同一实体顺序、历史回放或复杂事件处理？
  5. 组织是否具备部署、监控、排障和故障恢复 MQ 的能力？

如果前三个问题没有答案，先设计业务状态和失败补偿，而不是先部署 Broker。

5. RabbitMQ、RocketMQ、Kafka 怎么选？

维度RabbitMQ（传统队列）Apache RocketMQ 5.xApache Kafka
主要定位灵活消息路由、任务分发和服务间异步通信业务消息、顺序/定时/事务消息分布式事件日志、流式数据平台
基本组织方式Exchange → Queue → ConsumerTopic、MessageQueue、ConsumerTopic → Partition → Consumer Group
多订阅方为不同订阅方配置不同队列按订阅与消费分组组织不同组各自维护位点
路由能力Direct / Topic / Fanout 等比较灵活Topic、Tag、过滤等Topic + Key/Partition 为主
消费与重放队列 ACK 后通常不保留供回放；另有 Streams 产品形态具备按保留策略保存和重消费能力，视版本与模式以日志保留和位点回放为核心能力
顺序能力需结合队列、消费者并发、重投递控制FIFO + MessageGroup（满足约束）单分区内记录有序
定时/延时TTL+DLX、插件或业务调度等实现5.x 有专门延时消息类型不是普通 Topic 的原生定时投递语义
事务相关发布确认不等于数据库事务有事务消息与回查机制有生产者幂等和 Kafka 事务，范围有限
常见优先场景中小规模业务异步任务、丰富路由以业务可靠投递、顺序和定时消息为重点的系统埋点、日志、CDC、大规模事件流与回放

经验性选型建议：业务任务/通知和灵活路由，可优先评估 RabbitMQ；业务要求较多 FIFO、延时、事务消息特性且团队已有生态时，评估 RocketMQ；大规模事件流、数据平台、持久保留和重放，评估 Kafka。最终应以吞吐、延迟、故障演练、托管运维成本、团队经验和实际版本 PoC 决定，而不是“某个 MQ 永远更快”。

补充：RabbitMQ 也支持 Streams，Kafka 也可实现简单任务处理，表格是典型架构定位而不是产品能力的绝对边界。

5.1 RabbitMQ 交换机的四种常见路由

类型规则举例
Direct路由键精确匹配绑定键order.paid
Topic按点号分段通配：* 匹配一段，# 匹配零段及以上order.* 可匹配 order.paid
Fanout无视路由键，向所有绑定队列分发将订单事件广播给多个订阅方
Headers按头部属性进行匹配特殊属性路由，业务中相对少用

注意：RabbitMQ Topic Exchange 是路由类型，不是 Kafka Topic。

6. 实践：使用 Docker + Spring Boot 跑通 RabbitMQ

这一节建立最小可运行的“发送订单支付事件、路由到队列、Spring 监听消费”链路，沿用上文的 OrderPaid 事件。为控制示例复杂度，只配置一个接收队列；多订阅方的实际部署需要像第 3 节所述，为各业务消费者配置各自的队列和绑定。

实践边界：本节的 HTTP 接口只模拟“支付成功后发布事件”，不发起真实支付、不验证支付回调，也不更新订单数据库；不能据此认为已实现支付业务或可靠的 DB/MQ 一致性。

import org.springframework.amqp.core.*;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class RabbitConfig {
    public static final String EXCHANGE = "demo.order.events";
    public static final String QUEUE = "demo.order.paid.q";
    public static final String ROUTING_KEY = "order.paid";

    @Bean
    TopicExchange eventExchange() {
        return new TopicExchange(EXCHANGE, true, false);
    }

    @Bean
    DirectExchange deadExchange() {
        return new DirectExchange("demo.dlx", true, false);
    }

    @Bean
    Queue orderPaidQueue() {
        return QueueBuilder.durable(QUEUE)
                .deadLetterExchange("demo.dlx")
                .deadLetterRoutingKey("order.paid.dead")
                .build();
    }

    @Bean
    Queue deadQueue() {
        return QueueBuilder.durable("demo.order.paid.dlq").build();
    }

    @Bean
    Binding mainBinding(@Qualifier("orderPaidQueue") Queue orderPaidQueue,
                        TopicExchange eventExchange) {
        return BindingBuilder.bind(orderPaidQueue)
                .to(eventExchange).with(ROUTING_KEY);
    }

    @Bean
    Binding deadBinding(@Qualifier("deadQueue") Queue deadQueue,
                        DirectExchange deadExchange) {
        return BindingBuilder.bind(deadQueue)
                .to(deadExchange).with("order.paid.dead");
    }
}

如果同名队列已经存在，但类型或声明参数不同，应用重新声明可能触发 PRECONDITION_FAILED；更改拓扑时应采用明确的迁移策略。生产环境可优先评估通过 Broker Policy 配置死信参数，便于运维调整；同时应根据队列类型、版本和集群配置评估死信转移的可靠性。

import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.springframework.amqp.core.MessageDeliveryMode;
import org.springframework.amqp.rabbit.core.RabbitTemplate;
import org.springframework.web.bind.annotation.*;

import java.time.Instant;
import java.util.Map;
import java.util.UUID;

@RestController
@RequestMapping("/demo")
public class OrderController {
    private final RabbitTemplate rabbitTemplate;
    private final ObjectMapper objectMapper;

    public OrderController(RabbitTemplate rabbitTemplate,
                           ObjectMapper objectMapper) {
        this.rabbitTemplate = rabbitTemplate;
        this.objectMapper = objectMapper;
    }

    record OrderPaidEvent(
            String eventId,
            String eventType,
            int eventVersion,
            String aggregateId,
            Instant occurredAt,
            Map<String, Object> data) {}

    @PostMapping("/orders/{orderId}/paid-event")
    public String publish(@PathVariable Long orderId)
            throws JsonProcessingException {
        OrderPaidEvent event = new OrderPaidEvent(
                UUID.randomUUID().toString(),
                "OrderPaid",
                1,
                String.valueOf(orderId),
                Instant.now(),
                Map.of("orderId", orderId)
        );

        // 学习用：只发送消息，不更改订单支付状态。
        String payload = objectMapper.writeValueAsString(event);
        rabbitTemplate.convertAndSend(
                RabbitConfig.EXCHANGE,
                RabbitConfig.ROUTING_KEY,
                payload,
                message -> {
                    message.getMessageProperties()
                           .setMessageId(event.eventId());
                    message.getMessageProperties()
                           .setDeliveryMode(MessageDeliveryMode.PERSISTENT);
                    return message;
                }
        );
        return "send invoked, eventId=" + event.eventId();
    }
}

这里把 JSON 序列化后作为字符串消息发送，便于直接由下一节的 String 监听方法接收；不是完整的生产消息协议配置。每次调用演示接口都会生成新的 eventId，不能将重复请求当作同一业务事件的可靠重试。真实项目应持久化稳定事件标识，并统一配置 JSON MessageConverter、强类型 DTO、Schema 校验和版本兼容策略。

特别注意：convertAndSend() 正常返回，只表示发送方法执行完成，不能单凭它断定 Broker 已可靠保存消息，更不能断定消费者处理成功。生产环境还需处理 Publisher Confirms、不可路由消息的 Returns，以及数据库状态和事件发布的一致性。

6.6 发布确认与消息路由

RabbitMQ 可以对不可路由的消息发出 Publisher Confirm ACK。开启 mandatory 并处理 Returns，可以发现消息未路由到任何队列。消息如果进入了其他绑定的队列，或通过备用交换机完成路由，发布者可能收不到 Return。

要核对某个目标队列，先确认交换机存在、目标队列已绑定且路由键匹配，再检查消息是否已被消费者取走、过期、因容量策略被移除或进入死信队列。见 RabbitMQ 发布确认和备用交换机。

7. Kafka 的基本使用方式与 RabbitMQ 的差异

Kafka 特别值得理解的是 Partition、Consumer Group 和 Offset。仍以订单事件为例：订单服务向 order-events Topic 发布 OrderPaid，统计服务和审计服务属于两个独立的消费组。

Kafka 结构示例含义
Topicorder-events保存订单相关事件的主题
PartitionPartition 0、1、2Topic 内用于分布存储与并行消费的分区
Consumer Group Areport-service统计服务实例共同分摊各分区
Consumer Group Baudit-service审计服务独立读取相同 Topic，并维护自己的消费进度
Offset每个分区中的记录位置消费组的已提交位点标识其处理进度，不表示外部业务一定只执行一次

例如，report-service 有两个实例时，一个实例可能负责分区 0、1，另一个负责分区 2；实际分配可能随再均衡而变化。audit-service 则以另一个消费组独立读取订单事件。

同一分区内的记录按写入日志的先后排列，不同分区之间没有全局顺序。如果要求同一订单事件尽量进入同一分区，通常使用 orderId 作为消息 Key；但进入同一分区不等于整个业务处理严格有序，还需处理生产并发、重试、分区数调整和消费者业务逻辑。

8. 生产设计的重点：可靠性不是一个开关

8.1 要区分四个成功状态

  1. 业务数据提交成功：本地数据库事务已提交。
  2. Broker 确认发布：确认范围取决于产品和配置。RabbitMQ 还需核对路由结果，Kafka 需结合 acks 和副本配置判断确认范围。
  3. 消息交付成功：消费者收到某次消息投递。
  4. 业务处理成功：消费者的数据库更新或外部副作用真正生效。

这四件事可能在不同时间发生。MQ 的 ACK/Confirm 覆盖不同阶段，不能混为一谈。

8.2 三种交付语义

语义直观含义后果
At most once最多交付一次可能丢失，不重复交付
At least once至少交付一次（满足前提条件时）尽量避免丢失，但可能重复
Exactly once特定范围内恰好处理一次必须明确范围与前提；不是所有外部副作用都天然恰好一次

对于关键业务，常见务实方案是 At-least-once 投递 + 消费者幂等 + 故障补偿 + 可审计记录。

Kafka 的幂等生产者和事务能力可在 Kafka 内部的特定生产/消费处理链路上提供更强语义，但向 MySQL、HTTP、邮件系统写入时，仍需单独设计一致性和幂等性。

8.3 生产者侧如何防丢失

  • 发送前校验业务数据与消息格式，使用稳定的 eventId。
  • 配置 Broker 持久化、合适的复制/队列类型和发布确认；确认参数需结合当前产品版本。
  • 对超时、NACK、不可路由结果记录状态并按策略重试；超时不代表一定没有发送成功，重试可能导致重复消息。
  • 在业务数据库状态与事件必须一致时，使用 Transactional Outbox 等模式。

8.4 Transactional Outbox：数据库和消息之间的一致性

以 OrderPaid 为例：订单数据库已经成功把订单 1001 更新为已支付，但进程在发送 MQ 消息前崩溃。结果是订单已支付，下游却可能永远收不到支付事件。如果先发送消息、再提交数据库事务，则可能出现相反问题：下游已经看到 OrderPaid，订单状态却因事务回滚仍是未支付。

Transactional Outbox 的做法是在同一个本地数据库事务中，同时更新订单状态并写入待发布事件。事务提交后，由后台 Publisher 或 CDC 组件读取 Outbox，向 MQ 发布事件。

flowchart TD
    subgraph T[同一个本地数据库事务]
        A[更新订单支付状态] --> B[插入 OrderPaid 的 outbox_event 记录]
    end
    B --> C[事务提交]
    C --> D[Outbox Publisher / CDC]
    D --> E[(MQ)]
    E --> F[通知、积分、统计等消费者]

这样，订单状态更新与 Outbox 事件记录在本地数据库内具备原子性；它并没有让数据库事务与 MQ 发送变成一个跨系统原子事务。Publisher 仍然需要发布确认、失败重试、去重、监控和清理，否则消息仍可能积压或重复发布。

8.5 消费者幂等：防止同一事件被执行两次

假设积分服务消费 OrderPaid 后，为订单 1001 增加 100 积分。第一次消费已经成功写入积分数据库，但消费者在 ACK 前断线。Broker 随后重投递同一事件，如果没有幂等控制，积分就可能再次增加 100。

如果积分更新与去重记录在同一个关系数据库，可以设计以下表：

CREATE TABLE processed_message (
    consumer_name VARCHAR(100) NOT NULL,
    event_id      VARCHAR(64) NOT NULL,
    processed_at  DATETIME(3) NOT NULL DEFAULT CURRENT_TIMESTAMP(3),
    PRIMARY KEY (consumer_name, event_id)
);

消费者处理过程如下：

  1. 开启数据库事务，尝试插入 (consumer_name, event_id)。
  2. 如果唯一键冲突且确认是已处理的同一事件，终止重复业务操作；其他数据库异常不可误当作重复消息。
  3. 首次处理时，校验订单或积分业务约束，并更新积分账户。
  4. 在同一数据库事务中提交去重记录和积分变更；事务失败时一同回滚。
  5. 数据库提交成功后，再完成消息 ACK 或符合框架约定的位点提交。

这样同一消费者的重复投递不会重复执行这次数据库内的积分变更。不能只使用单机内存 Set，也不能依赖简单的“先查询再插入”，因为并发和进程重启都可能让这些方法失效。

对于发送邮件、调用支付网关等数据库之外的副作用，还需要目标系统支持幂等键，或设计专门的业务状态机；本地去重表不能自动消除所有外部调用失败窗口。

8.6 消息顺序：明确顺序作用于什么范围

同一个订单可能依次发生 OrderCreated(v1)、OrderPaid(v2)、OrderShipped(v3)。消息先进入 Broker，不代表多个消费者最终写入的数据一定按这个顺序生效。并行生产、分区、消费者并发、超时、重试和死信重放都可能破坏业务观察到的处理顺序。

常见思路是按 aggregateId（订单 ID）选择相同分区、队列或 MessageGroup；在需要顺序的范围控制并发，并在业务事件中携带单调递增的订单版本号。

例如，统计服务收到 OrderPaid(v2) 时仍未处理 OrderCreated(v1)，可按业务需要延迟重试、主动读取订单最新状态，或使用快照与版本校验收敛；不能直接无条件覆盖旧状态。不同产品的严格顺序条件不同，应依据具体版本和消费模式验证。

8.7 重试和死信：先分类错误，再决定行动

失败类型建议策略
数据库短暂不可用、网络抖动有界重试 + 退避 + 抖动
下游限流、服务过载降低并发、延时重试、背压
消息字段不合法/版本不兼容直接隔离到错误队列/死信，通知负责人
业务状态不满足处理条件区分暂时未满足与永久非法，不能盲目无限重试
消费已成功但确认丢失依赖幂等安全重投递

不要让失败消息立即入原队列无限循环；会形成“毒消息”风暴。死信队列需要明确所有者、告警阈值、定位信息、修复和重放流程；重放必须继续遵守幂等和顺序约束。

8.8 削峰与背压：队列不是无限蓄水池

速率相对稳定时，可以用 积压增长速率 = max(0, 生产速率 - 有效消费速率) 估算峰值期间新增的消息积压。

假设大促期间订单事件峰值生产速率为 2,000 条/秒，统计服务的稳定有效消费速率为 1,200 条/秒，峰值持续 10 分钟，则该订阅队列约新增 800 × 600 = 480,000 条积压（忽略重试及消息大小变化）。峰值结束后能否消化取决于后续消费余量。要同时设置入口限流、队列容量/保留策略、消费者横向扩容和积压告警。

10. 与数据库、Redis、Canal、定时任务有什么关系？

  • 数据库：保存权威业务状态。MQ 传递动作/事件，通常不代替业务数据的持久存储。
  • Redis：可作为缓存、轻量队列或 Streams 使用，但其交付语义、持久化、消费组、运维与成熟 MQ 产品不同；不能把 Redis List 和可靠事务消息视为等价。
  • Canal / Debezium（CDC）：读取数据库变更日志，向下游同步数据变更；MQ 可作为 CDC 下游通道。业务事件最好通过明确的契约或 Outbox 表表达，不应直接用任意字段变化推断业务事实。
  • 定时任务：按时间触发检查；延时消息也可能承担触发角色。无论采用哪种方式，最终执行前都要重新校验业务状态。
  • HTTP/gRPC：同步查询、需立即返回结果的操作仍适用；MQ 和同步 RPC 是互补关系。

如果需要把订单支付状态同步到搜索服务，可以由业务代码可靠发布 OrderPaid 事件，也可以使用 CDC 同步订单表的增量变更。前者表达“订单已支付”的业务事实，后者更适合数据复制和集成。数据库某字段发生变化，不必然等同于一个完整的业务事件；不能因为已有 Canal，就默认所有业务流程都应该由表变更触发。

11. 上线前检查：把“能运行”变成“可交付”

11.1 业务契约

  • 定义事件名称、生产时机、状态变化和消费者责任。
  • 明确数据一致性目标：实时、秒级最终一致还是可延迟补偿。
  • 有稳定消息 ID、关联 ID、版本和 Schema 兼容策略。
  • 判断重复处理、乱序处理可能造成的业务后果。

11.2 消息可靠性

  • 业务事务与消息发布之间的失败窗口有处理方案。
  • 发布确认、不可路由、消息持久化和副本策略经过验证。
  • 消费 ACK/位点提交发生在正确业务处理边界。
  • 消费者幂等、重试次数、死信隔离、人工重放都有方案。
  • 消费服务停机/重启/故障恢复时不会静默丢失关键任务。

11.3 性能与运维

  • 压测正常、峰值和下游故障时的吞吐、延迟、积压增长。
  • 定义消息端到端延迟 SLO（如 P95/P99）、积压容量和可接受恢复时间。
  • 监控生产失败、消费失败、重试、死信、积压量/积压时间、CPU、内存、磁盘和复制健康度。
  • 明确消息保存时长、容量配额、敏感数据权限和清理机制。
  • 设计鉴权、最小权限、TLS、网络隔离及密钥轮换。

11.4 故障演练

建议至少做五个实验：

  1. 消费者业务成功后、ACK 前退出：确认重复投递不会重复执行业务。
  2. 业务 DB 提交后、消息发送前退出：验证 Outbox/可靠发布机制。
  3. Broker 暂不可用：确认生产接口行为与重试策略符合预期。
  4. 持续发送无效消息：确认重试有界、死信与告警正常。
  5. 消费者速度小于生产速度：确认背压、积压告警及恢复能力。

这些实验比只验证“控制台能收到消息”更能说明设计是否可靠。

12. 常见误区与排障思路

误区 1：消息已经发出去 = 整条链路成功。

要分别验证生产者确认、路由、消息保存、消费者业务事务和最终 ACK。

误区 2：只要开了持久化就不会丢消息。

持久化需要结合发布确认、队列/分区复制与故障条件。未收到确认的发送和未建立一致性保障的业务事件仍可能出问题。

误区 3：MQ 保证 Exactly Once，所以不用幂等。

必须先问“Exactly Once 的边界是什么”。数据库/HTTP/第三方外部副作用通常仍需业务幂等。

误区 4：消费者越多吞吐就一定越高。

Kafka 同组分区数限制有效并行消费单元；RabbitMQ 还受 Prefetch、负载公平性和后端处理容量限制。数据库热点、锁竞争和限流都可能成为瓶颈。

误区 5：消息积压直接清空队列就能恢复。

清空可能丢失未处理业务。先隔离异常流量、确认消费者状态、估算积压价值和恢复时间，再制定回放或废弃方案并获得业务授权。

排障顺序：先定位一条 eventId 的完整路径，检查生产日志 → Broker 主题/路由/队列 → 消费者是否在线 → ACK/位点和错误日志 → 业务数据库效果 → 重试/死信；随后扩大到批量指标，判断是单消息问题还是系统性容量问题。
