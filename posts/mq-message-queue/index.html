1. 为什么需要消息队列

1.1 从一次普通 HTTP 请求说起

假设组织管理系统完成一次组织架构调整后，需要：

  • 更新组织数据；
  • 发送审批结果通知；
  • 同步搜索索引；
  • 更新统计报表。

该模式简单直接，但存在三个典型问题：

  1. 响应时间叠加：如果通知耗时 200 ms、索引耗时 300 ms、报表耗时 500 ms，且按顺序执行，额外等待时间就可能达到 1 s。
  2. 服务耦合：组织服务必须知道多个下游系统及其接口。一旦某个下游不可用，需要处理超时、降级和失败补偿。
  3. 流量冲击：某一时段突然出现大量组织变更，数据库或下游服务可能无法承受瞬时并发。

在正确设计事务一致性的前提下，接口可以先完成核心业务并返回；后续非关键动作由消费者异步执行。

1.2 消息队列到底是什么

消息队列（Message Queue，MQ）是一类用于应用之间异步传递消息的基础设施。 在常见架构中，生产者将消息交给消息中间件（Broker），消费者从中接收或读取消息并执行业务处理。

最简模型：

1

Producer（生产者）──► Broker / Queue ──► Consumer（消费者）
  • Producer：构造并发布消息，例如组织服务。
  • Broker：接收、存储、路由和分发消息，例如 RabbitMQ 或 Kafka Broker。
  • Consumer：读取消息并执行业务逻辑，例如通知服务。
  • Message：承载业务事件或任务的数据，通常包含消息 ID、业务 ID、事件类型、发生时间、版本与数据载荷。

注意：消息队列是概念总称；RabbitMQ 的队列模型、Kafka 的分区日志模型、RocketMQ 的消息模型并不完全相同，不能把它们都理解成“一个先进先出的列表”。

1.3 主要价值与代价

价值对应机制典型场景
异步处理把非核心操作移到消费端发送通知、生成文件
系统解耦生产者不必同步调用每个订阅方业务事件通知多个系统
削峰缓冲消息先积累，消费者按能力处理批量导入、短时高峰
故障隔离下游暂时不可用时可延后处理搜索索引更新
扩展订阅方增加新的消费者而不改生产者核心逻辑审计、分析

使用 MQ 同时引入了新的系统复杂度：消息可能重复、延迟或乱序；消息生产与数据库事务可能不一致；消费者可能积压；Broker 也需要部署、监控和治理。

因此，不是所有任务都应该异步。用户必须立即知道结果、且执行成功是主业务提交必要条件的操作，通常不能简单地移到 MQ 后就直接返回成功。

需要区分三个不同的“成功”：

  1. 生产者调用发送 API 未报错：只能说明本地调用按预期执行，不必然代表 Broker 已收到消息。
  2. Broker 确认发布：表明消息已按对应 Broker 的确认语义被接受，但不说明消费者处理成功。
  3. 消费者业务处理成功：需要业务逻辑完成，并在适当时机确认消息或提交消费进度。

后续可靠性设计基本都围绕这三个阶段展开。

2.3 RabbitMQ 的 Exchange、Queue、Binding

下面用 RabbitMQ 和 Kafka 对照说明：不同消息系统如何组织消息，以及多个消费者如何分工。

RabbitMQ 基于 AMQP 0-9-1 使用时，典型投递链路是：

1

生产者 ─► Exchange（交换机） ──Binding / Routing Key──► Queue ─► 消费者

生产者一般把消息发布到 Exchange，交换机依据绑定规则把消息路由到一个或多个 Queue；消费者从 Queue 取消息。同一消息也可能路由到多个队列。

常见交换机：

类型路由规则例子
directRouting Key 精确匹配 Binding Keyorg.change.completed
topic单词模式匹配：* 匹配一个单词，# 匹配零个或多个单词org.*、org.#
fanout忽略 Routing Key，广播至绑定队列通知多个独立系统
headers根据消息头属性路由特殊多条件路由

消费竞争与广播要区分：同一个 Queue 上的多个竞争消费者，一条投递通常交给其中一个消费者；若希望通知服务、报表服务分别收到同一事件，应该配置不同的 Queue 并进行相应绑定。

2.4 Kafka 的 Topic、Partition、Offset、Consumer Group

Kafka 更接近可持久保存、可按位置读取的分区追加日志：

                   Topic: org-events
                     ┌───────────────┐
生产者 ── key=A ───► │ Partition 0   │  offset: 0,1,2,3...
        ── key=B ───► │ Partition 1   │  offset: 0,1,2,3...
                     └───────────────┘
                              │
                  ┌───────────┴───────────┐
                  ▼                       ▼
           Group: notification     Group: analytics
           各自维护消费位置          各自维护消费位置
  • Topic：逻辑消息主题。
  • Partition：Topic 的分区，是并行读写和顺序保证的重要单位。
  • Offset：记录在某个分区内的位置；消费组维护已提交的消费位置。
  • Consumer Group：一组协作消费同一订阅的消费者。传统消费组内，一个分区在同一时刻通常分配给一个成员；不同组独立消费同一 Topic。
  • Retention：消息由保留策略控制生命周期，不会因为某个消费组读过就立即删除。

举例：一个 Topic 有 4 个分区，同一个传统消费组有 2 个消费者时，通常各消费 2 个分区；如果增加到 6 个消费者，通常仍只有最多 4 个消费者有该 Topic 分区可消费。消费并发能力受分区数量、分配方式及业务处理模型限制。

Kafka 还提供不同于传统 Consumer Group 的 Share Group 等机制；本指南入门部分讨论最常见的传统消费组模型。

3. 消息模型与基础实践

3.1 任务队列：多个 Worker 分摊任务

1
2
3

                         ┌─► Worker A
生产者 ─► 任务队列 ──────────┼─► Worker B
                         └─► Worker C

同一任务通常只应由一个 Worker 完成，但失败后可能重新投递；例如导出报表、图片处理、邮件发送。

3.2 发布/订阅：一个业务事件触发多个订阅方

1
2
3
4

组织服务 ─► org.change.completed
                    ├─► 通知服务
                    ├─► 审计服务
                    └─► 搜索服务

RabbitMQ 通常为每个独立订阅方建立独立 Queue；Kafka 通常为每个独立订阅方使用独立 Consumer Group。

3.3 事件通知与异步命令的区别

  • 事件：OrgChangeCompleted，表达“组织调整已完成”，不强制某个消费者存在。
  • 命令：GenerateReport，表达“请生成报表”，常由指定服务负责处理。

事件偏向发布既成事实，命令偏向指定执行动作。区分两者有助于明确责任、失败处理和消息契约。

3.4 延迟任务

例如订单创建后 30 分钟仍未付款则尝试关闭。到达延迟时间不意味着业务条件仍成立：消费者必须再次查订单状态，并通过条件更新或其他并发控制阻止误关闭已付款订单。

3.5 批量与削峰

如果瞬间来了 10,000 个任务，而消费端每秒只能完成 500 个，消息队列可以暂时承接积压。但当生产速度长期超过消费速度时，积压会持续增长，最终受到存储、保留策略和资源限制影响。MQ 只能缓冲突发流量，不会凭空提高下游的长期处理能力。

3.7 发布并取出第一条消息

通过管理页面完成以下操作：

  1. 进入 Queues and Streams，在虚拟主机 / 中创建名为 learning.hello 的队列，类型选择 Classic，其他选项保持默认。
  2. 打开该队列的详情页，在 Publish message 区域的消息体中输入 hello mq，然后发布。
  3. 暂不取出消息，等待统计刷新，观察 Ready 变为 1。此时消息保存在队列中，尚未被消费。
  4. 在 Get messages 区域设置读取 1 条消息，确认模式选择 Automatic ack，然后取出消息。页面应显示消息体 hello mq。
  5. 等待统计刷新，确认 Ready 回到 0；再次取消息，应显示队列为空。

这里由管理页面代替应用程序完成发布和取消息。页面中的 Automatic ack 会使取出的消息被移出队列；生产消费者则需要按业务处理结果决定何时确认。

这个实验对应前文的最简模型：发布消息 → 队列保存 → 消费者取出并确认。如果消息体可以读到，且确认后队列恢复为空，就完成了一次基本收发。接下来需要进一步考虑：发送时断网怎么办、处理失败怎么办，以及同一消息被处理两次会怎样。

4. RabbitMQ、Kafka、RocketMQ 如何选

下面是技术特征层面的比较，并非绝对性能排名。不同版本、部署规模、消息大小、持久化策略和客户端参数都会影响实际表现。

维度RabbitMQ（典型队列模式）Kafka（传统消费组）RocketMQ
核心模型Exchange 路由 + Queue分区日志 + OffsetTopic、队列/消息组等
擅长场景业务任务、路由、复杂消费控制高吞吐事件流、日志、数据管道、可回放数据业务事件、延时消息、顺序消息、事务消息
消费进度消费确认 ACK提交 Offset由消费模式与客户端机制管理确认/进度
消息回放传统队列确认后通常无法回放；Streams 是另一种模型在保留期内可按 Offset 重读在保留与消费机制允许的范围内可重读
路由Direct / Topic / Fanout 等交换机Topic + PartitionTopic + 过滤 / 消息类型等
顺序性受多消费者、重投递等影响主要保证分区内日志顺序支持按消息组进行 FIFO 顺序处理
延时能力可用 TTL+DLX、特定队列能力或插件等方式实现，注意版本差异通常在应用层或配套系统实现具有专门的定时/延时消息机制

入门建议：

  1. 首先用 RabbitMQ 理解生产、路由、消费、ACK、死信与重试：概念直观，便于建立可靠性模型。
  2. 接着学习 Kafka 的分区、Offset、消费组、重平衡、重放和日志保留：理解日志型消息系统的设计取舍。
  3. 如果业务中实际使用 RocketMQ，深入学习顺序消息、定时消息、事务消息及其版本差异。

选型时优先核实组织现有基础设施、团队运维经验、消息量、可回放需求、延时需求、一致性要求及故障恢复目标。不要仅根据“谁的吞吐量更高”决定。

5. 消息可靠性：如何降低丢失风险

“消息发送了”并不等于“消息一定会被正确处理”。可靠性至少要分生产端、Broker 和消费端三个阶段考虑。

5.1 生产端：发送成功如何确认

可能出现如下情况：

1
2

Producer ──发送消息──► Broker
Producer ◄──确认响应── Broker

如果网络在“Broker 已接收、Producer 尚未收到确认”时断开，Producer 不知道消息是否成功。这是分布式系统中典型的结果不确定问题。贸然重试可能带来重复消息；不重试则可能丢消息。

在 RabbitMQ 中：

  • Publisher Confirm：确认消息已按 Broker 对应的发布确认规则被处理。
  • Publisher Return + mandatory：帮助发现消息到达交换机后无法路由到目标队列的情况。
  • 持久化消息 + 持久化队列：有助于应对重启，仍需结合确认、存储机制和副本配置评估实际数据安全性。

Publisher Confirm 对应第 2.1 节的发布成功，Consumer ACK 对应消费阶段的确认；排障时需要分别检查。

在 Kafka 中，可关注 acks、生产者幂等性、重试配置、分区副本与 ISR、最小同步副本数等条件。不能单凭某一项配置就宣布“绝对不会丢消息”。

5.2 Broker：存储、复制与高可用

需要理解四个问题：

  1. 消息是只存在内存、已写入持久存储，还是按副本同步策略被确认？
  2. 节点宕机时，是否还有可接管的有效副本？
  3. 磁盘耗尽、流控、超过保留期或队列长度限制时如何处理？
  4. 路由失败、死信转发失败、过期删除时是否能够观测到？

在 RabbitMQ 中，业务可靠队列可以结合部署要求评估 Quorum Queue 等方案；在 Kafka 中要评估副本数、ISR 和确认策略。单机 Docker 教学环境不能代表生产高可用。

5.3 消费端：先处理业务，后确认消息

可靠消费的基本次序：

1

取得消息 → 校验消息 → 执行业务 → 本地事务提交 → ACK

如果先 ACK 后执行业务，业务处理期间宕机就可能丢失这次处理机会。

如果先处理并提交，再 ACK，宕机发生在两者之间，Broker 可能重新投递，所以消费者必须能够应对重复。

RabbitMQ 的 ACK 和 Kafka 的 Offset 提交不是同一个协议机制，但在失败恢复上的设计思想相似：都需要把“什么时候算处理完成”定义清楚。

5.4 故障时序速查

故障位置可能后果常用处理
发送请求未到 Broker消息未入队发送重试、持久化待发送记录
Broker 收到，确认响应丢失发送方不确定；重试可能重复发布确认、事件 ID、消费者幂等
Exchange 无匹配队列可能无法投递到预期消费者mandatory/Return、路由检查
消费者收到但尚未执行业务就 ACK业务可能永远不执行在业务成功后确认
业务已提交，ACK 之前进程宕机消息可能重投幂等处理
消费持续失败反复重试或积压有界重试、退避、死信与人工处置

6. 重复消费、幂等与投递语义

6.1 三种常见语义

语义直观理解主要权衡
At-most-once（至多一次）可能丢失，但不主动重投性能和简单性优先，不适合不能丢的核心事件
At-least-once（至少一次）在满足系统可靠性条件下重试送达，但可能重复需要消费者幂等
Exactly-once（恰好一次）在明确界定的处理范围内使结果只生效一次往往需要事务、去重或与外部系统配合

不要把 Broker 宣称的 Exactly-once 直接理解为“数据库、短信、第三方 HTTP 调用等所有副作用天然只执行一次”。例如 Kafka 在 Kafka 内部的事务性读取、处理、写入链路能提供特定的一次性语义；写到外部数据库仍需与该系统协调。

6.2 什么是幂等

如果同一个事件被处理两次，最终业务结果与处理一次相同，就称这种业务处理具有幂等性。

例如：

  • 将订单状态设置为 PAID，在合理的状态校验下容易做成幂等。
  • 账户余额增加 100 元，如果无去重，执行两次就会多加 100 元。
  • 发送短信，并非天然幂等；即使本地防重成功，外部调用超时也会产生“发送结果未知”的问题。

核心条件是去重记录与业务数据库修改在同一个本地事务中提交。否则“先写去重记录、业务失败”可能使后续重试被错误跳过。

还要考虑：

  • 同一个事件由多个不同业务消费者消费时，去重键应包含 consumer_name 或订阅逻辑标识。
  • 不同消息版本是否共用事件 ID，要由业务事件契约明确。
  • 去重记录要有可管理的保留周期，但不能短于可能发生的重复投递窗口，否则旧消息重放仍可能重复生效。
  • 涉及跨库、远程 API、资金与外部副作用时，仅靠这张表不能自动实现端到端 Exactly-once，需要目标系统的幂等键、事务边界或补偿机制。

7. 消息顺序、并发与积压

7.1 为什么“按顺序发送”不等于“按顺序生效”

例如依次发送：

1

组织创建 → 组织负责人变更 → 组织撤销

如果由多个消费者并发处理，或前一个事件失败重试而后一个事件先成功，最终业务生效顺序就可能被打乱。

7.2 局部顺序比全局顺序更常见

业务通常只需要同一个实体的事件有序。例如不同部门可以并行处理，同一个部门的变更需要按版本顺序执行。

Kafka 常见方案：

  1. 按 orgId 选择消息 Key，让同一个 orgId 的消息在分区策略保持稳定时进入同一分区。
  2. 对同一分区内需要严格顺序处理的记录，避免不受控的并发执行与异步提交。
  3. 使用业务版本号或状态机校验，防止重试、补发和分区数变更等场景导致错误覆盖。

RabbitMQ 和 RocketMQ 也应按照自身队列模型和顺序消息机制设计；不能简单认为“FIFO 队列”足以保证最终数据库更新严格有序。

7.3 消息积压如何分析

定义一个简化指标：

1

净积压变化率 ≈ 生产速率 - 消费成功速率

例如每秒新增 800 条、实际成功消费 500 条，积压平均每秒增加约 300 条。持续 10 分钟，会新增约 180,000 条待处理消息（忽略重试和其他变化）。

常见原因：

  • 下游 MySQL、Redis、HTTP API 变慢；
  • 消费者实例不足或某些分区热点严重；
  • 大量异常消息导致重试占用消费能力；
  • 单条消息处理过慢、批量参数不合理；
  • 消费线程、连接池或数据库连接数耗尽。

治理顺序：先确认生产速率、消费成功速率、失败率、延迟与热点，再决定优化业务耗时、扩容、调整分区/并发或限流。仅扩大消费者线程数，可能把压力转移到下游并引发更严重的故障。

8. 失败重试、延迟消息和死信队列

8.1 临时失败与永久失败

  • 临时失败：网络超时、下游瞬时不可用、数据库短暂拥堵。通常适合有限次数重试。
  • 永久失败：数据格式不合法、关键字段缺失、业务状态不允许。重复尝试通常没有意义，应记录原因并进入异常处置流程。

8.2 为什么不能无限立即重试

如果消息每次消费都失败，消费者立即 NACK 并重新入队，可能形成高频循环：

1

取消息 → 执行失败 → requeue=true → 再取消息 → 再失败 → ...

这会占满消费资源、刷爆日志，甚至持续冲击本来已经过载的下游系统。

更合理的是：最大次数限制 + 退避间隔 + 死信/隔离队列 + 告警 + 人工或自动恢复机制。

一个应用层重试计划示例（非默认产品行为）：

1
2
3
4

第一次失败 → 10 秒后重试
第二次失败 → 1 分钟后重试
第三次失败 → 5 分钟后重试
仍失败 → 死信队列 / 失败任务表

通常还会引入随机抖动，避免大量消息在同一时刻再次冲击下游。

8.3 什么是死信队列（DLQ）

死信队列用于集中存放无法正常完成处理、需要后续检查的消息。RabbitMQ 的 Dead Letter Exchange（DLX） 是死信转发所用交换机；具体存放消息的仍是绑定到 DLX 的队列。

可能产生死信的场景包括消费者拒绝且不重新入队、消息 TTL 过期、队列长度限制以及 Quorum Queue 投递次数超过限制等；具体受队列类型和版本影响。

1

主业务 Queue ──消费失败 / nack(requeue=false)──► DLX ─► Dead Letter Queue

注意：死信转发本身也涉及可靠性。RabbitMQ 官方说明，部分默认死信转发配置并不提供跨队列转发的严格确认；对要求高的场景应评估 Quorum Queue 的 at-least-once dead-lettering 等策略。

8.4 延迟消息与定时消息

应用示例：组织变更审批超时检查、订单超时、延迟通知。

不同 MQ 的实现不同：

  • RabbitMQ：可使用 TTL + DLX 等方案，但要考虑队头阻塞、队列模式和版本差异；新版本的 Quorum Queue 也有专门的延迟重试能力。
  • RocketMQ：提供专门的延迟/定时消息机制，时间参数和消息类型必须按实际版本的官方要求设置。
  • Kafka：延迟调度通常通过业务调度系统或配套主题、状态存储实现，不宜直接假设 Topic 自带通用定时投递。

9. 数据库事务与消息一致性

9.1 最容易踩的坑：数据库成功，消息没有发出去

1
2
3
4
5

@Transactional
public void completeOrgChange(...) {
    updateDatabase();
    rabbitTemplate.convertAndSend(...);
}

上面的 @Transactional 一般只管理其配置的数据库事务，并不会天然将 MySQL 与 MQ 发送纳入同一个原子事务。

可能出现：

  • MySQL 已提交，但随后消息发送失败；
  • 消息已成功发送，但本地数据库事务最终回滚；
  • 网络超时导致生产者无法判定 Broker 是否接收，重试可能造成重复。

9.2 Transactional Outbox（本地消息表）

通过数据库同一个事务，把业务更新和待发送事件一起提交。

                     同一个 MySQL 事务

业务请求 ────────►│ 更新业务表             │
                 │ INSERT outbox_event   │
                 └───────────────────────┘
                            │ COMMIT
                            ▼
                   异步发布器扫描 / CDC
                            │
                            ▼
                           MQ
                            │
                            ▼
                     消费者幂等处理

简化表结构：

1
2
3
4

7
8

10

CREATE TABLE outbox_event (
    id BIGINT PRIMARY KEY AUTO_INCREMENT,
    event_id VARCHAR(64) NOT NULL UNIQUE,
    event_type VARCHAR(128) NOT NULL,
    payload JSON NOT NULL,
    status VARCHAR(20) NOT NULL DEFAULT 'PENDING',
    created_at DATETIME NOT NULL DEFAULT CURRENT_TIMESTAMP,
    sent_at DATETIME NULL,
    KEY idx_outbox_status_time (status, created_at)
);

核心流程：

  1. 业务服务在 MySQL 事务内修改业务表，同时写入 outbox_event。
  2. 独立发布器扫描未发送记录，或通过 CDC 捕获新事件；向 MQ 投递。
  3. 得到必要的 Broker 确认后，更新消息表状态；如果响应丢失或更新状态失败，则可能重复发送。
  4. 消费者用 eventId 做幂等处理。

这个方案的目标是业务数据与待发送事件不会出现“只提交一边”的状态，它并不消除重复发布。实际生产还要实现并发任务领取、锁或租约、重试状态、故障恢复、历史清理、失败告警及数据校验。

9.3 事务消息与 CDC 的边界

  • RocketMQ 事务消息：依赖半事务消息、本地事务执行及事务状态回查等机制，适合相应的业务一致性需求，但并不意味着所有下游处理自动纳入同一事务。
  • CDC（Change Data Capture）：例如读取 MySQL Binlog 的变更捕获体系，常用于数据同步，也可作为 Outbox 事件转发的一部分。
  • Canal：可用于解析 MySQL 增量变更，但“监听到某张表变化”与“获取经过设计的业务事件”不是同一个概念。若用于业务集成，应明确事件语义、初始快照、重复投递、位点管理和故障恢复等问题。

选择哪种方案，取决于现有 MQ、数据库、部署复杂度和业务对延迟及一致性的要求。

package com.example.mqlearning;

import org.springframework.amqp.core.Binding;
import org.springframework.amqp.core.BindingBuilder;
import org.springframework.amqp.core.DirectExchange;
import org.springframework.amqp.core.Queue;
import org.springframework.amqp.core.QueueBuilder;
import org.springframework.beans.factory.annotation.Qualifier;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;

@Configuration
public class RabbitTopology {
    public static final String EXCHANGE = "org.events";
    public static final String QUEUE = "org.change.completed.q";
    public static final String ROUTING_KEY = "org.change.completed";

    public static final String DLX = "org.dlx";
    public static final String DLQ = "org.change.failed.q";
    public static final String DLQ_KEY = "org.change.failed";

    @Bean
    DirectExchange orgExchange() {
        return new DirectExchange(EXCHANGE, true, false);
    }

    @Bean
    DirectExchange deadLetterExchange() {
        return new DirectExchange(DLX, true, false);
    }

    @Bean
    Queue orgQueue() {
        return QueueBuilder.durable(QUEUE)
                .deadLetterExchange(DLX)
                .deadLetterRoutingKey(DLQ_KEY)
                .build();
    }

    @Bean
    Queue deadLetterQueue() {
        return QueueBuilder.durable(DLQ).build();
    }

    @Bean
    Binding orgBinding(@Qualifier("orgQueue") Queue orgQueue,
                       @Qualifier("orgExchange") DirectExchange orgExchange) {
        return BindingBuilder.bind(orgQueue).to(orgExchange).with(ROUTING_KEY);
    }

    @Bean
    Binding deadLetterBinding(@Qualifier("deadLetterQueue") Queue deadLetterQueue,
                              @Qualifier("deadLetterExchange") DirectExchange deadLetterExchange) {
        return BindingBuilder.bind(deadLetterQueue)
                .to(deadLetterExchange).with(DLQ_KEY);
    }
}

这里用 Queue 声明参数指定 DLX，只是为了让入门实验自包含。RabbitMQ 官方建议在生产中优先考虑Policy 管理死信路由，避免硬编码队列参数导致后续变更必须重新声明队列。

package com.example.mqlearning;

import com.fasterxml.jackson.core.JsonProcessingException;
import com.fasterxml.jackson.databind.ObjectMapper;
import org.springframework.amqp.rabbit.connection.CorrelationData;
import org.springframework.amqp.rabbit.core.RabbitTemplate;
import org.springframework.stereotype.Service;

import java.time.Instant;
import java.util.UUID;
import java.util.concurrent.TimeUnit;

@Service
public class OrgEventPublisher {
    private final RabbitTemplate rabbitTemplate;
    private final ObjectMapper objectMapper;

    public OrgEventPublisher(RabbitTemplate rabbitTemplate,
                             ObjectMapper objectMapper) {
        this.rabbitTemplate = rabbitTemplate;
        this.objectMapper = objectMapper;
    }

    public String publish(String orgId, String changeType) throws Exception {
        OrgChangedEvent event = new OrgChangedEvent(
                UUID.randomUUID().toString(), orgId, changeType, Instant.now());

        String json = toJson(event);
        CorrelationData correlationData = new CorrelationData(event.eventId());

        rabbitTemplate.convertAndSend(
                RabbitTopology.EXCHANGE,
                RabbitTopology.ROUTING_KEY,
                json,
                correlationData
        );

        // 教学演示：同步等待 Broker 确认，便于区分“调用成功”和“发布确认”。
        // 高吞吐生产环境通常应考虑异步确认，而非每条消息阻塞等待。
        CorrelationData.Confirm confirm =
                correlationData.getFuture().get(5, TimeUnit.SECONDS);

        if (!confirm.isAck()) {
            throw new IllegalStateException(
                    "Broker rejected publish: " + confirm.getReason());
        }
        if (correlationData.getReturn() != null) {
            throw new IllegalStateException("Message was not routed to a queue");
        }
        return event.eventId();
    }

    private String toJson(OrgChangedEvent event)
            throws JsonProcessingException {
        return objectMapper.writeValueAsString(event);
    }
}

等待确认超时时，发布结果仍可能不确定，不能直接判定消息未送达。恢复与重试的处理方式见第 5.1 节。

    public OrgChangeController(OrgEventPublisher publisher) {
        this.publisher = publisher;
    }

    public record CompleteRequest(String orgId, String changeType) {}

    @PostMapping("/complete")
    public ResponseEntity<Map<String, String>> complete(
            @RequestBody CompleteRequest request) throws Exception {
        String eventId = publisher.publish(request.orgId(), request.changeType());
        return ResponseEntity.accepted().body(Map.of(
                "eventId", eventId,
                "status", "PUBLISHED_TO_BROKER"
        ));
    }
}

这里的 HTTP 202 表示已通过发布确认和不可路由检查；消费结果需要在后续步骤中通过日志和队列状态验证。

package com.example.mqlearning;

import com.fasterxml.jackson.databind.ObjectMapper;
import com.rabbitmq.client.Channel;
import org.slf4j.Logger;
import org.slf4j.LoggerFactory;
import org.springframework.amqp.core.AmqpHeaders;
import org.springframework.amqp.rabbit.annotation.RabbitListener;
import org.springframework.messaging.handler.annotation.Header;
import org.springframework.stereotype.Component;

@Component
public class OrgEventConsumer {
    private static final Logger log = LoggerFactory.getLogger(OrgEventConsumer.class);
    private final ObjectMapper objectMapper;

    public OrgEventConsumer(ObjectMapper objectMapper) {
        this.objectMapper = objectMapper;
    }

    @RabbitListener(queues = RabbitTopology.QUEUE)
    public void consume(String body, Channel channel,
                        @Header(AmqpHeaders.DELIVERY_TAG) long deliveryTag)
            throws Exception {
        try {
            OrgChangedEvent event =
                    objectMapper.readValue(body, OrgChangedEvent.class);

            if ("FAIL".equalsIgnoreCase(event.changeType())) {
                throw new IllegalStateException("Simulated processing failure");
            }

            // 真实项目应在这里完成业务处理与数据库事务提交，
            // 并在提交成功后确认；日志输出仅用于本地演示。
            log.info("Processed eventId={}, orgId={}, changeType={}",
                    event.eventId(), event.orgId(), event.changeType());

        } catch (Exception ex) {
            log.error("Failed to consume, deliveryTag={}", deliveryTag, ex);
            // requeue=false：不立即回到主队列，而是按死信规则转发。
            // 演示环境的本次错误不做中间重试。
            if (channel.isOpen()) {
                channel.basicNack(deliveryTag, false, false);
            }
            return;
        }
        // 只在业务处理成功后 ACK，ACK 自身失败时让容器/连接恢复机制处理。
        channel.basicAck(deliveryTag, false);
    }
}

入门阶段需要认识两件事：

  1. basicAck(tag, false) 表示确认本次投递；basicNack(tag, false, false) 表示拒绝且不重新入主队列。因为已经绑定 DLX，拒绝的消息会尝试死信转发。
  2. 这里统一捕获异常并直接死信是有意简化。生产环境应区分临时和永久失败，处理确认失败、连接中断、消费者重启、有界重试和死信转发可靠性，不应让所有异常都直接进入 DLQ。

11. 生产环境设计与排障

11.1 上线前需要逐项确认

方面应确认的问题
消息契约消息类型、版本、业务键、幂等键、兼容策略是否明确？
生产可靠性是否有确认、不可路由处理、失败重试和不确定状态恢复？
存储可靠性消息/队列持久化、副本、磁盘容量与消息保留策略是否满足要求？
消费可靠性ACK 或 Offset 提交时机是否在业务提交之后？
幂等性重复消费是否会重复扣款、重复创建、重复发通知？
顺序是否要求同实体有序？有无业务版本或状态校验？
失败恢复重试上限、退避、DLQ、人工补偿与重新投递流程是否明确？
一致性DB 和 MQ 的双写问题是否有 Outbox、事务消息或其他可验证方案？
安全连接是否鉴权、最小权限、加密传输；消息是否包含敏感信息？
观测业务日志、事件 ID、追踪链路、积压、消费失败率、延迟与告警是否齐全？

11.2 应重点关注的监控指标

RabbitMQ 常见指标：

  • Queue Ready：队列中等待投递的消息数；
  • Queue Unacked：已投递但尚未确认的消息数；
  • Publish / Deliver / Ack rate：生产、投递和确认速率；
  • Consumer count：消费实例/订阅者数量；
  • 连接数、Channel 数、内存水位、磁盘水位、节点健康状态；
  • DLQ 消息数量及异常原因分布。

Kafka 常见指标：

  • Consumer Lag：消费组与日志最新可读位置之间的差距；
  • Lag 增长趋势与消息处理耗时；
  • 分区热点、消费组重平衡频率；
  • 生产请求错误、重试、确认延迟；
  • Broker、副本状态、ISR 和存储压力。

不要把“积压条数”直接当成“积压时长”；应结合实际消费速率、最老待处理消息时间和队列/分区特性判断。

11.3 遇到“消费者没收到消息”时如何排查

按照链路从前到后：

  1. 生产端：是否发出了消息？有没有异常、超时、Broker NACK 或 Return？
  2. 路由层：Exchange/Topic 是否正确？Routing Key、Binding、分区 Key 是否匹配？
  3. 存储层：队列是否存在？是否过期、达到限制或被策略转移？
  4. 消费端：订阅队列/Topic 是否正确？消费者在线吗？是否有权限和连接异常？
  5. 处理层：消息是否已经投递但尚未 ACK？业务代码是否抛异常？
  6. 异常通道：DLQ、失败任务表或重试主题里是否有这条事件？
  7. 追踪与证据：以 eventId 联查生产者日志、Broker 状态、消费者日志和业务数据库，而不是只凭某一端日志下结论。

11.4 遇到“消息积压”时如何排查

先判断是生产速率突然增加，还是消费成功速率下降；再检查慢 SQL、远程接口超时、线程池饱和、连接池耗尽、失败重试风暴及热点分区。治理措施可能包括限流、优化消费逻辑、按能力扩容、拆分热点、批处理和隔离异常任务。

11.5 如何验证异常情况下的处理结果

至少设计以下异常测试：

测试关键验证点
生产时断网发布失败或结果不确定能否恢复
Consumer 处理前宕机消息是否重新投递
本地事务提交后、ACK 前宕机幂等是否阻止重复生效
下游短暂不可用重试是否退避、有上限
毒丸消息持续失败是否被隔离，是否阻塞其他消息
消费端处理变慢积压、内存和连接数是否可控
先后发送同实体多次变更最终业务状态是否正确
大量消息同时到达是否出现过载、超时与资源耗尽

12. 常见误区与面试问题

Q1：消息队列和线程池有什么区别？
线程池通常在同一个进程内调度任务，进程崩溃时内存中的未完成任务可能丢失。MQ 通过独立的消息基础设施在应用之间传递消息，可以提供特定条件下的持久化、跨进程消费和失败恢复能力，但运维成本更高。

Q2：有了 MQ，系统就一定更快吗？
不一定。MQ 主要能缩短部分请求的同步等待、缓冲流量并提高架构弹性，可能提高系统整体吞吐，但会增加消息传输、序列化、存储和排队延迟。

Q3：消费者消费成功了，消息为什么还可能再次出现？
因为业务完成与 ACK/Offset 提交不是天然原子操作。两者之间宕机会引发重新投递或重新读取。

Q4：消息积压时加消费者就行吗？
不一定。要看队列/分区并发限制、消费端瓶颈和下游承载能力；增加消费线程可能加剧数据库拥堵。

Q5：RabbitMQ 的 Exchange 是存放消息的地方吗？
典型 AMQP 0-9-1 队列模型中，Exchange 主要负责路由，消息由 Queue 承载；其他模型例如 Streams 的存储语义有所不同。

Q6：Kafka 消费过的消息会立即删除吗？
不会。Kafka 的消息保留由 Topic 的保留/清理策略控制，消费组的 Offset 不直接删除消息。

Q7：Kafka 的 Offset 是全 Topic 全局递增的吗？
不是。Offset 的语义在具体 Partition 内；不同分区的 Offset 不能直接比较先后。

Q8：Kafka 可以保证所有消息全局有序吗？
常见分区 Topic 模型主要保证每个分区内的日志顺序，不自动保证跨分区全局顺序，也不自动保证异步业务副作用的最终执行顺序。

Q9：死信队列等于重试队列吗？
不是。重试负责“仍有希望成功的再次处理”，死信更常用于隔离需要特殊处理的失败消息。工程上可以组合，但目的不同。

Q10：业务数据库已经有事务，还需要考虑消息一致性吗？
需要。本地 MySQL 事务不能自动覆盖发送到独立 MQ 的操作。应根据需求采用 Outbox、事务消息或其他一致性设计。

Q11：只要配置了持久化，就绝不会丢消息吗？
不能这么推断。还要检查发布确认、路由、存储、副本、磁盘容量、保留策略、消费确认和应用级恢复机制。

Q12：是不是所有项目都应该引入 MQ？
不是。若只是简单、低频且必须立即返回结果的操作，直接调用通常更容易实现、测试与运维。只有明确存在异步、解耦、缓冲或事件分发需求时，引入 MQ 才可能值得。
