1. MQ 是什么？为什么会出现？

MQ 是应用之间异步传递消息的基础设施。 生产者（Producer）把业务消息发送到消息代理（Broker）；消息代理负责接收、路由、存储或保留消息；消费者（Consumer）按约定获取并处理消息。

它解决的核心问题不是“把一个 HTTP 请求换成消息”，而是让业务处理和下游执行在时间上解耦，并以队列、订阅、确认、持久化、重试等机制管理异步协作。

假设用户提交一份组织调整申请，系统需要：

  1. 保存申请和审批状态；
  2. 通知有关人员；
  3. 更新搜索索引或报表；
  4. 同步其他业务系统。

不使用 MQ 时，主服务可能依次调用通知、索引和同步服务。一个非核心下游超时，就可能拖慢甚至影响用户提交。采用事件驱动后，可以让主服务在完成关键数据库事务后，可靠地产生 OrgAdjustmentSubmitted 事件；通知、索引、同步模块各自处理。

注意：如果“保存数据库”与“发送消息”分成两步执行，中间存在一致性缺口。生产设计需要 Outbox、合适的事务消息等机制，不能仅凭 save(); send(); 就宣称可靠。

1.1 MQ 的三个主要价值

  • 异步处理：把非关键路径工作放到后台，降低用户接口的等待时间。
  • 系统解耦：生产者不必知道所有下游的地址、扩缩容状态和内部实现。
  • 削峰与缓冲：短时间写入大量任务，下游按照可承受速度处理。这里缓冲的是工作量，不是凭空增加处理能力。

MQ 还常被用于事件广播、最终一致性、任务分发、数据集成和日志/埋点处理。

1.2 MQ 会引入哪些新问题？

它不是免费提升架构质量：异步后要面对消息重复、乱序、积压、消费延迟、发送失败、链路可观测性不足、事件版本兼容和跨系统数据一致性。如果业务很简单、流程必须立即完成，直接调用通常更容易理解和维护。

2. 核心概念与一条消息的生命周期

概念含义常见误区
Producer创建、发送消息的应用调用发送 API 返回，不代表下游业务完成
Broker接收、路由、保存、投递消息的中间件服务Broker 确认，不等于消费者处理成功
Consumer订阅和处理消息的应用同一消息可能被重复交付
Message / Event传递的数据及其元数据消息应描述清楚业务语义，不要只放含糊的 type=1
Queue任务等待处理的逻辑队列不同产品的“队列”语义并不完全一致
Topic按主题组织消息或事件RabbitMQ 的 Topic Exchange 与 Kafka Topic 不是同一种存储结构
ExchangeRabbitMQ 按路由规则转发消息的实体Exchange 不是消费者直接消费的队列
Routing Key / Message Key路由或分区依据，具体取决于产品RabbitMQ 路由键 ≠ Kafka 消息键
Consumer Group消费者协作或订阅隔离的逻辑单位Kafka 中同组实例分摊分区，不同组可以独立读取同一 Topic
ACK / Offset确认处理或推进消费位置不能证明外部数据库或第三方接口绝不会重复执行
DLQ死信队列，用于隔离无法正常处理的消息放入死信并不等于问题解决

RabbitMQ 的传统队列一般通过成功 ACK 使消息完成队列消费；Kafka 以保留日志和消费者位点为核心，消费后消息仍可在保留期内被其他消费组或重放任务读取。二者不能简单类比成“都是消费后删除消息”。

2.2 “命令”和“事件”要分清

  • 命令（Command）：要求特定处理者执行操作，如 GenerateReport、SendNotification，强调“请做这件事”。
  • 事件（Event）：表示已发生的事实，如 ApprovalCompleted、EmployeeTransferred，强调“这件事已经发生”。

命令通常只希望一条工作链执行；事件可让多个独立订阅方各自处理。一个事件不应承诺某个下游已经完成动作。

3. 两种最常见的消费模型

3.1 竞争消费者：一份工作交给一个执行者

1
2
3
4

              ┌── Worker A
任务队列 ──────┼── Worker B
              └── Worker C
         每条任务通常由其中一个实例领取处理

适合发短信任务、生成报表、文件处理等。增加 Worker 能提升并行处理能力，但实际吞吐还取决于队列、下游接口、数据库和热点资源。重投递时，同一任务可能先后交给不同 Worker。

3.2 发布/订阅：同一个事件由多个业务方独立处理

1
2
3

                     ┌── 通知订阅/队列
审批完成事件 → MQ ────┼── 审计订阅/队列
                     └── 数据同步订阅/队列

适合业务事件通知、系统间状态传播。

RabbitMQ：通过 Exchange 和不同绑定队列实现广播或规则路由；一个服务多实例通常竞争消费它自己的队列。Kafka：多个 Consumer Group 能独立读取同一 Topic；同组实例分摊分区。

常见设计错误是让通知、审计和数据同步服务竞争同一个 RabbitMQ 队列，结果每条消息只由其中一个服务处理，而不是三个服务都处理。

4. 什么场景值得用 MQ？什么场景不值得？

场景是否适合设计重点
用户注册后发送邮件/站内信适合主流程与通知解耦；重试和防重复发送
审批完成后更新搜索索引、报表适合事件发布可靠性、版本顺序、最终一致性
秒杀/抢票任务排队有条件适合入口限流、库存原子扣减、幂等、队列容量、用户状态反馈
海量埋点、访问日志、CDC 数据流适合吞吐、分区、保留与回放，常考虑 Kafka
订单超时自动关闭有条件适合定时任务、延时消息、状态再次校验；允许触发时间误差
必须立刻拿到库存扣减结果才能下单不宜把关键确认完全异步化同步事务/接口或明确的状态机与补偿
单体应用内很轻量的后台计算不一定需要本地任务队列/线程池可能已足够，注意重启后任务丢失风险
跨服务强一致事务MQ 本身不能直接保证事务边界、Outbox、业务补偿和状态机
高频同步查询或用户等待响应的 RPC通常不优先直接 HTTP/gRPC 往往更直观

4.1 选型前的五个问题

  1. 这项工作能否稍后完成？用户能否看到“处理中”状态？
  2. 下游失败时，是否允许重试？重复执行有什么副作用？
  3. 业务要求多久处理完成？积压最多能承受多久？
  4. 是否需要广播、同一实体顺序、历史回放或复杂事件处理？
  5. 组织是否具备部署、监控、排障和故障恢复 MQ 的能力？

如果前三个问题没有答案，先设计业务状态和失败补偿，而不是先部署 Broker。

5. RabbitMQ、RocketMQ、Kafka 怎么选？

维度RabbitMQ（传统队列）Apache RocketMQ 5.xApache Kafka
主要定位灵活消息路由、任务分发和服务间异步通信业务消息、顺序/定时/事务消息分布式事件日志、流式数据平台
基本组织方式Exchange → Queue → ConsumerTopic、MessageQueue、ConsumerTopic → Partition → Consumer Group
多订阅方为不同订阅方配置不同队列按订阅与消费分组组织不同组各自维护位点
路由能力Direct / Topic / Fanout 等比较灵活Topic、Tag、过滤等Topic + Key/Partition 为主
消费与重放队列 ACK 后通常不保留供回放；另有 Streams 产品形态具备按保留策略保存和重消费能力，视版本与模式以日志保留和位点回放为核心能力
顺序能力需结合队列、消费者并发、重投递控制FIFO + MessageGroup（满足约束）单分区内记录有序
定时/延时TTL+DLX、插件或业务调度等实现5.x 有专门延时消息类型不是普通 Topic 的原生定时投递语义
事务相关发布确认不等于数据库事务有事务消息与回查机制有生产者幂等和 Kafka 事务，范围有限
常见优先场景中小规模业务异步任务、丰富路由以业务可靠投递、顺序和定时消息为重点的系统埋点、日志、CDC、大规模事件流与回放

经验性选型建议：业务任务/通知和灵活路由，可优先评估 RabbitMQ；业务要求较多 FIFO、延时、事务消息特性且团队已有生态时，评估 RocketMQ；大规模事件流、数据平台、持久保留和重放，评估 Kafka。最终应以吞吐、延迟、故障演练、托管运维成本、团队经验和实际版本 PoC 决定，而不是“某个 MQ 永远更快”。

补充：RabbitMQ 也支持 Streams，Kafka 也可实现简单任务处理，表格是典型架构定位而不是产品能力的绝对边界。

5.1 RabbitMQ 交换机的四种常见路由

类型规则举例
Direct路由键精确匹配绑定键notification.email
Topic按点号分段通配：* 匹配一段，# 匹配零段及以上org.adjustment.*
Fanout无视路由键，向所有绑定队列分发一个业务事件广播给多个订阅方
Headers按头部属性进行匹配特殊属性路由，业务中相对少用

注意：RabbitMQ Topic Exchange 是路由类型，不是 Kafka Topic。

import org.springframework.amqp.core.*;
import org.springframework.context.annotation.Bean;
import org.springframework.context.annotation.Configuration;
import org.springframework.beans.factory.annotation.Qualifier;

@Configuration
public class RabbitConfig {
    public static final String EXCHANGE = "demo.events";
    public static final String QUEUE = "demo.order.created.q";
    public static final String ROUTING_KEY = "order.created";

    @Bean
    TopicExchange eventExchange() {
        return new TopicExchange(EXCHANGE, true, false);
    }

    @Bean
    DirectExchange deadExchange() {
        return new DirectExchange("demo.dlx", true, false);
    }

    @Bean
    Queue orderQueue() {
        return QueueBuilder.durable(QUEUE)
                .deadLetterExchange("demo.dlx")
                .deadLetterRoutingKey("order.created.dead")
                .build();
    }

    @Bean
    Queue deadQueue() {
        return QueueBuilder.durable("demo.order.created.dlq").build();
    }

    @Bean
    Binding mainBinding(@Qualifier("orderQueue") Queue orderQueue,
                        TopicExchange eventExchange) {
        return BindingBuilder.bind(orderQueue)
                .to(eventExchange).with(ROUTING_KEY);
    }

    @Bean
    Binding deadBinding(@Qualifier("deadQueue") Queue deadQueue,
                        DirectExchange deadExchange) {
        return BindingBuilder.bind(deadQueue)
                .to(deadExchange).with("order.created.dead");
    }
}

说明：如果原队列已经存在但类型或参数不同，重新声明可能发生 PRECONDITION_FAILED；更改队列拓扑时应采用明确的迁移策略。生产环境死信配置优先评估 Broker Policy，以便运维调整；并应根据队列类型和版本评估死信转移的可靠性。

import org.springframework.amqp.core.MessageDeliveryMode;
import org.springframework.amqp.rabbit.core.RabbitTemplate;
import org.springframework.web.bind.annotation.*;
import java.util.UUID;

@RestController
@RequestMapping("/demo")
public class OrderController {
    private final RabbitTemplate rabbitTemplate;

    public OrderController(RabbitTemplate rabbitTemplate) {
        this.rabbitTemplate = rabbitTemplate;
    }

    @PostMapping("/orders/{orderId}/event")
    public String publish(@PathVariable("orderId") Long orderId) {
        String eventId = UUID.randomUUID().toString();
        String payload = "{\"eventId\":\"" + eventId
                + "\",\"orderId\":" + orderId + "}";

        rabbitTemplate.convertAndSend(
                RabbitConfig.EXCHANGE,
                RabbitConfig.ROUTING_KEY,
                payload,
                message -> {
                    message.getMessageProperties().setMessageId(eventId);
                    message.getMessageProperties()
                           .setDeliveryMode(MessageDeliveryMode.PERSISTENT);
                    return message;
                }
        );
        return "send invoked, eventId=" + eventId;
    }
}

这里用简单字符串演示消息体；真实项目应使用 DTO + JSON 序列化、字段校验和 Schema/版本管理，避免字符串拼接。尤其注意：convertAndSend() 返回只代表方法执行到该处，不能由此断言 Broker 已可靠保存消息，更不能断言业务已消费。生产者还需配置并处理 Publisher Confirms 和 Return/不可路由结果。

用 HTTP 响应里的 eventId 核对应用日志中的 received: 记录。RabbitMQ 管理界面可查看交换机、绑定和队列的 Ready / Unacked 计数。消息被快速消费后，Ready 可能一直显示为 0。

验证死信：临时让监听方法抛出异常，发送新消息，查看 demo.order.created.dlq。它能帮助演示故障隔离，但不代表已经实现了安全的自动重试；上线前必须确定重试次数、间隔、告警、人工处理和重新投递流程。

6.6 发布确认与消息路由

RabbitMQ 可以对不可路由的消息发出 Publisher Confirm ACK。开启 mandatory 并处理 Returns，可以发现消息未路由到任何队列。消息如果进入了其他绑定的队列，或通过备用交换机完成路由，发布者可能收不到 Return。

要核对某个目标队列，先确认交换机存在、目标队列已绑定且路由键匹配，再检查消息是否已被消费者取走、过期、因容量策略被移除或进入死信队列。见 RabbitMQ 发布确认和备用交换机。

7. Kafka 的基本使用方式与 RabbitMQ 的差异

Kafka 特别值得理解的是 Partition、Consumer Group 和 Offset。

Topic: order-events
  Partition 0: [e1][e4][e7]...
  Partition 1: [e2][e5][e8]...
  Partition 2: [e3][e6][e9]...

Consumer Group: report-service
  instance-A → Partition 0 + 1
  instance-B → Partition 2

Consumer Group: audit-service
  independent offsets, reads the same topic

同一分区中的记录按写入日志的先后顺序排列；不同分区之间不存在全局顺序。若需要同一 orderId 的事件有序，一般把 orderId 作为消息 Key，使同一实体的消息进入相同分区（仍需考虑分区数调整、生产并发、消费重试等约束）。

import org.springframework.kafka.core.KafkaTemplate;
import org.springframework.kafka.annotation.KafkaListener;
import org.springframework.stereotype.Component;

@Component
class AuditMessaging {
    private final KafkaTemplate<String, String> kafkaTemplate;

    AuditMessaging(KafkaTemplate<String, String> kafkaTemplate) {
        this.kafkaTemplate = kafkaTemplate;
    }

    void publish(String orderId, String json) {
        kafkaTemplate.send("order-events", orderId, json);
        // 返回 CompletableFuture：按业务要求处理成功/失败结果。
    }

    @KafkaListener(topics = "order-events", groupId = "audit-service")
    void consume(String payload) {
        // 处理消息。这里仅演示 API，不包括消费失败/位点提交方案。
        System.out.println(payload);
    }
}

这段代码假设 Kafka Broker 和 Topic 已就绪；并未提供可直接启动的 Kafka 服务。生产应用还要处理 Producer acks、幂等生产者、重试、批量参数、消费提交策略和消费错误处理器等。

特别注意：auto-offset-reset: earliest 仅在该消费组没有有效已提交位点等特定情形生效，不是“每次启动都从头消费”。

8. 生产设计的重点：可靠性不是一个开关

8.1 要区分四个成功状态

  1. 业务数据提交成功：本地数据库事务已提交。
  2. Broker 确认发布：确认范围取决于产品和配置。RabbitMQ 还需核对路由结果，Kafka 需结合 acks 和副本配置判断确认范围。
  3. 消息交付成功：消费者收到某次消息投递。
  4. 业务处理成功：消费者的数据库更新或外部副作用真正生效。

这四件事可能在不同时间发生。MQ 的 ACK/Confirm 覆盖不同阶段，不能混为一谈。

8.2 三种交付语义

语义直观含义后果
At most once最多交付一次可能丢失，不重复交付
At least once至少交付一次（满足前提条件时）尽量避免丢失，但可能重复
Exactly once特定范围内恰好处理一次必须明确范围与前提；不是所有外部副作用都天然恰好一次

对于关键业务，常见务实方案是 At-least-once 投递 + 消费者幂等 + 故障补偿 + 可审计记录。

Kafka 的幂等生产者和事务能力可在 Kafka 内部的特定生产/消费处理链路上提供更强语义，但向 MySQL、HTTP、邮件系统写入时，仍需单独设计一致性和幂等性。

8.3 生产者侧如何防丢失

  • 发送前校验业务数据与消息格式，使用稳定的 eventId。
  • 配置 Broker 持久化、合适的复制/队列类型和发布确认；确认参数需结合当前产品版本。
  • 对超时、NACK、不可路由结果记录状态并按策略重试；超时不代表一定没有发送成功，重试可能导致重复消息。
  • 在业务数据库状态与事件必须一致时，使用 Transactional Outbox 等模式。

8.4 Transactional Outbox：数据库和消息之间的一致性

最典型的失败窗口：

1

DB 提交成功 → 进程崩溃 → MQ 消息还没发出去

反过来，先发消息再提交数据库，可能造成下游看到一个实际上已回滚的业务事件。

Outbox 方案：在一个本地数据库事务中同时修改业务表和插入待发送事件；事务提交后由后台任务或 CDC 工具读取 Outbox，把消息发送到 MQ。状态更新和待发送记录具备原子性；发送链路仍需重试、去重、监控和清理机制。

8.5 消费者幂等：防止同一事件被执行两次

假设用户审批通过后，消费者要给某个账户增加积分。第一次消费已写入数据库，但 ACK 返回前网络中断；Broker 重投递后，如不做幂等，积分就会重复增加。

8.6 消息顺序：明确顺序作用于什么范围

先收到 CREATED 再收到 APPROVED，不等于消费处理结果也一定按此顺序完成。顺序可能被并行生产、分区、消费者并发、超时、重试、死信重放打乱。

常用方案：按 aggregateId（如申请单 ID）选择同一队列/分区/MessageGroup；控制该顺序域的并发；业务表增加单调递增的版本号，在消费者侧校验版本和状态迁移合法性。

对于 CREATED(v1)、APPROVED(v2)，消费者收到 v2 却还没有 v1 时，可以延迟重试、主动补数或通过业务状态快照收敛；不要无条件覆盖更新。

8.7 重试和死信：先分类错误，再决定行动

失败类型建议策略
数据库短暂不可用、网络抖动有界重试 + 退避 + 抖动
下游限流、服务过载降低并发、延时重试、背压
消息字段不合法/版本不兼容直接隔离到错误队列/死信，通知负责人
业务状态不满足处理条件区分暂时未满足与永久非法，不能盲目无限重试
消费已成功但确认丢失依赖幂等安全重投递

不要让失败消息立即入原队列无限循环；会形成“毒消息”风暴。死信队列需要明确所有者、告警阈值、定位信息、修复和重放流程；重放必须继续遵守幂等和顺序约束。

8.8 削峰与背压：队列不是无限蓄水池

速率相对稳定时，可以用 积压增长速率 = max(0, 生产速率 - 有效消费速率) 估算峰值期间新增的消息积压。

假设峰值生产 2,000 条/秒，稳定有效消费 1,200 条/秒，峰值持续 10 分钟，则约新增 800 × 600 = 480,000 条积压（忽略重试及消息大小变化）。峰值结束后能否消化取决于后续消费余量。要同时设置入口限流、队列容量/保留策略、消费者横向扩容和积压告警。

10. 与数据库、Redis、Canal、定时任务有什么关系？

  • 数据库：保存权威业务状态。MQ 传递动作/事件，通常不代替业务数据的持久存储。
  • Redis：可作为缓存、轻量队列或 Streams 使用，但其交付语义、持久化、消费组、运维与成熟 MQ 产品不同；不能把 Redis List 和可靠事务消息视为等价。
  • Canal / Debezium（CDC）：读取数据库变更日志，向下游同步行级变更；MQ 可作为 CDC 下游通道。“数据库字段变了”不必然等于“某业务事件发生”，业务事件最好通过明确的契约或 Outbox 表表达。
  • 定时任务：按时间触发检查；延时消息也可能承担触发角色。无论采用哪种方式，最终执行前都要重新校验业务状态。
  • HTTP/gRPC：同步查询、需立即返回结果的操作仍适用；MQ 和同步 RPC 是互补关系。

如果需要将组织调整申请状态变化同步到搜索服务：可以由业务代码发布 OrgAdjustmentApproved 事件，也可以用 CDC 同步数据库增量；前者具有清晰的业务语义，后者适合数据复制与集成。不要因已有 Canal 就默认所有业务流程都通过表变更来驱动。

11. 上线前检查：把“能运行”变成“可交付”

11.1 业务契约

  • 定义事件名称、生产时机、状态变化和消费者责任。
  • 明确数据一致性目标：实时、秒级最终一致还是可延迟补偿。
  • 有稳定消息 ID、关联 ID、版本和 Schema 兼容策略。
  • 判断重复处理、乱序处理可能造成的业务后果。

11.2 消息可靠性

  • 业务事务与消息发布之间的失败窗口有处理方案。
  • 发布确认、不可路由、消息持久化和副本策略经过验证。
  • 消费 ACK/位点提交发生在正确业务处理边界。
  • 消费者幂等、重试次数、死信隔离、人工重放都有方案。
  • 消费服务停机/重启/故障恢复时不会静默丢失关键任务。

11.3 性能与运维

  • 压测正常、峰值和下游故障时的吞吐、延迟、积压增长。
  • 定义消息端到端延迟 SLO（如 P95/P99）、积压容量和可接受恢复时间。
  • 监控生产失败、消费失败、重试、死信、积压量/积压时间、CPU、内存、磁盘和复制健康度。
  • 明确消息保存时长、容量配额、敏感数据权限和清理机制。
  • 设计鉴权、最小权限、TLS、网络隔离及密钥轮换。

11.4 故障演练

建议至少做五个实验：

  1. 消费者业务成功后、ACK 前退出：确认重复投递不会重复执行业务。
  2. 业务 DB 提交后、消息发送前退出：验证 Outbox/可靠发布机制。
  3. Broker 暂不可用：确认生产接口行为与重试策略符合预期。
  4. 持续发送无效消息：确认重试有界、死信与告警正常。
  5. 消费者速度小于生产速度：确认背压、积压告警及恢复能力。

这些实验比只验证“控制台能收到消息”更能说明设计是否可靠。

12. 常见误区与排障思路

误区 1：消息已经发出去 = 整条链路成功。

要分别验证生产者确认、路由、消息保存、消费者业务事务和最终 ACK。

误区 2：只要开了持久化就不会丢消息。

持久化需要结合发布确认、队列/分区复制与故障条件。未收到确认的发送和未建立一致性保障的业务事件仍可能出问题。

误区 3：MQ 保证 Exactly Once，所以不用幂等。

必须先问“Exactly Once 的边界是什么”。数据库/HTTP/第三方外部副作用通常仍需业务幂等。

误区 4：消费者越多吞吐就一定越高。

Kafka 同组分区数限制有效并行消费单元；RabbitMQ 还受 Prefetch、负载公平性和后端处理容量限制。数据库热点、锁竞争和限流都可能成为瓶颈。

误区 5：消息积压直接清空队列就能恢复。

清空可能丢失未处理业务。先隔离异常流量、确认消费者状态、估算积压价值和恢复时间，再制定回放或废弃方案并获得业务授权。

排障顺序：先定位一条 eventId 的完整路径，检查生产日志 → Broker 主题/路由/队列 → 消费者是否在线 → ACK/位点和错误日志 → 业务数据库效果 → 重试/死信；随后扩大到批量指标，判断是单消息问题还是系统性容量问题。
