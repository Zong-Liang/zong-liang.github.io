适用读者：已掌握 HTML、CSS、JavaScript、TypeScript 和 React 核心概念的开发者，尤其是希望参与企业后台系统开发的 Java 后端工程师。

本篇以 React 19 + TypeScript + React Router 7 + Ant Design 6 + TanStack Query 5 为示例技术组合。重点是解释企业前端真实的业务开发过程：一个 URL 如何对应页面、表单如何组织和提交、HTTP 结果如何进入 UI、服务端数据如何保持一致、权限应由谁负责。

正文保留必要的、可以独立阅读的代码示例，但不插入章节练习、自测或每日任务。全文仅在最后设置一个综合实战：将上一阶段的 React 员工管理后台升级为具有路由、服务端分页、表单校验、HTTP CRUD、缓存管理和权限行为演示的业务应用。配套源码见示例仓库。

导读：从“会写 React 组件”到“能交付业务需求”

第四阶段重点解释组件、Props、State、Hooks 和 React 渲染机制。如果把单个组件视为一台机器，企业业务开发需要解决的是这些机器如何组成一个完整系统。页面之间要导航，接口之间存在依赖，列表、详情和弹窗可能同时使用相同的数据，表单输入与服务端业务规则也必须一致。

典型的员工管理需求可能是：

  1. 用户打开 /employees?page=2&status=active，页面应直接显示第 2 页在职员工。
  2. 搜索条件由用户填写，但只有点击“查询”后才影响列表请求。
  3. 点击员工姓名进入详情，再返回列表时，希望原有查询条件仍然存在。
  4. 管理员编辑员工并保存后，列表与详情要显示服务端确认后的最新数据。
  5. 服务器返回 409（工号重复）时，表单应保留已有输入并展示有针对性的反馈。
  6. 查看角色不应出现编辑、删除入口；无论是否隐藏按钮，服务器都必须独立验证操作权限。
  7. 网络缓慢、请求失败、数据为空和数据过期是不同的状态，需要不同的处理。

这些需求不能只靠记住 useState、useEffect 实现。它们要求把不同职责放到合理的位置。

第一部分：页面与交互

第 1 章 企业级 React 业务页面的基本结构

1.1 从组件到页面、从页面到应用

在 React 应用中，组件是可复用的 UI 单元，页面是与某个业务路由相对应的组合入口，应用则包含路由、全局配置、网络层和公共布局。三者不是同一个概念。

例如员工管理模块可以包含：

  • EmployeesPage：员工列表页面，承担路由参数解析、查询条件提交、列表数据加载与操作入口组织。
  • EmployeeTable：表格呈现，可复用但不应该直接决定后端业务权限。
  • EmployeeEditor：编辑表单，管理输入、校验、提交反馈。
  • EmployeeDetailPage：通过 URL 中的员工 ID 获取单个员工详情。
  • AppLayout：提供侧边导航、顶部信息、页面容器和路由出口。

如果所有 HTTP 请求、弹窗状态、表格、路由、校验和角色判断都放在一个 App.tsx 中，早期代码也许可以运行，但稍微增加功能就会使组件职责混乱。更合理的做法是按业务流程组织：页面协调，组件负责呈现，数据层负责服务端交互，后端负责业务规则。

1.2 页面状态并不是一种状态

企业后台常见五类状态，必须先区分再决定是否需要全局状态管理。

分类例子生命周期常见问题
地址状态page=2、status=active路由导航可恢复刷新丢失、返回后重置
组件局部状态弹窗开闭、展开面板随组件实例存活不必要提升至全局
表单草稿状态尚未提交的姓名、工号直到提交或取消输入即触发请求、提交后误清空
服务端状态员工数据、部门列表受网络及后端更新影响缓存过期、重复请求、保存后不一致
应用上下文演示角色、主题语言跨页面共享Context 过大导致耦合

典型错误是把员工数组既放在 useState，又放在 Context，还用 Query 缓存，最后出现三份副本。除非确实需要独立编辑草稿，否则服务器数据应由一个明确的缓存层管理。

第 2 章 React Router：路由、导航和 URL 状态

2.1 什么是前端路由

浏览器 URL 由协议、域名、端口、路径、查询参数和片段等组成。对单页应用而言，URL 变化不一定意味着整页重新加载。React Router 能够根据当前位置选择组件树并支持客户端导航。

1

3

http://localhost:5173/employees/emp-001?tab=profile
                      └──────────────┘ └──────────┘
                             pathname       search

/employees/emp-001 适合表达资源身份，?tab=profile 适合表达页面展示条件。# 片段可表示文档中的锚点，它不随普通 HTTP 请求的请求目标发送给服务端。

URL 设计原则： 页面身份用路径，能够恢复、分享、前进后退的检索条件用查询参数，临时弹窗开闭或输入法中间值通常由组件局部状态管理。

2.2 React Router 7 的三种模式

React Router 7 的官方文档区分 Declarative、Data 和 Framework 三种使用模式，它们的能力与配置方式不同。

模式典型入口核心能力本篇使用情况
DeclarativeBrowserRouter + Routes路由匹配、跳转、参数本篇采用
DatacreateBrowserRouter + RouterProvider增加 loader、action、导航 pending 等说明适用情形，不混用
Framework构建工具集成的框架配置约定式路由、服务端相关能力非本阶段重点

官方文档：Picking a Mode。

本篇使用 Declarative Mode，因此接口数据由 TanStack Query 管理。不要把 Data Mode 的 loader 或 action 示例不加区分地搬到 <BrowserRouter> 项目中。 若已有项目采用 Data Router，应以项目原有架构为准。

import { BrowserRouter, Routes, Route, Navigate, Outlet } from 'react-router';

function AppLayout() {
  return (
    <div className="app-layout">
      <aside>导航栏</aside>
      <main><Outlet /></main>
    </div>
  );
}

function App() {
  return (
    <BrowserRouter>
      <Routes>
        <Route element={<AppLayout />}>
          <Route index element={<Navigate to="/dashboard" replace />} />
          <Route path="dashboard" element={<DashboardPage />} />
          <Route path="employees" element={<EmployeesPage />} />
          <Route path="employees/:id" element={<EmployeeDetailPage />} />
          <Route path="*" element={<NotFoundPage />} />
        </Route>
      </Routes>
    </BrowserRouter>
  );
}

<Outlet /> 是匹配子路由内容的放置位置；index 匹配父级路径本身；<Navigate replace> 在重定向时替换历史记录项，避免返回时再次进入不必要的中间页面。示例组件名在实际代码中需分别实现与导入。

实际项目通常将 BrowserRouter 放在应用入口，由 App 只定义内部 Routes，避免重复嵌套多个路由容器。配套实战使用这一结构。

import { useParams, useSearchParams } from 'react-router';

function EmployeeDetailPage() {
  const { id } = useParams<{ id: string }>();
  if (!id) return <p>缺少员工 ID</p>;
  return <EmployeeProfile id={id} />;
}

function EmployeeListControls() {
  const [searchParams, setSearchParams] = useSearchParams();
  const page = Math.max(1, Number(searchParams.get('page')) || 1);
  return (
    <button onClick={() => setSearchParams(prev => {
      const next = new URLSearchParams(prev);
      next.set('page', String(page + 1));
      return next;
    })}>
      下一页
    </button>
  );
}

useParams 从路由模式中读取动态参数，它不能证明 ID 一定存在或合法。useSearchParams 读取和写入 URL 查询参数，字符串必须经过校验与规范化。Number(searchParams.get('page')) 可能得到 NaN、负数或小数，正式业务代码要处理这些边界。

URLSearchParams 是可变对象。修改查询条件时显式构造新实例，更方便保证更新可预测。setSearchParams 的函数式更新不像 React setState 那样排队累加：同一事件内连续调用多次，后一次拿到的仍是原始参数，而不是前一次的结果，前面的修改可能丢失。需要同时修改页码、筛选等多个参数时，应在一次调用中完成。

2.6 URL、历史记录和刷新

假设用户访问：

1

/employees?q=张&page=3&status=active

如果查询条件完全只存在于 useState，刷新页面就会丢失。同步到 URL 后，地址可以复制、收藏和分享，并且浏览器前进后退能够恢复查询状态。URL 不是存储隐私数据的安全容器：敏感字段、访问令牌、身份凭据不应放在普通查询参数中。

BrowserRouter 使用 History API；部署时应配置静态服务器，使未命中静态文件的应用路径回退到 index.html。否则从列表点击详情可以正常，但直接刷新 /employees/emp-001 可能返回服务器 404。

第 3 章 Ant Design：企业 UI 组件库的使用边界

3.1 为什么企业后台通常使用成熟组件库

常见管理后台需要大量高密度交互组件：输入框、级联选择、日期选择、表格、分页、树、抽屉、弹窗、提示反馈等。每个组件除了外观，还有焦点管理、键盘操作、校验、禁用态和交互一致性问题。

使用成熟组件库的意义是把开发精力放到业务行为，而不是重复实现这些基础交互。但是组件库不会替你设计业务状态，也不会自动理解后端接口契约和权限规则。

本篇选用 Ant Design 6 作为公开、可复现的示例。你实际工作的项目如果有既定内部组件库，应优先遵循已有设计系统与封装规范；不应仅为了学习新库而替换业务项目现有组件。

3.2 Ant Design 6 的版本边界

Ant Design 6 相比 5 在多项 API 上有弃用或调整。新项目可使用 Form、Table、Modal、App、ConfigProvider 等稳定主体接口，但使用网上教程时要确认版本。

例如：

  • 弹窗显隐使用 open。Ant Design 5 已将 Modal 的 visible 改为 open，v6 的 Modal API 中只有 open。
  • 表格常见配置包括 rowKey、dataSource、columns 和 pagination。
  • 弹窗销毁相关使用 destroyOnHidden；但表单是否重置仍需考虑 Form 自身的字段保留与组件身份。
  • 通知、对话框的推荐用法还涉及 App 上下文；避免在业务代码中依赖脱离上下文的全局静态调用。
  • 部分组件的旧 API 在 v6 中可运行但已标记弃用；准确迁移应查阅官方文档。

参考：Ant Design v5 → v6 迁移说明、组件文档。

import { Table, Tag } from 'antd';
import type { TableColumnsType } from 'antd';

type Status = 'active' | 'inactive';
interface EmployeeRow {
  id: string;
  employeeNo: string;
  name: string;
  status: Status;
}

const columns: TableColumnsType<EmployeeRow> = [
  { title: '工号', dataIndex: 'employeeNo' },
  { title: '姓名', dataIndex: 'name' },
  {
    title: '状态',
    dataIndex: 'status',
    render: (status: Status) => (
      <Tag color={status === 'active' ? 'green' : 'default'}>
        {status === 'active' ? '在职' : '离职'}
      </Tag>
    ),
  },
];

function EmployeeTable({ rows }: { rows: EmployeeRow[] }) {
  return <Table<EmployeeRow> rowKey="id" columns={columns} dataSource={rows} />;
}

rowKey 必须稳定且能唯一标识记录，尤其是增删改、行选择、分页和局部更新场景。不要简单把数组索引当成持久的行身份；排序或分页会改变索引与记录的对应关系。

表格内的自定义列 render 用于呈现状态，不能代替后端字段含义和数据转换。后端字段映射应在 API/adapter 层统一处理，而不是在很多组件中反复猜测。

3.5 组件库、业务组件与设计系统

组件库的 Table 不直接等于业务的“员工列表”。后者通常还包含状态文案、操作权限、空数据含义、行跳转逻辑、错误信息和业务列定义。可以建立自己的 EmployeeTable，但不要过度封装成一个无法透传常用属性的所谓“万能表格”。

推荐区分：

  1. 通用 UI 组件：由组件库负责，尽量复用。
  2. 设计系统封装：项目统一的布局、主题、表单宽度、提示规范。
  3. 业务组件：员工列表、组织选择器、权限操作区。
  4. 页面：路由参数、数据查询和业务动作的协调入口。

组件是否值得封装，取决于是否存在稳定、可复用的职责边界，而不是因为某段 JSX 超过多少行。

第 4 章 表单：草稿、校验、提交与编辑弹窗

4.1 表单是一个状态机，而不只是输入框集合

员工表单至少涉及：

  • 创建或编辑两种业务模式；
  • 原始数据与未提交的用户输入；
  • 字段格式校验和跨字段约束；
  • 正在提交、防重复提交；
  • 服务端返回的字段错误、冲突和全局异常；
  • 保存成功后缓存更新、弹窗关闭与提示。

这意味着表单要围绕一个明确的提交生命周期设计，而不只是实现 onChange。

4.3 initialValues、setFieldsValue 与弹窗重开

initialValues 不是任意时刻都自动跟随外部 Props 更新的“响应式属性”。尤其在“编辑员工 A → 关闭 → 编辑员工 B”的场景，如果复用相同 Form 实例而没有重置，就可能显示 A 的数据。

常见可用方案：

  • 在创建新的表单实例时传入该员工的初始值，例如通过稳定且不同的 key 重建表单组件。
  • 对长期复用的表单，明确使用 form.setFieldsValue 或 form.resetFields 与当前记录同步。
  • 检查 preserve、destroyOnHidden 以及弹窗的实际挂载/卸载过程。

配套实战使用 EditorState 区分新建和编辑，并为表单组件使用与员工 ID 对应的 key，避免交叉污染。编辑弹窗关闭也不能意外丢弃正在提交的请求或产生“保存成功但界面仍旧提示失败”的竞态。

5.1 为什么要封装请求层

type DemoRole = 'editor' | 'viewer';
interface ApiEnvelope<T> { data: T }
interface ErrorEnvelope {
  code?: string;
  message?: string;
  fieldErrors?: Record<string, string>;
}

export class ApiError extends Error {
  constructor(
    public readonly status: number,
    public readonly code: string,
    message: string,
    public readonly fieldErrors?: Record<string, string>,
  ) {
    super(message);
    this.name = 'ApiError';
  }
}

export async function request<T>(path: string, options: {
  method?: 'GET' | 'POST' | 'PUT' | 'DELETE';
  body?: unknown;
  signal?: AbortSignal;
  role?: DemoRole;
} = {}): Promise<T> {
  const response = await fetch(path, {
    method: options.method ?? 'GET',
    signal: options.signal,
    headers: {
      ...(options.body !== undefined ? { 'Content-Type': 'application/json' } : {}),
      ...(options.role ? { 'X-Demo-Role': options.role } : {}),
    },
    ...(options.body !== undefined ? { body: JSON.stringify(options.body) } : {}),
  });
  const payload: unknown = await response.json();
  if (!response.ok) {
    const error = payload as ErrorEnvelope;
    throw new ApiError(
      response.status,
      error.code ?? 'HTTP_ERROR',
      error.message ?? `HTTP ${response.status}`,
      error.fieldErrors,
    );
  }
  return (payload as ApiEnvelope<T>).data;
}

ApiError 保留 HTTP 状态码、业务错误码和字段错误，页面可以据此区分 403、409 等情况，并把 fieldErrors 映射回表单（见 4.5 节）。X-Demo-Role 是配套项目的演示角色请求头，第 10 章说明它为什么不具备安全意义。

这只是解释调用结构的简化示例，真实公共请求层还需要处理 204 No Content、下载文件、非 JSON 响应、无效 JSON、请求超时和不可信数据结构等差异。

5.3 错误分类、异常类型与业务错误码

HTTP 错误与业务错误不完全等价：

状态/现象可能含义页面处理建议
400请求参数不合法保留表单并展示字段校验信息
401缺少有效认证由统一认证流程处理登录态
403身份已识别但无权限告知无权操作，勿继续重试写入
404资源不存在或路由错误提示员工不存在或接口路径问题
409状态冲突、唯一约束冲突提示用户修正，必要时刷新数据
429请求超过限制根据服务端限流策略退避
500/503服务端异常/暂不可用告知失败并酌情允许重试
网络错误DNS、连接或浏览器网络失败提供网络状态与重试入口
AbortError主动取消请求通常不作为业务错误提示

第 6 章 TanStack Query：服务端数据的状态与缓存

6.1 为什么要区分服务端状态与 UI 状态

服务端状态具有几个特点：

  • 数据的真正所有者通常是远端服务；
  • 读取是异步的，可能失败；
  • 多个页面可能需要同一资源；
  • 本地副本可能过期；
  • 变更操作之后，需要判断哪些副本失效。

自己使用 useEffect、useState 可以实现简单请求，但多页面项目容易反复编写加载、错误、缓存、重试、竞态和刷新逻辑。TanStack Query 正是为这些问题提供统一模型。它不负责 URL 路由，也不替你决定本地编辑草稿。

6.4 staleTime、gcTime 与缓存新鲜度

staleTime 表示数据在多长时间内被认为仍是新鲜的。数据过期并不等于立刻从缓存中删除，它主要影响在某些触发条件下是否应重新获取。

gcTime 表示查询转为非活跃后，缓存数据最多保留多久才可被垃圾回收；它与新鲜时间不同。不能用 gcTime 控制请求是否重发，也不能假定缓存存在就保证数据新鲜。

参数主要控制什么常见误解
staleTime何时被标记为 stale以为超过时间缓存会被删除
gcTime非活跃查询缓存的清理时间以为它决定 API 请求是否刷新
refetchOnWindowFocus窗口重新获得焦点时是否按策略重取以为每次聚焦都会忽略新鲜度
retry查询失败后的重试把不允许重复的写入操作也随便重试

配套实战设置 staleTime: 30_000 并关闭聚焦自动刷新，便于观察缓存和手动失效行为。这是教学选择，不是生产项目统一推荐配置。

6.5 isPending、isFetching 与 isError

  • isPending：查询尚无可用的成功数据的状态表现，与初始加载有关。
  • isFetching：当前存在网络获取活动，背景刷新时也可能为真。
  • isError：查询处于错误状态，仍需结合是否有旧数据决定 UI 的展示方式。

例如已有列表时，后台刷新可以使用轻量 Loading，不必把整个表格清空；但首次加载失败不能伪装成“暂无数据”。

6.9 缓存失效与直接更新缓存

两种策略各有适用范围：

  1. invalidateQueries：把匹配的查询标记为过期，其中当前活跃（正在被组件使用）的查询会立即在后台重新获取，未活跃的查询等下次使用时再获取。逻辑较简单，适合后端可能补充或改变多个字段的场景。
  2. setQueryData：用服务端返回值直接更新某份已知缓存，交互更即时，但要正确维护列表、分页、筛选和详情之间的一致性。

例如更新员工姓名后，某些搜索列表中员工是否仍应出现可能发生变化；仅替换单个对象不一定正确。对复杂分页查询，失效后重取往往是更稳妥的初始选择。

invalidateQueries({ queryKey: ['employees'] }) 使用前缀匹配，会覆盖其下的列表与详情查询。实际应用也可以使用更细粒度的 Query Key，减少不必要的网络请求。

6.10 TanStack Query 与 Redux / Zustand 的关系

TanStack Query 专注服务端异步数据；Context、Redux、Zustand 等更多用于应用客户端状态及跨组件协调。并非项目一变大就必须引入 Redux，尤其不能仅因为“员工列表多个页面共用”而再存一份员工数组到 Redux 中。

一个合理的决策顺序是：

  • 已经能由 URL 表达的条件，优先考虑 URL。
  • 仅在单个表单、弹窗或页面使用的状态，保留在局部。
  • 跨页面、与服务器同步的数据，先考虑已有 Query 缓存。
  • 需要跨较大组件树共享的纯客户端状态，再评估 Context 或项目现有状态库。

6.11 版本与 API 注意事项

旧版 TanStack Query（包括更名前的 React Query）教程经常使用 useQuery(key, fn)、keepPreviousData: true 等不同于 v5 规范的写法。学习时必须同时核对版本。官方文档：TanStack Query v5 Quick Start、Invalidations from Mutations。

7.4 为什么筛选后通常回到第一页

假设用户正在第 8 页，新的筛选条件仅匹配 3 条数据。如果不把页码重置为 1，页面可能请求第 8 页并得到空数组；此时“没有数据”与“页码越界”就会混淆。

实践上，当查询条件、排序字段或排序方向改变时，通常将页码归一到第 1 页。只是改变每页条数时，也要明确页码转换策略：最简单的是归一到第一页；如果需要维持首条可见记录的位置，应按该产品的业务规则计算新页码。

7.7 排序不能只修改当前页

如果列表数据来自服务端分页，拿到的只是一页记录。直接对 items.sort() 排序只会调整这一页的顺序，不代表对所有符合条件的数据进行了正确排序。

服务端分页时，排序字段和方向应进入请求参数，让服务端在完整结果上排序后再分页。数据量较大时，排序字段应与后端可用索引和查询性能相协调。

7.8 分页数据在并发修改下的变化

即使服务端正确实现了分页，使用页码偏移量的列表也可能因为并发插入、删除而出现跨页重复或跳过记录。对于对一致性要求较高的长列表、实时变化频繁的事件流，可以评估游标分页；对于普通管理后台，页码分页往往更直接。

选择方案依赖数据增长速度、排序稳定性、是否需要“跳转到第 N 页”，以及后端数据库能力。前端不应擅自将后端现有 Offset 分页解释成游标分页。

第 8 章 CRUD 完整链路与数据一致性

8.1 列表、详情、修改之间的关系

一个员工可能同时出现在：

  • 列表页缓存；
  • 某个详情页缓存；
  • 概览统计缓存；
  • 当前编辑表单的未提交草稿。

前面三者通常是同一远端资源在不同查询条件下的只读副本。最后一份是用户明确编辑中的草稿，不能因为后台自动刷新就随意覆盖。

8.2 创建资源

推荐顺序：

  1. 表单通过客户端基本校验；
  2. 标记提交中，禁止无意识重复提交；
  3. 调用 POST；
  4. 服务器创建并返回结果；
  5. 相关列表、概览等缓存失效或更新；
  6. 展示成功反馈，关闭表单或根据业务规则跳转。

如果服务端返回 409 唯一性冲突，表单仍然保持打开，并展示具体字段错误。不要立即清空用户已填写的姓名、邮箱和部门。

8.3 更新资源

HTTP PUT 常用于替换某个资源的完整表示，PATCH 常用于部分修改；具体使用哪一个以项目后端契约为准。本篇 Mock 服务使用 PUT /api/employees/:id，要求提交完整的编辑字段集。

编辑更新还需要考虑：

  • 用户打开表单后，记录可能已被其他人修改；
  • 后端可能按乐观锁版本号或 ETag/If-Match 解决覆盖冲突；
  • 后端会再次验证业务规则，前端不能只信任打开弹窗时的旧数据；
  • 修改员工部门或状态后，列表筛选条件可能让该员工不再属于当前页。

综合实战为了聚焦前端机制，使用内存 API，并未实现多用户并发版本冲突控制。生产中的重要数据应结合后端版本号、冲突提示和审计策略设计。

8.4 删除资源

删除应先明确业务语义：是物理删除、逻辑删除，还是变更状态。在很多 HR 系统中，直接删除人员主数据可能影响历史关联记录，实际系统通常需要更严格的流程。

这里的实战删除仅针对教学样本数据；生产 HR 系统中更应遵循业务领域定义的离职、停用、归档和数据保留规则。

DELETE 成功后，相关列表和统计也应更新。如果当前页因删除而没有任何记录，可以按照产品规则退回上一页，或保留当前页并提示、由服务端统一纠正越界页码。不要直接把“删除按钮点击了”当作删除成功。

8.5 悲观交互与乐观更新

悲观交互：先等待服务器确认，再更新页面。实现简单，适合多数企业后台写操作。

乐观更新：在服务器确认前先更新本地界面，失败后回滚。适合高度即时的轻量操作，但需要处理并发变更、失败回滚和缓存一致性。

例如“给某条消息点赞”可以考虑乐观更新，而“修改员工组织归属并触发审批流程”通常不应仅因为用户点击就立即呈现最终成功状态。

综合实战选择先等待服务端成功，再失效查询并显示提示，优先保证可理解性与一致性。

8.6 幂等性和重试语义

HTTP GET 按语义应是安全的读取，PUT 和 DELETE 按语义具备幂等性，而 POST 通常不保证幂等。但具体后端实现是否符合语义，需要遵守实际 API 契约。

客户端发生网络超时，并不能推出服务端一定没有完成请求。对敏感写操作，自动重试可能产生重复写入。此时应使用业务幂等键、服务端唯一性约束或查询操作结果，而不是简单再次发送请求。

第 10 章 权限与身份：路由守卫不是安全边界

10.1 认证与授权的区别

  • 认证（Authentication）：确认请求者是谁，例如服务端会话或 OAuth/OIDC 登录。
  • 授权（Authorization）：确认该身份是否有权执行某个动作、访问某条数据。

前端通常需要根据已知用户权限控制菜单、按钮、操作提示和路由展示。但能否实际操作必须由后端验证；前端隐藏按钮不会让接口自动变安全。

10.2 四个常见权限层次

层次目的可信边界
菜单权限决定导航入口是否展示UI 体验
页面/路由权限决定是否显示相应页面UI 体验，不能替代 API 授权
操作权限决定是否展示编辑、删除等按钮UI 体验；服务端必须再次验证
数据权限决定能够查询和修改哪些具体记录必须由服务端执行可信检查

例如某用户可以进入“员工管理”页面，但不一定能查看所有部门员工；某用户有编辑权限，也可能只能编辑自己所在组织的特定记录。这属于对象级授权，不能只根据前端按钮权限判断。

10.4 Bearer Token、Cookie 和 CSRF

生产系统常见认证凭证传递方式包括 Cookie 会话和 Authorization: Bearer ... 等。如何储存和发送凭证取决于服务端设计、浏览器威胁模型及组织安全规范。

  • Cookie 方案应考虑 HttpOnly、Secure、SameSite、CSRF Token、会话过期与跨域配置。
  • Bearer Token 方案应特别关注令牌泄露、存储位置、过期更新和 XSS 风险。
  • 对外部第三方登录需遵循相应协议的状态验证、重定向及令牌校验规范。

不要在业务页面内散落处理刷新令牌的逻辑，也不应该因为学习教程简单就把敏感 Token 永久明文保存在 localStorage 中。

10.5 演示角色与真实权限的边界

配套项目允许在页面上切换“编辑者”和“查看者”，并将 X-Demo-Role 发送到 Mock API。Mock API 对查看者的写操作返回 403，从而演示“按钮控制”和“接口拒绝”的双层行为。

但任何人都可以伪造 X-Demo-Role 请求头。因此这只是学习路由、按钮展示、HTTP 403 处理的模拟环境，不具备真实身份认证和访问控制的安全性。绝不能将这种角色切换当成生产鉴权方案。

10.6 401、403 与业务行为

401 常见于缺少有效认证，应用需要与统一登录态维护逻辑协作。403 表示已理解请求但拒绝授权；继续弹出登录通常并不能解决权限不足。

当保存操作返回 403 时，不应直接关闭弹窗并显示“保存成功”。合理的行为是保留用户输入、提示权限不足，并在用户权限更新后由产品规则决定是否允许重试。

第 11 章 加载、空状态、错误与交互反馈

11.1 一个列表至少有多种状态

“列表没有记录”不应该只用 data.length === 0 判断：

  1. 初始加载：请求尚未完成，数据未知；
  2. 已成功且为空：请求完成，当前筛选条件确实无数据；
  3. 失败：请求没有成功，应提供错误与重试；
  4. 刷新中：旧数据可展示，后台正在更新；
  5. 权限拒绝：没有查看权限，不能伪装成空列表；
  6. 部分数据可用：例如部门字典失败，但员工列表已成功。

对应 UI 应有明显不同的含义。把所有失败都 catch(() => []) 会掩盖生产故障。

11.2 请求加载与操作加载不同

  • 页面首次加载可以展示骨架屏或表格 Loading。
  • 表格后台重新请求可保留旧内容，使用局部 Loading。
  • 表单提交应限制重复提交，但不必把整个应用阻塞。
  • 删除动作最好仅限制相关按钮，避免删除一条员工时所有操作都被不必要地锁定。

特别注意：Loading 是用户交互状态，不只是 CSS 动画。它必须准确反映真实操作是否已完成。

11.3 错误反馈应与可恢复行为对应

错误用户可以采取什么行动推荐反馈
网络暂时失败重试提示网络错误并提供重试按钮
字段不合法修改输入标记对应表单字段
工号冲突更换工号或查证明确指出冲突字段
无权访问联系管理员或更换合法身份提示权限不足，不无限重试
员工已删除返回列表详情不存在页
服务端故障稍后重试明确失败，不伪装成功

开发过程中应区分面向用户的提示和面向工程师的排错日志。不要把数据库连接字符串、异常堆栈或内部用户隐私原样展示在页面上。

11.4 异步竞态的两个方向

读请求竞态：用户连续改变搜索条件，旧请求可能比新请求更晚返回。使用 Query Key 和可取消查询降低数据串扰。

写请求竞态：用户连续提交相同表单，或在保存过程中切换页面、关闭弹窗。即使 UI 禁止重复点击，仍需要根据后端业务保证幂等与并发正确性。

这两种竞态处理不同，不能用同一个“防抖”方案解决所有问题。

11.5 Accessibility 与语义化交互

企业后台的复杂页面容易忽略键盘使用与无障碍基础：

  • 表单要有可关联的 label 与错误信息；
  • 链接用于导航，按钮用于动作；
  • 弹窗需要合理处理焦点与关闭行为；
  • 禁用按钮应有可理解的条件与说明；
  • 颜色不能是状态表达的唯一手段；
  • 表格列标题、排序和分页行为需要清晰。

成熟组件库可以帮助实现部分行为，但业务开发者仍需保证内容语义、状态提示和交互流程的合理性。

推荐让页面承担：

  • 对跨组件的页面行为进行协调。

  • 按传入数据绘制 UI；
  • 管理自身输入、校验和交互反馈；
  • 通过 Props 或明确的业务 Hook 通知外部动作；
  • 不擅自承担无关的路由、缓存或全局身份管理。

例如一个业务组件也可以使用某个独立查询 Hook；关键是职责是否清楚、测试是否方便、复用是否有意义。

12.4 错误处理应该在哪里完成

层次应处理什么
API ClientHTTP 状态、基础响应解析、标准异常类型
领域 API特定接口路径和契约，必要时做字段转换
Query / Mutation请求缓存、操作状态、失效、重试策略
页面 / 表单将错误转成对用户有意义的反馈
全局错误边界兜底渲染异常和应用级故障提示

错误边界（Error Boundary）用于捕获其子树渲染过程中以及受支持生命周期中的错误，它不会自动捕获所有异步 Promise reject、事件回调错误或网络请求失败。请求失败仍需由查询状态和业务 UI 明确处理。

12.5 代码复用不是“抽象越多越好”

常见的过度抽象：

  • 为单一页面封装一个只用一次且没有独立职责的 useEmployeePageManager，内部包含几十个 State；
  • 构造一个“通用 CRUD 配置系统”，反而让业务特殊规则只能依赖大量条件分支；
  • 所有业务字段都 any，以便通用组件兼容一切对象；
  • 为没有真实扩展点的组件暴露十几个透传 Props。

比较理想的复用是稳定机制的复用，例如：ApiError、请求客户端、分页 URL 解析、可访问的通用表单布局、Query Key 工厂等。

12.6 前端工程中的基本安全卫生

React 对普通文本插值默认进行转义，有助于减少直接拼接 HTML 的 XSS 风险，但不是所有场景都自动安全：

  • 不可信 HTML 通过 dangerouslySetInnerHTML 插入时需要可靠的清理策略；
  • 跳转 URL 需遵守协议白名单与可信域名规则；
  • 不把访问凭证、内部敏感信息直接写入仓库；
  • 不依赖前端权限隐藏实现数据安全；
  • 文件上传、富文本、下载等场景需要独立的服务端校验与安全设计。

虽然本篇不展开完整 Web 安全专题，这些基本边界在真正交付业务前端时必须理解。

第四部分：联调与综合实战

第 13 章 日常开发、前后端联调与排错

13.1 前端联调不是只看页面有没有渲染

一次规范的联调至少要核对：

  1. 请求地址、请求方法、URL 参数；
  2. 请求头、认证方式、请求体结构；
  3. 响应状态、错误码、数据形状；
  4. UI 的加载、成功、失败、空数据反馈；
  5. 列表和详情数据一致性；
  6. 权限不足、重复提交、刷新和返回路径行为。

对于 Java 后端开发者，可以从熟悉的 Controller DTO 契约入手，对照浏览器 Network 面板中实际发送的请求和收到的响应。不要因为后端 Postman 测试通过，就直接推断浏览器的 Cookie、代理、跨域或缓存行为也正确。

13.2 Chrome DevTools 中应观察什么

Network 面板：检查 Fetch/XHR 请求的 URL、Method、Status、Headers、Payload、Response、Timing；观察查询条件变化后是否重发请求、分页是否服务端实现、保存后哪些查询再次获取。

Elements 面板：检查 DOM 结构、CSS 规则和 Flex/Grid 布局；确认弹窗、表格滚动、响应式断点的实际行为。

Console 面板：定位 JavaScript 运行时异常、React key 警告、组件库弃用警告和未处理 Promise rejection。

Sources 面板：使用 Source Map 设置断点，跟踪 onFinish → Mutation → API Client → fetch 的调用过程。

React DevTools：观察 Props、State、Context 的变化，识别组件渲染与数据传递问题。

13.4 联调契约需要明确哪些细节

后端接口文档至少明确：

  • 请求方法、URL 和参数的含义；
  • ID 类型、字段必填及枚举取值；
  • 列表的分页参数和响应 total 语义；
  • 日期、时间字段的格式与时区约定；
  • 错误状态与业务错误码；
  • 身份认证与授权机制；
  • 数据一致性、重复提交和幂等语义；
  • 是否存在缓存、版本号或并发控制。

其中最容易引起业务 Bug 的往往不是语法，而是双方对字段和边界行为的理解不一致。例如 createdAt 是否带时区、total 是否表示过滤后的总条数、空数组和权限错误是否具有不同含义。

13.5 接口 Mock 的价值与限制

Mock 能够在后端环境暂不可用时，让前端先验证页面与交互契约。其价值在于减少等待并支持可控的异常模拟，不是证明生产接口一定符合契约。

本篇附带的 Mock API 使用 Node.js 内置 http 模块，依赖少、便于学习网络请求流程；但它使用内存数据，无法模拟数据库事务、真实认证和多人并发，也不等于正式后端服务。

  • test:api 通过 Node.js 的 node:test 检查 Mock API 的分页、角色拒绝、参数校验、唯一冲突和 CRUD 结果。
  • typecheck 进行 TypeScript 类型检查。
