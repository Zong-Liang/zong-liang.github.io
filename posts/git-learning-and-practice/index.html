第一部分：理解 Git，并能独立完成本地开发

1. Git 是什么？GitHub 又是什么？

Git 是分布式版本控制系统。它记录文件在一系列提交（commit）中的内容，让开发者能够比较版本、并行开发、合并变更和追溯历史。一个克隆得到的普通本地仓库通常包含可用的提交历史，因此许多版本管理操作不需要联网。

Git 负责版本控制；GitHub 是托管 Git 仓库、提供协作流程的平台。GitHub 在 Git 之上增加 Pull Request、代码评审、Issues、Actions、分支保护等功能。git commit 是 Git 操作，创建 PR 是 GitHub 协作操作。GitLab、Gitea 等平台也能托管 Git 仓库，但页面和权限规则不同。

概念用来做什么容易误解之处
Repository（仓库）保存项目文件、Git 对象和引用不只是一个代码文件夹；.git 存储版本元数据
Commit（提交）记录一次项目快照及其父提交、作者等元数据提交仅发生在本地，不等于上传 GitHub
Branch（分支）一个会随新提交移动的引用不是复制了一整套提交文件
HEAD表示当前检出位置，通常指向当前分支与某次提交的哈希不是同一概念
Remote（远程）对另一个仓库位置的命名配置origin 只是惯用名称，不表示某种特殊服务器
Pull Request（PR）请求评审并将变更合并到目标分支与 git pull 完全不是一回事
Fork在 GitHub 等平台创建归属于自己空间的仓库副本与 git clone 的本地复制不同

Git 本身可以记录谁提交了什么；至于为什么修改，需要依赖有信息量的提交说明、PR 讨论、Issue 或项目文档。Git 不会自动知道开发者的真实动机。

2. Git 的核心模型：一份文件为什么会有多个状态？

2.1 工作区、暂存区、HEAD

1
2
3
4
5
6
7

编辑器修改文件
    ↓
工作区（Working Tree）── git add ──→ 暂存区（Index）── git commit ──→ 新提交
    │                                 │
    └── git diff：与暂存区比较         └── git diff --staged：与 HEAD 提交比较

HEAD 通常指向当前分支（如 main），当前分支再指向最新提交。
  • 工作区（Working Tree）：你在编辑器中实际看到和修改的文件。
  • 暂存区（Index，又称 Staging Area）：Git 为下一次提交准备的内容清单。它不是一个单独的提交，而是提交之前的“候选快照”。
  • HEAD 指向的提交：当前分支最新提交的快照。git commit 创建新提交后，当前分支的指针会前进到新提交。

这里的关键不是“文件从 A 搬到 B”，而是：工作区、暂存区和 HEAD 可以同时保存同一路径的不同内容。 Git 借助这些差异决定下一次提交包含什么。

为什么不直接将所有修改提交？因为一次工作可能同时涉及修复 Bug、临时日志和无关格式调整。暂存区允许你只选择与这次提交相关的变更。git add -p 甚至可以将同一文件的一部分变更暂存，其他变更暂留工作区。

git status --short 的关键输出：

1

MM note.txt

短格式状态的两列分别对应暂存区相对于 HEAD 的变化（第一列）和工作区相对于暂存区的变化（第二列）。MM 表示 note.txt 有已暂存修改，同时又有尚未暂存的修改。

此时：

位置note.txt 的内容
HEAD只有 first line
暂存区first line + second line
工作区first line + second line + third line

因此，git diff 显示第三行相对暂存区的变化；git diff --staged 显示第二行相对 HEAD 的变化。如果现在提交：

1
2

git commit -m "docs: add second line"
git status --short

预期状态会从 MM note.txt 变成 M note.txt（第一列为空格），因为第二行进入了提交，第三行仍然留在工作区。随后执行：

1
2
3

git add note.txt
git commit -m "docs: add third line"
git status

最后应看到 nothing to commit, working tree clean 或等价的“工作区干净”提示。这组操作解释了为何 git add 后再次修改文件，需要重新 git add 才能包含新的修改。

如果版本过旧不支持 git init -b main，可先 git init，首次提交后执行 git branch -M main。本文后续练习默认分支叫 main。

2.3 常见状态怎么读

git status --short含义
?? a.txt新文件尚未跟踪
A a.txt新文件已加入暂存区
M a.txt已跟踪文件在工作区修改，未暂存
M a.txt修改已暂存，工作区没有额外变化
MM a.txt已暂存一次，之后又继续修改
D a.txt文件在工作区被删除，尚未暂存删除
UU a.txt合并时出现双方均未解决的冲突

Committed 不是与上述状态互斥的另一项“工作区状态”。提交是历史记录；是否还有待处理的文件变化，需要用工作区、暂存区和 HEAD 的差异判断。其他状态码可参考官方 git status。

2.4 Commit、Branch、HEAD 究竟是什么

1
2
3

A ── B ── C              main
      \
       D ── E            feature/login  ← HEAD

每个字母代表一个提交对象，保存项目树快照、父提交、作者、提交信息等；提交之间因此形成有向无环的历史关系。Git 通常用对象哈希标识提交（终端常显示缩写）。

上图中，main 指向 C，feature/login 指向 E。HEAD 通常指向当前分支 feature/login；在该分支提交新版本 F 后，是 feature/login 向前移动到 F，而不是另建一份完整的仓库。

HEAD~1 表示当前提交的第一个父提交，HEAD~2 表示连续沿第一个父提交向前两步。涉及合并提交（拥有多个父提交）时，需要格外注意父提交选择；初学时不要在复杂合并历史上直接套用清理命令。

如果直接检出某个历史提交或标签，Git 可能进入 detached HEAD（分离头指针） 状态：此时 HEAD 直接指向提交，而非某个分支。查看旧版本没有问题；如果要在此基础上继续开发并保留新提交，先执行 git switch -c <新分支名> 创建分支。

2.5 .git 目录里存了什么

通常可以把 .git 理解为当前仓库的数据库与管理信息所在位置，其中存储对象、引用、配置和日志等内容。git log、git show、git branch 是查看这些数据的友好入口。

不需要手工修改 .git/objects 或 .git/refs。要处理版本历史，优先使用 Git 命令。某些 linked worktree 的工作目录中，.git 也可能是指向实际 Git 管理目录的文件，而非目录。

3.2 先确定你使用一个账号，还是多个账号

Git 提交作者和 GitHub 登录账号是两套独立信息：

  • user.name、user.email：写入 Git 的提交记录；属于“作者是谁”。
  • SSH 密钥、HTTPS 凭据：控制谁有权限访问远程仓库；属于“用哪个账号登录”。

如果目前只使用一个 Git 身份，可配置全局默认值：

1
2
3

git config --global user.name "Your Name"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main

如果一开始就要管理个人、工作两套 GitHub 账号，建议先只设置 init.defaultBranch，把姓名和邮箱放在第 9 章的按目录配置中。 这样更不容易误把工作提交标记为个人身份。两套身份不意味着两个独立 Git 程序，也不需要创建两个操作系统用户。

仓库内部可以覆盖全局身份：

1
2

git config --local user.name "Project Author"
git config --local user.email "project@example.com"

--local 需要在 Git 仓库内执行。示例中的姓名、邮箱应换成实际用于提交的身份；工作仓库应遵守公司对提交邮箱的要求。配置可以查看其生效来源：

1
2
3

git config --list --show-origin
git config --show-origin --get user.name
git config --show-origin --get user.email

通常优先级为：系统级 → 全局级（包含 includeIf 引入的设置）→ 仓库级 → 命令行 -c；后面的同名配置通常覆盖前面的值。另外，Git 的环境变量可能覆盖作者、提交者等配置，极特殊情况应一起排查。

cd ~/git-study/git-lab

4.1 一个功能为什么要放在独立分支上

分支允许当前需求与 main 上已完成的版本分开演进。先在 main 上创建功能分支：

1
2
3
4
5
6
7
8

git switch main
git switch -c feature/greeting
printf 'hello from feature\n' > greeting.txt
git add greeting.txt
git diff --staged
git commit -m "feat: add greeting example"

git log --oneline --graph --decorate --all

结果：feature/greeting 指向新提交，而 main 仍指向创建分支时的提交。git switch main 可以切回主分支；此时工作区通常不会出现只存在于功能分支的 greeting.txt。

4.2 第一次合并：为什么看不到合并提交

1
2
3

git switch main
git merge feature/greeting
git log --oneline --graph --decorate --all

这里的历史没有分叉：主分支没有新提交，功能分支比它向前一步。因此 Git 通常直接将 main 指针移动到功能分支的位置，这称为 Fast-forward（快进合并），不会额外生成一个合并提交。随后可安全删除已合并的本地功能分支：

1

git branch -d feature/greeting

4.3 什么时候会生成合并提交

当 main 和功能分支从共同提交开始各自新增提交，历史出现分叉，常规的 git merge 会尝试将两条历史合并，通常形成一个带两个父提交的合并提交（前提是没有使用禁止合并提交等特殊策略）：

1
2
3

        D ── E   feature
       /      \
A ── B ── C ── M   main

合并提交 M 同时关联两条历史。无冲突时可以直接生成；双方修改冲突时，必须先解决冲突。是否强制保留合并提交，属于团队历史管理策略，不能因为图示好看就对所有项目设置 --no-ff。

4.4 提交前固定检查四件事

1
2
3
4

git status -sb              # 当前分支及改动概况
git diff                    # 工作区相对暂存区的改动
git diff --staged           # 下一次提交准备包含的改动
git diff --staged --check   # 检查已暂存改动中的空白字符等问题

对大型项目，运行相关单元测试、Lint 或构建检查再提交。一次提交最好只包含一项可理解的修改；需要时使用 git add -p 做部分暂存。提交说明重点写清改了什么、必要时解释为什么改，而不是“update code”。

目的推荐操作关键理解

查看未暂存差异git diff工作区与暂存区比较
查看待提交差异git diff --staged暂存区与 HEAD 比较

第二部分：远程仓库、GitHub 协作与多账号

6. 远程协作的基础：origin/main 到底是什么

本地独立开发解决了“保存版本”的问题，团队开发还需要交换提交。这时必须区分：远程服务器上的分支、你的本地分支、以及本地保存的远程跟踪引用。

6.1 三个容易混淆的名字

假设你克隆了 GitHub 上的 main 分支：

1
2
3
4
5
6

GitHub 服务器                       你的电脑

main ─── C                  main ─── C       （本地可直接提交的分支）
                               
                             origin/main ─── C
                             （上次获取远程信息后的本地记录）
  • 服务器的 main：远程仓库真实拥有的分支。
  • 本地 main：你正在开发或检出的本地分支。
  • origin/main：本地保存的远程跟踪引用，表示“上次获取到的 origin 上 main 的位置”；它不会因为别人推送到 GitHub 就即时变化。

比如同事已在服务器上将 main 推进到 D，而你尚未获取更新：

1
2
3

GitHub main ── D
本地 main   ── C
origin/main ── C   （过期）

执行 git fetch origin 后：

1
2
3

GitHub main ── D
本地 main   ── C   （还没合并）
origin/main ── D   （远程跟踪引用已更新）

再执行 git merge --ff-only origin/main，在没有本地分叉的前提下，本地 main 才会推进到 D。这解释了为什么 fetch 不会自动修改当前工作区的项目版本。

6.2 clone、fetch、pull、push 的分工

命令实际动作会不会直接整合进当前分支
git clone <url>获取仓库内容与历史，在本地创建仓库、远程和初始分支会建立初始工作区
git fetch origin获取远程对象和分支信息，更新本地远程跟踪引用不会
git pull --ff-only获取更新并且只允许快进整合到当前分支能快进才会，分叉则失败
git pull --rebase获取更新后将本地提交重放到目标历史之上会；可能改变本地提交哈希
git push将本地引用指定的提交发送给远程，并请求更新远程引用不会自动合并远端已有的不同提交

git pull 并不永远等于“先 fetch 再 merge”。它可以按参数或配置使用 rebase 等整合策略。初学阶段更新没有本地开发提交的主分支，推荐显式使用 git pull --ff-only，这样出现分叉时不会悄悄生成合并提交，也不会悄悄重写本地提交历史。

6.3 上游分支（upstream）与 -u

在已经配置 origin、并已创建 feature/user-profile 分支的仓库中，第一次推送可用：

1

git push -u origin feature/user-profile

-u（--set-upstream）建立当前本地分支与远程分支的跟踪关系。以后在这个分支上，通常可以直接执行 git push，并可让不带参数的 git pull 找到默认的上游分支。能否直接推送还受推送配置和远程权限影响。

查看跟踪关系：

1
2
3

git branch -vv
git status -sb
git remote -v

例如 feature/greeting [origin/feature/greeting: ahead 1] 表示根据当前本地远程跟踪信息，本地比上游多一个提交；为了获取服务器的最新状态，可以先 git fetch origin，再检查是否仍然 ahead / behind。

一个仓库可能有多个远程，如 origin 指向自己的 Fork，upstream 指向开源原仓库。origin 与 upstream 都只是名字，不是 Git 的保留字。

7. 把 Git 和 GitHub 连接起来

7.1 HTTPS 和 SSH，选哪个

GitHub 常见的远程地址有两种：

1
2

HTTPS: https://github.com/OWNER/REPO.git
SSH:   git@github.com:OWNER/REPO.git
  • HTTPS：常配合 Git Credential Manager（GCM）及浏览器授权使用。GitHub 不支持直接使用账号登录密码进行 Git HTTPS 认证；在相应认证流程中可以使用令牌等方法。
  • SSH：用本地私钥证明身份，并把相应公钥绑定到 GitHub 账号。适合终端开发和多账号隔离。

两种协议都能正常协作；不应为了“安全”就要求所有项目统一改为 SSH。团队代理网络、组织认证策略和现有凭据管理器都可能影响选择。以下使用 SSH 作为主要示例。

7.2 配置第一个 GitHub SSH 密钥

先查看本机是否已有可用 SSH 密钥，不要随意覆盖：

1

ls -al ~/.ssh

没有专用密钥时，生成一组新的 Ed25519 密钥：

1

ssh-keygen -t ed25519 -C "you@example.com" -f ~/.ssh/id_ed25519_github

按提示设置私钥口令（passphrase），生成：

1
2

~/.ssh/id_ed25519_github       私钥：留在本机，不能上传、发给别人或加入 Git
~/.ssh/id_ed25519_github.pub   公钥：可以添加到 GitHub 账号

按需添加到 ssh-agent：

1
2
3

eval "$(ssh-agent -s)"
ssh-add ~/.ssh/id_ed25519_github
cat ~/.ssh/id_ed25519_github.pub

复制 .pub 内容，登录 GitHub，前往 Settings → SSH and GPG keys → New SSH key，将其作为用于身份认证的 SSH key 添加。某些系统或企业策略下，菜单名称可能有细微差异。

在 ~/.ssh/config 中添加一段配置（如果文件已经存在，编辑原文件，不要覆盖其他 Host 配置）：

1
2
3
4
5
6

Host github.com
    HostName github.com
    User git
    IdentityFile ~/.ssh/id_ed25519_github
    IdentitiesOnly yes
    AddKeysToAgent yes

测试：

1

8. 一条完整的团队协作流程：从分支到 PR 合并

假设 GitHub 仓库 origin 已存在，默认分支为 main，你具有推送功能分支和创建 PR 的权限。此处不是演示真实仓库已存在的事实，而是说明一个常见、可复用的团队流程。

8.1 从最新的主分支开始工作

1
2
3
4
5

git switch main
git fetch origin
git merge --ff-only origin/main

git switch -c feature/user-profile

其中：

  • fetch 更新本地的 origin/main 引用；
  • merge --ff-only 只允许把本地 main 快进到远端状态，避免未经判断的分叉合并；
  • switch -c 从当前 main 新建并进入功能分支。

也可以用 git pull --ff-only origin main 完成前两条更新步骤。若本地主分支已出现分叉，命令会失败；先检查历史，而不是立即使用 reset --hard。

8.2 修改、验证、提交、推送

git push -u origin feature/user-profile

8.3 在 GitHub 创建 Pull Request

打开仓库页面，找到刚推送的分支，可使用 Compare & pull request；或从 Pull requests 页面创建。务必核对：

  • base：准备把修改合并到哪里，通常是 main；
  • compare：包含本次修改的来源分支，如 feature/user-profile；
  • PR 标题和描述：此次改动解决什么问题、主要改了什么、如何验证、是否有兼容性/数据迁移风险。

如果尚未准备好评审，可使用 Draft PR（草稿 PR）。发起 PR 后，代码评审者通常查看文件差异、提交记录与自动检查结果，而不是简单检查“是否有提交”。

8.4 收到评审意见，应该怎么更新 PR

回到本地同一功能分支修改代码、重新验证、继续提交并推送：

8.5 主分支在你开发期间更新了怎么办

先获取远程历史：

1
2
3

如果团队接受合并式历史，可以把新的主分支合入功能分支：

1

git merge origin/main

如果团队采用线性历史，并且该功能分支没有被其他开发者共同依赖，可以根据约定使用：

1

两者的历史差异在第 10 章详细解释。不要在多人共用的已发布分支上随意 rebase。若 rebase 后确需更新自己控制的远程功能分支，必须理解为什么普通 push 可能被拒绝，并在确认无他人新提交的前提下考虑 --force-with-lease；不要使用无条件 --force。

8.6 PR 合并后如何整理本地环境

GitHub 常见的 PR 合并策略有三种：Create a merge commit 保留分支上的提交并建立合并节点；Squash and merge 将 PR 的变化汇总为一个新提交；Rebase and merge 将提交重新应用到目标分支，通常形成新的提交哈希。可选方式取决于仓库设置与团队约定。

当 GitHub 页面确认 PR 已合并后，回到本地：

1
2
3
4
5

git switch main
git fetch origin
git merge --ff-only origin/main

git branch -d feature/user-profile

注意：如果 GitHub 使用 Squash and merge 或 Rebase and merge，本地原功能分支的提交可能不再被 main 以相同哈希包含。此时 git branch -d 可能拒绝删除，即使 PR 已完成。这是保护机制，并不说明 GitHub 合并失败。确认远端 PR 已合并、原分支工作不再需要且没有未保存修改后，可使用 git branch -D feature/user-profile 强制删除本地引用。

如果团队还需要清理远程功能分支，可在确认权限和协作约定后执行：

1

git push origin --delete feature/user-profile

删除远程分支前应确认没有其他 PR 或开发者依赖它。GitHub 页面也可能提供 Delete branch 操作。

10. Merge、Rebase 与冲突：知道历史发生了什么

10.1 Merge 和 Rebase 的区别，不是哪个命令“更高级”

假设在共同提交 B 后，主分支新增 C，功能分支新增 D、E：

1
2
3
4
5

      C            main
     /
A ─ B
     \
      D ─ E        feature

Merge 将两条历史连接起来，可能新建合并提交 M：

1
2
3
4
5

        C ──────┐             main（仍指向 C）
       /        │
A ── B          M            feature（合并完成后指向 M）
       \       /
        D ── E ┘

Rebase 把功能分支相对共同基点的提交重新应用在 C 后面，生成新的 D′、E′：

1

A ─ B ─ C ─ D′ ─ E′    feature

因此：

对比项git merge origin/maingit rebase origin/main
主要效果合并两条历史将当前分支提交重放到新基点
原始提交哈希通常保留被重放的提交通常变化
历史形态可能保留分叉和合并节点功能分支形成相对线性的历史
冲突发生点合并过程中处理逐个重放相关提交时可能处理
适用前提共享分支也通常可以合并更适合自己控制、允许改写历史的分支

两者都不能代替代码审查和测试。Merge 不保证不会发生语义冲突；Rebase 也不是简单的“移动分支指针”，因为它可能改写提交对象。

git status

预期结果：冲突标记消失，Git 生成合并提交，提交图能看到两个父提交，工作区恢复干净。真实项目还必须运行相关测试，因为“文本冲突已解决”并不代表“业务逻辑一定正确”。

10.3 中途不想继续，如何安全退出

合并遇到困难，想撤销这次尚未完成的合并：

1

git merge --abort

若冲突发生在 rebase 过程中，解决后要运行：

1
2

git add <resolved-file>
git rebase --continue

或者中止这次 rebase：

1

git rebase --abort

务必先用 git status 判断当前到底在 merge 还是 rebase；别把 git commit 和 git rebase --continue 混用，也不要为了退出冲突而直接 git reset --hard。有复杂的未提交改动时，--abort 也未必能把所有状态恢复到你想象的样子，开始整合前保持工作区干净更可靠。

10.4 用 Git 图形界面解决冲突是否可靠

IDE 的“三方合并”界面可以提高效率，但“Accept Current / Incoming”中的“当前”和“传入”会受工具和操作上下文影响，尤其在 rebase 时不能简单按字面理解。先确认哪个版本代表什么，再解决。检查最终 Diff 和跑测试，比选哪一个按钮更重要。

11. 误操作恢复：根据修改所处的位置选择命令

Git 的撤销命令看起来很多，但核心问题只有三个：要改变工作区、暂存区，还是提交历史？这段历史是否已经共享？

11.1 先用表格判断，避免选错命令

当前情况优先考虑具体影响
工作区修改不想要了，尚未暂存git restore <file>用暂存区内容覆盖对应工作区文件；会丢失未暂存修改
已暂存，但希望保留修改再调整git restore --staged <file>从暂存区撤出，工作区修改保留
最后一次未共享提交信息有误git commit --amend重新创建最后一次提交，哈希变化
想取消最新一次未共享提交，改动继续保持暂存git reset --soft HEAD~1移动分支指针，不改变暂存区或工作区
想取消最新一次未共享提交，改动留工作区git reset --mixed HEAD~1移动分支指针，重置暂存区，不覆盖工作区
想撤销已共享提交的变更git revert <hash>产生新的反向提交，保留共享历史
不小心移动了分支、找不到旧提交git reflog查询最近引用移动记录，再考虑恢复引用
确定丢弃被跟踪文件的本地改动git reset --hard ...高风险，可能覆盖工作区和未跟踪的阻挡文件
清理未跟踪文件与目录git clean -nd 预览，再慎用 git clean -fd高风险，不是普通撤销

对于 reset --hard，更准确的说明是：它让索引和工作区与指定提交一致；同时可能覆盖妨碍写入的未跟踪文件，但并不等同于清理全部未跟踪文件。这与 git clean 的职责不同。

11.2 实验一：从工作区撤销，和从暂存区撤销有什么区别

在干净的 git-lab 仓库中执行（note.txt 已被跟踪）：

1
2
3
4
5

cd ~/git-study/git-lab
printf 'temporary change\n' >> note.txt
git status --short
git restore note.txt
git status --short

预期：未暂存修改被丢弃；仓库恢复干净。下一组：

1
2
3
4
5

printf 'change to keep\n' >> note.txt
git add note.txt
git status --short              # M  note.txt
git restore --staged note.txt
git status --short              #  M note.txt

这次仅撤出了暂存区，change to keep 还在工作区。为了保持练习环境干净，可以先检查内容，再执行 git restore note.txt 丢弃这次练习的修改；不要对真实业务改动照做。

11.3 实验二：reset --soft、--mixed 和 revert 实际会改变什么

新建独立仓库，以免操作到其他实验的历史：

1
2
3
4
5

9
10
11

mkdir -p ~/git-study/git-recovery-lab
cd ~/git-study/git-recovery-lab

git config user.name "Git Learner"

printf 'version 1\n' > demo.txt
git add demo.txt
git commit -m "docs: add version 1"

git add demo.txt
git commit -m "docs: add version 2"

git log --oneline -2

第一步：--soft。

1
2
3

git reset --soft HEAD~1
git status --short
git diff --staged

预期：第二个提交不再是 main 的当前提交，但其文件修改仍在暂存区，git status --short 会显示 M demo.txt。

第二步：重建版本 2，再用 --mixed。

1
2
3
4

git commit -m "docs: recreate version 2"
git reset --mixed HEAD~1
git status --short
git diff

预期：第二个提交再次从当前分支历史顶部撤掉，但 demo.txt 在工作区仍是 version 2，状态显示 M demo.txt。--mixed 默认不覆盖工作区内容。

第三步：重建版本 2，再执行 revert。

1
2
3
4
5
6
7

git add demo.txt
git commit -m "docs: recreate version 2 again"
git revert --no-edit HEAD

git log --oneline -3
cat demo.txt
git status

预期：revert 新建一个撤销最新变更的提交，不会删除或重写被撤销的那个提交；demo.txt 回到 version 1，历史中仍可见新增版本 2 的提交和后续的 revert 提交。真实项目的 revert 也可能发生冲突，需要按 Git 提示处理。

操作分支指针 / 历史暂存区工作区

reset --mixed HEAD~1回到父提交重置为目标提交保持不变
reset --hard HEAD~1回到父提交重置为目标提交重置为目标提交；危险
revert HEAD新增一个反向提交成功完成后通常干净反映撤销后的文件内容

11.4 提交“丢失”时，先看 reflog

如果误执行了 reset，导致原先的提交从分支历史中消失，先查询引用移动记录：

1

git reflog --date=local

从输出中找出想恢复的提交哈希，例如 abc1234（仅为示例，执行时须替换成真实哈希）。先不要覆盖当前分支，可以创建一条救援分支保存该提交：

1
2

git branch rescue-lost-work abc1234
git log --oneline rescue-lost-work -5

确认恢复内容后，再决定是切换分支、cherry-pick 还是其他操作。reflog 主要记录引用/HEAD 的移动，不是万能文件恢复工具；未提交修改不一定能从它找回，记录与对象也会随时间过期、被清理。

11.5 什么情况下不要改写共享历史

已经推送到团队共同分支、被他人拉取或已有下游依赖的提交，应优先 revert，而不是通过 reset + 强推消除历史。只有确认分支由你独立控制、团队允许重写时，才可考虑 rebase / amend 后使用：

1

git push --force-with-lease

--force-with-lease 相较无条件 --force 能提供额外保护，但也不是完全不出错的保证：需要先检查远端是否有他人提交、确认推送目标，并遵守团队规则。不能把它当作普通 git push 的替代品。

12. 项目规范：哪些文件该提交，怎样保持历史可维护

12.1 .gitignore 是过滤规则，不是秘密保险箱

常见规则示例（按项目实际情况调整）：

1
2
3
4
5

# 本地运行时配置
.env

!.env.example

# 构建和依赖
node_modules/

# 日志与系统文件
*.log

.env.example 只应包含无敏感性的示例键和值。git check-ignore -v .env 可检查命中的规则；git status --short --ignored 可以查看哪些文件被忽略。

注意：.gitignore 只影响尚未跟踪的文件。 已提交过的文件即使后来加入 ignore 规则，也不会自动从历史和索引中消失。若要停止跟踪但保留工作区文件，可先确认路径，然后：

1
2

git rm --cached path/to/local-config
git commit -m "chore: stop tracking local config"

这并不会抹掉已有提交中的文件内容。因此如果曾经推送了真实密码、密钥、令牌：先撤销或轮换凭据，再按组织安全要求评估是否要清理历史、通知协作者。GitHub 的 敏感数据移除指南 也强调，重写远端历史不能保证所有克隆和缓存中的副本消失。

12.2 .gitattributes 控制文件属性和换行符

多人跨平台协作可能出现整个文件因 CRLF / LF 差异而被认为发生修改。仓库可以用 .gitattributes 约定：

1
2
3

* text=auto
*.sh text eol=lf
*.bat text eol=crlf

引入该文件后，如果存量项目出现大规模换行符调整，应该单独检查其影响，避免把格式归一化与业务改动混在一个提交中。不要把修改所有人的 core.autocrlf 作为唯一解决方案。

12.3 提交质量：小而完整，能解释变化

一次提交应尽量只处理一个可理解的目标：功能、修复、重构、测试或文档更新。不是强制一个文件一次提交，也不是文件越少越好，而是审查者能说明它做了什么、为什么需要、能否单独验证。

常见 Conventional Commits 风格（是一种项目约定，不是 Git 强制语法）：

1
2
3
4
5
6

feat: add user login API
fix: reject duplicate approval requests
refactor: extract permission check
test: cover organization validation
docs: document local setup
chore: update build tooling

有必要解释设计取舍时，可以在提交正文中写明原因。提交前运行：

1
2
3

git diff --staged --check
git diff --staged
git status -sb

不要因为 git add . 方便，就省掉审查暂存内容的步骤。

12.4 不必一开始就引入的进阶机制

  • Git LFS：适用于需要版本化管理的大型二进制文件；不意味着大文件一律适合进入 Git。
  • Submodule：把另一个仓库的特定提交作为依赖引用，适合明确需要独立仓库与固定版本的场景；增加协作复杂度。
  • Git Hooks：可以在本地提交前运行格式检查等；默认 .git/hooks 不会随仓库提交自动同步到其他开发者，团队需另行管理。
  • GitHub Actions / CI：可在 PR 或推送后运行测试、Lint 等检查；它不替代开发者对业务正确性的判断。

先满足项目现有规范，再引入额外工具。不能因为工具存在就必须把它加进每个仓库。

2
3

git fetch origin
git status -sb
git log --oneline --graph --left-right HEAD...origin/feature/user-profile

带左右标记的历史可帮助判断哪些提交只在本地、哪些只在远程。之后再选择 git merge origin/feature/user-profile、按团队约定 rebase，或请同事确认远程改动。不要把报错误读成“必须强推”。

13.3 Git 显示“文件改动被覆盖风险”时

先明确这批修改是否还有价值。常见选择：

  • 已完成且应该纳入历史：检查暂存区后提交。
  • 临时打断当前任务：使用 git stash push -u -m "wip" 暂存现场，然后检查 git stash list。
  • 确定不要：只针对已确认文件执行相应 restore，而不是对整个仓库强制重置。

stash 保存的是 Git 能管理的临时改动，不是可靠的长期备份方案；使用它之前也应注意忽略文件、未跟踪文件和未提交工作状态。

第四部分：进阶能力与日常速查

14. 开发到一定阶段后，再学这些工具

14.1 stash：暂存还不能提交的工作现场

场景：功能开发做了一半，需要暂时切换去处理紧急 Bug，但当前改动还不适合形成提交。

1
2
3
4
5
6
7

git status
git stash push -u -m "wip: user profile validation"
git stash list

# 处理完临时任务后，切回原分支
git stash apply 'stash@{0}'
git status

-u 额外包含未跟踪文件，但不包含被 ignore 的文件。相比 git stash pop，apply 默认不会移除 stash 记录，适合不确定能否干净恢复的场景；确认变更恢复并不再需要后，可以使用 git stash drop 'stash@{0}' 删除相应 stash。pop 会尝试应用并移除记录，但冲突时通常保留记录供处理。stash 不能替代提交、远端备份和文件备份。

14.2 cherry-pick：把一个提交带到另一条分支

场景：release 已上线但需要把 main 上某次独立修复移植过去。

1
2

git switch release
git cherry-pick <fix-commit-hash>

Git 会在目标分支尝试应用该提交的变更，通常生成一个新的提交。它不是简单移动原提交，也可能产生冲突。使用前确认修复提交是否依赖其他未包含的提交，避免只挑一个提交却引入不完整改动。

14.3 worktree：一个仓库同时打开多个开发目录

场景：当前正在开发功能 A，又要在另一个目录并行修复 Bug，不希望反复 stash 和切换分支。

1
2
3

# 在已有 Git 仓库目录执行
git worktree add -b hotfix/issue-123 ../repo-hotfix main
git worktree list

这样 ../repo-hotfix 会以新建的 hotfix/issue-123 分支检出；两个工作目录共享同一个仓库的对象与常规引用，但各有独立的工作区和暂存区。一般不能在两个 worktree 中同时检出同一条本地分支，这是 Git 的保护行为。

任务结束并确认目录内没有需要保存的修改后，可在其他工作区执行：

1
2

git worktree remove ../repo-hotfix
git worktree list

如果在 worktree 中采用 includeIf "gitdir:..." 做账号隔离，应特别检查配置来源；因为 linked worktree 的实际 Git 目录位置可能位于主仓库的 .git/worktrees/...，不能仅凭工作目录名推断作者配置一定命中。需要时改用仓库级身份、仔细配置适用的 worktree: 条件，或逐仓库核验。

14.4 bisect：用二分定位从哪个提交开始出错

已知某个历史提交没有 Bug，当前版本存在 Bug，且有可重复执行的验证方式时，可以使用：

1
2
3

git bisect start
git bisect bad
git bisect good <known-good-commit>

Git 会让你测试中间版本，运行测试后标注 git bisect good 或 git bisect bad；找到可疑提交后执行 git bisect reset 恢复正常检出状态。它要求“好/坏”的判断相对稳定，否则二分结论不可靠。

14.5 Tag 与发布版本

如果团队要对某个版本进行标记，常见使用带注释标签：

1
2

git tag -a v1.0.0 -m "release v1.0.0"
git push origin v1.0.0

普通 git push 不保证自动推送全部标签。标签用来命名特定提交，不等于 GitHub Release：后者还可以包含发布说明和构建产物。
