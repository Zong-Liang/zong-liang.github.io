第一部分：React 的表达模型

第 1 章 从原生 DOM 编程到 React

1.1 命令式更新的复杂性

第二、三阶段的员工管理项目可能通过下面的过程更新列表：

1.2 React、React DOM 和浏览器分别承担什么

  • react：提供组件、Hooks、元素描述等核心 API。
  • react-dom/client：负责将 React UI 渲染到浏览器 DOM，例如 createRoot。
  • 浏览器：解析最终 DOM/CSS，处理布局、绘制、交互、网络与平台 API。
  • Vite：开发服务器和构建工具，并不是 React 的运行时组成部分。

React 并不替代 HTML、CSS、HTTP 或 JavaScript 的基础机制。例如浏览器的同源策略、Cookie 限制、布局算法不会因为使用 React 而改变。

1.3 React 元素、组件与 DOM 节点

组件是负责描述 UI 的函数：

1
2
3

function Greeting({ name }: { name: string }) {
  return <p>你好，{name}</p>;
}

<Greeting name="张三" /> 是 JSX 写法，表达一个组件元素；它不是在那一行直接调用浏览器 document.createElement。React 会根据组件树计算结果，再协调宿主节点。React 组件、React 元素与真实 DOM 元素是不同层面的对象。

一般不应把组件函数直接当作普通函数调用，例如 Greeting({ name: "张三" })。应由 React 通过 JSX 渲染，这样组件才能正确参与 React 的生命周期、身份和 Hooks 机制。

1.4 React 组件的纯度

渲染期间组件应该像纯函数：相同的 Props、State 和相关上下文输入应产生可预测的 UI 描述，不应在渲染过程中写本地存储、发 POST 请求、修改传入的数组或操纵 DOM。

// 错误示例：渲染时直接改变 props 传入的数据

// 正确：创建副本，不改动外部传入对象

  const sorted = [...names].sort();
  return <p>{sorted.join("、")}</p>;
}

开发环境启用 StrictMode 时，React 会重复调用组件函数，用来暴露不纯的渲染。生产环境中 React 也可能中断并重新开始尚未提交的渲染，例如 Transition 被更紧急的更新打断时。渲染纯度因此是一条正确性约束，而非单纯的编码偏好，也不只在开发期才需要。

1.5 React 不负责什么

React 核心不默认提供服务端业务接口、客户端路由、完整全局状态方案或生产级数据缓存方案。React 可以与这些能力集成，但需要框架、库或项目自身的设计。它也不替代后端鉴权；前端按钮是否展示不能决定 API 是否有权限。

第 2 章 JSX、TSX 与应用入口

2.1 JSX 的定位

JSX 是可以在 JavaScript / TypeScript 中描述 UI 的语法扩展。.tsx 文件是 TypeScript 与 JSX 的常见组合。JSX 不是浏览器原生 HTML 文本；构建工具会将其转换为 JavaScript 可执行形式。

1
2
3
4
5
6
7
8
9

const title = "员工管理";
const count = 10;

const section = (
  <section className="panel">
    <h2>{title}</h2>
    <p>当前共有 {count} 人</p>
  </section>
);

JSX 的标签看起来像 HTML，但规则不完全相同：

  • class 属性写成 className；可访问性属性继续使用 aria-label 等标准名称。
  • JSX 表达式使用 {}，在其中可以放 JavaScript 表达式，不能直接写 if 语句。
  • 返回的元素需要有一个共同的父层，或使用 Fragment：<>...</>。
  • 标签必须正确闭合，例如 <input />。
  • style 接收对象，例如 style={{ color: "red", fontSize: 16 }}；一般业务样式优先使用 CSS 类。
  • {undefined}、{null}、{false} 本身不会显示文本，但数字 0 会显示。

2.2 JSX 的表达式与安全边界

1
2
3
4
5

function EmployeeTag({ active }: { active: boolean }) {
  return <span className={active ? "status--active" : "status--inactive"}>
    {active ? "在职" : "离职"}
  </span>;
}

React 会按文本节点的语义处理普通插值，而不是把字符串自动解释为 HTML：

1
2

const input = "<script>alert(1)</script>";
return <p>{input}</p>; // 显示为文本，不执行其中的 script

不要把“普通 JSX 文本会转义”推广为“所有动态内容天然安全”。URL、外部脚本、第三方组件、dangerouslySetInnerHTML 等仍需要独立审查。涉及 HTML 富文本时必须明确可信来源、清洗策略与 CSP 等约束。

2.3 条件表达式的细节

1
2

{error && <p role="alert">{error}</p>}

注意下面的常见陷阱：

1

{count && <p>有数据</p>}

当 count 为 0 时，整个表达式求值为数值 0，React 会渲染字符 0。更稳妥的是：

1

{count > 0 && <p>有数据</p>}

2.5 TSX 中的类型规则

TSX 允许为 Props、事件、Ref 等声明类型。与 .ts 文件相比，尖括号语法可能与 JSX 标签冲突，因此部分泛型箭头函数会写成 <T,> 以消除歧义：

1

const identity = <T,>(value: T): T => value;

ReactNode 用于表达“可以渲染的子内容”，ReactElement 更接近 React 元素对象。它们不应无差别互换；后续组件示例会按需要使用。

第 3 章 组件、Props 与组合

3.1 组件的职责与命名

React 函数组件通常使用大驼峰命名，并返回可渲染内容：

1
2
3

function DepartmentBadge({ name }: { name: string }) {
  return <span className="badge">{name}</span>;
}

小写 JSX 名称通常表示宿主 DOM 标签；大写名称通常表示自定义组件。区分不是风格问题，而是 JSX 语义的一部分。

组件边界应围绕界面职责、数据变化与复用需求决定，而不是“一段 HTML 就必须抽成一个组件”。实际项目中可以将员工管理页拆为：页面容器、条件筛选、员工表格、统计卡片、编辑弹窗。页面级组件负责协调数据和交互，子组件负责明确的展示或局部输入逻辑。

在通常的父子组件关系中，数据由父组件通过 Props 向下传递；子组件通过回调描述发生了什么，再由父组件决定是否更新自己的状态：

function EmployeeSelector({ value, onChange }: {
  value: string;

3.5 组件设计的三个边界

问题判断方法
哪个组件持有状态？谁需要读写这项数据？找到最近的共同祖先，尽量避免把状态抬得过高
哪个组件负责业务规则？规则是纯计算还是 UI 交互？纯计算优先放独立函数，方便测试
什么值得复用？复用的是稳定职责和行为，还是仅仅视觉上相似？不急于抽象一次性页面

第 4 章 条件渲染、列表渲染与 key

4.1 三种常见条件渲染形式

1
2
3

if (load.kind === "loading") return <p>加载中…</p>;
if (load.kind === "error") return <p role="alert">{load.message}</p>;
return <EmployeeTable employees={load.employees} />;

也可以使用三元表达式或 &&，但分支较多时，提前 return 或显式分支更容易阅读。return null 表示当前组件不输出节点，但组件仍然存在于 React 组件关系中，不等于没有执行渲染函数。

4.2 数据渲染

1
2
3
4
5
6
7
8

<tbody>
  {employees.map((employee) => (
    <tr key={employee.id}>
      <td>{employee.id}</td>
      <td>{employee.name}</td>
    </tr>
  ))}
</tbody>

React 需要稳定的 key 在同一层兄弟节点之间区分列表项。key 在兄弟节点范围内必须唯一；不同列表可以重复相同 key。它不会作为普通 props.key 传给组件，若业务确实需要 ID，应再显式传递。

优先使用员工工号、数据库 ID 等稳定且真正代表项目身份的字段。数组索引只有在列表顺序、插入和删除行为都不会影响状态身份时才适合作为 key。Math.random() 等每次渲染改变的 key 会导致组件失去稳定身份，造成状态丢失与不必要的卸载、重新挂载。

4.3 key 与条件渲染不能割裂

当列表项内部包含输入框、展开区域或局部状态时，错误的 key 可能把某个列表项的状态错误地匹配给另一个项目。例如按姓名重新排序后，如果 key 是数组索引，处于同一位置的组件可能保留了原来另一位员工的输入状态。

这与 Java 后端中的实体 ID 概念有关，但 key 是 React 在特定组件树位置使用的身份提示；它不是业务后端主键约束的替代方案。

4.4 空状态、加载状态与错误状态

在实际管理后台中，employees.length === 0 无法判断是“尚未加载”“成功返回空数组”还是“加载失败”。推荐明确建模：

1
2
3
4

type LoadState =
  | { kind: "loading" }
  | { kind: "ready"; employees: Employee[] }
  | { kind: "error"; message: string };

这种判别联合避免 isLoading、hasError、employees 三组值互相矛盾。TS 类型可以帮助穷尽分支，也能让 React UI 渲染路径更加清晰。

第 5 章 React 事件系统与受控输入

5.1 事件处理函数与 JSX 属性

1
2
3
4
5
6

function Toolbar() {
  function handleClick() {
    console.log("查询按钮被点击");
  }
  return <button onClick={handleClick}>查询</button>;
}

onClick={handleClick} 传入函数；onClick={handleClick()} 则会在渲染时调用它，通常是错误。需要传参数时：

1

<button onClick={() => onEdit(employee.id)}>编辑</button>

React 的事件接口与浏览器原生事件 API 有关联，但并非简单的 addEventListener 拼写替换。常见事件可使用类型化的 React.MouseEvent、React.ChangeEvent、React.FormEvent 等。事件处理函数中的 event.currentTarget 是绑定该监听器的元素，与可能指向内部元素的 event.target 要区分。

5.2 默认行为与事件传播

1

import type { FormEvent } from "react";

function SearchForm() {
  function handleSubmit(event: FormEvent<HTMLFormElement>) {
    event.preventDefault(); // 避免浏览器提交表单导致页面导航
  }
  return <form onSubmit={handleSubmit}><button type="submit">查询</button></form>;

preventDefault() 阻止可取消的默认行为，stopPropagation() 阻止事件继续传播；这两个动作不是一回事。组件内部要不要阻止冒泡，应由具体的交互语义决定，不应普遍拦截。

受控输入的显示值由 React State 决定，输入变化通过事件更新状态：

value 和 onChange 是成对出现的常见组合。只设置 value 不提供更新路径会让字段难以编辑。对于 checkbox，通常使用 checked 与 onChange。

5.4 受控与非受控表单的取舍

  • 受控表单：适用于实时校验、多个字段联动、条件禁用、复杂编辑弹窗；React 对当前显示值负责。
  • 非受控表单：可通过 defaultValue/defaultChecked 设置初值，提交时再使用 FormData 等读取；简单一次性输入可能更简洁。
  • type="file" 的文件输入通常由浏览器管理选择结果，不能像普通文本框一样直接控制其选中路径。

不要将受控模式理解为“高级、非受控模式低级”。判断依据是状态管理需求与组件 API。

5.5 表单初始化与重新编辑

一个编辑弹窗从“张三”切换到“李四”时，如果只是把新的 employee Props 传给一个已经挂载的表单组件，而表单内部 useState(employee.name) 只在首次挂载时初始化，就可能仍然显示张三。

可选方案：根据 employee.id 设置不同的 key，使 React 重新建立表单组件的身份；或者将表单状态完全交由父组件控制。不要第一反应就在 Effect 中无条件把 Props 复制到 State，因为这会增加同步链和覆盖用户输入的风险。

第 6 章 useState：状态快照、更新队列与批处理

6.1 为什么普通变量不够

1
2
3
4

function Counter() {
  let count = 0;
  return <button onClick={() => { count += 1; }}>计数：{count}</button>;
}

点击不会自动要求 React 重新执行组件，普通局部变量也不在下一次组件调用之间保持 React 所管理的状态。正确方式：

1
2
3
4
5
6

function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount((previous) => previous + 1)}>
    计数：{count}
  </button>;
}

useState(initialState) 返回当前渲染的状态值以及调度更新的 setter。React 保存状态，并把它与组件在 UI 树中的身份关联起来。

6.2 State 是当前渲染的一份快照

1
2
3
4
5
6

const [count, setCount] = useState(0);

function handleClick() {
  setCount(count + 1);
  console.log(count); // 这里仍是当前渲染快照中的值，不是下次渲染值
}

setter 的含义是安排 React 在后续渲染中使用新的状态；不会原地改写当前函数闭包里 count 的值。

6.3 更新队列与函数式更新

1
2
3
4
5

function addThree() {
  setCount(count + 1);
  setCount(count + 1);
  setCount(count + 1);
}

三次读取的都是当前渲染快照中的 count，它们都要求替换成同一个值。需要依赖上一次排队更新的结果时：

1
2
3
4
5

function addThree() {
  setCount((value) => value + 1);
  setCount((value) => value + 1);
  setCount((value) => value + 1);
}

React 会依次处理这些更新函数。更新函数需要保持纯净：不能在其中发送请求、写入浏览器存储、随机分配 ID 或直接修改共享对象。开发期 StrictMode 可能额外调用更新函数用于检查纯度。

6.4 批处理不是“所有操作同步执行”

React 会将同一批次内的多个状态更新合并处理，减少不必要的渲染。现代 React 对不同异步上下文也支持自动批处理，但不意味着所有跨时间的更新必然落在同一个批次。不要用“每调用一次 setState 必定渲染一次”或“调用完 setter 立即可读到新值”推导业务逻辑。

第 7 章 状态结构、派生状态与状态提升

7.1 什么应该成为 State

在员工管理页中：

  • 员工原始集合：需要保留并可编辑，属于 State。
  • 搜索关键词、筛选条件、当前页码：用户可修改，属于 State。
  • 在职总人数：由员工集合计算得到，不必重复保存。
  • 当前页员工数据：由员工集合、筛选条件、页码计算得到，不必重复保存。
1
2
3
4
5

const [employees, setEmployees] = useState<Employee[]>([]);
const [filters, setFilters] = useState<EmployeeFilters>(DEFAULT_FILTERS);
const [page, setPage] = useState(1);

const result = queryEmployees(employees, filters, page, 5);

如果为了“同步”又额外维护 filteredEmployees、visibleEmployees、totalCount 等 State，往往会让数据出现多份不一致的副本。

7.2 状态建模的基本原则

  1. 避免相互矛盾的状态：例如 isLoading=true 与 isSuccess=true 同时存在；使用判别联合。
  2. 避免冗余数据：能由现有 State/Props 计算就直接计算。
  3. 避免同一业务对象重复保存：选中员工只保存 ID，必要时通过 ID 查找。
  4. 相互关联、总是一起变更的数据可以组合：如复杂表单或 Reducer 状态。
  5. 避免不必要的深层嵌套：降低不可变更新成本。

这些原则与后端数据库的数据规范化有相似之处：尽量只保存事实，减少需要同步的派生副本。

第 8 章 组件身份、状态保留与 key 重置

8.1 组件位置与身份

React 会根据组件在渲染树中的位置与类型等信息追踪其状态。一个组件在逻辑上“看起来是另一个人”并不自动意味着 React 会清空内部状态。

1
2
3

function Page({ employee }: { employee: Employee }) {
  return <Editor employee={employee} />;
}

如果传给 Editor 的员工由张三切换为李四，而 Editor 仍处在相同的位置和组件类型上，它内部的状态可能继续保留。

8.2 用 key 表达“这是新的实例”

1
2
3

function Page({ employee }: { employee: Employee }) {
  return <Editor key={employee.id} employee={employee} />;
}

当 employee.id 改变时，React 会把新旧节点视为不同的组件身份，卸载旧实例并挂载新实例，其局部 State 从初始值重新创建。这是编辑不同记录时重置表单的一种清晰方案。

8.3 不恰当的 key 与条件组件嵌套

当父组件在不同分支返回不同组件类型、位置改变或 key 改变时，子树的状态可能被重置。React 状态不属于某个组件文件，也不是“只要变量名相同就保持”。

当表单输入意外清空，应检查：

  • 是否每次渲染都产生新的 key。
  • 是否在父组件函数内动态声明子组件，使组件类型每次都不同。
  • 是否在条件分支中切换了组件位置或类型。
  • 是否误把“员工 ID”与“当前页序号”混用。

不要通过给整个页面设置随机 key 来“强制刷新”；这往往把局部同步问题掩盖成全面卸载和重新挂载。

第三部分：渲染与副作用

第 9 章 React 的渲染、协调与提交

9.1 三个过程不能混为一谈

React 的一次更新可以概括为：

  1. Trigger：初次挂载、State 更新或其他 React 更新使某些组件需要重新计算。
  2. Render：React 执行组件函数，结合当前 Props、State 和 Context 计算 React 元素树。
  3. Commit：React 将需要的变化应用到宿主环境，Web 中通常是 DOM。
flowchart TD
  Trigger["Trigger：初次挂载或更新"] --> Render["Render：计算新的 React 元素树"]
  Render --> Commit["Commit：把需要的变化提交到 DOM"]
  Render -. "可能重试或放弃本次计算" .-> Render
  Commit --> Browser["浏览器按需计算样式、布局和绘制"]

随后浏览器处理样式、布局和绘制。React 不是浏览器渲染引擎；React 的 render 与浏览器的 CSS layout / paint 是两个不同过程。

9.2 “组件重渲染”不等于“DOM 被重建”

1
2
3
4

function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount((n) => n + 1)}>点击 {count} 次</button>;
}

更新 count 会触发组件计算新的 JSX，但 React 并不需要销毁整个按钮再创建一个按钮。它可以保持按钮 DOM 节点，仅更新发生改变的文本等必要部分。

因此排查性能问题至少要区分：

  • 函数组件是否被再次调用，渲染计算是否昂贵。
  • 是否产生实际 DOM 变更。
  • DOM 变化是否导致浏览器布局、重绘、合成开销。
  • 数据请求、事件回调或应用层业务逻辑是否重复执行。

把四种开销统称为“React 更新很慢”通常不足以指导优化。

9.3 协调过程与 key 的作用

React 比较新旧 UI 结果以确定提交变化。组件类型与位置、列表 key 等共同帮助 React 判断节点身份。稳定 key 有助于保留列表项的对应关系；它不是数据差异比较的唯一依据，也不是让列表“完全不渲染”的开关。

不要把 React 的内部协调实现细节当成业务接口依赖。业务代码需要理解渲染纯度、状态身份和 React 可观察的 API 保证，而不应依赖某次版本中的具体调度顺序。

9.4 render 阶段不能执行外部副作用

下面的写法很危险：

1
2
3
4

function EmployeePage({ employees }: { employees: Employee[] }) {
  localStorage.setItem("employees", JSON.stringify(employees)); // 不应在渲染期写入
  return <p>{employees.length} 位员工</p>;
}

渲染可能被重复、被放弃或被延后。应在用户操作的事件处理函数中保存数据，或者在确实需要持续同步外部系统时使用 Effect，并正确安排依赖与清理。

9.5 StrictMode 为什么会“多执行一次”

开发环境在 StrictMode 启用时，React 会执行额外检查，包括额外调用组件渲染和部分纯函数、额外执行 Effect 的 setup/cleanup 循环以及检查某些 Ref 回调。目的在于发现隐藏的不纯行为与资源泄漏。

应区分：

  • “组件函数重新执行”不意味着用户触发的 onClick 会自动执行两次。
  • “Effect 在开发模式额外 setup/cleanup”不意味着生产环境保证只运行一次；生产环境也可能因为依赖变化、卸载后重新挂载等原因再次执行。
  • 将重复请求的根本问题简单归结为 StrictMode 并在项目中关闭它，通常会失去诊断价值。应当先保证 Effect 可以正确清理、取消或忽略过期结果。

9.6 纯渲染与事件处理职责不同

渲染函数负责描述“现在应显示什么”；事件处理函数负责描述“用户做了某个操作后要采取什么行动”；Effect 负责“组件当前已提交的状态需要如何与外部系统保持同步”。这条边界直接影响数据请求、弹窗、表单和本地存储的架构。

10.1 为什么存在 Effect

React 的渲染计算是纯粹的 UI 推导，但应用仍要访问外部系统：网络、订阅、浏览器事件、命令式 DOM API、WebSocket 等。Effect 允许在组件提交之后建立这种同步关系。

10.2 Effect 的 setup、依赖与 cleanup

11.1 Ref 与 State 的区别

11.2 不要在渲染过程中随意读写 Ref

第 12 章 Hooks 的规则与自定义逻辑的边界

12.1 两条核心规则

Hooks 的使用必须遵循官方约束：

  1. 在 React 函数组件或自定义 Hook 的顶层调用，不在 if、for、循环回调、普通嵌套函数、try/catch 等内部调用。
  2. 只从 React 函数组件或自定义 Hook 调用 Hooks，不从任意普通 JavaScript 函数调用。
1

3
4

function EmployeePage({ enabled }: { enabled: boolean }) {
  // 错误：Hook 的调用顺序由条件控制
  // if (enabled) useEffect(() => {}, []);

  useEffect(() => {
    if (!enabled) return;
    // 条件可以写在 Effect 内部
  }, [enabled]);
  return null;
}

Hooks 依赖 React 在渲染组件时对各次 Hook 调用的追踪。Hook 规则是正确性约束。推荐用 eslint-plugin-react-hooks 辅助检查，不能仅凭“这次运行没有报错”确认规则正确。

function useOnlineStatus() {

  useEffect(() => {
    const update = () => setOnline(navigator.onLine);
    window.addEventListener("online", update);

      window.removeEventListener("offline", update);

12.3 什么逻辑应该提取为 Hook

常见候选包括：

  • 与 React 生命周期和 State 强相关的异步资源加载。
  • 一套表单的状态与提交行为。
  • 需要成对添加/清理监听器的浏览器 API。
  • 多个组件共享的复杂交互状态机。

纯业务计算不需要包装为 Hook。例如 queryEmployees、nextEmployeeId 就应保留普通纯函数，方便在 React 以外复用并独立测试。

12.4 避免“万能 Hook”

若一个 Hook 同时负责权限校验、路由、弹窗、HTTP 请求、页面布局、Excel 导出等，大概率在掩盖职责边界。优秀的自定义 Hook 应有清晰输入、输出和资源生命周期，使调用方知道它持有什么状态、发生什么副作用，以及何时更新。

第四部分：复杂组件组织

第 13 章 useMemo、useCallback 与 memo

13.1 先有问题，再考虑优化

React 性能优化常见误区是把所有函数包上 useCallback，把所有计算包上 useMemo，把所有组件包上 memo。这些工具本身有使用和依赖维护成本，也不会消除所有重渲染。应先识别实际瓶颈。

13.2 useMemo：缓存计算结果

1
2
3
4

const visible = useMemo(
  () => queryEmployees(employees, filters, page, 20),
  [employees, filters, page],
);

当依赖值不变时，React 通常可以复用之前的计算结果。useMemo 主要用于性能优化，不应成为程序正确性的必要条件。缓存并非永久持有的语义保证；计算函数本身仍应纯净。

对于十几条员工数据的筛选，直接计算往往足够快；配套项目保留 useMemo 是为了展示依赖关系，并非声称此处存在性能瓶颈。

13.3 useCallback：缓存函数引用

1
2
3

const handleSelect = useCallback((id: string) => {
  setSelectedId(id);
}, []);

它缓存的是函数引用而不是调用结果。当函数作为 Props 传给经 memo 优化的子组件，或者该函数必须成为某个 Effect 的稳定依赖时，才可能产生可测量收益。反过来，如果依赖总是在变化，包装函数也不会让它稳定。

setState setter 的引用是稳定的；不需要为了“防止 setter 变化”再额外包装一层。

当父组件重新渲染时，如果这个子组件的 Props 与上次相比没有变化，React 可以跳过它的渲染。默认比较使用浅层 Props 对比（每项以 Object.is 为基础）。但组件自己的 State 更新、读取的 Context 改变等仍可能使它渲染。

不要为“让 memo 生效”而把本来清晰的数据流强行变成不透明的可变引用。React 的更新模型必须先正确，再谈性能。

13.5 React Compiler 的关系

较新的 React 工具链引入了 React Compiler，可以自动应用部分 memo 化优化；是否启用取决于编译工具、配置与兼容性。不能因为项目使用 React 19 就假定已经启用 Compiler，也不能把某个优化在特定编译器下的表现当作所有项目的稳定保证。

13.6 常见优化优先级

先优化架构和实际瓶颈：

  1. 避免无意义的重复 State 与 Effect 链条。
  2. 降低不必要的状态提升范围。
  3. 减少昂贵的渲染计算与过大的列表 DOM（必要时虚拟列表）。
  4. 对已测量的热点使用 useMemo、useCallback、memo。
  5. 用 React DevTools Profiler 等工具检查优化前后的实际变化。

type State =

  | { kind: "ready"; employees: Employee[] }
  | { kind: "error"; message: string };

type Action =
  | { type: "started" }
  | { type: "loaded"; employees: Employee[] }
  | { type: "failed"; message: string }
  | { type: "deleted"; id: string };

function reducer(state: State, action: Action): State {
  switch (action.type) {
    case "started": return { kind: "loading" };
    case "loaded": return { kind: "ready", employees: action.employees };
    case "failed": return { kind: "error", message: action.message };
    case "deleted":

        ? { kind: "ready", employees: state.employees.filter((item) => item.id !== action.id) }
        : state;
  }
}

14.2 Reducer 与后端状态机的联系

可以借助后端状态机/事件处理的直觉理解：一个明确的状态类型加上有限的动作集合，产生合法的下一状态。但 Reducer 并不自动获得数据库事务、持久化或并发控制保证。后端一致性和提交语义仍由相应的数据层负责。

14.4 Context 与共享可变存储不是一回事

Context 分发值，并在 Provider 值变化时让对应消费者更新；它本身没有提供复杂状态更新算法、异步缓存、服务端同步或全局业务流程。状态通常仍由 useState、useReducer 或外部状态源维护。

对于大量独立变化的数据，把所有内容塞进一个 Context 对象可能放大消费组件的渲染范围。可按职责拆分 Context，或在真正需要时选择外部状态管理方案。无需在 React 入门阶段就上 Redux。

14.5 何时不用 Context

  • 数据只在父子之间传一两层：直接 Props 更清晰。
  • 只是想让一个局部组件可以复用：优先组合和 children。
  • 需要复杂服务端数据缓存：Context 通常不是专门的查询缓存替代品。
  • 只为避免写几个 Props 而引入多个全局 Provider：可能使数据依赖更隐蔽。

第 16 章 React 工程中的常见问题与调试方法

16.1 页面为什么没有更新？

建议按照以下次序定位：

  1. 事件是否触发？在处理函数内打断点。
  2. setter 是否实际调用，传入的状态值是什么？
  3. 新旧对象是否意外共用同一个引用？
  4. 页面是否使用了错误的数据来源或旧闭包值？
  5. 是否把计算结果缓存到不正确的 useMemo 依赖中？
  6. 是否由组件身份、列表 key 或条件渲染改变了期望状态？

不要一开始就强制刷新页面或引入 forceUpdate 类技巧。

16.2 Effect 为什么重复触发？

检查依赖是否包含每次渲染都新建的对象或函数、是否在 Effect 内更新自己依赖的 State、是否处于开发期 StrictMode、组件是否被卸载重新挂载。真正的修复往往是删除不必要的 Effect、把派生计算移到 render、把用户操作移到事件，或完善清理。

16.3 “点击编辑，输入框内容不对”

检查组件内部 State 是否只在首次挂载使用 Props 初始化。如果希望切换员工时重建独立草稿状态，使用稳定的业务 ID 作为编辑器 key 是一种明确方案。如果希望未提交的草稿保留，则应显式设计草稿的作用域，而不是依赖偶然的组件保留行为。

16.4 列表更新后焦点或输入状态跑到别的行

首先检查 key 是否稳定；尤其关注排序、分页、插入、删除后是否仍以数组索引作为 key。同时检查是否在每次渲染时重新定义子组件类型，以及是否用 Math.random() 创建 key。

16.5 查询后分页出现空白

假设原来第 3 页有数据，用户切换过滤条件后符合条件的记录只有 1 页。应在应用过滤条件时将页码重置为 1，或在查询函数中把实际页码限制在合法范围。配套实战同时使用“查询重置页码”和“查询结果计算时页码钳制”，避免删除数据后页码越界。

16.6 本地存储与界面状态为什么不同步？

本地存储是浏览器外部系统，不会因为调用 setState 自动改变。应在明确的操作边界保证更新：计算新的员工集合、尝试保存、更新 React State，并给出保存失败提示。不要在 State updater 或 render 中写存储。若项目要求跨标签页同步，还需要设计 storage 事件或 useSyncExternalStore 等订阅机制；本阶段没有实现跨标签页一致性。

16.7 为什么需要 React DevTools？

普通 Chrome DevTools 观察 DOM、CSS、网络和 JS 断点；React DevTools 可以帮助查看组件树、Props、State、Hooks 和 Profiler 结果。两者互补。实际问题排查要从数据如何改变、哪个组件拥有状态、哪些组件渲染，到真实 DOM 和网络响应形成完整链路。

16.8 开发中值得长期保留的原则

  • 尽可能让组件渲染保持纯净，让事件处理执行明确的用户操作。
  • Props 只读，State 通过 setter 或 dispatch 更新，不直接修改现有数据结构。
  • State 只保存必要事实，不重复保存可以即时推导的结果。
  • Hook 在顶层调用，不通过条件和循环改变调用顺序。
  • Effect 用于真正的外部系统同步，依赖完整，清理可靠。
  • 组件的身份和 key 由真实语义决定，而不是用来随意“刷新”组件。
  • 不要为了表面减少渲染而牺牲正确的数据流；先测量，再优化。

Effect 依赖 reloadId，初始加载与点击重试都会使用同一套逻辑。cleanup 用于尽量取消请求，并防止过期响应回写。这个设计同时应对开发环境 StrictMode 的额外 setup/cleanup。

需要理解三层不同职责：

  1. loadEmployees：网络读取与 JSON 运行时校验。
  2. useEmployees：将外部加载结果映射为 React 加载状态。
  3. App：根据 loading、ready、error 选择合适的 UI。

当业务需要复杂缓存与同步时，应将第一、二层迁移至更完善的数据获取机制，而不是持续往一个页面 Effect 中增加缓存、重试和失效逻辑。

17.8 新增、编辑与删除：从事件到状态更新

操作流程：

flowchart TD
  Save["用户点击保存"] --> Draft["EmployeeDialog：校验并组合 EmployeeDraft"]
  Draft --> App["App：判断新增或编辑"]
  App --> Model["useEmployees：调用 model.ts 计算新集合"]
  Model --> Persist["尝试写入 localStorage"]
  Persist --> State["setLoad：更新内存中的员工集合并反馈保存结果"]
  State --> Page["返回新集合，校正页码 State"]
  Page --> Render["React 重新计算统计、查询结果和表格"]

与第三阶段不同，页面不需要再显式调用一次 renderTable() 或更新统计 DOM；这些都由相应组件根据最新 Props 自动计算。

示例中本地持久化由用户动作直接触发，没有放进 setState((old) => { ... }) 更新函数中，因为更新函数应保持纯净。持久化失败会告知用户：此次页面内存中的修改可能在刷新后丢失。

新增、编辑和删除还可能改变当前筛选结果的页数。仅让 queryEmployees 在返回结果中钳制页码，会留下过期的 page State：删完末页记录后显示上一页，但再次新增数据时可能跳回旧页。因此，useEmployees 的修改方法返回更新后的员工集合，由事件处理函数用相同筛选条件计算合法页码并同步 State：

17.11 如何验收完整的用户路径

按一次完整业务链路验证，而不是孤立地逐个点按钮：

  1. 打开页面后成功加载 10 条员工初始数据，统计数量与数据一致。
  2. 在查询表单中输入姓名并选择部门，点击查询，列表与统计逻辑正确；清空条件后恢复列表。
  3. 切换排序方式，查看工号升序、降序、姓名排序是否按预期变化。
  4. 翻页到第二页，新增员工后仍能在正确分页条件下查询到该记录。
  5. 打开编辑弹窗修改一名员工，保存后列表和统计结果相应更新。
  6. 删除一条数据，确认后列表和总数变化；删除末页数据后不出现无效页码。
  7. 刷新页面，检查本地数据持久化；随后点击“恢复初始数据”，验证还原 JSON 中的初始值。
  8. 使用浏览器 Network 面板确认初始数据来自 GET 请求，新增、编辑和删除不产生对应的后端写请求。
  9. 暂时使 JSON 地址不可达或模拟网络失败，检查错误提示与重新加载路径。

这份验收属于本章唯一综合实战的验证范围，并不要求在正文各章单独完成练习。
