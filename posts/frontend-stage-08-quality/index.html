第一部分：测试设计与质量模型

第 1 章 前端质量的边界、风险和责任

1.1 把需求翻译成可验证的行为

需求“员工列表支持编辑”看似简单，但至少需要明确：什么角色可编辑；哪些字段可修改；哪些字段必填；工号是否全局唯一；网络请求失败如何提示；保存后是否关闭弹窗；列表和统计是否刷新；并发修改是否会覆盖他人的数据。

测试设计的起点不是“我要写多少个 test”，而是把业务需求转换为具有输入、操作和可观察结果的契约：

这些结果落在不同技术层：纯函数校验、组件交互、HTTP 协议、应用间协作、后端授权。测试应选择最能直接证明对应契约的层级。

1.2 风险驱动优先级

没有必要平均覆盖所有页面与函数。一个常见的优先级模型是同时考察：

  • 影响：发生错误会造成数据损坏、越权、资金影响，还是仅仅影响展示？
  • 发生可能性：逻辑复杂、变更频繁、第三方依赖多、边界状态多吗？
  • 可发现性：开发阶段容易察觉，还是容易潜伏到线上？
  • 修复成本：涉及多少系统与人员，是否有回滚与恢复手段？

优先覆盖高影响、高变化和难以发现的问题。例如只读权限绕过、编辑后数据不一致、批量操作误删，与纯装饰性图标的间距差异相比，通常更值得投入自动化。

实际项目可以使用轻量风险台账：

风险场景影响对应验证

缓存未失效导致列表仍是旧数据中～高Mutation 后的组件和 E2E 行为

1.3 测试与其他质量手段的关系

TypeScript 检查类型约束；ESLint 检查可静态识别的缺陷模式；测试验证具体输入与行为；代码审查检验设计合理性；监控观察真实运行。它们相互补充，不能把“TypeScript 无错误”推导成“业务逻辑正确”，也不能把“E2E 通过”推导成“没有授权漏洞”。

一个可信的质量结论应说明对象、版本、环境、验证维度和实际结果。例如“提交 abc123，Node.js 22，本地 Mock API，执行 npm run test:api：HTTP/结构测试共 N 项，失败 0 项，跳过 0 项”，比“质量已保障”更可审计。

第 2 章 测试分层与测试边界

2.1 单元、组件、集成、API、E2E 的关系

这些名称描述验证对象和依赖边界，不是绝对、互斥的技术分类。实践中需要关注测试真正调用了哪些系统。

测试层主要对象常用工具发现的问题主要局限
纯函数单元URL 参数解析、格式转换、业务规则Vitest边界、逻辑、类型转换错误不证明浏览器和接口工作
React 组件用户操作、可访问名称、状态展示React Testing Library组件交互与渲染回归jsdom 不是完整浏览器
前端网络集成API Client、错误映射、缓存行为Vitest + MSW请求参数、HTTP 响应和异常处理Mock 可能与真实服务契约漂移
API 集成实际启动的后端或 Mock APINode test / HTTP 客户端服务端校验、会话、授权、CRUD不验证真实 DOM 和路由
端到端浏览器 + 主应用 + 子应用 + 服务端Playwright跨模块用户旅程、部署集成更慢，环境与数据治理成本更高

“测试金字塔”常用于表达更多稳定的底层测试、少量高价值端到端测试的资源配置。它不是要求固定 70/20/10 的比例。不同应用边界、失败代价和技术能力会影响各层投入。

2.2 为什么不全用 E2E

设想一个分页函数把页码 0 当成合法值：单元测试几毫秒即可定位该条件；E2E 需要等待浏览器、API 和微前端启动，错误可能在屏幕上表现为“空列表”。同样，组件测试能快速证明错误提示与重试按钮的交互；但只有真实浏览器才可靠覆盖路由、CSS、焦点、网络资源和实际渲染。

正确取舍是：在最接近问题发生层级的位置写可解释的测试，再用少量跨层测试确认集成契约。

2.4 Mock 选择：替身应替代什么

  • Stub：预设确定返回值，不检查交互；适合纯 UI 状态。
  • Mock / Spy：记录调用次数与参数；适合组件回调和明确的边界行为。
  • Fake：具备简化行为的可执行替代实现，例如内存数据仓库。
  • 网络拦截：在 fetch/XHR 所在边界拦截 HTTP，模拟成功和错误，而不是替换页面代码内部的所有函数。
  • 真实依赖：当接口语义、缓存、授权或跨系统交互是验证目标时，应尽量保留真实调用。

不要同时 Mock 业务逻辑、API Client、Query 缓存和组件，最后只断言 Mock 被调用。这类测试对真实回归的识别能力非常有限。

第 3 章 有效测试用例如何设计

3.1 正常路径与异常路径

一个典型的错误用例是只检查：正确输入 → 成功。对于员工录入，更重要的是梳理不合法输入、边界长度、重复工号、只读会话、网络故障和重复提交。

以员工工号规则“2～20 位英文字母、数字或连字符”为例，等价类至少包括：

输入类别预期
A1合法下边界接受
20 个合法字符合法上边界接受
A低于下边界拒绝
21 个合法字符超过上边界拒绝
A_1含不合法字符拒绝
空字符串或非字符串缺失/类型错误拒绝

这里的测试不必每种随机字符都写一条，而应选能够证明规则分支的代表值。输入校验应同时在前端提升体验、在后端强制执行。

3.2 边界值、判定表和状态迁移

边界值分析适用于长度、页码、金额、时间、最大文件大小等。判定表适用于多个条件组合：

角色表单有效工号重复服务端响应用户可见结果
editor是否2xx保存成功、刷新页面
editor否-无请求或 400具体字段错误
editor是是409冲突提示、保留输入
viewer是否403写入被拒绝

状态迁移适用于弹窗：关闭 → 编辑中 → 提交中 → 成功关闭，以及 提交中 → 失败保留编辑。若允许保存期间再次点击提交，可能出现重复请求。测试要覆盖状态间不允许的迁移，而不仅是最终文字。

3.3 测试数据与“测试神谕”

测试神谕（Test Oracle）是判断结果对错的依据。例如 API 规范、用户故事中的验收条件、业务计算公式或基于已知数据的确定期望。不要直接复制被测函数的算法作为期望结果，否则实现与测试可能犯同一错误。

测试数据应可控且可追溯。避免依赖线上实时数据、其他用户账户或运行顺序。E2E 创建员工时应使用唯一工号并在结束后清理；必要时通过隔离数据库、独立租户或测试专用重置接口控制状态。这个教材的 Mock API 每次启动都会生成独立内存数据，适合本地验证，但不能替代正式环境的数据隔离方案。

第 4 章 测试隔离、重复性与异步行为

4.1 隔离什么

测试可能共享：内存对象、localStorage、DOM、Fake Timer、请求处理器、Mock 调用历史、服务端会话、数据库和端口。共享状态不清理是偶发失败的重要原因。

理想情况下，测试不依赖执行顺序、可以单独运行、失败后能够复现。常见措施包括：

  • 每个测试使用独立的 QueryClient，避免 React Query 缓存串扰。
  • afterEach 清理 DOM、恢复 Mock 和计时器。
  • MSW 每个测试后重置临时 handler。
  • Playwright 每个测试使用隔离的 Browser Context（默认 fixture 行为），服务端数据仍需单独治理。
  • Node API 测试为每个测试启动单独端口和内存仓库。

4.2 处理异步而不是猜测时机

页面加载需要网络，网络完成后还需要 React 提交渲染。使用固定 sleep：

1

await new Promise(resolve => setTimeout(resolve, 2000));

不仅浪费时间，而且慢机或偶发重试仍会失败。组件测试使用 findByRole / waitFor；Playwright 使用 Locator 和自动重试断言。等待的是业务可观察条件，不是任意时间。

4.3 重试与 flaky 的本质

测试偶发失败（Flaky Test）可能来自真实产品竞态，也可能是测试本身不可靠。增加重试能收集证据，却不能替代根因修复。遇到 flaky 应保留 Trace、网络记录、运行环境、测试数据和失败频率，先分类：

  1. 产品逻辑竞态：例如请求 A 慢于请求 B，却覆盖 B 的较新结果。
  2. 测试定位不稳定：例如依赖动态 CSS class 或宽泛的文本匹配。
  3. 数据污染：例如上一个测试新增的员工改变分页总数。
  4. 外部服务波动：网络、限流、共享环境或认证过期。
  5. 资源竞争：并行测试复用固定端口或共享账户。

把失败用例标记跳过，应视为短期隔离措施，记录责任人与恢复条件，而不是永久增加“通过率”。

import { describe, it, expect } from 'vitest';

function clampPage(page: number): number {
  return Number.isInteger(page) && page >= 1 ? page : 1;

describe('clampPage', () => {
  it.each([-1, 0, NaN, 1.5])('非法页码 %s 回退到首页', (value) => {

5.4 Fake Timer 与异步测试

定时行为（防抖、倒计时、轮询）可以使用 vi.useFakeTimers() 控制时间，测试完成后调用 vi.useRealTimers()。需要注意：模拟计时器与 Promise 微任务、React act、user-event 交互时可能产生额外要求。对于不依赖定时器的用户交互，优先使用真实计时器与异步查询。

6.1 为什么首先拆出纯函数

import type { SearchParams } from './api';

export function parseEmployeeSearchParams(params: URLSearchParams): SearchParams {
  const rawPage = params.get('page');
  const page = rawPage === null ? 1 : Number(rawPage);
  const rawSize = params.get('pageSize');
  const size = rawSize === null ? 10 : Number(rawSize);
  const rawStatus = params.get('status');

  return {
    q: params.get('q') ?? '',
    departmentId: params.get('departmentId') ?? '',
    status: rawStatus === 'active' || rawStatus === 'inactive' ? rawStatus : '',
    page: Number.isInteger(page) && page >= 1 && page <= 9999 ? page : 1,
    pageSize: [5, 10, 20].includes(size) ? size : 10,
  };
}

这里涉及几个重要边界：

  • URLSearchParams 的值是字符串，需要显式转换。
  • Number('') 为 0；非法数值 NaN、Infinity 不应进入分页 API。
  • 状态只接受允许的离散取值；不要把任意 URL 字符串断言为 TypeScript 联合类型。
  • 默认值属于业务规则；例如 pageSize 只能是 5、10、20。

6.3 测试重构的稳定性

好的纯函数测试以输入输出契约为中心：把 if 改成三元表达式、修改内部变量名，不应导致测试失败。反过来，如果把合法状态 'inactive' 错误解析为空字符串，应立即失败。

对于复杂的数据转换，可以补充不变式：例如分页总数不受 page 影响、序列化和解析在合法输入上的往返一致、排序不会改变数据条数。属性测试（Property-based Testing）可进一步自动生成输入，但本阶段不强制引入额外框架。

第 7 章 React Testing Library：以用户行为为中心

7.1 测试组件做了什么，而不是如何实现

React Testing Library 提供 render、screen、within 和异步查询。它鼓励从用户可感知的文本、语义角色、标签和状态观察组件，而不是读取 React 组件内部的 State。

查询选择通常优先使用：

  1. getByRole('button', {name: '保存'})：语义角色和可访问名称。
  2. getByLabelText('姓名')：带关联标签的表单控件。
  3. getByText：确实以可见内容为契约的文本。
  4. getByTestId：以上方式均不适用、且存在稳定测试标识时。

getBy 找不到时抛错；queryBy 找不到时返回 null，适合验证不存在；findBy 异步等待元素出现，等价于 getBy 加 waitFor。不要用 getBy 立即查找异步加载后才出现的 DOM。断言元素已消失时，用 queryBy 检查结果为 null，或用 waitForElementToBeRemoved 等待它被移除。

React 严格模式在开发环境中会执行额外渲染与 Effect 设置/清理过程，以暴露不纯渲染和清理缺陷。因此“Effect 必须只调用一次”往往不是正确的业务断言。若需要验证 API 请求去重，应检查最终业务状态、缓存和必要的请求契约，而不是把开发模式内部调用次数当成通用规范。

7.5 组件测试常见误区

  • 直接读 useState、组件实例或内部函数，导致重构即失败。
  • 把第三方 UI 库的 DOM 结构、类名视为业务契约。
  • 在组件内部塞入 data-testid 仅为绕开可访问性问题，而不改善语义。
  • 使用 act 不完整或异步断言遗漏 await，导致测试偶发成功。
  • 在 jsdom 中验证实际布局宽度和动画帧率；这些属于浏览器测试。

import { setupServer } from 'msw/node';
import { http, HttpResponse } from 'msw';
import { beforeAll, afterEach, afterAll, expect, it } from 'vitest';
import { api } from '../../apps/organization/src/api';

8.3 Mock 的三个风险

契约漂移：前端 Mock 返回 {data: ...}，真实接口却变成 {result: ...}。解决方法是在 CI 中跑真实 API 契约或集成测试，并让 Mock 来源于共同定义、Schema 或经过明确版本管理的示例。

过度理想化：只模拟 200，忽略慢请求、404、409、429、503。解决方法是围绕真实故障模式补充少量高价值负例。

Mock 层级错误：为了验证请求客户端，却直接 vi.mock('./api') 替换了它，使测试绕过请求序列化和响应解析。对于 API Client 的测试，应在 HTTP 边界替换服务端响应，而不是替换客户端自身。

8.4 API 集成测试为何独立存在

配套项目的 Node API 测试会真实启动 HTTP Server，使用 fetch 发送请求，检查：

  • GET /api/employees 分页筛选与响应结构。
  • POST /api/employees 成功创建与返回 201。
  • 工号冲突返回 409、非法字段返回 400。
  • 只读角色通过 HTTP 直接写入，返回 403。
  • 同一服务端不同 Cookie 会话具有独立角色。
  • 创建 → 详情 → 更新 → 删除 → 404 的操作序列。

要特别关注授权验证所在位置。前端隐藏“编辑”按钮属于交互体验，不能防止绕过浏览器直接调用接口。服务端必须独立校验可信会话及操作权限。本文的 POST /api/demo/role 是供教学环境模拟角色的特殊入口，生产服务不得保留这种直接切换角色的机制。

8.5 何时需要契约测试

当团队分别维护前后端、接口变更多、升级频繁时，可以引入 OpenAPI Schema 校验、消费者驱动契约或提供方契约验证。合同的核心是明确字段、类型、可空性、状态码和错误语义，并在双方发布流程中自动验证。仅靠 TypeScript as T 不会在运行时校验网络响应；面对不可信或经常变化的外部响应，应引入 Zod 等运行时 Schema 或等价校验机制。

第三部分：端到端测试与故障定位

第 9 章 Playwright：在真实浏览器验证用户旅程

9.1 E2E 的关注对象

端到端测试（End-to-End Testing）从用户入口开始，跨越路由、前端组件、浏览器行为、网络接口与服务端，验证一条完整旅程。员工管理系统的典型 E2E 路径是：打开企业主应用 → 进入组织人员 → 查看员工列表 → 查询员工 → 进入详情；另一条关键路径是只读用户无法写入。

真实浏览器测试可以识别 DOM、CSS、路由、资源加载、Cookie、浏览器历史和某些接口集成问题。但它不能穷尽安全性，也不能替代后端数据库隔离、压测和所有浏览器的兼容性验证。

9.2 定位器：应选择稳定的语义

Playwright Locator 支持自动等待元素满足交互条件。常用方法包括：

await page.getByRole('button', { name: '查询' }).click();
await expect(page.getByRole('row').filter({ hasText: '张三' })).toBeVisible();

与 page.locator('.ant-btn:nth-child(3)') 相比，基于角色、名称和明确业务文本的 Locator 更接近用户行为，也更容易在失败时说明原因。

定位器应保持足够精确：同一页面可能同时出现菜单“员工管理”和标题“员工管理”，此时使用 getByRole('link', {name: '员工管理', exact: true}) 或先定位导航区域再链式查找，例如 page.getByRole('navigation').getByRole('link', { name: '员工管理' })。不要依赖 .first() 掩盖重复元素问题。

9.3 Playwright 自动等待的边界

Playwright 在点击时检查元素是否可交互，并对 expect(locator) 进行自动重试。但自动等待不会替你定义业务完成条件。

例如点击保存后，按钮可点击不等于数据已写入、缓存已更新。正确断言可以是：成功提示出现、弹窗关闭、列表中出现新员工，再重新打开详情验证数据。对于修改数据的断言，应把返回码、页面表现和重新读取的一致性联系起来。

9.4 独立测试环境与 Browser Context

Playwright 的 page、context fixture 默认按测试提供隔离浏览器上下文，Cookie 和 localStorage 不会跨测试共享。但是测试数据服务不会自动隔离：两个测试操作同一个共享员工列表，仍可能互相影响。

本教材通过默认串行执行 E2E（workers: 1）并减少写入场景来降低干扰。真实项目更合适的做法是为每个测试创建独立租户、数据命名空间或数据库事务，允许有控制地并行，而不是永久依靠单线程规避数据冲突。

9.6 E2E 不应过度断言内部实现

浏览器测试应该描述：用户可以操作什么、看到什么、得到什么反馈。避免断言 Hook 调用次数、Query Key、特定 React 组件名。这些属于实现细节；修改 React 架构不应该导致所有 E2E 失效。

对于工程集成，允许单独断言运行时边界，例如子应用切换后的挂载或卸载结果，但要说明这是对架构契约的验证，而非用户界面的通用测试模式。

10.1 微前端新增了哪些失败点

浏览器

页面空白可能因为：Shell 路由未激活、子应用模块 404、CORS 拒绝脚本、动态 import 失败、CSS 未加载、React Root 挂载目标丢失、路由 basename 不一致、API 连接失败。仅看到“前端请求出错”不足以定位原因。

10.2 生命周期需要验证的契约

single-spa 子应用通常具备 bootstrap、mount、unmount 生命周期。对应的业务风险包括：

  • bootstrap 重复执行导致全局监听器或单例重复初始化。
  • mount 重复调用或挂载到错误 DOM 节点。
  • unmount 忘记清理 React Root、定时器、订阅或缓存，造成内存泄漏、重复处理事件。
  • 先跳离子应用，再导航回来，出现无法重新挂载。
  • Shell 切换语言后，子应用仍保留旧配置或重复注册事件监听。

本实战保留第七阶段的生命周期代码，不额外绕过 single-spa 写一个仅供测试的入口。API 与 UI 测试验证局部行为，Playwright 验证实际装配。

10.3 跨应用运行时常见误判

微前端的路由通常有两个层次：Shell 判断 /organization 是否属于子应用；子应用 BrowserRouter basename="/organization" 再处理 /employees、/dashboard。如果子应用内部把 /organization/employees 作为完整相对路径，可能形成重复前缀或跳转错误。

模块加载使用 ES Module 动态导入时，需要服务端正确提供资源、CORS、MIME Type 与缓存策略。测试只在本地开发服务器通过，不能直接推导生产网关重写和 CDN 路径也正确。生产预发布环境应增加少量冒烟检查，覆盖真实资源路径、刷新深层路由以及一次回退和重新进入子应用。

10.4 角色与跨应用通信

本项目 Shell 提供演示角色选择，角色变更会请求服务端，并向子应用广播展示设置。测试需要分别验证：

  1. UI 反馈：viewer 看不到“新增员工”等写入入口。
  2. 安全边界：viewer 即使绕开 UI 直接请求 POST /api/employees，仍得到 403。

第二个断言必须保留。只验证按钮不存在会产生错误的安全感。对于真实企业项目，身份与授权信息应由可信服务端验证；跨应用事件只是配置同步机制，不是安全凭证。

11.1 从现象映射到故障层

出现“员工列表没有数据”，不要立刻添加 console.log 或怀疑 React。可以按以下顺序排查：

这种分层方法可以先缩小故障范围，再检查具体代码。每一步都有对应的 DevTools 能力。

11.2 Elements：布局、样式和 DOM

Elements 用于查看最终 DOM、计算后的 CSS、盒模型、样式优先级、事件监听器等。常见问题如：按钮看不到是因为条件渲染未生成，还是生成了但被 display:none / overflow:hidden 隐藏；弹窗层级错误是定位上下文或 stacking context 问题；输入框不可点击是否有透明遮罩层覆盖。

检查时应区分 DOM 树与 React 组件树。Elements 展示浏览器 DOM；React DevTools 的 Components 面板展示组件、Props 和 Hooks，二者回答的问题不同。

11.3 Network：请求链路和缓存

排查接口问题，应至少观察：

  • Request URL / Method：请求实际发到了哪个环境，是否经过 Vite 代理。
  • Status / Response：401、403、404、409、429、500、503 分别意味着不同的处理分支。
  • Request Headers / Cookies：请求是否携带会话凭证，是否出现预检。
  • Payload / Query String：分页、筛选或表单参数是否正确。
  • Timing：连接、等待响应、内容下载等耗时分布。
  • Initiator：请求由谁触发，是否出现重复请求。
  • Size / Cache：缓存命中、资源大小、304 协商缓存。

Network 看到接口为 200，不等于页面一定正确。 响应字段可能不符合前端契约、缓存未失效或组件渲染失败。应继续检查 Console、React DevTools 和页面状态。

11.4 Sources：断点与异步堆栈

在 Sources 给事件处理函数、API Client、Mutation onSuccess 设置断点，观察局部变量和调用栈。启用 Source Map 后，通常可以从压缩构建代码定位到源 TypeScript；但生产 Source Map 可能暴露源码和内部结构，公开部署方式需与安全要求协调。

异步代码的关键是识别“什么时刻读取状态”。例如 React 状态快照、Promise 微任务、网络响应、Effect 清理之间的执行顺序，不能简单视为同步线性过程。

11.5 Application：存储与 Service Worker

Application 可检查 Cookie、localStorage、sessionStorage、IndexedDB、Cache Storage 和 Service Worker。登录态问题可优先确认 Cookie 作用域、SameSite、Secure、过期时间与请求上下文。不要在页面脚本或测试报告中输出真实身份凭证。

11.6 React DevTools：组件与性能

Components 面板适合看 Props、Hooks、Context 的值，Profiler 适合定位某次交互中哪些组件发生了渲染提交以及提交成本。React Profiler 结果需要结合具体环境解释：开发模式、StrictMode、设备性能和生产构建行为可能不同。

第四部分：性能、安全、可访问性与质量治理

第 13 章 前端性能测量与优化

13.1 先分清测量对象

浏览器性能包含网络加载、JavaScript 解析执行、样式计算、布局与绘制，以及交互响应。只看到 Bundle 体积增大，不能直接判断页面实际体验下降；只看到某次 Lighthouse 分数提高，也不能说明所有真实用户都更快。

需要区分：

  • 实验室数据（Lab）：在受控设备、网络和脚本中重复测量，利于诊断与回归。
  • 真实用户监测（RUM / Field）：在用户实际设备、网络和使用场景中测量，反映真实体验分布。
  • 合成监控（Synthetic）：定期模拟固定访问路径，检测性能变化和可用性故障。

实验室工具适合快速定位原因；真实用户数据适合评估整体体验和用户影响。二者应配合使用。

13.2 Core Web Vitals 的当前核心指标

指标含义良好阈值（通常以第 75 百分位评估）常见影响因素
LCP — Largest Contentful Paint视口内最大内容元素的加载呈现时间≤ 2.5 s首屏资源、服务器响应、关键 CSS、字体、图片
INP — Interaction to Next Paint页面整个生命周期内交互响应能力≤ 200 ms主线程长任务、同步计算、事件处理、渲染
CLS — Cumulative Layout Shift页面生命周期内最大一次会话窗口中意外布局偏移分数之和（会话窗口：相邻偏移间隔小于 1 秒，总长不超过 5 秒）≤ 0.1图片/广告未预留尺寸、动态插入内容、字体变化

上述阈值来自 Google 的 Core Web Vitals 体系，用于通常意义上的“良好”体验；对业务内部办公系统，还需结合设备基线、核心操作场景和团队 SLO 设置性能预算。不要把一次本机 LCP 结果当成真实用户的 P75。

INP 已取代旧的 FID，不能继续把 FID 当作当前三大核心指标之一。 INP 关注交互到下次呈现的响应表现，而不只是首次输入延迟。

13.3 怎么在 DevTools 中测量

现代 Chrome DevTools 使用 Performance 面板及其中的 Insights；独立的旧 Performance insights 面板已被移除，不应照搬过时教程截图。

实际排查路线：

  1. 记录真实交互或加载路径；对比基准环境与问题环境。
  2. 观察 Main Thread 长任务、脚本执行、Style/Layout/Paint 及网络瀑布。
  3. 对照 LCP 元素、CLS 来源及交互对应的任务链。
  4. 使用 React Profiler 确认是否出现不必要的大范围 React 提交。
  5. 只针对已识别的瓶颈做改动，再在同一条件下复测。

13.4 React 应用常见优化策略

渲染： 如果筛选动作导致上千行表格重新渲染，首先确认是否在客户端一次渲染了过多节点；服务端分页或虚拟列表通常比盲目添加 useMemo 更根本。memo、useMemo、useCallback 只有在存在可证明的重复计算或重复渲染成本时才值得使用，且会增加代码和依赖管理成本。

请求： 避免同一操作重复触发请求；对查询参数构建稳定的缓存 key；使用取消与过期机制避免旧请求覆盖新请求；修改后只失效必要的缓存；必要时使用预取，不能无限制预取所有列表。

资源： 采用路由级动态加载，避免把所有业务打包到首页；压缩图片并正确声明尺寸；根据缓存策略配置带 hash 的静态资源；排查 CSS、字体或第三方脚本阻塞。

微前端： 子应用共享依赖可能减少总下载量，但也引入版本耦合。是否共享 React、组件库等应根据重复体积、版本兼容、独立发布和故障隔离决定。不要为了追求 Bundle 数字而破坏稳定的运行时边界。

13.5 性能预算的设计

性能预算可以分为静态约束（每个路由 JS/CSS 体积）、实验室约束（固定场景中的加载、交互耗时）和真实用户指标（P75 LCP/INP/CLS）。不同预算的误报风险不同：CI 中冷启动构建的毫秒级浮动，不适合直接作为真实用户体验的硬门禁。

对员工管理系统，优先监控首屏概览、员工列表首次进入、表单打开、筛选后结果呈现、大表格分页以及子应用二次挂载。若某指标超标，应能追踪页面、版本与变更范围。

第 14 章 前端安全：哪些问题必须守住边界

14.1 输入与输出编码：XSS

跨站脚本（XSS）通常发生在不可信内容被当作 HTML/脚本执行。React 默认对 JSX 文本插值进行转义，例如：

1
2

const name = '<img src=x onerror=alert(1) />';
return <p>{name}</p>; // 普通文本输出，不将字符串作为 HTML 执行

但如果使用 dangerouslySetInnerHTML、拼接 HTML 字符串、将不可信 URL 放进特殊执行上下文，仍可能产生安全风险。确实需要渲染富文本时，应采用经过审查的 HTML Sanitizer、严格的允许列表，并结合内容安全策略（CSP）；不能仅靠正则删除 <script> 标签。

14.2 CSRF 与 Cookie

使用 Cookie 自动携带会话时，需考虑跨站请求伪造（CSRF）。SameSite 能降低某些跨站请求风险，但不能覆盖所有安全边界。对于有状态的写入 API，通常还需结合可信来源校验、CSRF Token、适当的 SameSite 策略和后端授权。

HttpOnly Cookie 可以限制页面 JavaScript 直接读取 Cookie 值，但不阻止浏览器在合适条件下自动发送；因此它不是防 CSRF 的独立充分条件。Cookie 的 Secure、SameSite、Domain、Path 与实际跨站/跨子域部署关系必须一起设计。

14.3 认证与授权不是同一概念

认证回答“是谁”；授权回答“这个身份是否可以操作这条资源”。前端页面隐藏按钮、路由守卫或本地角色变量只能改善体验；真正的资源访问限制必须由可信服务端实施。

在多租户系统中，即使用户拥有“员工编辑”权限，也不一定可以修改其他租户、部门或组织下的员工。这属于对象级授权，需要后端在资源查询和写入时检查，不是一个统一的角色字符串就能充分表达。

14.4 敏感信息与配置泄漏

Vite 等工具的客户端环境变量会进入前端构建产物。不能把数据库密码、内部密钥和服务端签名密钥放进前端 .env 中，即使变量名看起来像“内部配置”。浏览器代码、网络请求、Source Map、错误日志和测试 Trace 都可能带出敏感信息。

公开 Source Map、测试报告、错误监控、录屏与截图也需要数据脱敏。日志避免记录 Authorization、Cookie、身份证号、电话号码等敏感字段。

14.5 供应链与依赖治理

第三方包可能引入漏洞、错误版本或被恶意篡改。核心措施包括：保留真实 lockfile、使用受信任 Registry、审查高风险依赖和安装脚本、及时升级安全修复，以及为构建产物保留可追溯版本信息。

npm audit 可以提供依赖风险信号，但不能验证业务自身的 XSS、越权与逻辑漏洞；自动扫描也无法替代代码审查和授权集成测试。

第 15 章 可访问性与跨设备兼容

15.1 可访问性不是附加的视觉效果

企业后台常使用表单、表格、弹窗、下拉和导航。语义化 HTML 带来的可访问名称和键盘行为，直接影响实际可用性，也提高自动化测试的稳定性。

关键关注点包括：

  • 表单控件要有明确可访问标签，错误说明与字段关联。
  • 按钮使用 button，链接使用 a；不要随意用可点击 div 代替。
  • 弹窗打开后焦点转移合理，关闭后焦点可恢复。
  • 键盘可完成主要操作，焦点位置可见且顺序符合界面逻辑。
  • 状态变化有适当的可访问提示，如错误消息使用 role="alert"。
  • 对比度、缩放、响应式布局与触控目标尺寸符合实际产品要求。

15.2 自动化扫描的边界

axe 等自动化检查工具可以发现部分可访问性问题，但不能证明所有交互对屏幕阅读器使用者都可理解，也难以代替完整的键盘和实际辅助技术测试。

建议将核心路径（登录、查询、编辑、保存、错误恢复）纳入键盘检查，并对高复用组件库建立统一规范。业务页面直接使用成熟组件库通常能降低一部分基础风险，但复杂组件的配置仍需核对语义和行为。

15.3 浏览器与设备矩阵

Chromium 单浏览器 E2E 适合作为起步；对用户分布广的应用，可逐步验证 Firefox、WebKit、移动端视口。不能仅凭模拟移动视口推断真实触摸、输入法和设备性能表现。选择矩阵应根据实际用户设备、浏览器支持策略和风险决定。

第 16 章 质量指标、CI/CD 与持续治理

16.1 覆盖率是什么，不能说明什么

代码覆盖率通常包括语句、分支、函数与行覆盖。高覆盖率说明大量代码在测试中被执行，却不能保证断言正确或业务场景充分。例如一个测试只调用函数、不检查输出，也可能提高覆盖率。

覆盖率适合用来定位未测分支，尤其是错误处理与边界路径；不宜把全仓库的某个数字直接当作“测试质量等级”。新项目可以针对可稳定测量的关键业务模块设置适度覆盖率门禁，并定期评估其有效性。

本配套工程在 vitest.config.ts 中只统计 search-params.ts、RequestError.tsx、api.ts 三个明确模块，门禁是演示值：行、语句、函数 65%，分支 55%。运行前需确保 Vitest 与对应 coverage provider 版本一致。

16.2 可以长期追踪的质量指标

指标定义建议作用与限制
核心测试通过率通过用例 / 实际执行用例监测基线；应同时报告跳过与失败项
Flaky 比例在相同代码与条件下出现不稳定结果的用例占比反映自动化可信度，需排除真实系统不稳定
缺陷逃逸发布后发现的缺陷数量/严重度/影响用户数评估测试盲区，受报告与业务规模影响

在原 employees.tsx 中，URL 分页参数解析与组件状态混合。第八阶段把它提取为 search-params.ts，让分页和过滤规则可以直接做边界测试。

这样拆分把有清晰输入输出的业务规则与 React 渲染分开。页面仍通过 useSearchParams 管理 URL，解析函数本身不依赖 React、Router 或浏览器生命周期。

17.4 变更二：统一错误恢复组件

RequestError 接收错误消息和可选重试回调，EmployeesPage 和 DashboardPage 复用它。组件测试验证两件事：

  • 出错时存在可识别的 role="alert" 错误提示。
  • 提供重试时可以点击；没有回调时不显示无效按钮。

这个组件足够简单，但作为一个“最小的真实组件测试”很合适。更复杂的员工表单可以在理解本章后继续扩展，但不在教材正文安排另一套练习。

17.5 变更三：测试 HTTP 客户端和服务端权限

MSW 测试使用 HTTP handler 返回正常数据、409 冲突和缺失 data 的响应，检查 ApiError。它证明前端请求边界的行为。

Node.js 测试真实启动 Mock API，验证：

  1. 查询筛选与分页响应。
  2. 创建、详情、更新、删除的 HTTP 契约。
  3. 工号冲突 409 和字段校验 400。
  4. viewer 通过直接 HTTP 请求写入被 403 拒绝。
  5. 不同 Cookie 会话的角色隔离。

两个层级的意义不同：MSW 验证前端如何理解接口；API 集成测试验证服务端是否真的按契约执行。

17.6 变更四：用 Playwright 验证跨应用用户旅程

Playwright 用例覆盖：

  • Shell 首页点击“组织人员”后进入子应用，员工列表能显示真实 Mock API 提供的“张三”。
  • 切换到只读角色，前端写入入口消失，并且同一会话直接 POST API 返回 403。
  • 首次请求及一次自动重试返回 503，错误组件出现，用户点击重试后恢复列表。

这些断言覆盖三类真实风险：动态加载与路由、UI/服务端授权边界、请求失败恢复。它们不依赖 UI 库生成的随机 className。

附录 B：概念速查

断言（Assertion）：把实际结果与预期行为比较；应与业务契约直接相关。

Fixture：准备测试环境和依赖的机制；用于隔离 Context、浏览器会话、数据及外部资源。

Mock / Stub / Fake / Spy：不同目的的测试替身。Stub 预设返回值、不检查交互；Mock 记录调用次数与参数；Fake 是具备简化行为的可执行替代实现；Spy 包裹真实实现，在保留原行为的同时记录调用（如 vi.spyOn）。

Unit / Component / Integration / E2E：根据验证对象与依赖边界划分的测试层级，不以某一个工具名决定。

Flaky Test：代码未变、相似环境下结果不稳定的测试；可能暴露产品竞态或测试缺陷。

Coverage：代码执行覆盖情况，不能直接表示断言的有效性或需求覆盖。

RUM：真实用户监测，观察真实设备和网络下的性能分布。

LCP / INP / CLS：加载呈现、交互响应和布局稳定性的核心指标；常结合第 75 百分位评估。

Contract Test：检验调用双方共同约定的请求、响应、错误语义及兼容性。

Trace：浏览器操作、页面状态及网络信息的诊断记录，注意敏感信息保护。

Risk-based Testing：根据影响、发生概率与可检测性配置测试资源。
