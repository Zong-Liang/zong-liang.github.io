软件测试基础：概念、分类与应用场景

一、软件测试是什么

1.1 软件测试的目标

软件测试（Software Testing）是通过检查工作成果、设计验证条件、执行软件并分析结果，评估软件是否满足要求、识别缺陷与风险的活动。测试对象既可以是正在运行的程序，也可以是尚未实现的需求、设计和代码。

以购物系统为例，测试可能关注几个不同的问题：

  • 功能与业务规则：库存不足时能否阻止下单？优惠券是否只在有效期内生效？
  • 权限与安全：普通用户是否只能查看自己的订单？
  • 性能与可靠性：高并发时能否保持可接受的响应时间？依赖服务失败后会发生什么？
  • 交互与兼容性：用户能否在目标浏览器中完成购买，错误信息是否易于理解？

这些问题不能只靠“把程序运行一遍”回答。实际测试包含测试分析、用例设计、数据与环境准备、执行、结果判断、缺陷报告及后续确认。需求评审、代码检查等不执行程序的活动也属于测试范畴。[1]

测试和调试（Debugging）需要区分：测试提供关于问题及质量状态的证据；调试主要定位问题原因并修改实现。开发者可以同时承担这两类工作，但两项活动的目标不同。

1.2 测试能证明程序没有缺陷吗？

通常不能。程序可能接受大量输入，受到用户状态、并发、运行环境和第三方服务的影响。测试无法穷尽所有输入、状态组合和执行路径。测试通过只能说明：在已执行的条件、已采用的判断标准下，没有观察到对应的失败，不能推导出系统在所有条件下都正确。

因此，设计测试时需要回答两个问题：

  1. 哪些失败最值得优先发现？
  2. 在成本和时间约束下，哪些验证能够为这些风险提供充分证据？

这意味着测试数量、自动化比例和代码覆盖率都不能单独代表软件质量。

1.3 验证与确认

验证（Verification）关注工作成果是否符合规定的要求、规格或设计；确认（Validation）关注软件是否满足预期使用需求。

假设注册功能的规格规定密码长度为 8～20 个字符。检查系统是否正确执行这条规则，属于验证；检查这套注册要求是否让预期用户顺利完成注册，属于确认。两者并不对应两个彼此隔离的测试阶段，也可能在同一项测试活动中同时涉及。[1]

1.4 错误、缺陷与失效

概念英文含义
错误Error人在理解、设计、编码等活动中作出的错误判断或行为
缺陷Defect / Bug需求、设计、代码、配置等工作成果中存在的问题
失效Failure软件运行时出现的与预期不符的可观察行为

例如，开发者误以为库存可以扣减到负数，因此在代码中遗漏库存约束。错误判断形成了实现缺陷；当并发请求触发负库存时，系统发生失效。缺陷不一定在每次执行时都表现为失效，必须考虑触发条件。

二、如何理解软件测试的分类

2.1 不同术语回答的是不同问题

“单元测试、接口测试、黑盒测试、回归测试、自动化测试”不能简单排列成相互排斥的五种测试。它们分别描述测试的不同属性。

观察维度要回答的问题代表性概念
测试层级与范围被测软件涉及多大范围，集成到什么程度？组件（单元）、组件集成、系统、系统集成、验收；实践中还有 E2E
测试对象或入口直接检查系统的哪个部分或边界？API、UI、数据库、消息、契约、文件
质量目标具体要验证哪项要求？功能、性能、安全、可靠性、兼容性、可用性
测试设计依据根据哪些信息推导测试条件？黑盒、白盒、经验驱动；实践中也常说灰盒
执行目的与时机为什么在此时运行？冒烟、回归、确认、发布验证
是否运行被测软件如何获得证据？静态测试、动态测试
执行与判断方式由谁或什么机制完成操作和判断？手工测试、自动化测试

这张表是为了帮助理解概念关系而建立的工程化整理，不是宣称所有术语都属于一个正式、互斥的标准分类。尤其要注意：ISTQB CTFL 4.0.1 的“测试层级”和“测试类型”各自有明确的标准口径，不能把上表当成 ISTQB 的原始分类表。[1]

例如，一个浏览器自动执行“登录—下单—确认订单成功”的用例，可以同时被描述为：

  • E2E 测试：它验证一条完整业务流程；
  • UI 驱动测试：从浏览器界面发起操作；
  • 功能测试：判断订单是否正确创建；
  • 黑盒设计：根据业务要求选择输入和预期结果；
  • 回归测试：每次相关代码变更后再次运行；
  • 自动化动态测试：用脚本执行软件并判断结果。

这些标签分别回答不同问题，并不矛盾。

2.2 标准术语与工程习惯不完全相同

ISTQB CTFL 4.0.1 将测试层级定义为五类：组件测试、组件集成测试、系统测试、系统集成测试、验收测试。工程上广泛使用的“单元测试”通常对应组件测试；“E2E”则强调从业务起点到终点的链路，不是该标准额外规定的固定第六层。[1]

同样，“接口测试”经常按测试入口命名，“集成测试”按集成边界命名。因此，一条验证 HTTP 请求能够正确写入真实数据库的测试，既可以是接口测试，也可以是集成测试。

三、按测试层级：从局部代码到交付验收

测试层级关注被测范围、依赖边界及需要建立的信心。层级更高不代表“更高级”，而是验证的问题不同。

3.1 组件测试与单元测试

组件测试（Component Testing）验证相对独立的组件是否按预期工作。“单元测试”（Unit Testing）在多数开发语境下与组件测试相近，但“单元”可以是函数、方法、类或较小的逻辑模块，不存在所有技术栈通用的固定尺寸。

以订单金额计算为例：

1
2

def calculate_total(price, quantity):
    return price * quantity

可以用 price=100, quantity=2 断言结果为 200，再考虑 quantity=0、非法数量和金额精度等需求。这里的示例函数只展示基础乘法；如果业务还规定数量必须大于零、折扣规则或金额舍入，必须在规格和实现中明确后再测试，不能凭测试用例擅自定义业务行为。

这类测试通常速度快、容易定位失败，也不需要启动整个系统。JUnit、pytest、Jest、Vitest 等可以用于不同技术栈的组件或单元测试。

前端工程中的“组件测试”还有常见的具体用法：独立渲染商品数量选择器，验证加减按钮、禁用态及提示文本。它同样是在较小范围内验证组件，不意味着一定要运行完整的前后端应用。

边界：通过单元测试不能证明真实数据库连接、序列化、网络调用和整个下单链路正确。

3.2 组件集成测试

组件集成测试（Component Integration Testing）验证同一系统内部组件之间的接口和协作。比如：订单业务服务调用持久化组件，将订单写入 MySQL。

即使订单金额的单元测试已通过，也仍可能存在：

  • SQL 或对象字段映射错误；
  • 数据库约束与代码假设不一致；
  • 事务异常时没有正确回滚；
  • 缓存读写或消息发送的行为与约定不符。

可使用真实的隔离数据库验证这类交互。Spring Boot Test、Testcontainers、REST Assured 等可以分别帮助建立测试环境或驱动验证，具体选择取决于项目技术栈。

3.3 系统测试

系统测试（System Testing）将一个已集成、可运行的系统作为被测对象，检查其功能及非功能要求。购物系统的系统测试可能包括登录、商品查询、订单管理、权限、异常处理和响应性能。

系统测试不要求一定通过浏览器执行；从 API、命令行或其他公开入口检查完整系统，也可能属于系统测试。它的重点是完整系统是否符合要求，而不是“有没有点开 UI”。

3.4 系统集成测试

系统集成测试（System Integration Testing）验证被测系统与其他独立系统或外部服务之间的交互。例如购物系统调用独立支付服务：

  • 请求和响应格式是否兼容；
  • 超时和失败如何处理；
  • 支付回调能否正确更新订单状态；
  • 重复通知是否按照约定处理。

测试必须说明外部依赖边界：使用真实测试环境、官方沙箱还是受控替身。若支付服务完全被替换为模拟对象，测试只能证明被测系统对该模拟协议与行为的处理，不能证明真实支付系统的集成已验证。

3.5 验收测试

验收测试（Acceptance Testing）用于判断软件是否满足约定的接受条件并具备交付、部署或使用的准备程度。它常与业务需求直接相关，例如：库存不足的订单不能创建、退款流程遵守规则、管理员只能查询授权范围内的数据。

验收的常见形式包括用户验收（UAT）、运维验收（OAT）、合同验收和监管验收；Alpha、Beta 也属于常见的预发布接受或反馈形式。由谁参与、采用什么环境、依据什么标准，需要在项目中明确。验收既可以人工进行，也可以通过自动化验证部分条件。[1]

3.6 端到端测试（E2E）如何定位

E2E（End-to-End Testing）强调一条完整业务流程从起点到终点的结果。例如：

1

登录 → 选择商品 → 提交订单 → 库存检查 → 保存订单 → 页面展示结果

如果验证这条链路，还要确认关键结果而非只观察“按钮能点击”：订单是否实际创建、数量和金额是否正确、异常时状态是否一致。

E2E 可以通过浏览器驱动，也可以通过 API 驱动完整业务流程。前者通常同时验证 UI 集成，后者不一定覆盖界面。E2E 可能落在系统测试或跨系统集成的范围内，其覆盖边界取决于实际接入哪些服务。浏览器驱动的常见工具有 Playwright、Cypress、Selenium，但工具名称本身并不能决定一条测试是否属于 E2E。[3]

概念关注点不应据此推断
组件/单元测试局部逻辑或组件行为真实依赖必然正确
组件集成测试系统内组件的交互完整用户流程已通过
系统测试整个系统的各项要求所有跨系统依赖都已验证
系统集成测试与独立系统的交互必然覆盖完整用户旅程
验收测试满足接受条件与交付准备一定由浏览器或人工执行
E2E 测试业务链路及最终结果必须是独立的第六测试层级

四、按测试对象：检查哪个部分或边界

4.1 API 测试

API 测试（API Testing）验证程序对外提供的接口是否按约定工作。在 Web 项目中常指 HTTP API，但 API 并不限于 HTTP。

例如创建订单：

1
2
3
4

POST /api/orders
Content-Type: application/json

{"productId":1001,"quantity":2}

根据接口规格，需要检查的可能包括：参数校验、认证与授权、业务规则、状态码与响应结构、数据持久化、重复请求的幂等性约定，以及错误处理。

这里的 POST /api/orders 仅为教学示例，不代表真实系统的接口定义；是否要求幂等、返回哪个错误码，必须以实际 API 契约为准。

API 测试不需要启动浏览器页面，通常适合覆盖较多输入和异常组合。Postman、REST Assured、Supertest、pytest 和 Playwright 的 API 功能都可用于相关工作。Playwright 也支持用 API 请求准备浏览器测试数据和验证服务端状态。[4]

4.2 UI 测试与视觉回归测试

UI 测试（User Interface Testing）验证界面呈现和交互行为，包括：

  • 按钮、表单、弹窗和路由是否按要求工作；
  • 错误、加载、空数据等状态是否合理；
  • 键盘交互是否有效；
  • 页面与服务端状态是否正确衔接。

UI 测试既可能是仅挂载前端组件并模拟 API 的测试，也可能是连接真实后端的浏览器测试。UI 测试不等于 E2E 测试：前者由测试对象定义，后者由流程范围定义。

视觉回归测试（Visual Regression Testing）主要通过截图或视觉特征比较，发现布局错位、文字溢出、样式丢失等非预期变化。截图差异不自动等于缺陷：字体渲染、时间戳、动态数据和屏幕环境差异都会产生噪声。需要控制测试条件，并对可疑差异作出判断。

4.3 契约测试

契约测试（Contract Testing）检查通信双方遵守的交互约定是否兼容。例如订单服务依赖商品服务返回：

1
2
3
4

{
  "productId": 1001,
  "stock": 20
}

如果提供方删除 stock 字段或更改为消费者无法处理的结构，就可能破坏兼容性。消费者驱动契约测试会将消费者实际依赖的交互以契约形式表达，再由提供方验证其实现是否满足契约。[5]

契约测试特别适用于前后端分离、多团队 API、微服务和消息生产者—消费者协作。它不负责穷尽业务规则，也不能完全替代真实环境下的集成或端到端验证。常用工具有 Pact、Spring Cloud Contract。

4.4 数据、消息及其他对象

对象重点验证的问题示例
数据库SQL、字段映射、约束、事务、数据一致性下单失败时订单与库存能否一致回滚
消息队列发送、消费、顺序要求、重试、幂等、死信同一支付通知重复投递后是否重复记账
文件处理格式、解析、存储、上传下载和异常导入包含错误行的表格如何反馈
定时任务触发时机、重跑、补偿和幂等超时订单是否按规则取消
数据迁移完整性、转换规则、兼容性旧系统订单状态能否正确迁移
安装与部署配置、升级、回滚和部署后行为切换版本后服务能否恢复
移动应用设备权限、前后台切换、平台差异来电打断后操作是否可以恢复
配置与功能开关不同配置组合下的行为开关关闭后旧逻辑是否仍然有效

这些分类反映测试的直接对象，可以同时与某个测试层级、质量目标或执行方式结合。

五、按质量目标：要验证什么要求

5.1 功能测试

功能测试（Functional Testing）判断软件提供的功能、业务规则和可观察行为是否符合要求。

订单业务中的功能要求可能是：

  • 库存充足时允许创建订单；
  • 库存不足时拒绝下单；
  • 成功支付后订单状态按规则变化；
  • 未授权用户不能查看他人的订单。

功能测试可以在单元、接口、集成、系统、E2E 等多个范围内开展。功能正确性不局限于“正常路径”，还包括非法输入、边界、状态变化及错误处理。

5.2 非功能测试

非功能测试（Non-functional Testing）关注系统在满足功能之外的质量特征，典型问题是：系统做得有多好、在什么条件下仍然满足质量要求。ISO/IEC 25010:2023 提供产品质量模型，包含九项质量特征及其子特征，可用于梳理质量需求，但它不是要求每个项目针对所有特征各建一套测试工程。[2]

质量方向主要验证内容可操作的要求示例
性能指定负载下的响应时间、吞吐量和资源使用在约定并发、数据规模和环境下，订单查询接口 P95 响应时间不超过 500 ms
安全认证、授权、输入处理、会话和敏感数据保护普通用户不能读取其他人的订单
兼容性目标运行环境及系统之间的兼容指定版本的 Chrome、Firefox、Safari 可以完成主要流程
可靠性在规定条件下持续正确运行及处理故障短暂依赖故障不会造成重复创建有效订单
恢复能力故障后服务、数据和状态恢复数据库故障后能在约定恢复目标内恢复业务
可用性用户能否有效、有效率且满意地完成任务新用户在定义的任务条件下完成下单流程
可访问性不同能力用户能否操作与感知界面核心表单可用键盘操作，输入项有可识别标签

上述数值与规则是说明需求怎样写具体的例子，不是软件测试行业通用阈值。实际验收时还必须明确测试环境、负载模型、样本量、统计口径和失败条件。

性能测试的常见形式

  • 负载测试（Load Testing）：检查预期业务负载下的表现。
  • 压力测试（Stress Testing）：超过预期负载，观察瓶颈、失效和恢复行为。
  • 峰值测试（Spike Testing）：观察负载突然增减时的表现。
  • 耐久测试（Soak/Endurance Testing）：在较长时间运行中检查性能退化或资源泄漏。
  • 容量测试（Capacity Testing）：评估满足目标要求的最大业务规模。
  • 可伸缩性测试（Scalability Testing）：观察资源增加时能力如何变化。

常见指标包括吞吐量、响应时间分位数、错误率、CPU/内存使用、数据库连接和队列积压。工具可选 JMeter、k6 或 Gatling，工具本身不能替代负载模型设计。

安全、可访问性与故障测试

安全测试可能包含认证、越权、SQL 注入、会话管理和依赖漏洞评估，也可能涉及漏洞扫描及渗透测试。真实系统上的主动安全测试需要合法授权及清晰的范围，可参考 OWASP Web Security Testing Guide。[6]

可访问性测试可以参照 W3C WCAG 2.2 检查键盘可操作性、控件标签、对比度等可验证要求。自动化检查只能覆盖其中一部分，必要时还需人工测试或辅助技术验证。[7]

故障恢复测试关注恢复动作及结果；故障注入和混沌工程则在受控条件下引入扰动，研究系统面对故障时的表现。这些并非所有项目的入门必选项，应从实际风险出发。

其他质量与专项活动还包括国际化、本地化、可维护性分析、可移植性验证以及资源使用测试。是否引入，要取决于产品需求，而不是分类表中是否列出了名称。

六、如何根据要求设计测试用例

知道“测什么”之后，还要解决“选哪些输入、如何判断正确”的问题。

6.1 从测试依据到预期结果

测试依据（Test Basis）可以是需求、验收标准、接口契约、设计、代码或已确认的业务规则。测试分析先识别测试条件，再选择输入、状态和操作，最终写出预期结果。

以“订单金额满 100 元可以使用优惠券”为例，已经明确的是金额门槛包含 100 元；测试应据此设计 99、100、101 等数据。若文档未规定优惠券叠加、有效期、税费前后金额等细则，不能擅自将自己的理解作为唯一正确答案，应先澄清规则。

测试预言机（Test Oracle）指用来判断正确结果的依据或机制；断言（Assertion）是将该判断落实为可执行或可检查的条件。断言不应只检查请求成功，还应覆盖业务结果和必要副作用。

6.2 黑盒测试及常用设计技术

黑盒测试（Black-box Testing）以规格和外部可观察行为为依据，不依赖程序内部代码结构。它适用于单元、接口、系统、验收等不同层级。

等价类划分

把预期处理方式相同的输入分成类别，再从每类选择代表数据。若数量规则为 1～10：

等价类示例数据预期
小于 10非法
1～105合法
大于 1011非法

这并不保证同类中每个输入都正确；它是在成本有限时选择代表样本的办法。

边界值分析

对 1～10 的整数范围，可重点测试 0、1、2、9、10、11。其中 1、10 是有效边界，0、11 紧邻边界外，2、9 可用于检查边界内侧。选择哪些值取决于输入类型和边界规则。

判定表测试

多个条件共同决定结果时，判定表比逐条口述更容易发现遗漏。例如：优惠券是否过期、订单金额是否达标，共有四种组合。

已过期金额达到门槛可使用优惠券
否是是
否否否
是是否
是否否

此表只建立在上述两个条件决定使用资格的假设下。如果还有用户范围、领取状态、商品限制等条件，应继续补全规则，而不是认为四行已经穷尽业务。

状态迁移测试

对有生命周期的业务，需要检查允许的状态变化以及不允许的状态变化：

6.3 白盒测试：利用内部结构识别遗漏

白盒测试（White-box Testing）根据代码控制流、分支、条件等内部结构设计测试。例如：

1
2
3
4

if amount >= 100:
    apply_discount()
else:
    reject_discount()

仅测试 amount=150 会执行第一分支，但第二分支尚未执行。至少还需有覆盖第二分支的输入。

常见覆盖对象包括语句、分支、复合条件及特定执行路径。需要区分：

  • 语句覆盖：哪些可执行语句曾被运行；
  • 分支覆盖：哪些控制流分支曾被执行；
  • 条件覆盖：复合判断中各原子条件的取值是否得到覆盖；
  • 路径覆盖：指定执行路径是否得到覆盖，复杂程序通常难以穷尽所有路径。

覆盖率只说明相关代码或结构曾被触及，不能说明断言正确，也不能证明需求没有遗漏。

6.4 灰盒与经验驱动

“灰盒测试”（Gray-box Testing）通常指结合内部知识与外部行为进行设计。例如通过 HTTP 创建订单，同时根据架构知识检查测试数据库中对应状态。它是工程上的便利描述，不应机械当成与所有标准术语完全互斥的正式类别。

经验驱动技术则利用既往缺陷、领域风险和测试人员的观察，包括：

  • 错误推测：根据历史问题重点检查重复提交、空值、超时等场景；
  • 检查表测试：依据权限、输入校验、异常处理等风险清单设计检查；
  • 探索性测试：在了解系统、设计实验、执行和观察之间持续迭代，而非先列出所有固定用例再执行。[8]

探索性测试可以有明确的探索目标、时间范围和记录要求。它既是一种测试方法，也常用于尚不熟悉或风险未知的功能；不宜简单归类为某个固定“执行时机”。

6.5 按需引入的其他技术

技术解决的问题适用示例
两两组合 / 组合测试大量参数组合无法穷举时，按约定组合覆盖目标选取数据浏览器、操作系统、用户角色组合
基于属性的测试对大量生成输入检查通用性质数据转换后满足不变量
模糊测试（Fuzzing）通过异常、变异或生成输入寻找崩溃和边界缺陷文件解析器、协议接口
变异测试对实现作受控修改，检查现有测试能否识别变化评估断言的缺陷检出能力
差异测试比较多个实现或版本在相同输入下的行为老系统与新系统迁移
基于模型的测试根据状态或行为模型生成场景复杂状态机和协议

这些技术与黑盒、白盒等并非始终处于同一分类层级，作用也不完全相同。选择依据应是风险、可用信息和维护成本。

七、按执行目的、验证方式与开发过程区分

7.1 为什么现在要运行测试

名称主要目的订单系统示例
冒烟测试（Smoke Testing）快速判断新构建或部署是否具备基本可用性首页、登录、商品查询和基本下单正常
确认测试（Confirmation Testing）验证已报告缺陷是否得到修复再次执行曾触发重复订单的步骤
回归测试（Regression Testing）检查变更是否意外破坏已有行为修改折扣规则后检查普通订单、退款和历史金额
健全性测试（Sanity Testing）针对特定变更进行快速、定向检查仅检查本次修改的优惠券规则
发布验证检查实际部署版本、配置及关键能力生产发布后执行经过批准的无破坏性检查
维护测试验证升级、迁移、修改等活动造成的影响升级数据库版本后检查关键查询与事务

Smoke 和 Sanity 在一些团队中用法交叉，重要的是约定套件范围、进入条件和执行成本。冒烟、确认、回归不是三个独立的测试层级：同一条测试可能被纳入多个套件，只是执行目的不同。

生产环境合成测试、金丝雀发布验证和线上监控属于更广义的运行质量保障手段，不能代替发布前测试。涉及真实订单、资金或通知的场景，应使用受控数据和明确的环境保护措施。

7.2 静态测试与动态测试

静态测试（Static Testing）不需要执行被测软件：需求评审、设计评审、代码评审、静态分析都属于相关活动。例如需求只有“订单超时自动取消”，却没有规定超时时间，在编码前的评审中就可以识别规格缺口。

动态测试（Dynamic Testing）通过执行被测软件观察行为。单元、API、系统、性能和 UI 测试通常属于动态测试。

两者关注的是是否运行被测软件，不能与“手工或自动化”混为同一个二选一的分类：代码评审可能由人完成，静态代码分析可自动化；运行系统的测试既可以人工执行，也可以自动化。

7.3 手工测试与自动化测试

手工测试适合探索未知行为、评价可用性、判断复杂视觉问题或处理一次性场景。自动化测试适合重复执行、预期明确、环境和数据可控的场景。

自动化并不意味着维护成本为零，脚本、测试数据、依赖服务和运行环境都需要持续维护。决定是否自动化时，可以检查：执行频率、断言是否可靠、失败诊断成本、数据隔离难度以及维护收益。

7.4 TDD、BDD 与 ATDD

它们主要描述开发与协作方法，而不是新的测试层级：

  • TDD（测试驱动开发）：通常采用“先写失败测试 → 实现通过 → 重构”的循环，让测试约束实现。
  • BDD（行为驱动开发）：围绕可观察的业务行为和具体示例，让业务、开发和测试形成共同理解，常使用 Given / When / Then 组织场景。
  • ATDD（验收测试驱动开发）：在功能实现前协作确定验收条件和代表性测试，再据此指导开发。

三者可以与组件、接口、集成和 E2E 测试组合使用。采用 Given / When / Then 的写法，并不自动意味着团队已经实施了完整的 BDD 流程。

八、测试依赖、数据与环境

8.1 真实依赖与测试替身

测试替身（Test Double）是为了控制依赖而使用的替代实现。常见术语如下：

类型主要作用订单测试示例
Stub提供预设响应库存查询固定返回 10
Mock验证某种交互是否发生验证通知接口是否按约定调用一次
Fake使用简化但可工作的实现用内存存储实现替代持久化数据库
Spy记录调用情况以供检查记录发送通知的参数和次数

不同框架对 Mock、Spy 等命名可能不严格遵循上述区分。更重要的是明确：哪些依赖是真实的，哪些被替换，以及测试因此能证明什么、不能证明什么。

例如，库存服务被 Stub 固定返回“有库存”时，订单模块的单元测试可以验证自身控制逻辑，但不能证明真实库存查询的 SQL 或网络调用正确。

8.2 测试环境与数据隔离

一个测试能否稳定复现，往往取决于执行环境是否可控。至少需要识别：

  • 被测服务及依赖的版本、配置和启动方式；
  • 数据库、缓存、消息队列等外部依赖的状态；
  • 测试账号权限、有效期和必要的密钥管理；
  • 测试数据如何生成、隔离、清理；
  • 并行执行时是否可能相互干扰；
  • 失败后如何保留足够日志和证据。

尽量让用例能够独立运行，不依赖其他用例先执行。与外部服务协作时，明确沙箱或模拟边界，避免自动化测试意外影响真实用户与生产数据。

8.3 几个常用的测试组织术语

术语在测试工作中的含义
被测对象（SUT / Test Object）当前要评估的系统、组件或功能，决定测试边界
测试条件（Test Condition）从需求或风险中识别的需要验证的行为、属性或情形
测试用例（Test Case）为验证某个条件而定义的前提、输入、操作及预期结果
测试套件（Test Suite）按共同目的组织的一组测试用例，例如登录冒烟套件
测试夹具（Test Fixture）为测试建立和清理所需数据、对象或环境的安排

测试套件是一种组织方式，并不代表新的测试层级。例如一条 API 用例可以同时放入“订单回归套件”和“发布冒烟套件”，不需要复制两份实现。

九、实际案例：为“库存不足时不能下单”设计测试

单个需求可以用来串联前面的概念。以下是用于演示测试设计方法的业务约定，不是某个真实系统已经确认的需求。

9.1 先明确需求与验收边界

假设产品规则为：

  1. 用户一次下单购买一个商品，购买数量必须为正整数。
  2. 仅当可售库存不少于购买数量时，才能创建有效订单。
  3. 库存不足时，接口应返回可识别的业务失败结果，不创建有效订单，库存保持不变。
  4. 成功创建订单时，需要按业务约定扣减库存。
  5. 不允许两个并发请求使可售库存被重复扣减为负数。

真实项目还需要确认：库存什么时候扣减、订单是否允许预占库存、取消时怎样释放、幂等键是否必需，以及什么叫“有效订单”。这些问题影响断言，不能通过测试人员自行假定而绕开。

9.2 从风险推导测试组合

风险或需要回答的问题建议验证方式重点断言
数量判断边界错误单元测试、边界值分析数量为零、负数、整数边界时的规则处理
库存判断逻辑错误单元测试、判定表可售库存与购买数量组合的结果
SQL 或事务不符合预期数据库组件集成测试数据变更及回滚符合约定
并发下超卖并发集成测试成功数量与最终库存一致，不出现负库存
API 参数与错误处理不符合契约API 测试响应结构、错误标识与数据结果
前端错误提示缺失UI 组件测试用户看到库存不足反馈，操作状态正确
跨模块完整流程出错少量 E2E 测试从页面操作到订单结果的关键链路可用
用户越权访问订单权限与安全测试无权用户无法读取或操作他人订单
高负载下性能不达标性能测试在定义的负载模型下满足约定指标

这里并不是要求每个风险都独立写一套重复用例，而是选择能够有效发现该风险、又容易维护的测试边界。真实数据库并发问题不能仅靠模拟仓库的单元测试证明；页面完整流程也不需要承担所有数值边界的穷举工作。

9.3 将一条规则写成可验收的测试用例

字段内容
用例名称库存不足时拒绝创建订单
测试依据第 9.1 节第 2、3 条规则
前置条件已登录测试用户；商品 A 可售库存为 2；测试环境中的数据由本用例独立控制
输入对商品 A 请求购买 3 件
操作调用创建订单 API
预期响应返回符合接口契约的库存不足业务结果；具体 HTTP 状态码和错误字段以正式契约为准
业务断言不创建有效订单；商品 A 可售库存仍为 2
清理与隔离清理本次创建的测试数据；避免与其他用例共享可变库存

这条用例可以用 API 自动化执行；如果通过页面触发同一规则，还需检查页面是否准确传达失败原因。不要只检查“接口返回了某个状态码”，也不要只检查“页面出现了提示文字”，而忽略真正的业务状态。

9.4 用一个并发场景补足单元测试覆盖不到的风险

假设商品 A 可售库存为 1，两个请求几乎同时购买 1 件。在不允许预售、超卖，且只有这两个请求改变库存的前提下，预期应当是：

  • 两个请求最多一个成功创建有效订单；
  • 若测试环境没有其他故障且其中一个请求成功，则最终库存为 0；
  • 不会出现负库存、重复扣减或部分事务残留；
  • 失败请求得到符合约定的业务结果。

这项验证需要控制并发、检查最终数据，并根据系统实现决定是否测试数据库锁、乐观版本号或原子更新等机制。单纯创建两个线程但无法确认请求是否重叠，不足以说明已覆盖典型的竞态条件。

9.5 测试怎样进入开发与交付流程

可按反馈速度、依赖成本和风险安排执行，而不是要求所有测试每次都全部运行：

时机常见活动目的
需求与设计需求评审、验收条件、风险分析在实现前识别规格缺口
开发与提交前静态检查、单元/组件测试快速发现局部问题
持续集成单元、关键组件集成、契约和 API 测试检查变更对主要行为及边界的影响
共享测试环境关键系统场景、少量 E2E、专项测试验证真实集成与业务链路
交付与发布验收、发布检查、受控的冒烟验证判断是否满足交付和运行条件
修改或修复后确认测试与影响范围内的回归测试验证修复并防止引入新问题

测试金字塔（Test Pyramid）是组织自动化测试组合的参考：通常用较多成本低、反馈快的测试覆盖局部逻辑，用适量集成测试覆盖真实交互，用数量受控的高层测试覆盖关键业务链路。它不是要求所有团队遵守某个固定比例；不同架构的合理分布可能不同。[3]

十、如何判断测试结果与测试质量

10.1 测试通过的含义

测试通过至少需要明确的预期结果、实际执行证据和可靠的结果判断。例如订单 API 返回 HTTP 200，不代表下单正确；还可能存在订单金额错误、库存未扣减或重复订单。对业务有状态影响的操作，必要时应检查状态与副作用。

测试报告可以包括：被测版本、环境、范围、已执行用例及结果、未执行项、发现的缺陷、剩余风险、接受条件是否满足。不能把“已执行部分用例通过”直接写成“系统不存在问题”。

10.2 覆盖率是证据的一部分

指标通常描述什么主要局限
语句覆盖率已执行语句占目标可执行语句的比例执行过不代表断言正确
分支覆盖率已执行分支占目标分支的比例不能代表业务场景完整
需求覆盖率已建立测试关联的需求比例关联不代表测试质量或执行通过
风险覆盖已针对关键风险实施验证的程度依赖风险识别和验证标准的准确性
用例通过率已执行用例中通过的比例受用例粒度、选择范围与环境影响
缺陷逃逸情况交付后才发现的相关问题受反馈渠道、统计窗口和缺陷口径影响
Flaky 比例未改变相关被测行为却出现不一致结果的测试比例需要稳定的判定与统计口径

例如 100 条可执行语句中执行了 80 条，语句覆盖率为 80%；这并不意味着功能正确率是 80%。测试质量需要结合业务风险、断言有效性、缺陷发现与残余风险判断，不能把某个数字设为所有项目统一的合格线。

10.3 测试偶尔失败、重跑却通过怎么办

这类现象通常称为不稳定测试（Flaky Test）。可能涉及异步等待、竞态、数据干扰、测试顺序、外部依赖或环境资源。应先保存失败日志、环境和测试数据，判断是产品问题、测试实现问题还是环境问题。

重试可以帮助收集证据，但不能靠无限重试掩盖不稳定性。关键测试持续出现无法解释的失败，会降低团队对整套结果的信任。

十一、容易混淆的概念对照

容易混淆的概念核心区别
单元测试与集成测试前者主要验证局部代码或组件；后者主要验证组件之间的真实或受控交互。关键在被测边界。
集成测试与系统测试前者聚焦接口与交互；后者评估完整系统是否满足要求。
系统测试与 E2E系统测试可覆盖系统的多种功能与质量要求；E2E 聚焦一条从起点到终点的业务流程。两者可以重叠。
UI 测试与 E2EUI 描述验证对象或入口；E2E 描述流程范围。模拟后端的按钮测试是 UI 测试，但通常不能证明完整链路。
API 测试与集成测试API 描述接口入口；集成描述协作边界。一次测试可能同时属于二者。
API 功能测试与契约测试前者检查接口处理和业务结果；后者重点检查消费者与提供者约定的兼容性。
黑盒与白盒前者主要依据规格与外部行为；后者利用内部控制流与结构。两者可以互补。
冒烟与回归前者快速判断基础可用性；后者检查变更是否破坏既有行为。
确认与回归确认检查特定缺陷是否修复；回归检查修复是否影响其他行为。
功能与自动化功能描述验证目标；自动化描述执行方式。功能测试可以手工或自动执行。
静态与手工静态描述不执行被测软件；手工描述由人执行或判断，两个维度并不对应。
覆盖率与正确性覆盖率表示触及了哪些目标，不证明断言完整、需求正确或系统没有缺陷。
