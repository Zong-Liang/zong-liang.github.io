一、软件测试究竟在做什么

1.1 软件测试的定义与目的

软件测试（Software Testing）是通过评审、分析和执行等活动，评价软件及相关工作成果是否满足规定要求、识别缺陷和质量风险，并为质量决策提供依据。

假设购物系统提供登录、浏览商品、下单和支付功能。测试需要考虑的不仅是“按钮能否点击”或“接口能否返回成功”，还包括：

关注方面需要回答的问题
功能与业务规则库存不足时能否阻止下单？优惠券能否按规则使用？
性能预期并发量下，下单接口能否在要求的时间内响应？
安全普通用户能否读取或修改其他用户的订单？
兼容性目标浏览器、设备和运行环境中是否正常？
可靠性与恢复数据库或外部服务故障时，系统如何响应与恢复？
可用性用户是否能理解操作，并完成购买任务？

因此，测试既可能发生在代码编写之后，也可能发生在需求和设计阶段。例如，需求只写了“订单超时后自动取消”，但没有定义超时时间、取消条件和支付中的订单如何处理，需求评审就能提前识别这一问题。

软件测试与修复缺陷不是同一活动。测试负责发现和提供问题证据，开发、产品或其他责任方再根据问题性质决定如何修复或调整要求。

1.2 为什么测试无法证明软件绝对没有缺陷

软件通常存在大量输入组合、执行路径、依赖版本和运行条件，无法穷尽检查。即使一批测试全部通过，也只能说明：在本次覆盖的条件、数据、环境和判定标准下，没有发现相应问题。

例如，登录接口的密码输入可能包含不同长度、字符类型和编码。测试人员需要通过边界值、等价类、历史缺陷及风险分析选择样本，而不能依赖任意几组正常输入得出“登录功能完全正确”的结论。

实际测试工作的核心不是追求用例数量，而是在有限成本下，对重要需求和高风险失效提供足够的验证证据。

1.3 验证与确认：符合规格，不等于适合使用

  • 验证（Verification）：检查工作成果是否符合规定的需求、设计或技术规格。例如，密码长度规定为 8～20 个字符，程序是否正确执行这一限制。
  • 确认（Validation）：评估软件是否满足实际使用需求、适合预期用途。例如，注册规则虽然满足技术规格，但流程复杂到使目标用户难以完成注册，仍然存在适用性问题。

两者并不分别固定在开发的某两个阶段；需求评审、功能测试和用户验收都可能为验证或确认提供证据。

1.4 错误、缺陷与失效

概念英文含义
错误Error人在理解、判断、设计或实现过程中产生的错误
缺陷Defect / Bug代码、需求、设计、配置等工作成果中存在的问题
失效Failure软件运行时出现与预期不一致的可观察行为

例如，开发人员误以为库存允许减少到负数（错误），于是遗漏库存限制（缺陷）；用户购买超过库存的商品时，系统实际生成了负库存（失效）。缺陷不一定在每次执行时都触发，是否出现失效取决于具体条件。

二、测试分类的六个维度

2.1 六个互相补充的观察维度

维度判断问题代表性术语
测试层级与范围被测范围有多大？单元/组件、组件集成、系统、系统集成、验收；E2E 描述完整链路
测试对象与边界直接检查什么？API、UI、数据库、消息、契约、文件、部署
测试设计依据根据什么挑选场景和数据？黑盒、白盒、灰盒；等价类、边界值、判定表
测试目标检查哪种质量属性？功能、性能、安全、可靠性、兼容性、可用性
测试目的与时机为什么在此时执行？冒烟、回归、缺陷确认、发布验证
测试实施方式如何开展检查？静态/动态、手工/自动化、探索性等

这些维度可以交叉使用。例如，需求评审是手工静态测试，静态代码扫描是自动化静态测试，浏览器脚本执行的是自动化动态测试。

假设商品只剩 2 件，用户从购物车提交购买 3 件的订单。按业务规则，系统应拒绝下单，给出库存不足提示，库存仍为 2。可以从几个维度描述这条检查。

  • 从流程范围看，浏览器脚本从购物车操作到下单被拒绝，覆盖了一条 E2E 路径。
  • 从被测对象和设计依据看，可以按业务规格检查页面提示和订单状态。如果还依据表结构检查库存和订单记录，就用到了灰盒方法。
  • 从目标和时机看，它验证库存规则。修改下单逻辑后重跑这条用例，可以检查原有规则是否仍然成立。

同一条规则也可以用单元测试验证数量比较，用集成测试检查事务后的数据库状态。第十节将这些风险和验证手段放在一起比较。

三、按测试层级与业务范围划分

测试层级关注被测范围和集成程度。ISTQB CTFL 4.0.1 大纲 §2.2.1 列出五个层级，包括组件测试、组件集成测试、系统测试、系统集成测试和验收测试。E2E 描述业务流程覆盖的起点和终点，可以出现在系统测试或系统集成测试中。

3.1 单元测试与组件测试

单元测试（Unit Testing）针对一个相对独立的代码单元，如函数、方法、类或较小的业务模块，验证其行为是否符合预期。它通常执行较快、失败定位比较直接，适合参数校验、金额计算、规则判断、数据转换与状态处理。

例如，订单金额计算函数：

1
2

def calculate_total(price, quantity):
    return price * quantity

至少可验证正常数量、零数量等输入；如果业务要求限定数量范围、支持折扣或金额舍入，还应针对这些规则设计测试。单元测试能验证该函数的计算逻辑，但无法据此证明真实数据库写入和完整下单流程正确。

组件测试（Component Testing）验证独立的软件组件。ISTQB 的组件测试与日常所说的单元测试范围经常重叠，但前端团队通常赋予“组件测试”更具体的含义：独立渲染一个 UI 组件，验证其显示和交互。

例如，商品数量选择器需要处理加减数量、库存上限、非法输入和无库存禁用状态。可以只渲染该组件，用受控数据模拟必要依赖，无须启动整套购物系统。

常见工具：后端有 JUnit、pytest、xUnit；前端有 Jest、Vitest 等。具体工具不决定测试层级，实际被测范围才是判断依据。

3.2 组件集成测试

组件集成测试（Component Integration Testing）关注同一系统内部多个组件连接后的交互，例如订单业务服务、数据访问层和 MySQL 之间的协作。

即使订单金额计算的单元测试全部通过，仍可能发生以下问题：

  • SQL 语句与真实表结构不匹配，字段映射或约束配置错误。
  • 订单保存成功，但库存扣减失败，事务没有正确回滚。
  • 缓存和数据库中的状态不一致。
  • 消息发送、消费、重试或幂等处理不符合预期。

这类问题需要让相应的真实组件参与测试。数据库可以使用隔离的测试实例；无法接入的外部依赖则按测试目标决定是否使用替身。Spring Boot Test、Testcontainers 及各种语言的测试框架都可用于此类测试。

3.3 系统测试

系统测试（System Testing）以完整系统为被测对象，检查它是否满足功能和非功能要求。

例如，将购物系统的前端、后端及必要依赖组合为可运行的整体，验证登录、商品查询、订单管理、权限、错误处理或性能。系统测试不必通过浏览器执行：通过 API 或其他系统入口验证整体行为，也可以属于系统测试。

3.4 系统集成测试

系统集成测试（System Integration Testing）验证不同系统之间的交互，例如购物系统与独立支付平台、商品服务与第三方库存系统的集成。重点是跨系统协议、数据格式、调用时序、错误处理、兼容性等。

组件集成与系统集成的区分，主要取决于“一个系统的内部组件”还是“多个独立系统之间的协作”。项目里笼统称作“集成测试”的场景，需要结合依赖边界具体判断。

3.5 端到端测试（E2E）

端到端测试（End-to-End Testing）沿着一条明确的业务流程，从起点执行到终点，检查关键步骤及最终业务结果。

以购物流程为例，测试从登录开始，依次浏览商品、加入购物车并提交订单，再检查库存是否经过校验、订单是否创建以及页面是否正确显示下单结果。

它能够发现局部测试容易遗漏的跨模块问题，例如页面显示已下单，但后端未生成订单。E2E 的优势是贴近真实业务结果；代价是数据准备、环境治理、执行耗时和失败定位通常更复杂。

需要注意三点：

  1. E2E 不等于 UI 测试。 通过 API 串联并验证完整业务链路，也可以是 E2E。
  2. E2E 不保证使用所有真实外部服务。 例如支付系统可能使用沙箱或受控替身；测试覆盖范围取决于实际依赖边界，不能把模拟环节宣称为已完成真实集成验证。
  3. E2E 与系统测试可能重叠。 前者强调业务流程的起点和终点，后者强调被测系统整体要求。

常见 Web E2E 工具有 Playwright、Cypress、Selenium。工具适用性应结合浏览器控制能力、系统架构和团队维护成本判断。

3.6 验收测试

验收测试（Acceptance Testing）检查系统是否达到商定的接受条件、是否满足交付或投入使用要求。它不只关心技术接口是否正确，还关心业务方是否认可系统实际完成了所需工作。

常见形式主要关注点
用户验收测试（UAT）业务用户或代表确认业务需求是否得到满足
运维验收测试（OAT）部署、监控、备份、恢复、运维准备情况
合同验收测试合同约定的交付要求
监管验收测试适用的监管约束及交付条件

此外，Alpha 和 Beta 通常用于描述不同条件下的预发布试用和反馈活动：前者更偏受控环境，后者通常面向限定的外部真实用户。它们可能服务于验收与发布决策，但不能仅凭名称认定其覆盖了全部验收要求。

3.7 层级对照

测试类型核心问题典型示例不能单独证明什么
单元/组件测试局部逻辑或组件行为正确吗？金额计算、数量选择器真实依赖与跨模块链路正确
组件集成测试系统内部组件协作正确吗？订单服务访问数据库完整系统所有要求满足
系统测试完整系统满足要求吗？购物系统功能和性能其外部所有系统间交互都正确
系统集成测试不同系统能否正确交互？调用独立支付平台整个用户旅程均正确
验收测试是否达到接受条件？业务方确认交付底层实现不存在技术缺陷

例如，「登录到成功下单」描述的是 E2E 流程。如果整个流程都在购物系统内完成，它可以属于系统测试。如果验证还覆盖与独立支付平台的真实交互，也能为系统集成测试提供证据。

四、按测试对象划分

“接口测试、UI 测试、数据库测试”等术语主要指被测对象或交互边界，而不是独立的测试层级。

4.1 接口测试（API Testing）

接口测试检查 API 能否按规定处理输入、返回结果并完成预期操作。API 不限于 HTTP，但在 Web 研发中通常指 HTTP API。

例如创建订单接口：

1
2
3
4

POST /api/orders
Content-Type: application/json

{"productId": 1001, "quantity": 2}

应按业务要求覆盖合法输入、商品不存在、库存不足、身份认证失败、重复请求、响应格式、状态码与业务副作用。对创建操作而言，仅断言 HTTP 2xx 往往不充分；还需确认实际订单状态、库存变化以及是否产生重复记录。

接口测试可以是单个控制器的隔离测试，也可以连接数据库开展集成测试，甚至通过多个 API 构成 E2E。常见工具有 Postman、REST Assured、Supertest、pytest、Playwright API Testing 等。

4.2 UI 测试与视觉回归测试

UI 测试（User Interface Testing）检查界面的显示、操作与反馈，例如购物车中删除商品、修改数量、弹窗操作、错误提示、键盘交互。它既可以针对孤立的前端组件，也可以连接真实后端；是否属于 E2E，取决于是否覆盖完整业务链路。

视觉回归测试（Visual Regression Testing）通过截图或视觉特征比较识别非预期变化，例如文字溢出、按钮错位、样式丢失和布局破坏。截图存在差异并不必然是缺陷：字体、动态内容、操作系统或渲染环境的变化也可能产生差异。使用前应稳定测试环境和动态内容，并对有争议的变化进行确认。

4.3 契约测试（Contract Testing）

契约测试关注通信双方所约定的接口结构和交互行为是否保持兼容。

例如订单服务依赖商品服务返回 stock 数值字段，商品服务如果删除该字段或将其修改为不兼容的结构，消费者可能无法继续处理库存。契约测试能够提前识别这类跨团队变更风险。

常见方式包括消费者驱动契约测试，以及依据 OpenAPI 等接口规格进行契约验证；Pact、Spring Cloud Contract 是相关工具。契约兼容不等于业务逻辑正确，因此契约测试不能完全替代接口功能测试或真实集成测试。

4.4 其他常见测试对象

五、测试用例应该怎样设计

明确测试对象之后，还需要回答：从哪些数据和场景入手，才有可能发现重要问题？

5.1 黑盒、白盒与灰盒

方法主要设计依据例子
黑盒测试（Black-box）需求、规格、业务规则、外部可观察行为满 100 元可用优惠券：测试 99、100、101 元
白盒测试（White-box）源码、控制流程、分支或内部结构让 amount >= 100 判断的真、假分支都执行
灰盒测试（Gray-box）外部行为与已知的内部实现信息相结合调用下单 API，再检查订单记录与库存变化

黑盒与白盒的主要区别在用例设计依据，而不是能否打开源码或是否通过 API 执行。灰盒是常见工程描述，不应理解为与前两者完全互斥的严格标准层级。

白盒测试常用的覆盖指标包括语句、分支、条件与路径覆盖。覆盖率只能说明指定结构被执行到什么程度，不能直接证明断言正确、需求完整或不存在缺陷。

5.2 基于输入范围设计：等价类与边界值

等价类划分（Equivalence Partitioning）将预期采用相似处理规则的输入分组，从各组中选择代表性数据。

例如年龄只允许 18～60 岁，可以划分为：小于 18、18～60、大于 60 三类，分别选择代表值。

边界值分析（Boundary Value Analysis）关注临界点附近行为。例如允许商品购买数量为 1～10，可以选择 0、1、2、9、10、11。实际应结合类型约束和业务要求补充空值、非整数等情况。

这两种技术适合组合使用：先找等价类，再针对高风险边界补充测试，而不是机械遍历每个数值。

5.3 基于条件组合设计：判定表

当结果受多个条件共同影响时，判定表测试（Decision Table Testing）比只测试一条正常路径更合适。

5.4 基于状态变化设计：状态迁移

状态迁移测试（State Transition Testing）验证状态及其允许的变化，尤其要检查非法迁移。

    Paid --> Shipped: 发货
    Shipped --> Completed: 确认收货

这组规则下，待支付订单可以取消。支付成功后，订单依次经过已支付、已发货和已完成，分别由支付、发货和确认收货触发。

除了验证正常流转，还应检查已取消订单是否能再次支付、已完成订单是否能直接退回待支付等。具体迁移规则应以业务规格为准。

5.5 面对复杂组合和未知风险

技术使用方式
组合测试（Combinatorial Testing）从大量参数组合中选择具备指定组合覆盖的测试集合
两两组合（Pairwise Testing）给定参数和约束后，每对参数的每种可行取值组合至少出现在一条用例中
错误推测（Error Guessing）利用历史缺陷、经验和系统特性选择高风险场景
基于检查表的测试围绕权限、异常、边界、数据一致性等检查项组织用例
探索性测试（Exploratory Testing）在学习、设计、执行与分析之间持续迭代，发现事先未明确的风险

探索性测试不是随机点击，可以事先设定探索目标和时间范围。例如针对订单取消功能，重点探索网络中断、重复取消和超时重试对状态一致性的影响。

两两组合的覆盖范围见 NIST 组合测试说明。

六、按质量目标划分：功能与非功能测试

6.1 功能测试

功能测试（Functional Testing）检查系统功能与业务规则是否按要求实现。包括登录、订单创建、价格计算、状态迁移、参数拒绝、权限判断等。

功能测试不是某个固定层级：单元、接口、集成、系统和 E2E 都可以验证功能要求。

6.2 性能测试

性能测试（Performance Testing）关注指定负载和运行条件下的响应时间、吞吐量、错误率及资源消耗。

“系统要快”不是可直接验证的要求。更合适的表达是：在约定的测试环境和负载模型下，订单查询接口的第 95 百分位响应时间不超过 500 毫秒。这只是指标写法示例，并非所有系统都应采用该阈值。

类型重点
负载测试（Load）预期负载下表现是否符合要求
压力测试（Stress）超过预期负载后系统的极限与失效行为
峰值测试（Spike）流量突增或突降时的表现
耐久测试（Soak / Endurance）长时间运行是否退化、泄漏资源
容量测试（Capacity）满足目标指标时能承受多少业务量
可伸缩性测试（Scalability）扩容后系统能力如何变化

常用观察指标包括响应时间分布、吞吐量、错误率、CPU、内存和数据库连接数。相关工具有 JMeter、k6、Gatling。

6.3 安全、兼容性、可靠性与恢复

安全测试（Security Testing）检查身份认证、访问控制、会话管理、输入校验、敏感信息保护及已知漏洞风险。例如，普通用户是否能读取其他用户订单；输入是否可能导致 SQL 注入。漏洞扫描、渗透测试属于可能采用的安全测试活动，对真实系统开展主动测试时应获得授权并明确范围。

兼容性测试（Compatibility Testing）检查软件在目标浏览器、设备、操作系统、屏幕规格及依赖版本中的行为。测试矩阵应由实际用户分布和风险决定，而非默认覆盖一切环境。

可靠性测试（Reliability Testing）关注系统在规定条件和时间内持续提供预期能力，例如外部服务短暂不可用时是否合理处理、重试是否引起重复写入、长时间运行是否出现资源泄漏。

恢复测试（Recovery Testing）侧重故障发生后能否按要求恢复业务与数据，例如数据库重启后的服务恢复、备份恢复的有效性。恢复能力是可靠性相关的重要方面，但两者关注点并不相同。

6.4 用户体验与其他质量属性

类型关注问题
可用性测试（Usability）用户能否理解操作、高效完成任务，是否容易误操作
可访问性测试（Accessibility）键盘、屏幕阅读器、控件标签、对比度等是否满足相关要求
国际化测试（i18n）系统设计能否适应不同语言和地区格式
本地化测试（l10n）特定语言、地区的文案、时间、数字和格式是否正确
可维护性相关分析软件修改、诊断和验证的难易程度
可移植性相关测试软件迁移到目标运行环境的能力
资源使用测试CPU、内存、磁盘、网络等消耗是否符合要求
故障注入与混沌工程实验在受控条件下引入故障，研究系统承受扰动的行为

Web 可访问性可参考 W3C WCAG 2.2；ISO/IEC 25010:2023 提供了软件与系统产品质量模型，可帮助定义相关质量要求。质量模型是需求分析的参考，并不意味着所有项目都应对每种质量特征建立独立的测试工程。

七、按执行目的与时机划分

这组术语经常与具体测试层级混用，实际上它们更偏向回答：为什么现在执行这批测试？

类型目的示例
冒烟测试（Smoke）新构建或部署后快速确认核心能力是否基本可用首页可访问、用户可登录、可创建基本订单
健全性测试（Sanity）对特定变更快速做定向检查修改优惠规则后先验证相关主要路径
确认测试（Confirmation）判断特定已知缺陷是否修复重复提交曾生成两个订单，修复后复测原场景
回归测试（Regression）检查变更是否意外影响原有行为修改价格逻辑后复测原价、优惠、总价和历史订单
维护测试系统修改、升级、迁移或退役期间的验证依赖版本升级后的兼容性检查
发布验证确认部署后的核心业务与配置发布后执行受控业务验证

Smoke 与 Sanity 在团队实践中的边界可能重叠，具体应在项目内约定。确认测试围绕“原来的 Bug 是否修好了”，回归测试围绕“修复是否破坏了其他功能”，两者目的不同，但可以共享测试用例。

此外，生产环境合成测试、金丝雀发布验证和监控告警属于更广义的线上质量保障手段。它们可以补充发布后的证据，但不应替代发布前测试；线上测试尤其要控制数据与实际业务影响。

八、按实施方式与开发方法划分

8.1 静态测试与动态测试

  • 静态测试（Static Testing）：不运行被测软件，检查需求、设计、代码和其他工作成果。例如需求评审、设计评审、代码评审及静态代码分析。
  • 动态测试（Dynamic Testing）：运行软件，观察结果并进行判断。例如执行单元测试、发起接口请求、运行浏览器测试或性能测试。

静态测试可以在缺陷进入代码前识别问题；动态测试能够观察实际运行行为。两者互相补充。

8.2 手工测试与自动化测试

  • 手工测试（Manual Testing）：由测试人员直接操作、观察并作出判断，适合探索新功能、复杂体验评价、主观视觉判断及一次性检查。
  • 自动化测试（Automated Testing）：利用脚本或工具自动执行步骤并检查结果，适合高频重复、预期明确、数据可控、环境稳定的场景。

自动化不等于测试层级，也不代表天然更高质量。自动化代码需要持续维护，尤其是依赖真实浏览器和多服务环境的测试；手工测试在未知问题探索和体验评价方面仍然必要。

8.3 其他常用技术

技术基本思路适用场景
模糊测试（Fuzz Testing）构造大量异常或变异输入寻找缺陷解析器、协议、安全敏感接口
基于属性的测试（Property-based Testing）自动生成多组输入，检查通用性质计算、转换、数据处理
变异测试（Mutation Testing）对实现作受控小修改，看测试能否识别变化评估测试断言与检错能力
差异测试（Differential Testing）用相同输入比较多个实现或版本新旧系统替换、算法重构
基于模型的测试（Model-based Testing）根据状态或行为模型生成验证状态机、复杂协议

8.4 TDD、BDD 与 ATDD 并非三种测试层级

  • TDD（Test-Driven Development）：通常采用“先写失败测试—实现功能—重构”的循环，以测试反馈指导实现。
  • BDD（Behavior-Driven Development）：通过具体业务行为示例协调产品、开发和测试的理解，常用 Given / When / Then 表达情境、动作与结果。
  • ATDD（Acceptance Test-Driven Development）：在实现前共同定义验收条件和代表性验收场景，再以此指导开发与验证。

它们描述开发与协作实践，可以与单元、接口、集成和 E2E 测试结合，并不互相排斥。

九、测试工作的基本构成

9.1 从测试依据到测试结果

术语英文含义
被测对象SUT / Test Object当前要测试的软件、组件、系统或功能
测试依据Test Basis需求、设计、接口规格、代码等设计测试所依据的信息
测试条件Test Condition需要验证的具体行为、属性或情形
测试用例Test Case包含前提、输入、执行方式和预期结果的验证方案
测试套件Test Suite为共同目标组织的一组测试用例
测试数据Test Data用于执行的输入与预置数据
测试环境Test Environment运行测试依赖的软件、硬件、配置和服务
测试断言Assertion判定实际结果是否符合预期的检查
测试预言机Test Oracle确定正确结果的依据或机制
测试夹具Test Fixture为测试进行数据、对象、环境准备和清理的机制
测试报告Test Report测试范围、结果、问题、风险与结论的记录
不稳定测试Flaky Test没有相关产品变化，却可能出现不一致结果的测试

测试预言机与断言的区别尤其重要：预言机解决“为什么这个结果才正确”，断言解决“如何检查实际结果是否符合它”。例如“库存不足不允许创建订单”来自业务规格；断言则可以是“返回预期业务错误，数据库不产生有效订单，库存不改变”。

9.2 一个可执行的测试用例

以“库存不足时不能成功下单”为例：

项目内容
用例名称库存不足时拒绝创建订单
目标验证库存不足规则及数据一致性
前置条件商品可售库存为 2，测试用户具备下单权限
输入请求购买该商品 3 件
操作调用创建订单接口
预期响应请求按接口约定被拒绝，返回可识别的库存不足错误
业务断言不生成有效订单，不扣减库存，不产生非预期副作用
清理与隔离使用独立测试数据，执行后按约定恢复或清理

真实项目需要根据接口协议明确错误码、字段和具体状态，而不应凭空假定某个 HTTP 状态码。测试用例不必一律写成表格，但至少要让执行者可以判断成功或失败。

9.3 Mock、Stub、Fake、Spy

它们都与测试替身（Test Double）有关，但典型用途不同。

类型典型用途示例
Stub提供预设响应库存查询固定返回 10
Mock验证预期调用或交互通知发送方法是否被调用一次
Fake用可工作的简化实现替代真实依赖内存仓库替代持久化数据库
Spy记录调用数据，供后续验证捕获通知服务收到的参数

不同框架对这些名称的使用可能不完全一致。关键是明确替身承担什么职责，以及它隔离了哪些风险。使用全部模拟依赖的测试，不能代替与真实数据库、网络或外部系统的集成验证。

9.4 覆盖率与测试质量

覆盖率（Coverage）描述测试覆盖了多少指定目标，常见有语句、分支、条件、需求、功能和风险项覆盖率。

例如，一段程序有 100 条可执行语句，测试执行到了其中 80 条，语句覆盖率为 80%。但执行到一行代码，不代表断言能够发现该行的错误。类似地，覆盖了所有已列出的需求，也不等于需求本身完整或正确。

评估一套测试应综合考虑：重要风险是否覆盖、断言能否识别错误、测试是否稳定、失败是否容易定位、执行成本是否合理，以及变更后是否便于维护。

十、以“库存不足不能下单”为例设计测试组合

以可售库存为 2 件为例，先约定请求 2 件时允许下单，请求 3 件时拒绝且库存保持为 2。在此前提下，可以分别验证数量比较、数据库事务、并发扣减和用户看到的结果。

具体风险适合的验证手段关键证据
库存数量比较逻辑写错单元测试、边界值测试分别验证购买 1 件、2 件和 3 件的判定结果
SQL 或实体映射错误数据库集成测试实际数据库状态与预期一致
下单失败但已扣库存事务集成测试失败后订单与库存均符合事务要求
并发请求导致超卖并发集成测试竞争条件下库存及订单结果符合约束
API 拒绝逻辑、响应结构错误接口测试错误信息、状态码、实际副作用符合接口约定
页面未提示库存不足UI 组件或页面测试可见提示与交互状态正确
整个下单过程不能完成E2E 测试从用户操作到最终业务结果一致
重复提交产生重复订单接口与集成测试按业务幂等性规则验证最终记录
大量请求下响应不满足要求性能测试目标负载下延迟、吞吐和错误率满足指标
普通用户能操作他人订单权限与安全测试未授权操作按要求被拒绝，无不当数据变更

这不是要求为每行都建设独立框架。多个风险可以放进同一个测试套件，某些现有用例也能提供多种证据。但要警惕：通过模拟服务的 E2E 无法验证被模拟系统的真实集成问题；只检查接口返回成功，也无法证明数据状态正确。

10.1 从一个功能要求形成测试方案

  1. 明确要求和判定标准。 识别业务前置条件、正常结果、异常结果及必要的非功能指标。
  2. 列出失效模式。 考虑数值边界、状态迁移、权限、并发、事务、外部依赖和用户界面。
  3. 匹配验证范围。 纯规则优先用局部测试；真实组件协作采用集成测试；跨业务步骤采用受控的 E2E。
  4. 选择设计技术。 数值规则用等价类和边界值；多条件规则用判定表；复杂状态用状态迁移；未知风险采用探索性测试。
  5. 确定测试数据与环境。 明确哪些依赖是真实的，哪些是替身；建立数据隔离、初始化和清理策略。
  6. 决定自动化和执行时机。 将高频、稳定、可断言的检查纳入自动化；将体验判断和未知风险探索保留给人工活动。
  7. 检查结果与剩余风险。 测试通过只说明已覆盖条件下的结果；对未覆盖风险、环境限制和失败问题作出明确记录。

10.2 测试应当在研发流程中何时出现

研发活动常见测试及质量活动
需求与设计需求评审、验收条件、风险分析、测试设计
编码与提交代码评审、静态分析、单元测试、组件测试
模块协作数据库集成、服务接口、契约测试
系统验证系统测试、核心 E2E、性能和安全专项
交付准备UAT、运维验收、部署验证
变更与缺陷修复缺陷确认、受影响范围的回归测试
上线之后受控冒烟验证、监控、合成测试及金丝雀验证

这些活动不是严格串行的阶段门。持续集成环境中，单元、集成和部分系统级测试可能在多个阶段反复执行。

10.3 如何理解测试金字塔

测试金字塔（Test Pyramid）用来说明自动化测试组合中的一种常见取舍。底层以单元测试验证大量局部逻辑，中层用必要的真实集成测试发现协作问题，顶层用数量受控的端到端测试守护关键业务链路。

这并不要求所有项目采用固定比例。服务间交互复杂的系统可能需要更多接口与契约测试；前端交互复杂的产品可能需要较多组件测试。评价标准是新增验证价值与长期维护成本，不是是否把金字塔画得标准。

十一、最容易混淆的概念

容易混淆的概念判断关键
单元测试与集成测试验证独立代码逻辑，还是验证组件之间的真实协作？
组件集成与系统集成同一系统内部的协作，还是不同系统之间的协作？
集成测试与系统测试着重交互边界，还是完整系统的整体要求？
系统测试与 E2E检查整个系统，还是检查一条完整业务流程？两者可重叠。
UI 测试与 E2EUI 是对象和入口，E2E 是业务流程范围；二者不等价。
API 测试与集成测试API 是接口对象，集成是依赖边界；同一用例可能同时属于两者。
API 测试与契约测试前者检查接口行为，后者重点检查通信约定的兼容性。
黑盒与白盒根据外部规格设计，还是根据内部结构设计？
冒烟与回归判断构建基本可用，还是检查变更是否破坏原有行为？
确认与回归验证已知缺陷得到修复，还是识别修复产生的其他影响？
功能测试与自动化测试功能是验证目标，自动化是执行方式。

自动化用例偶发失败时，重跑可以帮助判断是否与执行顺序、数据隔离、异步等待或外部依赖有关。修复后，应在原先容易失败的条件下验证。
