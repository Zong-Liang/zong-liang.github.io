软件测试基础：概念、分类与应用场景

—— 从基本概念、分类体系到实际应用场景

一、认识软件测试

1.1 什么是软件测试？

软件测试（Software Testing）是通过检查、分析和执行软件，评估软件是否满足规定的需求，并发现缺陷、风险和质量问题的一系列活动。

例如，开发了一款购物软件，用户可以登录、浏览商品、下单和支付。

测试时可能需要确认：

  • 功能正确性： 用户能否成功下单？库存不足时是否禁止下单？

  • 业务规则： 优惠券是否只能在规定时间内使用？

  • 性能： 大量用户同时下单时，系统是否仍能及时响应？

  • 安全性： 普通用户能否查看其他人的订单？

  • 兼容性： 软件能否在不同浏览器和手机上正常使用？

  • 可靠性： 数据库或外部服务发生故障时，系统是否能妥善处理？

这些都属于软件测试的范畴。

软件测试不只是运行程序、寻找 Bug，还包括需求评审、测试设计、执行验证、缺陷分析和质量评估。

1.2 软件测试能证明程序没有问题吗？

不能。

测试可以发现缺陷，并提供软件满足特定要求的证据，但通常无法穷尽所有输入、运行环境和执行路径。

假设一个登录接口接受任意长度的字符串作为密码，可能存在无限多种输入组合。测试人员只能选择有代表性的输入和高风险场景。

因此，测试需要解决两个问题：

  1. 哪些问题最值得优先验证？

  2. 使用什么方法，可以用合理的成本获得足够的质量信心？

这也是为什么软件工程中会出现多种不同的测试类型。

1.3 验证与确认

软件测试中有两个基础概念。

验证（Verification）

检查软件是否符合规定的需求、设计或技术规格。

例如，需求规定密码长度为 8～20 个字符，测试确认系统是否按照这一规则处理。

确认（Validation）

评估软件是否满足实际使用需求，是否适合预期用途。

例如，密码规则虽然完全符合规格，但注册流程过于复杂，导致真实用户难以完成注册。此时仍然存在产品适用性问题。

两者存在交叉，并非只能分别发生在不同测试阶段。

1.4 错误、缺陷和失效

这三个概念经常被混用，但含义不同。

术语
英文
含义
错误
Error
人在理解、设计或实现过程中产生的错误行为或判断
缺陷
Defect / Bug
软件代码、设计、配置等工作成果中存在的问题
失效
Failure
软件运行时出现与预期不符的外部行为

例如，程序员错误地认为商品库存可以减少到负数，因此漏写库存检查。这是人为错误，并在代码中形成缺陷。当用户购买超过库存的商品时，系统真的产生了负库存，这就是一次失效。

存在缺陷不代表每次运行都会发生失效。只有触发相应条件时，问题才可能暴露。

二、如何理解软件测试的分类？

学习软件测试时，最容易出现的误区，是将单元测试、接口测试、黑盒测试、回归测试放在同一个分类层级。

实际上，它们描述的是不同方面。

同一个测试可以同时具有以下属性：

  • 从层级看，属于端到端测试。

  • 从实施方式看，属于自动化动态测试。

理解这一点，后面遇到新的测试术语时，就更容易判断它究竟描述什么。

三、按测试层级分类

测试层级（Test Level）用于区分测试活动针对的软件范围和集成程度。

从一个独立函数，到整个系统，再到多个系统之间的交互，不同层级需要关注的问题不同。

ISTQB CTFL 4.0.1 将基础测试层级划分为组件测试、组件集成测试、系统测试、系统集成测试和验收测试。

工程实践中经常使用的单元测试和 E2E 测试也将在本节解释。

3.1 单元测试（Unit Testing）

定义

单元测试用于验证一个相对独立的代码单元是否按照预期工作。

这里的“单元”通常是函数、方法、类或较小的逻辑模块，并没有所有语言和框架都适用的统一大小。

示例

购物系统中有一个计算订单金额的函数：

1
2

def calculate_total(price, quantity):
    return price * quantity

可以验证：

输入
预期结果
单价 100，数量 2
200
单价 50，数量 0
0
单价 10，数量 3
30

如果函数还有折扣计算、数量限制、舍入规则等逻辑，需要相应补充测试。

适用场景

业务规则计算、参数处理、数据转换、条件判断、状态判断以及其他可以相对独立验证的逻辑。

主要特点

执行速度通常较快，失败时容易定位。测试一般不需要完整部署系统，可以通过替身对象隔离数据库和网络等外部依赖。

但单元测试不能证明真实数据库连接、HTTP 通信和完整业务链路一定正确。

常见工具包括 JUnit、pytest、Jest、Vitest、xUnit 等。

3.2 组件测试（Component Testing）

定义

组件测试用于验证独立软件组件的行为。

它与单元测试的概念经常重叠。在 ISTQB 术语中，Unit Testing 通常可以视为 Component Testing 的同义或近义表达。

不过，在前端工程中，组件测试往往有更具体的含义：测试一个能够独立渲染和交互的界面组件。

示例

购物网站有一个商品数量选择组件。

需要验证：

  • 点击加号是否增加数量。

  • 数量达到库存上限时是否禁止继续增加。

  • 输入非法数量时是否显示提示。

  • 商品无库存时，购买按钮是否禁用。

测试可以只渲染这个组件，并模拟必要的外部数据，不必运行完整购物网站。

适用场景

具有独立输入、输出或交互行为的软件模块，尤其是前端组件和可单独运行的业务组件。

3.3 集成测试（Integration Testing）

定义

集成测试用于验证多个组件或系统连接后，其接口和相互作用是否正确。

一个组件单独工作正常，不代表它与其他组件连接后也能正常工作。

示例

购物系统的订单创建流程包含：

1
2
3
4
5

订单业务模块
    ↓
数据库访问模块
    ↓
MySQL 数据库

单元测试已经验证了订单金额计算规则，但无法确认：

  • 数据库字段映射是否正确。

  • SQL 能否正常执行。

  • 订单是否成功保存。

  • 数据库约束是否按预期生效。

  • 事务失败时是否正确回滚。

这些需要通过集成测试验证。

购物系统与独立支付服务

实际项目中也经常将较窄范围的组件与数据库测试直接称为“集成测试”。

适用场景

数据库、缓存、消息队列、文件系统、第三方 API、跨服务调用以及多个模块之间存在依赖的场景。

主要特点

需要一定的外部依赖或测试环境，执行成本通常高于纯单元测试。它能够发现接口不兼容、配置错误、数据格式不一致、事务问题等缺陷。

常见工具包括 Spring Boot Test、Testcontainers、pytest、REST Assured 等。

3.4 系统测试（System Testing）

定义

系统测试用于验证一个完整系统是否满足指定的功能和非功能要求。

此时测试对象不再只是单个模块，而是作为一个整体运行的软件系统。

示例

完整启动购物系统，包括前端、后端和必要的运行依赖。

测试内容可以包括：

  • 用户注册与登录。

  • 商品查询。

  • 购物车管理。

  • 订单创建与查询。

  • 用户权限。

  • 错误处理。

  • 系统响应性能。

系统测试不要求一定通过图形界面进行。通过 API、命令行或其他系统入口验证完整系统，也可能属于系统测试。

适用场景

多个模块已经集成为可运行系统，需要评估整体行为及其质量要求时。

3.5 端到端测试（End-to-End Testing，E2E）

定义

端到端测试从业务流程的起点执行到终点，验证一条完整业务链路能否正确完成。

E2E 是工程实践中广泛使用的概念。它的范围取决于所定义的业务链路，可能跨越系统内部的多个组件，也可能涉及多个独立系统，因此不能简单当作 ISTQB 五个正式测试层级之外的固定第六层。

示例

用户购买商品：

如果支付是流程的一部分，还需要明确支付系统使用真实测试环境、沙箱，还是受控替身。不同依赖边界决定了测试究竟覆盖哪些系统。

适用场景

关键用户旅程、核心交易流程、多模块协作、跨系统业务链路以及发布前的重要业务验证。

主要特点

它能发现局部测试难以发现的跨组件问题，但环境准备、数据维护、执行时间和失败定位的成本通常较高。

常见工具包括 Playwright、Cypress、Selenium 等。

需要特别注意：E2E 不一定通过浏览器执行。 通过 API 驱动并验证完整业务链路，也可以构成端到端测试。

3.6 验收测试（Acceptance Testing）

定义

验收测试用于判断系统是否满足预定的接受条件，以及是否具备交付或投入使用的条件。

它关注业务需求和交付标准。

示例

购物系统已经通过开发团队的测试，业务方准备验收。

业务方可能要求：

  • 普通用户可以完成购物流程。

  • 商品无库存时不能创建有效订单。

  • 退款流程符合业务规则。

  • 管理人员可以查询规定范围内的订单。

  • 核心业务数据满足验收要求。

这些验证可以使用手工测试，也可以使用自动化测试。

四、按测试对象分类

测试对象指测试活动直接关注的软件部分或交互边界。

4.1 接口测试（API Testing）

定义

接口测试验证软件提供的 API 是否按照约定处理请求、返回响应并完成预期操作。

这里的 API 不限于 HTTP 接口，也包括其他类型的程序接口。不过，在 Web 开发中，接口测试通常指 HTTP API 测试。

示例

一个创建订单的 API：

1
2
3
4
5
6
7

POST /api/orders
Content-Type: application/json

{
  "productId": 1001,
  "quantity": 2
}

测试时需要验证：

  • 参数合法时能否创建订单。

  • 商品不存在时如何处理。

  • 库存不足时是否拒绝创建。

  • 未登录用户是否被拒绝。

  • 重复请求是否按照幂等性要求处理。

  • 响应状态码和数据结构是否正确。

接口测试通常不需要打开浏览器，因此适合验证大量输入组合、业务规则及异常处理。

常见工具

Postman、REST Assured、Supertest、pytest、Playwright API Testing 等。

4.2 UI 测试（User Interface Testing）

定义

UI 测试验证用户界面的显示、交互以及相关行为是否符合要求。

示例

购物车页面需要验证：

  • 点击删除按钮后商品是否被移除。

  • 修改数量后金额是否正确更新。

  • 加载失败时是否出现错误提示。

  • 弹窗是否能够正常打开和关闭。

  • 键盘操作是否可以完成必要交互。

UI 测试可以只验证界面组件，也可以连接真实后端。

UI 测试不等同于 E2E 测试。

4.3 视觉回归测试（Visual Regression Testing）

定义

通过比较界面截图或视觉特征，识别软件变更引入的非预期视觉差异。

示例

修改商品列表样式后，发现商品卡片中的价格和购买按钮发生错位。

视觉回归测试适合发现：

  • 布局变化。

  • 元素错位。

  • 样式丢失。

  • 文字溢出。

  • 非预期的颜色或尺寸变化。

截图变化不一定代表缺陷。字体渲染、动态内容和不同运行环境也可能导致差异，因此需要稳定截图条件并人工确认有争议的结果。

4.4 契约测试（Contract Testing）

定义

契约测试验证两个软件系统之间约定的交互是否保持兼容。

它尤其适合多个团队分别开发和发布服务的情况。

示例

订单服务调用商品服务获取库存：

1
2
3
4

{
  "productId": 1001,
  "stock": 20
}

订单服务依赖 stock 字段是数字。

如果商品服务将该字段删除，或者改为订单服务无法处理的结构，双方可能发生兼容性问题。

契约测试用于验证这些接口约定。

常见形式包括消费者驱动契约测试，以及根据 OpenAPI 等接口规格检查提供方行为的测试。

适用场景

微服务、前后端独立开发、多团队 API 协作以及消息生产者与消费者之间的兼容性验证。

常见工具有 Pact、Spring Cloud Contract。

五、按测试设计方法分类

这一维度关注：测试人员根据什么信息来选择测试数据、设计测试场景？

5.1 黑盒测试（Black-box Testing）

定义

黑盒测试主要依据软件规格、业务规则和外部可观察行为设计测试，不依赖内部代码结构。

示例

一个优惠券功能规定：

  • 订单金额满 100 元可以使用优惠券。

  • 订单金额不足 100 元不能使用。

测试人员不需要查看源码，也能设计这些用例：

101 元

黑盒测试广泛用于功能测试、接口测试、系统测试、验收测试等场景。

它强调软件对外表现是否正确，但不能直接保证内部所有代码分支都已覆盖。

5.2 白盒测试（White-box Testing）

定义

白盒测试根据程序内部结构、控制流程或代码逻辑设计测试。

示例

程序存在如下判断：

1
2
3
4

if amount >= 100:
    apply_discount()
else:
    reject_discount()

测试需要考虑两个分支：

  • amount >= 100

  • amount < 100

如果测试只使用 150 元的订单，则没有覆盖第二个分支。

常见的白盒覆盖技术包括：

含义

路径覆盖

白盒测试通常适合代码层面的逻辑验证。

覆盖率高并不意味着行为一定正确，因为覆盖指标不能证明断言充分，也不能证明需求没有遗漏。

5.3 灰盒测试（Gray-box Testing）

定义

灰盒测试结合软件内部实现信息和外部可观察行为设计测试。

这是工程实践中常用的描述方式，不应将它理解为任何情况下都与黑盒、白盒完全互斥的正式分类。

示例

测试订单创建 API：

  1. 通过 HTTP 提交订单。

  2. 根据业务设计了解订单会经过库存检查。

  3. 查询测试数据库中的订单状态。

  4. 确认库存扣减和订单创建符合预期。

测试入口是外部 API，但测试人员利用了系统内部结构和数据状态。

灰盒思路适合接口、集成、数据库以及涉及复杂状态变化的业务测试。

5.4 常见测试用例设计技术

等价类划分（Equivalence Partitioning）

将输入划分为预期处理行为相同的类别，从每个类别选取代表值。

例如年龄必须在 18～60 岁：

  • 小于 18 岁：无效等价类。

  • 18～60 岁：有效等价类。

  • 大于 60 岁：无效等价类。

可以选取 17、30、61 作为代表输入，再通过边界值分析补充临界数据。

边界值分析（Boundary Value Analysis）

针对规则的临界点及附近数据设计测试。

例如允许的数量为 1～10，可以重点验证 0、1、2、9、10、11。

边界值是软件缺陷比较容易出现的位置。

当业务行为由多个条件共同决定时，使用条件组合与预期动作组成表格。

例如优惠券是否可用，取决于：

  • 订单金额是否满足门槛。

六、按测试目标分类

测试目标主要涉及功能质量和非功能质量。

6.1 功能测试（Functional Testing）

定义

功能测试验证软件提供的功能和业务行为是否满足要求。

例如：

  • 用户能否登录。

  • 订单金额是否正确。

  • 订单状态是否正确流转。

  • 非法参数是否被拒绝。

  • 用户是否只能访问自己的订单。

功能测试可以发生在单元、接口、集成、系统及 E2E 等多个层级。

6.2 非功能测试（Non-functional Testing）

非功能测试关注软件在功能之外的质量特征，例如性能、可靠性、安全性、交互体验等。

非功能需求也需要具体验收标准，而不能只写“系统要快”“系统要稳定”。

性能测试（Performance Testing）

验证软件在指定负载和运行条件下的性能表现。

例如要求订单查询接口在某个目标并发负载下，95% 的请求响应时间不超过 500 毫秒。

常见关注指标包括响应时间、吞吐量、错误率、CPU 使用率、内存占用和数据库连接数。

常见工具包括 JMeter、k6、Gatling。

安全测试（Security Testing）

验证软件是否满足安全要求，并识别可能被利用的安全缺陷。

常见内容包括：

  • 身份认证是否正确。

  • 用户是否能够越权访问。

  • 输入是否可能导致 SQL 注入。

  • 敏感信息是否泄露。

  • 会话是否得到正确保护。

  • 已知依赖漏洞是否影响系统。

安全测试还包含漏洞扫描、渗透测试等活动。

涉及真实系统的主动安全测试必须获得适当授权，并明确测试范围。

兼容性测试（Compatibility Testing）

验证软件在不同运行环境中的行为，以及在需要交互的环境或系统之间能否正常协作。

例如：

  • Chrome、Firefox、Safari 的显示和交互差异。

  • Android 与 iOS 的运行差异。

  • 不同屏幕尺寸下的布局。

  • 软件与依赖组件版本之间的兼容性。

并不一定要测试所有设备，而是根据实际用户环境和风险确定测试矩阵。

可靠性测试（Reliability Testing）

验证软件在指定条件和时间范围内持续完成预期功能的能力。

例如：

  • 长时间运行是否发生资源泄漏。

  • 外部服务短暂不可用时能否正确处理。

  • 节点故障时是否影响业务连续性。

  • 重试机制是否导致重复处理。

故障恢复测试（Recovery Testing）

验证系统在发生故障后，是否能按照既定要求恢复服务或数据。

例如数据库服务重启后能否恢复正常业务，备份是否可以成功还原。

可靠性测试关注故障前后的整体行为；恢复测试重点关注恢复能力和恢复结果。

可用性测试（Usability Testing）

验证系统是否容易理解和使用，以及用户能否有效完成目标。

例如邀请真实用户完成购买流程，观察：

  • 是否能够理解界面。

  • 是否容易找到所需操作。

  • 是否容易发生误操作。

  • 完成任务需要多少时间。

可访问性测试（Accessibility Testing）

验证不同身体或感知能力的用户能否有效使用软件。

例如：

  • 能否仅使用键盘完成操作。

  • 屏幕阅读器能否识别按钮含义。

  • 输入控件是否有明确标签。

  • 文字与背景是否具有足够对比度。

Web 可访问性测试可以参考 W3C WCAG 2.2。

七、按测试时机和用途分类

这类测试回答的是：当前为什么要执行这些测试？

7.1 冒烟测试（Smoke Testing）

定义

快速验证一个构建版本或部署后的系统是否具备基本可用性，以判断是否适合继续开展更深入的测试。

示例

购物系统发布新版本后，快速检查：

  • 首页能否打开。

  • 用户能否登录。

  • 商品列表能否查询。

  • 是否可以创建一笔基本订单。

冒烟测试通常选择数量较少、影响较大的核心场景。

它不能代替完整的功能测试。

7.2 回归测试（Regression Testing）

定义

在软件发生修改后，验证原本正常的行为是否受到意外影响。

示例

开发人员修改了订单价格计算规则。

除了验证新增计算逻辑，还应检查：

  • 普通商品金额是否仍然正确。

  • 优惠券计算是否受影响。

  • 订单总价是否保持一致。

  • 历史订单展示是否异常。

回归测试可以由单元测试、接口测试、UI 测试和 E2E 测试共同组成。

回归测试描述的是执行目的，不是一个独立的测试层级。

7.3 确认测试（Confirmation Testing）

定义

验证某个已发现的缺陷在修复后是否得到解决。

例如发现重复提交订单会生成两笔订单。开发修复后，使用原问题的触发步骤再次验证。

确认测试关注具体缺陷是否已经消失。

回归测试则进一步检查本次修复是否影响其他正常行为。

7.4 健全性测试（Sanity Testing）

通常指针对特定变更或某个功能范围开展的快速、定向检查。

例如只修改了优惠券使用规则，在继续完整测试之前，先检查该规则是否正常。

Sanity Testing 和 Smoke Testing 在不同团队中的实际用法存在交叉，项目中需要提前约定名称和范围。

7.5 探索性测试（Exploratory Testing）

探索性测试强调测试人员在学习软件、设计场景和执行测试之间不断迭代。

例如测试人员在尝试订单取消功能时，发现网络中断可能影响订单状态，于是进一步设计重复取消、超时重试等场景。

探索性测试不等于毫无计划地随意点击。它可以具有明确的探索目标、时间范围和记录要求。

八、按测试实施方式分类

8.1 手工测试（Manual Testing）

由测试人员直接执行操作、观察结果并进行判断。

适用于：

  • 探索新功能。

  • 评估交互体验。

  • 判断复杂视觉问题。

  • 验证难以自动化的特殊场景。

手工测试并不意味着缺少技术含量，尤其在探索性测试、需求确认和复杂业务分析中，人的判断仍然重要。

8.2 自动化测试（Automated Testing）

使用脚本和工具自动执行测试步骤，并检查实际结果。

例如自动化程序：

  1. 打开购物网站。

  2. 登录测试账号。

  3. 选择商品并提交订单。

  4. 检查页面状态。

  5. 验证订单是否创建。

自动化测试适合重复执行、预期明确且结果可以稳定判断的场景。

但自动化脚本也需要开发、维护、环境治理和失败排查。

自动化测试不是单独的测试层级。

单元测试、接口测试、集成测试、UI 测试和 E2E 测试都可以自动化。

8.3 静态测试（Static Testing）

定义

在不执行被测软件的情况下，通过检查工作成果发现问题。

常见活动包括：

  • 需求评审。

  • 设计评审。

  • 代码评审。

  • 静态代码分析。

  • 代码规范检查。

例如评审需求时发现“订单超时自动取消”没有规定超时时间。

即使程序尚未编写，也已经可以识别这个问题。

8.4 动态测试（Dynamic Testing）

通过执行软件，观察其实际行为并进行判断。

例如启动服务，向订单接口发送请求，然后验证响应与数据库结果。

单元测试、接口测试、性能测试、UI 测试等通常都属于动态测试。

静态测试与动态测试可以相互补充。

8.6 TDD、BDD、ATDD 是什么？

它们经常与各种测试类型一起出现，但更准确地说属于开发与协作方法。

TDD（Test-Driven Development，测试驱动开发）

通常遵循“先写失败的测试，再实现功能，最后重构”的开发循环。

它强调使用测试来指导代码实现。

BDD（Behavior-Driven Development，行为驱动开发）

通过业务行为和具体示例促进产品、开发和测试人员对需求达成一致。

常见表达方式是 Given / When / Then，即给定条件、发生行为、预期结果。

ATDD（Acceptance Test-Driven Development，验收测试驱动开发）

在功能实现前，由相关人员共同定义验收条件和代表性场景，再据此指导开发与测试。

它们可以与单元、集成、接口和 E2E 测试结合，不是互斥的替代方案。

9.2 Mock、Stub、Fake、Spy 的区别

这些都是测试替身（Test Double）的相关概念。

9.3 测试覆盖率是什么？

覆盖率用于衡量测试对某个目标范围的覆盖程度。

常见指标包括：

  • 语句覆盖率。

  • 分支覆盖率。

  • 条件覆盖率。

  • 需求覆盖率。

  • 功能覆盖率。

  • 风险项覆盖率。

例如程序存在 100 条可执行语句，测试执行了其中 80 条，对应的语句覆盖率为 80%。

但执行到某行代码，不代表已经验证了该行代码的正确性。

因此，覆盖率需要和断言质量、缺陷情况、边界场景及业务风险一起考虑。

十、容易混淆的测试概念

10.1 单元测试 vs 集成测试

单元测试主要验证相对独立的代码逻辑。

集成测试主要验证多个真实或受控组件之间的协作关系。

例如：

  • 测试订单金额计算函数：单元测试。

  • 测试订单服务能否正确读写真实数据库：集成测试。

区别主要在被测范围和依赖边界。

10.2 集成测试 vs 系统测试

集成测试关注组件或系统之间的交互。

系统测试关注完整系统是否满足要求。

一个完整系统可以包含多个集成点，但不是所有集成测试都会验证整个系统。

10.3 系统测试 vs E2E 测试

系统测试关注整个系统的功能和质量要求。

E2E 测试关注一条完整业务链路。

系统测试范围可能更广，涵盖大量独立功能和非功能要求；E2E 则侧重从起点到终点的业务结果。

两者可以重叠。

10.4 UI 测试 vs E2E 测试

UI 测试验证用户界面行为。

E2E 测试验证完整业务流程。

一个仅使用模拟接口的按钮交互测试，属于 UI 测试，但通常不属于完整 E2E。

一个通过多个后端 API 完成订单创建、支付和状态确认的测试，可能属于 E2E，但并不是 UI 测试。

10.5 接口测试 vs 集成测试

接口测试描述测试的对象或入口。

集成测试描述被测组件之间的协作范围。

因此，一条通过 HTTP API 验证真实数据库写入的测试，既可以是接口测试，也可以是集成测试。

10.6 接口测试 vs 契约测试

接口测试可以验证请求处理、业务行为、数据和错误结果。

契约测试重点验证通信双方对交互格式和行为的约定是否兼容。

契约测试不能完全替代接口功能测试。

10.7 黑盒测试 vs 白盒测试

黑盒测试依据外部规格和行为设计测试。

白盒测试依据内部结构设计测试。

两者可以针对同一段代码分别提供验证证据。

10.8 冒烟测试 vs 回归测试

冒烟测试用于快速判断构建或部署后的核心功能是否正常。

回归测试用于检查软件变更是否影响已有行为。

一条核心用例可以既属于冒烟测试套件，也属于回归测试套件。

10.9 功能测试 vs 自动化测试

功能测试描述验证目标。

自动化测试描述执行方式。

功能测试可以手工执行，也可以自动执行。自动化同样可以用于性能、安全和其他类型的测试。

10.10 单元测试通过，是否代表功能一定正确？

不代表。

因为还可能存在：

  • 真实组件之间的接口问题。

  • 数据库和网络配置问题。

  • 错误的业务需求理解。

  • 未覆盖的边界条件。

  • 前后端协作问题。

  • 不满足性能或安全要求的情况。

不同层级的测试需要根据风险相互补充。

十一、面对一个实际功能，应该如何选择测试？

可以按照下面的顺序进行判断。

第一步：明确需要验证的要求

先确定期望系统完成什么，以及什么结果算正确。

例如：库存不足时不能成功创建订单。

如果没有明确的预期结果，就很难设计有效断言。

第二步：识别主要风险

判断什么地方容易出问题、出问题后影响多大。

例如：

  • 数量判断错误。

  • 并发请求导致库存超卖。

  • 事务失败后出现部分数据写入。

  • 前端没有正确显示失败信息。

  • 用户重复提交导致创建重复订单。

第三步：确定最合适的测试层级

尽量在能够充分验证风险的较低成本层级完成测试。

例如：

需要验证的问题
合适的测试方式
库存数量判断逻辑正确吗？
单元测试
库存扣减 SQL 正确吗？
数据库集成测试
多个事务并发扣减是否会超卖？
并发集成测试
API 能否正确处理库存不足？
API 测试
前端能否显示库存不足提示？
UI 组件测试
用户完整下单流程能否完成？
E2E 测试
高并发下订单服务是否满足指标？
性能测试
用户能否操作他人的订单？
安全与权限测试

同一业务需求可能需要多种测试共同验证。

第四步：选择测试数据和设计技术

根据业务特点决定使用哪些技术：

  • 数值范围：等价类、边界值。

  • 多条件规则：判定表。

  • 复杂业务状态：状态迁移。

  • 复杂参数组合：组合测试。

  • 代码分支：白盒覆盖技术。

  • 未知风险：探索性测试。

第五步：选择执行方式

判断测试是否适合自动化。

通常优先考虑：

  • 频繁重复执行。

  • 预期结果明确。

  • 测试数据可控制。

  • 环境可以稳定复现。

  • 自动化维护成本合理。

对于主观体验评价、一次性验证或尚不稳定的需求，可以先采用人工测试。

第六步：安排执行时机

不同测试适合放在不同阶段。

这里的阶段不是硬性顺序。现代持续集成和持续交付实践中，测试往往在多个阶段反复执行。

11.1 测试金字塔（Test Pyramid）

测试金字塔是一种组织自动化测试组合的参考模型。

常见的表达是：

1
2
3
4
5
6

         / E2E 测试 \
        /            \
       /   集成测试   \
      /                \
     /     单元测试     \
    /____________________\

它强调：

  • 在较小范围内充分验证业务逻辑。

  • 使用集成测试发现真实依赖之间的问题。

  • 使用数量受控的高层级测试验证重要业务链路。

通常，单元测试更快、维护成本较低；涉及真实环境的高层级测试成本可能更高。

不过，测试金字塔不是要求所有项目都遵循固定比例。测试数量与分布应取决于架构、系统风险和团队实际条件。

例如，以服务交互为核心的系统可能需要较多接口和契约测试，而复杂前端交互较多的应用可能需要较丰富的组件测试。

也不应该为了追求某个比例而重复编写没有新增验证价值的测试。

十二、常见问题与认识误区

12.1 测试是不是越多越好？

不是。

测试数量本身不能说明质量。

一个只有少量用例、却覆盖关键业务风险的测试套件，可能比包含大量重复、脆弱用例的测试套件更有价值。

12.2 覆盖率越高，程序质量就越好吗？

不一定。

覆盖率体现测试覆盖程度，但不能直接反映测试断言是否准确、需求是否正确，也不能证明系统不存在缺陷。

12.3 所有测试都应该自动化吗？

不应该将完全自动化作为无条件目标。

自动化适合重复、稳定且结果明确的验证。对于探索性活动、交互体验和部分复杂判断，人工测试仍有价值。

12.4 E2E 测试是否可以替代单元测试？

不能完全替代。

E2E 能验证完整业务链路，但通常不适合覆盖所有底层分支、参数组合及异常路径。

如果全部依赖 E2E，可能出现执行时间长、数据准备复杂和失败定位困难的问题。

12.5 单元测试是否必须 Mock 所有依赖？

不必须。

对于快速、确定性强且没有副作用的依赖，可以直接使用真实实现。

对于数据库、网络服务、外部 API 等依赖，可以根据测试目标决定是否替换。

选择替身时需要明确测试边界，不能用模拟依赖通过的结果证明真实依赖一定正常。

12.6 接口返回 200，是否代表测试通过？

不一定。

HTTP 状态码只是结果的一部分。

还需要根据业务要求检查：

  • 响应内容。

  • 实际业务状态。

  • 数据库变化。

  • 副作用是否符合预期。

  • 是否出现不应该发生的重复操作。

即使返回 200，如果订单金额错误，测试仍然应该失败。

12.7 自动化测试偶尔失败、重新运行又通过，该怎么办？

这类现象通常称为测试不稳定（Flaky Test）。

可能原因包括：

  • 测试依赖执行顺序。

  • 测试数据相互干扰。

  • 异步操作等待条件不合理。

  • 外部服务不稳定。

  • 环境资源不足。

  • 测试本身存在竞态条件。

应当调查失败原因，而不是无限重试或者简单忽略。

重试可以作为辅助诊断手段，但不能替代问题修复。

十四、参考资料

以下资料来自软件测试标准组织、相关技术文档和工程实践文章。不同资料使用的分类口径可能存在差异，阅读时应注意区分标准术语与工程习惯用语。

1. ISTQB — Certified Tester Foundation Level 4.0

https://www.istqb.org/certifications/certified-tester-foundation-level-ctfl-v4-0/

软件测试基础知识的系统学习资料，涵盖测试原则、测试层级、测试类型、测试设计技术、静态测试、缺陷管理等。

适合用于建立基础术语体系。

2. ISO/IEC 25010:2023 — Product Quality Model

https://www.iso.org/standard/78176.html

定义系统和软件产品质量特征，为性能、安全性、可靠性、兼容性等质量要求提供参考框架。

适合进一步理解非功能测试和软件质量模型。

3. Martin Fowler — The Practical Test Pyramid

https://martinfowler.com/articles/practical-test-pyramid.html

从实际工程角度讨论单元测试、集成测试、E2E 测试、测试替身和测试成本。

适合理解不同测试层级如何组合，以及为什么不能只依赖 E2E 测试。

4. Playwright — API Testing

https://playwright.dev/docs/api-testing

Playwright 官方 API 测试文档，介绍通过程序发送请求、准备测试数据和验证服务端状态等方法。

适合理解接口测试与浏览器测试之间的联系。

5. Pact — Contract Testing

https://docs.pact.io/

介绍消费者、提供者、契约验证以及服务之间的兼容性测试。

适合理解多系统协作场景中的契约测试。

6. OWASP — Web Security Testing Guide

https://owasp.org/www-project-web-security-testing-guide/

面向 Web 应用的安全测试指南，涵盖身份认证、授权、输入校验、会话管理等内容。

适合进一步学习安全测试。

7. W3C — Web Content Accessibility Guidelines 2.2

https://www.w3.org/TR/WCAG22/

Web 可访问性标准，提供可检验的成功准则。

适合学习可访问性测试的具体要求和判断依据。
