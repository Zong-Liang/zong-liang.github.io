软件测试基础：概念、分类与应用场景

软件测试是软件工程中的基础活动。无论是开发一个简单的计算程序，还是建设复杂的互联网系统，都需要通过测试判断软件是否符合要求，并识别潜在的质量问题。

学习软件测试时，常常会遇到单元测试、集成测试、接口测试、UI 测试、E2E 测试、黑盒测试、回归测试等术语。这些名称看起来属于同一类概念，实际却描述了测试的不同方面。

本文从基本概念出发，介绍常见测试类型的含义、区别和适用场景，并通过统一的业务案例说明如何选择测试方法。内容面向软件测试初学者，也可以作为日常开发中的概念参考手册。

一、软件测试是什么？

1.1 软件测试的定义

软件测试（Software Testing）是通过静态检查和动态执行等活动，评估软件是否满足规定的需求、发现缺陷，并为软件质量和相关决策提供信息的过程。

例如，一款购物软件提供商品查询、下单和支付等功能。

测试人员需要检查的不仅是功能能否正常使用，还可能包括：

  • 商品库存不足时，系统是否拒绝创建订单。
  • 用户是否只能查看自己的订单。
  • 多个用户同时购买商品时，是否可能超卖。
  • 大量用户访问时，系统能否满足响应时间要求。
  • 数据库发生故障时，系统能否正确处理请求。
  • 页面能否在目标浏览器和设备上正常使用。

这些问题涉及不同的质量要求，因此需要采用不同的测试方式。

软件测试主要有两个作用：一是发现缺陷和风险，二是提供软件在特定条件下符合要求的证据。

测试通过不等于软件不存在缺陷。 有限的测试无法穷尽所有输入、执行路径和运行环境。测试结果能够支持的结论，始终取决于测试覆盖了什么，以及采用了怎样的验证方式。

1.2 一个测试是如何完成的？

假设购物系统有一项需求：

用户购买商品时，如果购买数量超过当前可售库存，系统必须拒绝创建订单，且不得扣减库存。

为了验证这个需求，可以设计下面的测试用例。

项目内容
测试目标验证库存不足时的下单行为
前置条件商品 A 的可售库存为 2 件
测试输入用户请求购买商品 A，共 3 件
执行操作调用创建订单功能
预期结果下单被拒绝，并返回明确的失败结果
数据验证不生成有效订单，商品库存仍为 2 件

执行测试后，需要将实际结果与预期结果比较。

如果系统拒绝创建订单，但错误地扣减了库存，那么这个测试仍然不能通过。

这说明测试不能只检查表面结果，还需要根据需求验证相关状态和副作用。

一条完整的测试用例通常需要明确测试条件、输入、操作和预期结果。具体记录格式可以根据测试复杂度调整。

测试依据Test Basis设计测试所依据的需求、规格、设计或代码等资料
测试条件Test Condition需要检查的行为、属性或情形
测试用例Test Case为验证某个条件而设计的输入、前置条件、预期结果等信息

测试环境Test Environment运行测试所需的软件、硬件、配置和依赖
测试断言Assertion判断实际结果是否满足预期的检查
测试预言机Test Oracle用于确定正确结果的依据或机制
测试套件Test Suite为共同目的组织在一起的一组测试用例

测试断言是自动化测试中经常出现的概念。

例如：

1
2

actual_total = calculate_total(100, 2)
assert actual_total == 200

assert 用于检查实际结果是否等于预期的 200。如果不符合，测试就会失败。

断言是否充分非常重要。如果创建订单的测试只检查接口是否返回成功，却不检查订单金额和最终状态，就可能遗漏实际缺陷。

1.4 错误、缺陷与失效

软件测试中有三个相关但不同的概念。

概念英文含义
错误Error人在分析、设计或实现软件时产生的错误判断或行为
缺陷Defect / Bug软件代码、设计、配置等工作成果中存在的问题
失效Failure软件运行时表现出与预期不符的行为

例如：

开发人员错误地认为库存可以减为负数，因此没有编写库存不足的判断逻辑。

这个错误认识导致代码中产生缺陷。

当用户购买超过库存的商品时，系统产生负库存，表现出一次失效。

存在缺陷不意味着每次运行都会发生失效，只有满足相关触发条件时，问题才可能暴露。

1.5 软件测试、调试与质量保证

这三个概念的职责不同。

软件测试（Testing）：检查软件的行为和质量，识别问题并提供验证结果。

调试（Debugging）：定位缺陷产生的原因，并通过修改程序或配置解决问题。

质量保证（Quality Assurance，QA）：通过过程、规范、方法和改进措施，增强软件开发活动持续满足质量要求的能力。

例如，测试发现库存出现负数；开发人员通过调试定位到并发更新逻辑存在问题，随后修复；团队进一步改进代码评审和并发场景测试要求，以降低类似问题再次出现的风险。

测试和调试是不同活动，测试也只是软件质量保障的一部分。

另有两个常见概念：

  • 验证（Verification）：检查软件是否符合规定的需求或规格。
  • 确认（Validation）：评估软件是否满足实际使用需要和预期用途。

一个系统可以完全符合原始规格，却因为规格本身不合理而不能满足用户需求。

二、如何理解软件测试的分类？

软件测试有多种分类方式。理解这些分类的关键，是先判断一个测试术语究竟在描述什么。

例如：

  • 单元测试主要描述测试范围。
  • 接口测试主要描述测试对象或交互入口。
  • 黑盒测试主要描述测试设计依据。
  • 性能测试主要描述验证的质量属性。
  • 回归测试主要描述测试目的。
  • 自动化测试主要描述执行方式。

它们不是同一层级的并列概念，也不互相排斥。

2.1 常见测试概念的组织框架

为便于学习，本文使用以下六个维度组织常见术语。

维度主要回答的问题代表性概念
测试层级测试多大范围的软件？单元、组件集成、系统、系统集成、验收
测试对象与交互边界测试什么部分或交互？API、UI、数据库、消息、契约
测试设计方法根据什么设计测试？黑盒、白盒、灰盒、经验驱动
测试目标验证什么质量要求？功能、性能、安全、可靠性、兼容性
测试用途与时机为什么在此时执行？冒烟、回归、确认、发布验证
测试实施方式如何开展和执行？手工、自动化、静态、动态

这六个维度是本文为了教学和检索建立的组织框架，并不是直接照搬某一份标准中的正式分类。

其中，手工与自动化描述执行方式；静态与动态描述是否需要运行被测软件。两组概念本身也属于不同的划分角度。

2.2 同一个测试可以属于多个类别

假设一条自动化用例通过浏览器完成商品下单，并验证真实订单服务和数据库中的结果。

它可以同时具有以下属性：

维度对应分类
测试层级或范围端到端业务流程测试
测试对象UI、API、跨组件交互
测试设计方法黑盒测试技术
测试目标功能正确性
测试用途可作为回归测试用例
测试实施方式自动化、动态测试

因此，不能简单询问“接口测试和集成测试哪个更好”，因为两者描述的不是同一个维度。

更准确的问题应该是：这个接口测试需要覆盖哪些真实组件？是否需要数据库？需要验证哪些业务风险？

三、按测试层级分类：从代码单元到完整系统

测试层级（Test Level）用于区分测试针对的软件范围和集成程度。

按照 ISTQB CTFL 4.0.1 的基础测试层级体系，主要包括：

  1. 组件测试（Component Testing）。
  2. 组件集成测试（Component Integration Testing）。
  3. 系统测试（System Testing）。
  4. 系统集成测试（System Integration Testing）。
  5. 验收测试（Acceptance Testing）。

这五个层级不意味着所有项目都必须依次经过五个独立阶段。在迭代开发和持续集成中，它们可以交叉开展。

单元测试和 E2E 测试是日常工程中极为常见的术语，需要结合这套体系理解。

3.1 组件测试与单元测试（Component / Unit Testing）

定义

验证相对独立的软件组件或代码单元是否按照预期工作。

在 ISTQB CTFL 4.0.1 中，组件测试也称为单元测试，两者属于同一个基础测试层级。

日常开发中，“单元”可以是函数、方法、类或一个小型逻辑模块，不要求必须对应单个方法。

示例：订单金额计算

1
2

def calculate_total(price, quantity):
    return price * quantity

可以设计以下测试：

单价数量预期结果
1002200
503150
10000

这个示例假定函数只负责乘法计算；如果数量必须大于零，应另行通过输入校验或函数契约规定并测试。

单元测试通常不需要启动完整系统。外部数据库、网络或第三方服务可以根据测试目标使用测试替身替代。

适用场景

业务规则、金额计算、参数处理、条件判断、数据转换、状态判断等相对独立的逻辑。

前端组件测试的特殊用法

在 React、Vue 等前端开发中，Component Testing 通常还特指测试一个独立界面组件。

例如购物车数量选择器：

  • 点击加号后，数量是否增加。
  • 达到库存上限后，能否禁止继续增加。
  • 商品无库存时，购买按钮是否禁用。

这是组件测试在前端工程中的具体用法，不应理解为在单元测试之上额外增加了一个固定的测试层级。

常见工具包括 JUnit、pytest、Jest、Vitest、React Testing Library 等。

3.2 组件集成测试（Component Integration Testing）

定义

验证同一系统内部多个组件之间的接口和协作是否正确。

示例：订单服务与数据库

1
2
3
4
5

订单服务
   ↓
数据访问模块
   ↓
数据库

单元测试可以证明订单金额计算逻辑正确，但不能证明实际数据库操作一定正确。

组件集成测试可以检查：

  • SQL 是否能正确执行。
  • 字段映射是否正确。
  • 数据库约束是否正常生效。
  • 事务是否正确提交或回滚。
  • 数据写入后能否正确读取。

例如创建订单时需要同时写入订单记录和扣减库存。

如果订单写入成功，但库存扣减失败，测试需要验证事务或补偿机制是否符合系统设计，不能简单接受数据处于部分完成状态。

适用场景

业务模块与数据库、缓存、文件系统、消息组件等依赖之间的集成。

常见工具包括 Spring Boot Test、Testcontainers 以及各语言提供的集成测试工具。

3.3 系统测试（System Testing）

定义

将一个完整的软件系统作为测试对象，验证其整体行为和质量要求。

这里的“完整”是相对于已定义的系统边界而言的。

例如，一个购物系统由前端应用、订单服务、商品服务和数据库构成。系统测试可以检查：

  • 用户登录。
  • 商品查询。
  • 创建订单。
  • 订单查询。
  • 权限控制。
  • 异常处理。
  • 系统性能。

系统测试可以通过浏览器、API、命令行或其他入口执行，不一定必须包含图形界面。

适用场景

软件的主要组件已经具备集成运行条件，需要验证整个系统的功能和非功能要求。

3.4 系统集成测试（System Integration Testing）

定义

验证被测系统与其他独立系统或外部服务之间的接口和交互。

示例：购物系统与支付系统

1
2
3
4
5

购物系统
   ↓ 支付请求
支付服务
   ↓ 支付结果
购物系统更新订单

可以验证：

  • 请求参数是否符合支付服务要求。
  • 支付结果能否正确解析。
  • 回调重复发送时能否避免重复更新。
  • 支付服务超时时如何处理。
  • 两个系统的订单与支付状态是否保持业务一致性。

适用场景

第三方支付、统一身份认证、物流服务、企业内部跨系统调用等场景。

组件集成测试通常关注一个系统内部组件之间的协作；系统集成测试更强调独立系统之间的交互。

两者在具体工程中的边界，需要根据系统划分方式确定。

3.5 验收测试（Acceptance Testing）

定义

评估软件是否满足规定的接受条件，以及是否达到交付或投入使用的要求。

验收测试更关注软件是否满足实际业务需要，而不是逐行验证技术实现。

示例

购物系统准备上线，业务方需要确认：

  • 用户可以完成正常下单。
  • 库存不足时不会错误生成订单。
  • 订单金额和优惠规则符合要求。
  • 退款流程符合约定。
  • 管理员能完成必要的订单管理操作。

常见验收测试包括：

类型含义
用户验收测试（UAT）由业务用户或代表确认系统是否满足业务需求
运维验收测试（OAT）检查部署、监控、备份、恢复等运维准备
合同验收测试验证交付是否满足合同约定
监管验收测试验证是否满足相关监管要求
Alpha 测试发布前在受控条件下开展的预发布测试
Beta 测试向限定用户开放，观察实际使用情况并收集反馈

验收测试可以复用已有自动化测试，但通常还需要业务方根据约定的验收条件作出判断。

3.6 端到端测试（End-to-End Testing，E2E）

E2E 是日常开发中经常被单独讨论的一类测试。

定义

从业务流程的起点执行到终点，验证完整业务过程能否按照预期完成。

例如：

E2E 测试关注整个业务链路，而不只是其中一个函数、接口或模块。

E2E 与正式测试层级的关系

E2E 主要强调业务流程的端到端覆盖范围，不是必须插入五个标准层级之间的一个固定层级。

例如：

  • 通过浏览器完成一个系统内部的完整下单流程，通常可以属于系统级 E2E 测试。
  • 下单过程跨越购物、支付及物流等独立系统，可能涉及系统集成层面的 E2E 测试。
  • 通过 API 驱动完整业务流程，也可以构成 E2E 测试，不要求必须使用浏览器。

E2E 适合验证关键业务流程，尤其是多个组件或系统协作后才能完成的操作。

不过，它通常需要更复杂的环境、测试数据和依赖管理。因此不适合将全部业务规则和异常分支都放在 E2E 层逐一枚举。

3.7 不同测试层级的核心区别

类型重点验证什么典型例子
单元/组件测试独立代码或组件的行为订单金额计算
组件集成测试系统内部组件之间的协作订单服务读写数据库
系统测试完整系统的要求购物系统功能及性能
系统集成测试独立系统之间的交互购物系统调用支付服务
验收测试是否满足业务或交付条件业务方验收购物流程
E2E 测试完整业务链路是否成立从下单到最终结果

前三种并不是严格的包含关系，E2E 与系统测试、系统集成测试也可能发生重叠。判断时应以实际测试边界为准。

四、按测试对象与交互边界分类

这一类测试主要回答：具体测试软件的哪个部分，或者验证哪个交互边界？

4.1 接口测试（API Testing）

定义

接口测试验证程序接口能否正确接收输入、处理请求并返回符合约定的结果。

API 不仅包括 HTTP 接口。在 Web 开发中，接口测试通常特指 HTTP API 测试。

例如创建订单接口：

1
2
3
4
5
6
7

POST /api/orders
Content-Type: application/json

{
  "productId": 1001,
  "quantity": 2
}

常见验证内容包括：

  • 参数合法时能否正确处理。
  • 必填参数缺失时是否拒绝请求。
  • 商品不存在时如何返回错误。
  • 未登录或无权限的用户是否被拒绝。
  • 重复请求是否符合幂等性要求。
  • 返回结构是否符合接口约定。
  • 实际业务数据是否正确变化。

接口测试一般不需要打开浏览器，因此适合验证大量输入组合和异常情况。

接口测试与集成测试的关系

接口测试描述测试入口，集成测试描述被测范围。

例如：

  • 只启动 Web 控制器，模拟后端业务服务：可以是接口入口的组件级测试。
  • 启动真实后端，并连接测试数据库：可以同时是接口测试和集成测试。
  • 通过 API 完成多个服务之间的完整业务流程：可能是 API 驱动的 E2E 测试。

常见工具包括 Postman、REST Assured、Supertest、pytest、Playwright API Testing。

4.2 UI 测试（User Interface Testing）

定义

UI 测试验证用户界面的显示、交互和相关行为。

对于 Web 应用，常见内容包括：

  • 按钮是否可以点击。
  • 表单输入是否正确处理。
  • 弹窗是否正常打开和关闭。
  • 页面跳转是否符合预期。
  • 请求失败时是否展示错误信息。
  • 加载过程中是否显示正确状态。
  • 用户权限是否正确影响界面操作。

UI 测试不一定需要真实后端。

例如，将库存接口模拟为返回 0，检查购买按钮是否禁用。这属于 UI 测试，但不能证明真实库存服务与前端集成正确。

UI 测试不等于 E2E 测试。

UI 测试关注界面行为，E2E 关注完整业务流程。通过真实浏览器执行完整下单流程的测试，可以同时具有这两种属性。

4.3 视觉回归测试（Visual Regression Testing）

视觉回归测试主要检查软件修改后，界面是否产生非预期的视觉变化。

例如：

  • 商品卡片布局错位。
  • 按钮样式丢失。
  • 表格列宽异常。
  • 文字溢出。
  • 页面元素被遮挡。

常见方式是对同一界面在相同条件下生成截图，并与基准截图比较。

截图存在差异不一定代表缺陷。字体渲染、动态内容和运行环境都可能产生正常差异，因此需要控制截图条件，并判断差异是否符合预期。

视觉回归测试验证的是视觉表现，不能替代功能测试。

4.4 数据库测试（Database Testing）

数据库测试关注与数据存储、读取和维护有关的行为。

例如：

  • SQL 查询结果是否正确。
  • 数据库约束是否生效。
  • 事务是否正确提交或回滚。
  • 并发更新是否造成数据丢失。
  • 数据迁移后是否保持完整性。
  • 存储过程、触发器是否符合要求。

数据库测试经常作为集成测试的一部分开展，也可以针对数据库对象和数据质量设计专项测试。

4.5 消息与异步处理测试

许多系统通过消息队列或异步任务处理业务。

例如用户创建订单后，系统发送订单创建事件，由其他服务处理通知或后续业务。

需要关注：

  • 消息能否正确发送和消费。
  • 消费失败后是否按照策略重试。
  • 重复消息是否造成重复业务操作。
  • 消息乱序时系统如何处理。
  • 消息长期无法处理时是否进入死信队列或其他异常处理流程。
  • 消费成功与业务状态是否保持一致。

是否需要严格顺序、至少一次投递或去重保障，取决于消息系统与业务设计，不能假定所有消息系统具有相同语义。

4.6 契约测试（Contract Testing）

定义

契约测试用于验证两个软件系统之间约定的交互是否保持兼容。

它的重点不是完整业务流程，而是通信双方对请求、响应或消息的共同理解。

示例：订单服务依赖库存服务

订单服务需要通过库存服务查询商品库存。

1

GET /api/inventory/1001

返回：

1
2
3
4

{
  "productId": 1001,
  "available": 2
}

订单服务依赖 available 字段判断是否允许下单。

假设库存服务在一次升级后，将 available 删除或改为不兼容的数据结构，就可能导致订单服务出现问题。

契约测试可以帮助在双方正式集成或发布之前发现这类兼容性风险。

消费者驱动契约测试如何工作？

以 Pact 为例：

  1. 消费者定义依赖。 订单服务在测试中表达自己期望发送的请求，以及需要使用的响应数据。
  2. 生成契约。 消费方测试将这些交互要求保存为契约文件。
  3. 提供者验证契约。 库存服务运行契约验证，检查自身能否满足消费方的交互要求。
  4. 关联验证结果。 团队使用契约及验证结果辅助判断相关服务版本是否兼容。

这里的消费者是调用或接收数据的一方，提供者是提供接口或消息的一方。

除了消费者驱动契约测试，也可以根据 OpenAPI 等接口规格验证提供者行为，但两种方式提供的兼容性证据并不完全相同。

契约测试和接口测试的区别

接口测试可以验证库存查询逻辑本身是否正确；契约测试主要验证服务之间约定的交互是否兼容。

即使契约验证通过，也不能证明库存计算正确、数据库事务安全或完整下单流程正常。

契约测试适合微服务、跨团队 API、独立发布的前后端以及消息生产者与消费者之间的兼容性验证。

常见工具包括 Pact、Spring Cloud Contract。

类型主要内容典型场景
文件测试上传、下载、解析、格式和大小限制文件管理、报表导入导出
批处理测试批量处理的正确性和异常恢复数据同步、批量更新
定时任务测试调度、重复执行、失败补偿定时结算、定时清理

五、按测试设计方法分类

知道要测试什么，还需要决定怎样选择测试输入，以及如何判断是否覆盖了重要情况。

测试设计方法可以从外部规格、内部结构或者测试人员的知识与经验出发。

5.1 黑盒测试（Black-box Testing）

定义

黑盒测试根据需求、业务规则和外部可观察行为设计测试，不依赖被测软件内部代码结构。

例如，订单数量只允许在 1～10 之间。

测试人员不需要知道代码如何判断，也可以设计有效和无效的输入。

常见黑盒测试技术包括以下几种。

等价类划分（Equivalence Partitioning）

把输入划分为预期处理行为相同的类别，并从每类选择代表性数据。

对于允许数量 1～10 的规则：

等价类输入范围代表值
无效类小于 10
有效类1～105
无效类大于 1011

等价类划分可以减少没有必要的重复测试，但划分是否合理取决于业务规则。

边界值分析（Boundary Value Analysis）

重点检查临界值以及临界值附近的数据。

对于数量范围 1～10，可以测试：

0、1、2、9、10、11

因为范围判断中容易出现大于、大于等于、小于、小于等于等运算符使用错误。

判定表测试（Decision Table Testing）

当业务行为由多个条件共同决定时，可以使用判定表组织条件组合。

例如优惠券使用条件：

  • 优惠券未过期。
  • 订单金额达到门槛。
优惠券过期金额达标能否使用
否是可以
否否不可以
是是不可以
是否不可以

判定表适合优惠、权限、审批等多条件业务规则。

状态迁移测试（State Transition Testing）

根据状态及允许的状态变化设计测试。

例如订单状态：

1
2
3

待支付 → 已支付 → 已发货 → 已完成
   ↓
 已取消

如果业务规定只有待支付订单能够直接取消，就需要检查：

  • 待支付订单能否取消。
  • 已取消订单能否再次取消。
  • 已取消订单是否被错误允许进入已支付状态。
  • 已完成订单是否会发生非法状态回退。

状态迁移测试既要验证允许的变化，也要验证被禁止的变化。

5.2 白盒测试（White-box Testing）

定义

白盒测试根据代码内部结构和控制流程设计测试。

例如：

1
2
3
4

if amount >= 100:
    apply_discount()
else:
    reject_discount()

如果只测试金额 150，无法覆盖 amount < 100 的分支。

常见白盒测试技术包括：

技术主要含义
语句覆盖检查代码语句是否执行
分支覆盖检查控制流程的分支是否执行
条件覆盖检查判断中各个条件的不同取值
路径测试验证指定的程序执行路径

代码覆盖率不等于测试质量。

即使所有语句都执行过，也不意味着断言正确，更不代表所有输入边界、业务规则或系统风险都得到验证。

例如测试执行了金额计算函数，但没有检查计算结果是否正确，该测试仍可能遗漏明显缺陷。

5.3 灰盒测试（Gray-box Testing）

灰盒测试是工程实践中常用的术语，表示利用部分内部实现信息辅助设计外部行为测试。

例如：

  1. 通过 API 创建订单。
  2. 根据系统设计了解订单会修改库存。
  3. 查询测试数据库，检查订单和库存状态。
  4. 判断整体结果是否符合预期。

测试人员没有通过代码分支设计全部用例，但利用了内部结构和数据流信息。

灰盒测试可以用于接口、集成和系统测试等场景。它不是必须与黑盒、白盒严格互斥的独立测试层级。

5.4 基于经验的测试技术

这类技术利用测试人员的经验、知识和执行过程中的发现设计测试。

错误推测（Error Guessing）

根据历史缺陷和常见错误选择测试场景。

例如：重复点击支付按钮、网络中断后重试、输入超长字符串。

基于检查表的测试（Checklist-based Testing）

根据事先整理的检查项设计或执行测试。

例如检查一个表单是否正确处理必填项、长度限制、非法字符和错误提示。

探索性测试（Exploratory Testing）

在学习软件、设计测试和执行测试之间持续迭代。

例如测试人员在尝试取消订单时，发现网络超时可能引发状态异常，进而设计重试、重复取消和状态恢复场景。

探索性测试并不是没有目标地随意点击。它可以围绕明确的风险和探索任务开展。

5.5 其他进阶测试方法

方法含义常见场景
组合测试从大量参数组合中选择具有一定组合覆盖程度的数据多参数配置和规则
两两组合测试覆盖不同参数之间的取值对兼容性、配置测试
基于属性的测试对大量输入检查应始终成立的性质算法、转换逻辑
模糊测试使用异常、随机或变异输入发现缺陷解析器、协议、安全
变异测试对代码做微小修改，检查测试能否发现错误评估测试套件
差异测试比较不同实现对相同输入的行为新旧系统替换
基于模型的测试根据状态或行为模型生成测试复杂流程、状态机

这些方法不需要在初学阶段全部掌握。优先学会等价类、边界值、判定表和状态迁移，通常就能够覆盖大量基础业务测试设计工作。

六、按测试目标分类：验证什么质量要求？

从测试目标来看，常见的区分是功能测试与非功能测试。

6.1 功能测试（Functional Testing）

功能测试验证软件是否按照规定的功能要求工作。

例如：

  • 用户是否能够登录。
  • 订单金额是否计算正确。
  • 库存不足时是否拒绝下单。
  • 非法订单状态变化是否被阻止。
  • 用户是否只能访问授权范围内的数据。

功能测试可以在不同层级开展。

例如库存规则既可以通过单元测试验证，也可以通过 API 或完整下单流程验证。区别在于不同测试能够提供不同范围的证据。

6.2 性能测试（Performance Testing）

性能测试验证软件在指定工作负载和运行条件下的表现。

例如，假设系统规定：

在每秒 200 次订单查询请求的目标负载下，95% 的请求响应时间不超过 500 毫秒，且错误率满足既定要求。

测试人员需要在可控环境下施加负载，测量实际结果。

这里的 200 次请求和 500 毫秒只是示例，不代表通用性能标准。实际阈值应根据业务需要和系统能力确定。

常见性能测试包括：

类型含义主要关注点
负载测试（Load）验证预期负载下的性能是否满足正常业务要求
压力测试（Stress）超出正常负载进行验证系统极限和失效行为
峰值测试（Spike）模拟负载突然变化瞬时流量应对能力
耐久测试（Soak）在较长时间内持续运行内存泄漏、资源累积、性能退化
容量测试（Capacity）评估满足质量要求时的可承受规模最大业务容量
可伸缩性测试（Scalability）评估资源增加后的能力变化扩容效果

常见指标包括响应时间、吞吐量、错误率、CPU 使用率、内存占用和数据库连接数。

常见工具有 JMeter、k6、Gatling。

6.3 安全测试（Security Testing）

安全测试验证系统是否满足安全要求，并寻找可能被利用的缺陷。

常见验证内容包括：

  • 身份认证是否正确。
  • 用户是否能够越权访问资源。
  • 是否存在 SQL 注入等输入处理漏洞。
  • 会话管理是否安全。
  • 敏感数据是否受到保护。
  • 第三方依赖是否存在已知漏洞。

安全测试包括安全功能验证、漏洞扫描和渗透测试等不同活动。

对于真实系统，主动安全测试应获得适当授权并明确测试范围。

6.4 可靠性测试（Reliability Testing）

可靠性测试关注系统在规定条件和时间内持续提供正确功能的能力。

例如：

  • 外部服务短暂不可用时系统是否正确处理。
  • 长时间运行是否出现资源泄漏。
  • 重复消息是否导致业务重复处理。
  • 某个节点失效时，系统是否能够按照设计继续提供服务。

可靠性测试经常与容错测试、故障注入和长时间运行测试结合。

6.5 恢复测试（Recovery Testing）

恢复测试重点验证发生故障后，服务或数据能否按照要求恢复。

例如：

  • 数据库重启后，业务能否恢复正常。
  • 备份能否成功还原。
  • 故障切换是否正常。
  • 恢复过程是否满足规定的时间和数据恢复目标。

可靠性与恢复能力相关，但并不等同。

6.6 兼容性测试（Compatibility Testing）

验证软件在目标运行环境中，以及与相关系统协作时能否正确工作。

例如：

  • Chrome、Firefox、Safari 的兼容性。
  • Android、iOS 的运行差异。
  • 不同屏幕尺寸下的布局。
  • 不同数据库驱动或依赖版本之间的兼容性。

测试环境应该根据实际支持范围和使用风险选择，而不是无条件覆盖所有设备和版本。

6.7 可用性测试（Usability Testing）

可用性测试关注用户能否有效、高效且满意地完成任务。

例如邀请用户完成购物下单流程，观察：

  • 是否能够找到购买入口。
  • 是否理解操作提示。
  • 是否容易发生误操作。
  • 完成任务需要多长时间。
  • 出现错误后能否顺利恢复。

可用性测试不等于检查按钮是否能够点击。按钮技术上可以工作，不代表用户能够理解它。

6.8 可访问性测试（Accessibility Testing）

可访问性测试验证具有不同能力和辅助技术需求的用户能否使用软件。

例如：

  • 是否可以只用键盘完成操作。
  • 屏幕阅读器能否正确识别控件。
  • 输入框是否具有明确标签。
  • 文字与背景的对比度是否满足要求。
  • 页面结构是否支持合理的阅读和导航顺序。

Web 项目可以参考 W3C 的 WCAG 2.2。

6.9 其他非功能与专项测试

类型验证内容
资源使用测试CPU、内存、磁盘、网络等资源消耗
国际化测试软件是否正确支持不同语言和区域格式
本地化测试特定语言及地区的文字、日期、货币等是否正确
可维护性相关测试与分析软件修改、分析和验证的难易程度
可移植性相关测试软件在目标环境之间迁移和运行的能力
混沌工程实验在受控扰动下研究系统实际行为
数据迁移测试迁移前后数据的完整性和正确性

ISO/IEC 25010:2023 提供了软件产品质量模型，可用于理解和定义质量要求。

不过，质量模型不代表项目必须为每个质量属性建立独立测试套件。实际测试范围应依据业务要求、风险和成本确定。

七、按测试用途与实施方式分类

7.1 冒烟测试（Smoke Testing）

冒烟测试用于快速检查一个构建版本或部署后的系统是否具备基本可用性。

例如新版本部署后，检查：

  • 首页能否访问。
  • 用户能否登录。
  • 商品列表能否查询。
  • 是否能完成一笔基本下单。

冒烟测试通常只覆盖少量关键场景，用于判断是否适合继续进行更深入的测试。

它不能代替完整功能测试。

7.2 回归测试（Regression Testing）

回归测试用于检查软件发生变更后，已有功能是否受到意外影响。

例如修改了优惠券规则，除了测试新规则，还需要检查普通订单金额、已有优惠方式和历史订单展示是否受到影响。

回归测试可以包含单元、集成、接口、UI 和 E2E 等不同层级的用例。

因此，回归测试不是单独的测试层级，而是描述测试的目的。

7.3 确认测试（Confirmation Testing）

确认测试用于验证已发现的缺陷是否成功修复。

例如修复了重复提交订单产生两笔订单的问题，需要重新执行能够触发原缺陷的测试。

它与回归测试的区别在于：

  • 确认测试检查原问题是否已经解决。
  • 回归测试检查修复是否对其他行为造成影响。

两类测试可以在同一次测试活动中执行。

7.4 健全性测试（Sanity Testing）

健全性测试通常指针对某次修改或特定功能范围开展的快速检查。

例如只修改了购物车数量限制，可以先对该功能进行定向验证。

Sanity Testing 与 Smoke Testing 在不同团队中的用法有交叉，实际项目中应明确两者各自的范围和目的。

7.5 手工测试与自动化测试

两者主要区别在执行方式。

手工测试（Manual Testing）

由测试人员直接操作软件、观察结果并作出判断。

适用于交互体验评估、探索性测试、复杂主观判断等场景。

自动化测试（Automated Testing）

通过程序自动执行测试步骤、获取结果并进行断言。

适用于重复执行、预期明确、测试数据可控制且维护成本合理的场景。

例如使用 Playwright 自动完成登录、下单和订单状态检查。

自动化测试不是测试层级。单元、接口、集成、UI、E2E 等测试都可以采用自动化执行。

自动化也不是无条件越多越好。测试脚本需要维护，环境和数据同样需要管理。

7.6 静态测试与动态测试

这两个概念描述是否需要执行被测软件。

静态测试（Static Testing）

不运行被测软件，通过检查工作成果发现问题。

例如：

  • 需求评审。
  • 设计评审。
  • 代码评审。
  • 静态代码分析。

假设需求只写了“超时订单自动取消”，但没有规定超时时间。在需求评审阶段就可以发现这一缺口。

动态测试（Dynamic Testing）

通过执行被测软件，检查其实际行为。

例如运行订单服务，发送创建订单请求，再检查响应和数据库状态。

手工/自动化与静态/动态不是同一分类维度。例如代码静态分析可以自动运行，动态测试既可以手工执行，也可以自动执行。

7.7 TDD、BDD 和 ATDD

这三个术语经常和测试类型一起出现，但它们更接近开发与协作方法。

方法全称核心思想
TDDTest-Driven Development先编写测试，再完成实现，通过测试指导开发
BDDBehavior-Driven Development围绕业务行为和具体示例促进需求协作
ATDDAcceptance Test-Driven Development在开发前共同明确验收条件，并据此指导实现

例如 BDD 中经常使用 Given / When / Then 表达：

  • Given：商品库存为 2。
  • When：用户请求购买 3 件。
  • Then：系统拒绝下单，库存保持不变。

这些方法可以结合单元、接口和 E2E 等测试使用，不应作为与其互斥的测试类型。

八、综合案例：一个下单功能应该怎么测试？

前面分别介绍了各种测试概念，现在将它们应用到同一个业务需求中。

8.1 业务需求

假设某购物系统规定：

  1. 商品有明确的可售库存。
  2. 下单数量必须大于零。
  3. 下单数量不能超过当前可售库存。
  4. 成功创建订单时，立即占用对应库存。
  5. 库存不足时，不能创建有效订单，也不能错误占用库存。
  6. 系统不允许超卖。

这些是本节为了演示而设定的业务规则。其他购物系统可能采用预占库存、异步确认或允许部分履约等模式，其预期结果会有所不同。

8.2 识别风险

基于上述需求，可以识别出不同层面的风险。

风险可能出现的问题
参数校验错误数量为 0 或负数仍然允许下单
业务规则错误购买数量超过库存仍然成功
数据库操作错误订单创建失败，但库存已扣减
并发控制错误多个用户同时下单导致超卖
接口处理错误接口返回结果与真实业务状态不一致
前端交互错误库存不足时仍显示成功
系统集成错误库存服务返回数据后，订单服务解析错误

不同风险并不一定需要相同层级的测试。

8.3 设计测试组合

测试方式需要验证的内容
单元测试下单数量是否合法、库存判断逻辑是否正确
组件集成测试订单写入、库存更新、事务或一致性机制是否正确
API 测试非法数量、库存不足、请求成功等接口行为
契约测试订单服务和库存服务之间的数据约定是否兼容
UI 测试数量输入限制、错误提示、提交状态
E2E 测试用户从商品选择到订单结果的完整流程
并发测试多个请求同时操作库存时是否发生超卖
回归测试修改库存逻辑后，已有下单行为是否保持正确

这张表不是要求每个项目都必须建立八套独立测试。

它说明同一个需求在不同层面存在不同风险，需要结合系统架构选择足够且有效的验证方式。

8.4 具体测试场景

场景一：正常下单

前置条件：库存为 5，用户购买 2 件。

预期：订单创建成功，可售库存按照规则减少 2 件。

可以主要通过组件集成测试或 API 测试验证。

场景二：库存不足

前置条件：库存为 2，用户购买 3 件。

预期：创建订单被拒绝，不产生有效订单，库存不变。

可以在单元测试中覆盖库存判断逻辑，在集成测试中验证数据状态，再通过少量 API 测试检查对外行为。

场景三：并发下单

前置条件：商品库存为 2，两个用户几乎同时各购买 2 件。

预期：按照本节“不允许超卖、下单立即占用库存”的业务约定，最多一笔订单成功占用库存，最终库存不能为负。

需要使用能够制造真实并发竞争的测试方式，仅执行两个顺序请求不足以验证并发安全。

场景四：页面提示

前置条件：库存不足，后端按照约定拒绝请求。

预期：前端展示明确的库存不足提示，不显示订单创建成功。

可以使用模拟 API 的 UI 测试验证界面行为，再使用少量真实链路测试验证前后端协作。

8.5 如何避免重复测试？

一个重要原则是：

能在较小范围内充分验证的逻辑，不需要在每个更大的测试范围内重复枚举。

例如库存判断有十种边界情况，可以主要通过单元测试覆盖。

真实数据库操作与事务需要通过集成测试验证。

完整下单流程可以选择少量具有代表性的 E2E 场景。

这样既能获得不同范围的测试证据，也能减少测试运行与维护成本。

8.6 测试金字塔（Test Pyramid）

测试金字塔是一种组织自动化测试组合的参考模型。

1
2
3
4
5
6

          / E2E \
         /       \
        / 集成测试 \
       /           \
      /  单元测试    \
     /_______________\

它通常强调：

  • 通过大量较小范围的测试验证业务逻辑。
  • 通过集成测试验证真实依赖和接口。
  • 通过数量受控的高层级测试检查关键业务流程。

一般而言，测试范围越大，需要协调的环境和依赖越多，执行和失败排查的成本也可能越高。

但这不是强制比例，也不表示所有系统都必须采用完全相同的测试分布。

测试组合应根据业务风险、系统架构和维护成本决定。

8.7 如何判断应该增加哪种测试？

面对一个新功能，可以按以下顺序思考：

第一，明确需求与预期结果。

需要知道什么情况下应该成功，什么情况下应该失败，以及成功或失败后系统应处于什么状态。

第二，识别主要风险。

关注业务规则、数据一致性、系统依赖、权限、异常处理及其他可能产生较大影响的问题。

第三，选择能够有效验证风险的最小合理范围。

例如纯计算规则优先在单元层验证；真实 SQL 必须通过相应数据库集成验证；跨系统兼容性需要验证系统交互。

第四，选择测试设计技术。

数值范围使用等价类和边界值，多条件规则使用判定表，状态流转使用状态迁移测试。

第五，决定哪些测试自动化。

对于频繁重复、结果明确、环境稳定的验证，通常优先考虑自动化。

第六，确定执行时机。

例如在提交代码时执行快速测试，在集成环境执行依赖测试，在发布前执行关键业务回归和必要的专项测试。

这里的“最小合理范围”并不意味着只做低层级测试，而是避免在没有新增验证价值的情况下，把同一逻辑反复放到更昂贵的测试中。

九、常见混淆与测试概念速查

9.1 几组最容易混淆的概念

接口测试与集成测试

前者主要描述测试对象或入口，后者描述协作范围。一条通过 API 验证真实数据库写入的用例，可以同时属于两者。

UI 测试与 E2E 测试

前者关注界面行为，后者关注完整业务流程。UI 测试可以使用模拟后端；E2E 可以通过 API 驱动。

系统测试与 E2E 测试

前者验证完整系统是否满足要求，后者强调业务流程从起点到终点。两者可以重叠，但不能简单画等号。

接口测试与契约测试

接口测试可以检查实际业务行为；契约测试重点检查调用双方依赖的交互约定。

黑盒测试与白盒测试

前者依据外部规格设计用例，后者依据内部结构设计用例。同一功能可以同时使用两种技术。

冒烟测试与回归测试

前者快速判断构建或部署后的基本可用性；后者关注变更是否影响原有功能。

确认测试与回归测试

前者验证特定缺陷是否修复；后者验证修改是否产生新的问题。

测试覆盖率与测试质量

覆盖率说明指定内容被覆盖的程度，不能单独证明断言正确、需求充分或者系统不存在缺陷。

9.3 测试中常见的辅助技术术语

Mock、Stub、Fake、Spy

它们都是测试替身（Test Double）相关概念，用于在测试中替代真实依赖或观察交互。

类型典型用途
Stub提供预先设定的返回结果
Mock验证预期交互是否发生
Fake提供简化但可工作的替代实现
Spy记录调用信息，供后续检查

例如测试订单计算时，可以通过 Stub 让库存查询固定返回 10，而不必连接真实库存服务。

不同工具对 Mock 等名称的使用可能不完全一致，应以实际功能为准。

测试夹具（Test Fixture）

指测试执行所需的预置对象、环境、数据及清理机制。

例如在执行订单测试前创建测试商品和账号，结束后清理数据。

不稳定测试（Flaky Test）

指在没有相关产品变更的情况下，测试结果仍可能时而通过、时而失败。

常见原因包括时间依赖、执行顺序、测试数据相互干扰、并发竞争和外部服务不稳定。

反复重试不能代替原因分析和修复。
