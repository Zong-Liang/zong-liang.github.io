第一部分：开发环境与依赖体系

第 1 章 Node.js 与前端开发环境

1.1 为什么浏览器项目需要 Node.js

JavaScript 最早主要运行在浏览器中，但现代 React 项目往往使用 npm 下载开发依赖，再借助 Vite 转换 TypeScript、处理 CSS、构建输出文件。这些工具在开发机器或 CI 服务器上运行，因此需要 Node.js。React 本身并不依赖 Node.js 才能在浏览器运行；多数普通 SPA 在构建完成后可以通过静态服务器分发。

可以将两种运行环境对比理解：

维度浏览器 JavaScriptNode.js JavaScript
核心职责页面交互、DOM、网络请求构建、脚本、开发服务器、后端服务
典型 APIdocument、window、localStoragenode:fs、node:path、process
模块来源浏览器 ESM、构建产物ESM、CommonJS、Node 内置模块
权限模型浏览器沙箱与 Web 安全策略取决于操作系统、进程权限和运行选项
环境变量通常由构建工具选择性注入process.env 读取进程环境变量

本系列的 Mock API 使用了 node:http，说明 Node.js 同样能用于服务端应用，但这与 React SPA 的前端构建是不同职责。

1.2 Node.js 版本、LTS 与项目兼容性

Node.js 按主要版本发布，每个版本有明确的支持状态。企业项目应优先选择处于支持期内的 LTS 版本，并参考工具链的 engines 要求。截至 2026 年 11 月，Node.js 22、24、26 均有 LTS 版本；具体支持状态以 Node.js 官方发布页面为准。Vite 8 的最低 Node 版本要求为 20.19+ 或 22.12+，而一个具体项目中的其他依赖可能要求更高版本。

1.4 npm scripts 做了什么

package.json 中的 scripts 本质上为项目约定标准命令入口：

运行 npm run build 时，npm 会在脚本执行环境中将本项目的 node_modules/.bin 加入 PATH，因此通常不必全局安装 vite 或 tsc。这有助于不同仓库使用各自声明的工具版本。

npm run 与 npx/npm exec 的用途不同。前者执行项目预定义脚本；后者执行 npm 包提供的命令。在现代项目中应优先执行仓库规定的 npm run ...，避免临时工具版本与仓库约定不一致。

1.5 依赖 Node 的开发问题如何定位

常见排查顺序是：先看 node -v 与 package.json.engines，再看包管理器版本和 registry，之后查看依赖安装错误的原始日志。对于原生模块或构建工具，操作系统、CPU 架构和 Node ABI 也可能影响安装；node_modules 通常不应在 macOS、Linux 之间直接复制。

第 2 章 npm、依赖树与版本可复现性

2.1 package.json 不是依赖的完整快照

package.json 描述项目的名称、脚本、直接依赖与允许的版本范围。依赖还可以引用其他依赖，形成完整的依赖树。例如：

{
  "private": true,
  "type": "module",
  "dependencies": {
    "react": "^19.2.0",
    "react-dom": "^19.2.0"
  },
  "devDependencies": {
    "typescript": "^5.8.3",
    "vite": "^8.3.0"
  }
}

dependencies 通常包含应用运行时所需的包；devDependencies 通常包含开发、构建、检查与测试工具。对于最终生成纯静态文件的 SPA，这个划分并不表示浏览器生产服务器会执行 npm install --omit=dev；构建阶段仍需安装构建依赖。

peerDependencies 表示包对宿主项目的兼容性要求，例如 React 组件库声明支持哪些 React 主版本。optionalDependencies 允许某些依赖在不支持的平台或安装失败时不阻断整个安装，工具链中的平台特定二进制可能用到它。

2.2 SemVer 的含义及局限

通常约定版本号为 MAJOR.MINOR.PATCH：

  • 1.2.3：固定该版本。
  • ^1.2.3：允许兼容范围内的更新，即 >=1.2.3 <2.0.0。
  • ~1.2.3：允许补丁更新，即 >=1.2.3 <1.3.0。
  • >=1.2.3：下界约束，不限制后续主版本。

对于 0.x 版本，^ 的范围需要特别小心：例如 ^0.2.3 即 >=0.2.3 <0.3.0，不会升级到 0.3.0。SemVer 是包作者遵循的兼容约定，不等于任何补丁更新都绝不出现回归。

2.3 Lockfile 为什么不可省略

package-lock.json 记录 npm 解析出的具体依赖版本和安装元数据，包含依赖树与完整性信息。将 package.json 与 lockfile 一起提交，才能让团队或 CI 尽可能重现同一个解析结果。

两个场景要区分：

1
2
3
4
5

# 日常添加/更新依赖，可以调整锁文件
npm install

# CI、构建流水线和干净的验证环境：按已有锁文件安装
npm ci

npm ci 要求已存在 lockfile；如果 lockfile 与 package.json 不一致，会直接失败而非擅自修改锁文件。它会清理已有 node_modules 并安装项目完整依赖。这样可以及时发现“代码提交了依赖变更却忘记提交锁文件”的问题。

配套项目已提交 package-lock.json，本地和 CI 都用 npm ci 安装依赖；新增或升级依赖时用 npm install，并提交更新后的锁文件。

2.4 npm、pnpm 与 Yarn 的取舍

三者都是 JavaScript 生态的包管理器，但依赖布局、工作区支持、锁文件格式和版本管理策略不同。

工具典型锁文件常见特点
npmpackage-lock.jsonNode 生态默认工具，团队普及率较高
pnpmpnpm-lock.yaml内容寻址存储、相对严格的依赖可见性、工作区能力
Yarnyarn.lock多种安装与工作区模式，具体行为取决于 Yarn 版本和配置

选择包管理器首先服从仓库既有约定。不要在同一个项目中同时维护多套锁文件并混合使用安装命令。项目可通过 packageManager 字段与 Corepack 固定团队使用的工具和版本；具体 Corepack 可用性与 Node 安装方式有关，应按团队运行环境配置。

2.5 依赖风险与供应链

安装依赖意味着可能执行第三方包的安装脚本，生产代码也可能包含第三方运行时库。基本控制点包括：

  1. 限制依赖来源与可信仓库，谨慎审核新包的维护状态和权限需求。
  2. 提交锁文件，保留安装日志和构建来源信息。
  3. 使用 npm audit 等工具辅助发现已公开的漏洞，并结合影响范围人工评估。
  4. 不在仓库中保存 npm token、私有 registry 密码或明文环境密钥。
  5. 定期更新依赖，并验证兼容性与构建结果；不要把“升级到最新”当作没有测试的自动操作。

npm audit 是安全检查的一部分，不替代代码审查、运行环境控制和后端安全测试。

第 3 章 ES Modules、CommonJS 与模块解析

3.1 模块系统解决的核心问题

项目规模扩大后，所有变量都放在全局作用域会导致冲突、不可复用和依赖关系不透明。模块系统使代码拥有明确的导入与导出关系，构建工具则可以从入口开始追踪模块图。

这里 import type 表明仅导入类型，类型检查后不会成为运行时模块依赖。对使用单文件转译的工具链而言，显式类型导入更容易保证正确输出。

3.2 ESM 与 CommonJS 的不同

维度ECMAScript Modules（ESM）CommonJS（CJS）
语法import / exportrequire / module.exports

常见文件约定.mjs 或 type: module 下的 .js.cjs 或 type: commonjs 下的 .js

Node.js 根据文件扩展名和最近一级 package.json 的 type 等规则决定如何加载。显式声明 "type": "module" 可以减少歧义。TypeScript 的 moduleResolution: "Bundler" 则面向由打包器处理的应用源代码；这与 Node.js 不经打包执行 .mjs 时的解析规则不完全相同。

3.3 浏览器与打包器如何解析 import

浏览器原生 ESM 通常使用相对 URL、绝对 URL，或通过 import maps 配置裸模块说明符。在未经过构建工具处理、也未配置 import map 的浏览器页面中，直接写 import React from 'react' 并不等于浏览器知道如何到 npm 查找 React。

Vite、Webpack 等工具会分析裸导入说明符，根据依赖解析规则找到真实代码，并在开发转换或生产构建时生成浏览器可加载的资源。

1

3

import { debounce } from './utils/debounce';  // 本地模块
import { useState } from 'react';           // npm 依赖
import './styles.css';                     // 由构建工具处理的样式依赖

3.4 循环依赖与模块初始化顺序

模块 A 导入 B，B 又导入 A，形成循环依赖。ESM 的 live bindings 允许部分循环结构正常工作，但访问尚未初始化的绑定可能触发错误。比起依赖运行时次序，更可维护的方式通常是把共同依赖抽到第三个模块。

循环依赖并不是所有情况都必然报错，但在应用初始化、配置模块、全局单例中容易造成难以定位的问题。工程分析时需要关注具体加载顺序和访问时机，而不是只看文件之间有没有互相 import。

第 4 章 从源代码到浏览器：转译、打包和优化

4.1 前端构建到底做了什么

浏览器理解 HTML、CSS 和 JavaScript，但项目源文件还可能包含 TypeScript 类型、JSX、CSS 预处理语法，以及浏览器无法直接识别的 npm 包解析规则。构建工具需要把这些文件处理成可部署资源。

工程中常见阶段：

1

3
4
5
6

源码
  → 解析（建立语法树与模块依赖）
  → 转换（TS/JSX、CSS、资源处理）
  → 分块（将模块分配到一个或多个输出 chunk）
  → 优化（摇树、压缩、去重、作用域处理等）
  → 生成带引用关系的 JS/CSS/HTML/静态资源

这是一种理解用的逻辑划分，各构建工具的具体算法和执行顺序不尽相同。

4.2 TypeScript 类型检查与转译不是一件事

1

const count: number = '100';

编译型工具可能依然把类型信息剥离为 const count = '100'，但 TypeScript 静态检查会报告类型错误。只做 TS 到 JS 的转译，不等价于完成类型检查。

因此 Vite 项目通常明确区分：

1
2

npx tsc --noEmit  # TypeScript 语义与类型检查，不输出 JS
npx vite build    # 构建浏览器部署产物

生产脚本可组合：

1

{ "scripts": { "build": "tsc --noEmit && vite build" } }

tsc 可以既做类型检查又发射 JavaScript；上述 noEmit 是针对将输出交给 Vite 的项目设计。

4.3 Babel、SWC、esbuild、Oxc 分别是什么

这些名称经常出现在错误日志中，但职责应按具体使用场景区分：

工具典型用途理解重点
TypeScript（tsc）TypeScript 语义分析、类型检查，也可发射 JS处理完整的类型系统
BabelJavaScript 语法转换与插件处理强大的插件生态和语法变换能力
SWCRust 实现的高性能 JavaScript/TypeScript 转换工具在特定构建链中承担转译职责
esbuild高性能 JS/TS 处理和打包工具曾在 Vite 旧版构建链中承担关键职责
OxcJavaScript/TypeScript 相关解析、转换、压缩等工具链Vite 8 转译等环节采用的技术组成
RolldownRust 实现的模块打包器Vite 8 用于统一开发和构建核心的打包器

不能只凭名字认定项目采用了哪个版本或哪条转译链，应看 package.json、配置文件与实际启动日志。Vite 8 不再沿用旧版“开发 esbuild、生产 Rollup”的双打包器主线，而使用 Rolldown 作为统一底层打包器，并结合 Oxc。

4.4 Polyfill 与语法降级

语法转换（如把较新的 JavaScript 语法降级）与运行时补齐（如某个浏览器缺少 Web API）是不同问题。

  • 转译：改变输出代码的语法形式，使之适应目标环境。
  • Polyfill：向运行环境补充缺失的 API 或功能。
  • 特性检测：在运行时判断浏览器是否支持某特性，再选择实现策略。

即使构建目标指定为旧浏览器，仍然不能推断所有缺失 Web API 都会自动被补齐。应根据目标浏览器矩阵与实际功能需求评估兼容性。

第 5 章 Vite 8：开发服务、HMR 与生产构建

5.1 Vite 的职责和版本边界

Vite 是面向现代 Web 的开发服务器和构建工具。开发时它提供按需模块服务、转换、依赖处理和 HMR；生产时把源码变为适合部署的静态资源。

版本知识必须分清楚：

  • Vite 2～7 的典型官方叙述常提到开发时 esbuild 依赖预构建、生产时 Rollup 构建。
  • Vite 8（2026 年 3 月稳定发布）采用 Rolldown 统一打包器，并引入 Oxc 相关转译能力。按官方迁移指南，build.rollupOptions 更名为 build.rolldownOptions，JavaScript 转换由 esbuild 改为 Oxc，esbuild 配置项改用 oxc；旧名称目前仍兼容，但已标记为废弃，将在后续版本移除。旧版文章中的这些配置需要按新名称迁移。
  • 配套实战选择 Vite ^8.3.0 与 @vitejs/plugin-react ^6.0.0，突出当前主线；不主张为讲解工具链而随意改动工作仓库的版本。

5.2 开发服务器与原生 ESM

执行：

1

npm run dev

Vite 开发服务器负责返回 index.html、转换被请求的前端模块、管理源代码变化与热更新连接等。浏览器看到的是经开发服务器按需处理的模块 URL，并非原封不动地把 src/*.tsx 送给浏览器执行。

项目中输入 import { Button } from 'antd'，Vite 需要解析包依赖并做必要的模块转换。在有大量小模块的项目中，开发性能还受依赖处理、文件监听、插件和模块图变化影响。

5.3 HMR、React Fast Refresh 与整页刷新

HMR（Hot Module Replacement）允许开发服务器在源文件变化后推送更新模块，而无需总是完整刷新整个页面。

React 的 Fast Refresh 在满足组件边界条件时可尽量保留局部状态；但不是所有变更都能保证保留状态。例如修改模块导出结构、执行不可接受的顶层副作用或改动影响依赖边界的内容时，可能退化为重新加载。

需要把三个现象区别开：

  1. React 的组件重新渲染：由状态变化、父组件渲染等触发，属于运行时 React 行为。
  2. HMR/Fast Refresh：由开发时代码文件变化触发，属于工具链行为。
  3. 浏览器完整刷新：页面重新请求 HTML 与应用资源，内存状态通常重置。

三者不应混为一谈。

第三部分：环境管理与生产交付

第 8 章 环境变量、运行模式、API 代理与跨域

8.1 分清三个容易混淆的“环境”

在前端项目中，“环境”至少有三个层次：

  1. Node.js 进程环境：例如 process.env.CI、process.env.API_PROXY_TARGET，由操作系统或启动脚本提供。
  2. Vite mode：例如 development、staging、production，决定加载哪组 .env.[mode] 文件，并影响 import.meta.env.MODE。
  3. 部署环境：例如测试集群、预发布集群、正式环境，涉及真实 API 域名、网关、TLS、鉴权与发布平台。

这三个概念有关联，但不存在“一处设置自动解决全部问题”的关系。尤其是：

1

vite build --mode staging

命令通常仍进行生产优化构建，只是使用 staging 这组 mode 环境变量；不能把“staging mode”误解为“没有压缩的开发构建”。Vite 的 mode 与 NODE_ENV 是不同维度。

8.5 CORS 与凭证请求

若浏览器直接请求不同源 API，可能受到浏览器同源策略与 CORS 约束。后端需要以正确的 Access-Control-* 响应头告知浏览器允许的访问方式。

使用 Cookie 等凭证的跨源请求还涉及 credentials、Access-Control-Allow-Credentials、允许源不能使用通配符等约束，并需要结合 Cookie 的 SameSite、Secure 属性理解浏览器实际行为。

开发代理能够减少本地 CORS 配置复杂度，但其行为不应代替生产中对身份、授权、CSRF 和跨域信任的设计。

  return fetch('/api/employees');
}

这样便于本地开发代理与生产反向代理保持统一请求路径。若系统必须使用独立 API Origin，则需明确公开 API 地址、CORS、Cookie/Token 传播方式和环境切换策略。

8.7 配置故障如何排查

浏览器请求 404 时，先区分是：页面路由返回 404、静态资源返回 404、开发代理未命中，还是后端 API 返回 404。浏览器 Network 面板中的 Request URL、Status Code、Response Headers 和 Response Body，通常可以快速排除错误方向。

构建后页面地址错误时，重点检查 base、路由 basename、入口 HTML 的资源路径、CDN 前缀和反向代理规则。环境文件修改不生效时，检查是否重启了开发服务器、当前 mode 是否正确，以及是否存在更高优先级的系统环境变量。

第 9 章 资源构建、代码分割与浏览器性能

9.1 构建资源为什么需要优化

浏览器打开网页不仅消耗下载时间，还要解析、编译和执行 JavaScript，并进行布局与绘制。压缩文件传输体积可以降低网络成本，但不必然降低大量 JS 的解析和执行成本。因此前端资源优化通常同时考虑：

  • 初始 JS/CSS 体积与请求数量。
  • 首屏所需的关键资源是否优先加载。
  • 重复访问时能否有效使用缓存。
  • UI 交互是否被不必要的长任务阻塞。
  • 页面加载过程中的布局偏移与用户输入延迟。

9.2 Tree shaking 不是“删除所有没用的代码”

Tree shaking 利用静态模块依赖信息，识别有机会被排除的未使用导出。其效果受模块格式、静态可分析程度、包的副作用声明、导入方式与构建器优化策略影响。

// math.ts
export function sum(a: number, b: number) { return a + b; }
export function multiply(a: number, b: number) { return a * b; }

// main.ts
import { sum } from './math';
console.log(sum(1, 2));

在合适条件下，未引用的 multiply 有机会不进入最终产物。但如果某模块在加载时有副作用，或者使用动态取值而导致构建工具无法可靠判断，就不能保证被消除。判断优化效果应查看实际构建产物，而不是仅凭 import 写法做结论。

拆分会带来新的权衡：首次进入某个延迟加载页面时需要下载新 chunk；要评估骨架屏、加载提示、预取机制、共享依赖复用与失效处理。

9.4 资源文件名哈希与缓存

构建工具常输出形如：

1
2
3

/assets/index-B72abc.js
/assets/EmployeesPage-X90def.js
/assets/index-AC521.css

文件名哈希让不同内容通常产生不同资源 URL，因此对这类不可变资源可以采用长时间缓存策略。与此同时，index.html 应维持相对短的可验证缓存策略，以便客户端及时获取最新资源引用。

资源常见合理策略原因
带内容哈希的 JS/CSSCache-Control: public, max-age=31536000, immutable文件 URL 随内容变化，可长期复用
SPA 的 index.htmlCache-Control: no-cache允许存储，但每次使用前向服务器再验证
未哈希的公开配置文件短缓存或 no-cache内容可能在不改变 URL 的情况下更新
私密 API 响应依敏感性设计，如 private 或 no-store避免共享缓存泄露用户数据

no-cache 不是“不允许存储”；它表示复用前需要重新验证。若希望禁止存储，常考虑 no-store。实际项目还会受到 CDN、浏览器和代理缓存行为影响。

9.5 Chunk 更新与旧页面失效

用户打开旧版本页面后，系统发布了新版本。旧页面稍后尝试动态加载一个在新部署中已删除的 chunk，可能出现资源 404 或动态导入失败。

常见缓解措施有：保留一段时间的旧构建资源、原子发布构建目录、明确更新提示、在特定失败情况下引导用户刷新。Vite 提供了动态导入预加载错误相关事件，可在需要时做受控处理。不能直接把所有资源请求失败统一变成无条件刷新，否则可能产生刷新循环并丢失未提交的表单内容。

9.6 图片、字体和 CSS 的优化

图片体积过大往往比 JavaScript 体积更早影响页面体验。应结合使用场景选择合适格式、尺寸与响应式图像；可延后加载非关键图片，控制尺寸以减少布局偏移。字体则需要考虑子集化、按需加载与回退策略。

CSS 优化应优先检查重复全局样式、未使用的 UI 库样式、深层选择器与过大的布局计算负担。不要仅凭“文件越小越好”决定是否值得牺牲可读性和维护性。

9.7 Source Map 的作用与部署边界

Source Map 用于把构建后的代码位置映射回原始源码，便于定位压缩产物中的错误。

1
2
3

build: {
  sourcemap: false,
}

示例生产构建默认关闭公开 Source Map。如果企业有前端错误监控平台，可在受控的构建/发布流程中生成并上传 Map，再决定是否在公开静态资源服务器中提供对应文件。Source Map 本身不是鉴权边界：即使不公开它，浏览器中的业务 JavaScript 仍可被查看和分析。

9.8 如何衡量优化是否有效

不要把“感觉更快”作为唯一依据。建议在相同设备、网络条件和页面场景下比较：

  • 构建产物的总大小与主要 chunk 大小。
  • 首屏资源请求数量、传输体积和加载顺序。
  • LCP（最大内容绘制）、INP（交互到下次绘制）和 CLS（累积布局偏移）。
  • 主线程长任务、JavaScript 执行耗时、重复渲染等性能迹象。

真实用户监测与本地 Lighthouse 或 DevTools 的实验室数据反映的样本不同，分析时应保留测量环境和口径。

第 10 章 静态资源部署、SPA 路由与回滚

10.1 构建产物应该部署到哪里

对于采用客户端路由的传统 React SPA，dist/ 通常包含 HTML、JS、CSS 和静态资源。Nginx、对象存储、静态站点服务或 CDN 能负责这些文件的分发。

浏览器请求通常类似：

1
2
3
4
5

GET /employees/123
    └─ Nginx 返回 index.html
         └─ 加载前端 JS
              └─ React Router 匹配 /employees/123
                   └─ 前端调用 GET /api/employees/123

服务器返回 index.html 只代表让客户端应用接管路由；业务页面是否存在仍由路由配置和后端数据决定。

10.2 为什么直接刷新 /employees/123 会 404

通过 React Router 的客户端跳转时，浏览器一般不要求静态服务器读取真正的 /employees/123 文件。用户复制该地址后首次访问，Web 服务器却要实际处理这个 HTTP 路径。如果服务器没有按 SPA 规则回退到入口，就会返回 404。

需要关注匹配优先级与资源缺失处理：不能把不存在的 .js 请求误当作页面路径返回 HTML，否则浏览器会出现 MIME 类型错误，真正的 404 反而被隐藏。真实项目还需要 API 反向代理、TLS、认证入口、基础安全响应头与日志配置。

10.3 开发代理与生产反向代理不是同一个配置

开发阶段 Vite 在 5173 端口运行并代理 /api；生产环境静态服务器面对 /api 的请求时，必须有独立网关或代理规则。例如示例 Nginx 使用：

1
2
3

location /api/ {
  proxy_pass http://api:3100;
}

这里 api 是示例服务的 DNS 名，必须在真实部署环境中具有正确解析与网络可达性。不能直接复制到所有企业服务器上使用。若采用独立后端域名，则跨域、Cookie 和安全策略也需另行设计。

10.4 base 与 Router basename 的协同

如果站点部署在 /hr/，除了 Vite 的 base: '/hr/'，路由也可能需要 basename="/hr"，服务器需要把 /hr/employees/123 的导航路由正确回退到 /hr/index.html。

1
2
3

<BrowserRouter basename="/hr">
  <App />
</BrowserRouter>

本阶段实战默认部署站点根路径。VITE_PUBLIC_BASE 仅用于展示构建资源前缀，不提供完整的子路径部署方案；要部署 /hr/，应同时修改路由 basename、Nginx 路由回退与 API 访问路径。这一点不能遗漏。

10.5 发布需要做到“资源、页面与 API”协调

一次前端发布不仅要复制 dist，还应考虑：

  1. 后端 API 是否向后兼容。
  2. 新旧页面在用户浏览器中共存时是否都能工作。
  3. HTML 与静态资源是否原子发布。
  4. CDN 缓存是否会将旧 HTML 与新 chunk 混合。
  5. 是否能找到上一个经过验证的构建版本。
  6. 回滚时需要同步处理哪些后端或数据库变化。

前端静态文件可以相对简单地切换到旧版本，但不能由此推断整个业务系统一定可以无损回滚。特别是 API 契约发生不兼容变化、数据库已迁移的情况下，需要跨前后端协调。

10.6 可观测性与线上问题定位

生产应用通常需要采集控制台错误、资源加载失败、关键接口错误、前端路由耗时和用户体验指标。日志和监控应注意过滤敏感字段，不要把 Token、个人信息或原始表单内容直接上报到第三方。

对于压缩代码的错误堆栈，可以使用受控 Source Map 服务辅助定位版本和源码位置。上线时最好保留构建版本、Git commit、依赖锁文件以及产物指纹，降低“线上运行的到底是哪一份代码”的排查成本。

11.1 将人工步骤转化为流水线

11.3 构建缓存与 node_modules 的区别

CI 里常缓存 npm 下载包或工具缓存目录，从而减少网络请求，但不应该以缓存的存在替代锁文件一致性检查。npm ci 仍根据锁文件重建项目依赖。

错误的缓存 key 会导致不同分支、Node 版本或依赖树共用不兼容内容。缓存优化应以结果可靠为前提，并将“构建命中缓存”和“测试通过”作为两个独立状态。

11.4 环境变量与秘密信息管理

CI 中的发布凭证、私有包 Token、云平台密钥应由受控 Secrets 管理，并限制权限和可见范围。不要把它们写入 .env.production 并随构建产物公开，更不要用 VITE_ 前缀传递需要保密的值。

必须区分：

  • 公开前端配置：可以进入 JS，例如应用标题、非秘密的 API 公共地址。
  • 构建工具的私有配置：只应在 CI/构建端使用，例如部署凭证，不进入浏览器产物。
  • 服务端运行时秘密：由可信后端或秘密管理系统保管，例如数据库密码、服务端签名密钥。

11.5 发布质量门禁怎么设计

最基本的拉取请求门禁可以包含：类型检查、Lint、自动化测试、前端构建。对于高风险业务系统，还可能需要安全扫描、依赖许可检查、E2E 测试、可访问性检查、人工验收和变更审批。

门禁不应该仅追求数量。一个从不被维护、偶尔失败就手动跳过的检查，会降低团队对质量系统的信任。有效的质量门禁应具备明确的失败原因、责任人和修复路径。

第四部分：企业项目维护与综合实战

第 12 章 企业级前端项目的结构与协作方式

12.1 不同工程结构的技术含义

常见组织方式：

  • 单仓库单应用：一个 package.json，一个前端应用或服务。
  • Monorepo：一个仓库内有多个应用或包，借助 npm/pnpm/Yarn workspaces、任务编排器等管理共享代码。
  • 多仓库：多个业务应用或微前端子应用分别维护，各自构建发布。
  • 微前端：多个前端应用在浏览器运行时通过约定组合，可能共享路由、登录态、公共依赖或主应用布局。

仓库数量与部署单元数量不是一回事；一个 Monorepo 可以构建多个应用，一个多仓库系统也可能统一部署。

12.2 package workspaces 与共享组件

当团队有大量相同 UI 组件、类型模型和工具函数时，可以考虑共享包。但包本身需要明确版本、依赖边界、构建产物、公共 API 与发布策略。

12.3 微前端下的工程化关注点

对于采用 single-spa 的系统，除普通 React 构建外，还需检查：

  1. 子应用的注册、激活条件与生命周期导出。
  2. 构建输出的模块格式、公共路径与静态资源定位。
  3. 主应用与子应用的 React、Router、公共组件库版本是否协调。
  4. 全局 CSS、运行时事件、定时器、网络请求是否在卸载时清理。
  5. 部署时独立更新子应用是否会影响其他应用。

传统 SPA 模板通常不能不经调整就成为可被主应用正确加载的 single-spa 子应用。应参考已有仓库的入口和内部构建脚本，保留原有约定。阶段七将单独系统讲微前端及其应用组织，本篇重点理解与构建相关的前置条件。

12.5 对公共组件和依赖升级的判断

升级 UI 组件库或构建工具不是只改版本号。需要调查：

  • 直接与间接依赖是否满足兼容要求。
  • 类型定义、组件 API、构建插件是否发生破坏性变化。
  • CSS 变量、主题、动态加载和静态资源是否改变。
  • 单测、E2E 测试与 CI 是否能覆盖主要流程。
  • 目标浏览器是否仍满足要求。

对大型业务项目，可以先建立独立分支做兼容性验证，再按模块迁移。保持变更可归因比一次性升级所有工具更利于问题定位。

第 13 章 前端工程化故障的系统排查

13.1 根据失败阶段定位问题

工程化问题可以先划分为五类：

阶段典型表现优先检查
安装peer dependency、平台二进制、registry 错误Node 版本、锁文件、网络、包管理器配置
启动端口占用、配置无法加载npm scripts、Vite config、环境变量、工作目录

13.2 模块找不到：从导入语句到依赖解析

常见错误：

1

Cannot find module 'xxx'
Failed to resolve import './utils'

排查应区分：

  1. 依赖没声明或没安装。
  2. 导入路径、大小写或扩展名有误。
  3. TS 路径别名只配置了类型解析，构建工具没有对应配置。
  4. 包的 exports 字段不允许当前子路径导入。
  5. ESM/CJS 互操作或目标运行时不匹配。

例如一个别名 @/api 能在 IDE 中跳转，却在 Vite 构建时报错，说明 TypeScript 配置与 Vite 的解析配置需要进一步核对；具体方案取决于当前 Vite 版本和是否使用 resolve.tsconfigPaths 等能力。

13.3 浏览器出现空白页面

建议顺序：

  • 查看 Console 第一条真正的错误，而不是最后一条级联错误。
  • Network 查看入口 HTML、主 JS、动态 chunk、CSS 和 API 的状态码与 MIME 类型。
  • 确认 base 与当前访问子路径是否匹配。
  • 检查是否把 index.html 错误返回给了 .js 资源请求。
  • 如果在业务页面加载时失败，检查 React Error Boundary、Suspense、动态 import 与接口错误状态。

对于压缩 JS 堆栈，还需要找到对应构建版本，并使用匹配版本的 Source Map。

13.4 一直请求旧接口或旧资源

先看浏览器实际发出的 Request URL，再排查编译期间写入的环境值、开发代理、生产网关和 CDN 缓存。使用 DevTools 的“Disable cache”只影响调试期间对应浏览器会话，不能解决 CDN 上仍然缓存旧内容的问题。

若刚更新 .env.staging，但没有重新执行 vite build --mode staging 并发布新的静态产物，旧页面当然仍使用旧构建配置。需要明确区分构建期值与可在运行时变更的配置。

13.6 构建时间过长怎么办

需要区分“冷启动变慢”“增量更新变慢”“完整构建变慢”“类型检查变慢”“测试变慢”。原因可能完全不同：

  • 冷启动慢：依赖预处理、模块图规模、磁盘 IO、插件初始化。
  • 热更新慢：影响的模块范围大，或存在耗时的转换插件。
  • 类型检查慢：项目引用、复杂类型、依赖声明和 TypeScript 配置。
  • 生产构建慢：资源体积、插件生命周期、压缩、Source Map、分块策略。
  • CI 慢：依赖安装、缓存失效、并行度、测试环境启动。

应该先记录基线再做修改，尽量只改变一个因素，比较时间和产物正确性。盲目增加缓存或关闭检查可能只是隐藏问题。
